# Memory-budget probe samples

Hand-written filesystem roots for `rebuild/tools/memory_budget.py`'s probes, so the cgroup clamp and the `/proc/meminfo` fallback are proven by pointing a reader at a directory rather than by requiring a container. Each subdirectory is one plausible box: a `proc/meminfo`, a `proc/self/cgroup`, and the `sys/fs/cgroup` files that case turns on — pruned to those, so a directory here holds fewer files than a live kernel would create beside them. Nothing here is generated — no pin, no manifest, no regeneration script — and nothing globs the tree by extension, so the extensionless cgroup filenames are safe to keep as the kernel spells them.

`_cgroup_memory_limit_bytes` and `_cgroup_cpu_allowance` take the root to read under, and `total_memory_bytes` takes both that root and a `platform`, so a Darwin box drives the whole Linux path with `total_memory_bytes(platform="linux", cgroup_root=SAMPLES / "container-v2")`. The parsers beside them are pure and take text, so a test that only wants to check the sentinel or the literal `max` can read one file and skip the walk entirely.

| Root              | What it represents                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `container-v2/`   | A cgroup v2 container on a 67 GB host, four levels deep under `kubepods.slice`. The tightest memory limit is an _ancestor's_ `memory.max`, not the leaf's, so a reader that stops at the leaf gets a different answer; the chain also carries a `memory.high`, a literal `max`, and a `cpu.max` quota of two cores under an unquotaed `max 100000` |
| `container-v1/`   | A cgroup v1 Docker container on a 33 GB host. The memory mount's root holds the unlimited sentinel (`9223372036854771712`) and the container's own directory holds the real limit; the CPU mount is spelled `cpu,cpuacct`, its root quota is `-1`, and the container's quota and period are one and a half cores                                   |
| `host-unlimited/` | An ordinary cgroup v2 desktop with 16 GB and no limits at all — every `memory.max` and `memory.high` on the chain reads the literal `max` and `cpu.max` reads `max 100000` — so both readers must answer `None` and clamp nothing                                                                                                                  |
