# Corpus parent port plan

This plan moves the rest of the review corpus build's data path into the review crate: everything `build_m1` does in its Python parent around the units phase that `rebuild/CORPUS-UNITS-PORT-PLAN.md` moved to Rust. One Rust process runs the load, the plan, the units phase on the existing worker pool in process, the whole-corpus passes, the write with its manifest and check, the review facts and the cache. Python keeps the command line, the cycle, the land and everything else that is not the data path, and stays the engine of record: the Rust build is opt-in behind one switch until a whole-tree dual run passes on the live corpus.

The measurements behind it are in `var/keep/rust-port/profile-corpus-write.md` (the parent's warm path: where its time goes, its port surface phase by phase, what its peak holds, and which files a warm rebuild reproduces byte for byte) and `var/keep/rust-port/build-bench.md` (a full-recompute build under both units engines, with the parent as the drive's bottleneck), and the byte-identity spike that § Byte identity of written files folds in is `var/keep/rust-port/spike-parent-files.md`; all three are kept on the M4 Pro Mac mini and not checked in.

## Decided

These are settled and are not reopened here.

1. Rust only, in the existing crate `rebuild/review-rs/`, no PyO3. A new subcommand, `ams-review build`, runs the corpus build's whole data path in one process; its units phase calls the worker pool in process, with no frames between the parent and the units. Nothing under `rebuild/kernel-rs/` changes.
2. Python keeps what is not the data path: the command line and its arguments, the cycle's orchestration and the land (`rebuild/tools/artifact_cycle.py`, `rebuild/review/landing.py`), the journal and the pool records, the review server, and the small inputs it already prepares for the units engine (the spec dump, the font facts, the subset pack, the configuration fold). One interface module, `rebuild/review/corpus_exec.py`, owns everything that crosses, as `rebuild/review/units_exec.py` does for the units engine; nothing pickled crosses.
3. The gate is a whole-tree dual run: given the same inputs and the same prior corpus, the Rust build and the Python build write output trees that are byte-identical file for file, on the mini bundle and on the live corpus, for a full recompute, a warm rebuild and an incremental rebuild (§ Scenarios). Every written file, the compressed ones included, compares byte for byte (§ Byte identity of written files), so no file is compared after decompression.
4. Python stays the engine of record until the gate passes. The Rust build is opt-in behind `AMS_CORPUS_BUILD_ENGINE`, in the style of `AMS_CORPUS_UNITS_ENGINE`; no Python is deleted, and no existing test is weakened.
5. The work is built bottom-up, with stage fixtures dumped from the real Python build by `rebuild/tools/units_stage_fixtures.py`, extended rather than duplicated, so each Rust module passes alone before the build is wired end to end.
6. Memory is a goal beside speed: § Data model and phases states what the process holds per unit in each phase against the Python parent's peak, and the `memory-constant` task ends the work with measured constants in the pattern of `CORPUS_UNITS_RS_PROCESS_BYTES`.

## Boundary

### The switch

`corpus_exec.engine()` reads `AMS_CORPUS_BUILD_ENGINE` at call time: `python`, the default while Python is the engine of record, or `rust`, and it refuses any other value, as `units_exec.engine()` does. `build_m1` opens `audit.AuditParts` first, whichever engine runs, and under `rust` calls `_rust_build_m1` in place of `_build_m1`, in the m1-audit mode only: `--mode table-diff`, `refresh-assets` and `snapshot` never reach the switch. Under `rust` every m1-audit build runs in the crate at `--jobs` threads, one included: one process needs no serial path of its own, and the serial Python build stays one switch value away. `_rust_build_m1` refuses `AMS_CORPUS_UNITS_ENGINE=python`, since the crate computes every unit the Rust build writes and the unit store must stamp that, and `AMS_CORPUS_MEMORY_TALLY`, whose readings are Python objects.

`_rust_build_m1` does what `_build_m1` does before its load (the subset tables' check, `table_digests`, `ensure_pack`); computes every value of § The build input with the calls `_build_m1` makes; writes the units init through `units_exec.write_init` from the `init` dict `_RecomputeRunner.__init__` builds, which derives the configuration fold there, so its `review.build units:` line prints before the load rather than in the units phase; drops what it read (the spec, the fontTools fonts, the site pages); writes the build input through `corpus_exec.write_input`, both files in a `TemporaryDirectory` it holds until the process exits; runs the process (`corpus_exec.run_build`); writes the pool record; and returns the manifest the build wrote, read back from the output directory.

### The process

`ams-review build --input=PATH`:

- Standard input is a pipe `run_build` holds open and never writes, as `units_exec.UnitsProcess` holds the units engine's. One thread of the process blocks on reading it and, at its end, ends the process at once with status 1, committing nothing further, as a killed Python build stops. The cycle stops a pass by signalling the Python build child (`artifact_cycle`'s `terminate_all`), which dies without running a `finally`; its death closes the pipe, so the Rust build stops with it rather than writing on into the tree the next pass reads.
- Standard error carries the build's console lines (§ What it prints), passed through by the Python parent, which inherits the cycle's. Standard output carries one result line, written last.
- The audit's descriptors are inherited (`subprocess.Popen(pass_fds=parts.descriptors)`, as `_key_only_read` hands them to its processes), and the input names them beside the head document Python read. The process reads the audit only through them, so a `--gates-only` pass that commits a new head during the build cannot reach it.
- It reads no environment variable. What the Python build reads from the environment crosses in the input: the cycle's run and its fold-claim file, and the output-counts file. The allocator's own setting (`kernel_exec.KERNEL_ALLOCATOR_ENVIRONMENT`) reaches it as it reaches every process of the step.
- It exits 0 after a `done` line; 1 after an `exit` or `error` line, or when its standard input ends; and 2 for a usage mistake, as the other subcommands do. Any other ending, a signal or a missing result line, is a failure `run_build` reports with the exit status.

### What it prints

Standard error carries the console lines in `console`'s forms, at the moments the Python build prints them:

- `[phase] review.build <phase>`, and `[t] review.build <phase> <seconds>s rss_gb=… rss_now_gb=…` then a tab and the note, for `load`, `plan`, `units`, `manifest+check`, `review-facts` and `cache`, the tokens read from the Rust process. The load line's note starts `build=rust`, a token `cycle_timings.PHASE_TOKENS` reads (`memory-constant`); the units line keeps `jobs=N engine=rust`.
- The `[t] review.build units` line closes after the verification sample and the stale check, which releases a held gate:rebuild-contracts (`artifact_cycle.CORPUS_UNITS_LINE`); the `[t] review.build review-facts` line closes once the manifest, the sidecars and the facts are on disk, which lets `_do_corpus_build` return while the process writes its stores (`CORPUS_FACTS_LINE`).
- `[progress] <done>/<recomputed> units enriched` as each handout's projections are loaded.
- `[warn] ink-signature store: …` and `[warn] unit cache: …` with the Python build's text (`signature_miss_note`, `store_miss_note`), their plain `console.say` forms where Python says them (the no-store note), and the `Pruned …` line after the manifest.

The notes keep the Python notes' facts and words where they describe the same thing. They are not a byte-identity target; the dual run compares the labels, the `[warn]` lines, the plain miss notes and the `Pruned` line.

### The result

`{"op": "done", "peak_footprint": bytes, "threads": n, "write_threads": n, "signature_threads": n}`, the peak footprint as `ffi::peak_footprint` reads it. Python writes one `kind:"pool"` record under `corpus-build-rs`: the width is the threads, the process is its one worker with that footprint, and Python's own footprint is the controller's, in `_record_corpus_pool`'s form. It writes no `corpus`, `corpus-units-rs`, `corpus-write` or `signature` record, since no pool process runs.

`{"op": "exit", "message": …}` is a refusal the Python build raises as `SystemExit`, and `run_build` raises `SystemExit` with the message as written. `{"op": "error", "message": …}` is any other failure, a panic in any thread among them, which `run_build` raises as `corpus_exec.BuildRunError`.

### Failures

Every `SystemExit` that `_build_m1` and its callees raise past the subset check has an `exit` with the same text. What the output directory holds after one depends on where the build stops, and the Rust build leaves what the Python build at `--jobs 1` leaves:

| Refusal point                                      | Refusals                                                                                                                | What the output directory holds                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the load or the plan                               | a table with no rows, a repeated input key, a key-only read process that fails, an audit the Rust build refuses (below) | nothing new                                                                                                                                                                                                                                                                                                                                                       |
| from the units phase's start to the write's commit | a stale verification sample; a fragment that does not read back, inside the write's runs                                | the signature store, written when it changed; the write's staged parts deleted as `_discard_runs` deletes them; every other file the prior's                                                                                                                                                                                                                      |
| after the commit                                   | a font changed since its load, the contract check, a change group on an ink-identical pre-merge unit                    | the signature store as above; what `_write_corpus` wrote before the refusal, in its order (the renamed shard parts, the fonts, the manifest, the pruned shards, the static files, the sidecars), the contract check and the facts refusal coming after all of them; the unit store the prior's, and `review-facts.json` the prior's unless the facts were written |

The Rust build joins its signature store's write before it writes an `exit` or `error` result, as the serial Python build writes the store inline at the units phase's start. A pooled Python build writes it on a daemon thread joined only on success, so its failure tree depends on how far that thread got; the dual run therefore compares a failure whose build rewrites the signature store with the Python build at `--jobs 1`, whose units the Python engine computes. A failure over a unit reused from the prior store is compared at the default width: a build at `--jobs 1` stamps no `units_engine` line, so it reuses nothing from a store the Rust units engine stamped, and over unchanged inputs neither build writes the signature store. No file a failure leaves records the units engine: the unit store, which does, is written only by a build that succeeds.

A failure after the commit leaves the prior's unit store beside a manifest it was not written for, as a pass the cycle stops after `CORPUS_FACTS_LINE` does, and the next build reads that store through its manifest-moved branch (the `torn` scenario).

A refusal's first line is the Python build's. For the contract check, the mismatch line that follows it, when any unit's re-settled cells diverge, is Python's too, from the mismatches in ordinal order. The drafting-time errors after it are kept in arrival order up to `CONTRACT_ERRORS_SHOWN`, as the pooled Python build keeps them (`_keep_contract_errors`), and their order is not compared.

An audit that is not in sorted sections, or whose key-only read or stream breaks, is refused with an `exit` that names why and names `AMS_CORPUS_BUILD_ENGINE=python` as the build that reads it (§ What stays in Python).

## What stays in Python

- The command line, `refuse_the_served_corpus`, and the other modes: `--mode table-diff`, `refresh-assets` and `snapshot` never reach the switch.
- Everything read before the load: the subset tables' check, `table_digests` and `ensure_pack`, which writes the pack the units engine already maps and runs only when the tables change; the ledger and the change groups, which are YAML; the spec, its dump and the family keys (`unit_cache.family_content_keys` reads the after font through fontTools); the font facts, the Junior tracking and the configuration fold, which `units_exec.write_init` already writes.
- Every stamp: the unit store's environment stamp and the signature store's, the inputs fingerprint, `repo_head` and `generated_at`. They hash code closures and fonts through `fingerprint`, whose rules live in Python and which the closure tests check there. `generated_at` is computed as the process starts rather than as the manifest is written, from the same modification times and the held audit's content time, so `datetime.fromtimestamp`'s rounding stays in Python; the two times differ only when an input is touched during the build, and the dual run holds its inputs still.
- The in-memory source (`audit.load_workload`, `_resolve_signature_digests`, `merge_ink_duplicate_units` over row columns), which no audit `run_m1` writes reaches. The Rust build refuses such an audit, and the switch's `python` value builds it.
- The journal and its pool record, the cycle's widths (`artifact_cycle.corpus_job_budget`, `corpus_write_job_budget`), the debug tally, the review server and the land.
- The Python parent and its workers, untouched: they stay the engine of record and the reference every dual run compares with.

The ink-signature shaping at load moves. The crate already shapes through the HarfBuzz release uharfbuzz links, carries every glyph's shape key in the font facts and reads the ink as `InkComparator` does (`ink::InkComparator::run_ink`), so a signature is the sha256 of both sides' `run_ink` pieces in marshal version 2's bytes. Kept in Python, the load would split across two processes, with Python's key-only read and shaping before the process starts and a late miss (a wrong skip of the key-only read) that the process could not shape. Moved, the misses shape on threads that share one set of fonts, where the Python pool holds a comparator in each spawn process. The signature store's stamp stays `signature_environment` as Python computes it, which hashes the comparator's Python closure and no crate file, so both builds write the same header (open point 2).

### Expected peak

The units phase sets it: about 400 B a unit of columns (the table, the store, the window index and the snapshot's share) beside `Resources` and the threads, under 2 GB at eleven threads at the corpus `build-bench.md` measured (estimated), against the Python parent's 3.3 to 3.7 GB with the units engine's 0.6 GB beside it. The load stays below it, since its transients are one column's copy and the permutation; so does the write, since the arena and the sidecar lines are on disk where the Python parent holds them in memory. What the Rust process never holds that the Python parent does: the interpreter and the freed load memory its allocator keeps (about 0.7 GB, and 1.6 GB after the load, by the profile's inference), the arena, the compressed sidecar lines, the pickled chunks and the write workers' copies, and, outside the units phase, the subset pack's mapping.

The spill files take the arena's bytes and the plain sidecar lines' bytes on disk in `scratch` for the build's length; each is unlinked as it is opened, so a killed build leaves none.

`memory-constant` measures `CORPUS_BUILD_RS_PROCESS_BYTES` (the process at any width, which grows with the corpus as `CORPUS_PARENT_BYTES` does), `CORPUS_BUILD_RS_THREAD_BYTES` (what each thread adds, the divisor) and `CORPUS_BUILD_RS_LAUNCHER_BYTES` (the Python process waiting on it).

## Byte identity of written files

The spike re-encoded every compressed file of the live corpus in Rust from its own inflated bytes, through zlib functions declared by hand as `src/ffi.rs` declares them, and each came out byte for byte as Python wrote it; it checked the plain files and the JSON shapes against the writers and `pyfmt::json`. So every written file compares byte for byte.

### Which zlib

Both sides deflate with the system zlib, `/usr/lib/libz.1.dylib`: uv's CPython builds its `zlib` module against it, with no zlib-ng, and the crate links it (`-lz`). Given the same parameters the library writes the same stream however the input is cut into `deflate` calls at every level the parent writes (1 and 6), so the writers need not reproduce Python's write sizes; level 0, whose stored blocks fall where the calls cut the input and the output, is written by no writer. The identity holds for two builds on one machine with one system zlib: another macOS release, another operating system, or a Python that bundles its own zlib moves every compressed byte of the side that moves. `ams-review version` prints `zlibVersion()`, and the dual run records it beside Python's `zlib.ZLIB_RUNTIME_VERSION` and treats a difference as inputs moved (§ The dual run).

### Containers

Every gzip stream has MTIME 0 and OS 255. A `GzipFile` stream is `1f 8b 08`, FLG FNAME, MTIME, XFL 4 at level 1 and 0 at level 6, OS, the name and a NUL; then raw deflate (`wbits` −15, memLevel 8, strategy 0, `Z_NO_FLUSH` writes and one `Z_FINISH`), CRC-32, and ISIZE modulo 2^32. A `gzip.compress` member is `zlib.compress(piece, level, wbits=31)` with its MTIME zeroed and its OS byte set to 255: FLG 0, no name, XFL from zlib. Every staged file is written under `.partial` and renamed.

### Reading what Python wrote

The Rust readers keep Python's fallbacks as well as its happy paths:

- Row-delta heads (store, index, audit) refuse as `HeadError` refuses: a parse failure, another format or output, missing stamps or segment list, a non-int generation or content, an unknown merge, base or segment names other than `<out>.<gen>.base` and `<out>.<gen>.<n>.delta` in order, settled keys out of range. `open_parts` refuses a missing part or a size mismatch and checks sha256 only when asked. A store head that fails is a full recompute; an index head that fails, or one stamped for another manifest, sends the sidecars to projecting fragments in place of copying lines forward.
- A store body line not starting `{"key": "`, or whose key cannot be sliced, is skipped. A read failure mid-body (`StoreUnreadable`, from `OSError`, `EOFError`, `ValueError`, `KeyError`, `TypeError` or `StopIteration`) drops everything loaded from the store, and the plan restarts over an emptied store. A headless single `unit-cache.ndjson.gz` reads as a base by its inline header. An address is trusted only while its part's size equals the header's `parts` entry; records without one are placed by the walk.
- A segment's header is checked against the output, generation, number and merge; rows split on the first three tabs; an unknown op refuses; the keyed merge refuses keys that do not strictly ascend.
- Audit sections held as gzip members are found through the head's member index and inflated one gzip stream each under the CRC and length checks; any mismatch is `MemberError` and fails the build. Plain parts are bisected by `pread`.
- Every whole-file gzip read follows Python's reader: concatenated members read as one stream; NUL padding after a member is skipped; truncation is an `EOFError`; a bad CRC or ISIZE, or non-gzip bytes after a member, is a `BadGzipFile`; FEXTRA, FNAME, FCOMMENT and FHCRC are parsed, and the header CRC16 is not checked.
- The signature store reads as absent, and every window is reshaped, on any read error, another format or environment, a line other than 16 hex digits, a tab and 64, or keys that do not strictly ascend.
- A prior fragment is read by address. A deflated one must inflate as exactly one raw stream to its recorded length, the inflate capped one byte past it, and the bytes must hold `"id": "<id>"` and the reused content key, or the build fails.
- Prior index and app lines are read only when stamped for the manifest beside them; once a requested id is missed, every later request misses and the unit is projected afresh, which writes the same bytes. App sidecars are current when the header's format and `manifest_sha256` match and, for the locator, the rows file's size equals `rows_bytes`.
- Where Python's `json.loads` reads what the Rust reader refuses (a float, `NaN` and `Infinity` among them, a lone surrogate, escaped or in the bytes, UTF-16 and UTF-32 text, ints beyond `i64`), the Rust build fails; no file Python writes here holds any of them.

## Dual-run harness and stage fixtures

### Scenarios

`units_stage_fixtures.open_build_source(source, scenario)` prepares a build's inputs and its prior corpus, and both tools share it. Every scenario starts from a base prior:

- The mini's is the `first` build, made afresh by each run of the tool over a spec the run materializes once at the fixed `var/rust-port/build-scenarios/mini-spec/`, with its ledger's modification time pinned (`os.utime`) to the bundle audit's. ### The dual run

`rebuild/tools/corpus_dual_run.py` runs two builds of one scenario and compares their trees file for file. It is the gate (decision 3) and the check the late tasks end with.

- Sides: `--engines python,rust` by default. The Python side is `build_m1` at the harness's default width, `artifact_cycle.corpus_job_budget(skip_gates=True)`, under the Rust units engine, so its unit store carries the Rust build's `units_engine` line; for the `refusals` case that rewrites the signature store it is `build_m1` at `--jobs 1`, and for the two that refuse a reused unit the default width (§ Failures). The Rust side is `corpus_exec.run_build` (through the switch once `opt-in-switch` lands) at `--threads`, by default the same width. `--engines python,python` runs the Python build at the default width and at two, which `_write_corpus` holds to write the same tree; `--engines rust` runs the Rust build alone, for `--memory`.
- Each side builds in a fresh subprocess (the Python side through `units_stage_fixtures`' `python-build` child, as `prepare --check` runs it), so its fold claims start from a fresh process as in a cycle, into its own clone of the scenario's prior, with `cycle_timings.JOURNAL` redirected into its run directory, `AMS_CYCLE_RUN` unset unless the build's pass holds a fold claim another output took (the chain's held steps), when it names a run whose claim file, in the side's run directory, names that output, `AMS_OUTPUT_COUNTS` naming the side's own counts file, and, on macOS, `MallocLargeCache=0`, as the cycle's step runs the build. The sides run one after the other.
- Inputs moved: each side reads the working tree as it starts, and another agent's commit or edit between the sides moves `repo_head`, `inputs_fingerprint`, `generated_at` or a store's `environment`, and with them nearly every file. Before comparing bytes, the dual run compares those fields where both sides wrote them, and both sides' zlib versions; a difference exits 3 naming the field, and the run is repeated rather than debugged.
- The comparison: the set of relative paths; every file byte for byte, with the first differing offset of a file that differs and, for a gzip file, whether the inflated bytes agree, to tell a container difference from a content one; the `[phase]` and `[t]` labels in order, the `[warn]` lines, the plain miss notes and the `Pruned` line, equal; the counts files, equal as sorted lists; for a refusal, both exit statuses and the message as § Failures compares it; and the scenario's assertions on the Python side.
- The report is JSON under `var/rust-port/corpus-dual-run/`: per scenario, the files compared and each difference, each side's wall time, phase seconds and peak footprint (the Python side's parent and units engine from their pool records), and both zlib versions. Any difference, or a scenario that did not reach what its row names, exits 1. `--plant shard` corrupts one shard part of the second side after its build, to show the comparison reports it.
- `--scenario all` on the mini runs every mini scenario but `refusals`, which runs by name, and takes minutes at most. A live run names one scenario; it is a heavy pass that starts with the base prior's refresh: detach it, watch its log (`doc/running-long-steps.md`), and run nothing beside it.
- `--memory` with a `--threads` list runs the Rust build alone over a live scenario once per width and fits a process figure and a per-thread figure to its peak footprints by least squares, as `units_dual_run --memory` does.

### Stage fixtures

`units_stage_fixtures.py` gains build stages beside the worker's: a `Stage` whose `run` is `build`.

- `dump --source mini|live --scenario S --stage … --out DIR` prepares the scenario, which must run one build, and runs that build's `build_m1` in this process over a clone of the prior, reading the scenario's own inputs, at the harness's default width under the Rust units engine and `write_jobs=1`. The write's pool workers are the only processes that would run hooked Python away from this one; the key-only read's processes and the signature pool are recorded where this process takes their results (`_find_misses`, `_shape_misses`). It writes `source.json`; the prior corpus as the build found it (`DIR/prior/`, which nothing writes again); the scenario's inputs (`DIR/inputs/`: clones of the audit, the fonts, the subset tables and pack, and the ledger), the units init and its spec dump (`DIR/init/`), so `compare` reads nothing outside `DIR`; the build input for that run's values (`DIR/build.json`, through `corpus_exec.write_input`, without descriptors); and one `STAGE.ndjson` a stage.
- A call stage hooks a helper and records each call's inputs and result, with generated inputs the source does not reach, as the worker's stages do; call stages are dumped on the mini only. A boundary stage records the build's state at a phase boundary: a line a unit (every unit on the mini, every `--every`th ordinal on a live dump, `LIVE_EVERY` by default) and a line a column with the sha256 of its canonical bytes over every unit, each value's typed encoding as one compact JSON line (`column_line`), which the Rust side computes the same way. A live dump records every boundary stage whose recorder exists.
- `compare STAGE --stages DIR` opens the dump's audit (`audit.AuditParts` over `DIR/inputs/`), writes the input with its descriptors, clones `DIR/prior/` into a scratch directory for a stage that writes, runs `ams-review stage STAGE --init=<input> DIR/STAGE.ndjson` with the descriptors inherited, and reports every difference. A boundary stage's Rust side runs the build from the input up to its boundary through modules that pass their own stages, and `compare` runs the compares of the upstream build stages first, in `BUILD_STAGES` order, where their files are in the dump, so a failure names the stage it starts in.
- `selfcheck --source S --scenario C` runs the build twice in this process, unwrapped and with every build stage recording, each with its own cycle directory so its fold claims start from none, and fails unless the two output trees are identical.
- Dumps live under `var/rust-port/build-stages/<source>-<scenario>/` and are never checked in. A task that changes the Python a stage records dumps that stage again; the dual run, which runs the live Python, is the gate.

## The units engine after the port

- `ams-review units`, its frames (`wire.rs`, `service.rs`) and `units_exec.UnitsProcess` stay: the Python parent drives its units phase through them while it is the engine of record, and `units_dual_run` and the worker's stage fixtures use them.
- Shared: `unit::Resources` and `unit::Worker`, the thread pool (`pool.rs`, which `units-pool-library` takes out of `service.rs`), the units init and its one producer (`units_exec.write_init`), and every module the worker runs. A change to the unit record or the projection is made once, in the crate, and both paths see it.
- Not shared: the frames. In the Rust build a handout is a `Vec<UnitRecord>` built from the columns, and a reply is a `unit::Batch` loaded straight into the store and the arena's files; `Projection::to_json` and the batch frame serve only the subprocess.
- Retiring the frames with the Python parent is the owner's decision, after the gate.

## Working rules

- One task per agent, in dependency order. A task is done when its acceptance commands pass, `make review-rs-check` passes after any Rust change, and after any Python change `make prettier`, a bare `uv run pyright` and the targeted tests pass; a task that changed Python under `rebuild/` ends with one `make test-rebuild`.
- A task whose Adds name a stage adds its recorder and generated inputs, runs `selfcheck --source mini --scenario incremental`, dumps the mini scenarios its Done line names, and runs its `compare`. Only the tasks that close a phase's boundaries (`load-phase`, `plan-phase`, `write-runs`) name a live scenario: each makes one live dump, detached, which records every boundary stage that exists by then, and compares them all.
- One heavy pass at a time across all agents (`doc/parallelism.md`): a live dump, a live dual run, `make test-rebuild` and a `make review-cycle` never overlap. A live dump or dual run starts with the base prior's refresh, itself a whole Python build. Targeted tests run as `uv run pytest <targets> -n auto --dist worksteal`.
- Never edit `rebuild/kernel-rs/`. Never write `rebuild/out/`; the tools read it and build into clones.
- Batch the edits to `build.py`, `corpus_exec.py` and `units_exec.py`: each moves the unit store's stamp, so the next cycle and the next live base prior refresh take a cold units phase. So does every crate edit, through `units_engine` (§ Open points).
- From `opt-in-switch` on, a change to Python a stage names ships with the mirrored crate change; `rebuild/test_corpus_exec.py`'s mini test fails the rebuild suite until it does.
- A disagreement a later task finds goes back to the stage that owns it: add the input to that stage's generated set, fix the module, and rerun that stage's `compare`. A live dual run that differs is narrowed by a live dump of its scenario, whose boundary compares name the first stage that disagrees.

## Open points

- Making the Rust build the default, and retiring the Python parent, its workers and the units frames, are the owner's decisions after the gate.
- The manifest's Stage B `review_code` stays engine-blind, since the trees must be identical, so `make verdict-ready` and the cycle's skip judge a Rust-built corpus by the Python sources. The unit store's `units_engine` line keeps a crate edit from serving stale units, but the signature store's stamp names no crate file, so a crate edit that changes only the write or a signature reaches no stamp until the gate's dual runs catch it. Naming the crate's signature modules in that stamp belongs with the decision to make the Rust build the default.
- `units_exec.engine_stamp` hashes the whole crate, so each parent-module edit during the port costs the next cycle and the next live base prior refresh a cold units phase, as an edit to `build.py` does. Narrowing that digest to the modules the units path compiles is possible, but it moves a stamp the units port pinned.
- The load's stream runs on one thread. Splitting it by window range, as the key-only read splits, is the next lever if the dual run's phase times show the load bounding the build.
