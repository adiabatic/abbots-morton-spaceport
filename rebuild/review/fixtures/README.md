# Review-corpus contract fixture

A small hand-written `build_m1` corpus that the Python contract tests and the review app's node tests (`rebuild/review/jstests/render.test.js` and `slim.test.js`) assert against. The units under `units/` are source files: no run of `rebuild.review.build` produces them, and the real builder cannot regenerate them. Enrichment needs live M1 artifacts, fonts, and subset TSVs, the provenance stamps (`generated_at`, `repo_head`, `inputs_fingerprint`) cannot be injected, and these units carry stub summaries, round-number highlight geometry, and mostly empty provenance that the real `Enricher` does not emit. `fixture-audit.tsv` and `fixture-ledger.yaml` are the pipeline's inputs in the real ingestion formats, so the shards' windows, classes, and counts can be checked against them.

## What binds it

- `check_manifest`, `check_unit`, and `check_shards` in `rebuild/review/build.py`, the §7 contract checker, which `rebuild/test_review_build.py` and `rebuild/test_corpus_checks.py` run over this directory. Every real build runs `check_unit` over the units it computes and the cross-unit predicates of `check_shards` over all its units; a cached unit skips `check_unit`. Its shard and its store record must agree on its `content_key` stamp, which covers every field outside `unit_cache.CARRY_PRESENTATION_KEYS`. The `duplicate_group`, `cluster`, and `secondary_junctions` fields that the write patches again are outside the stamp, so on a cached unit only the cross-unit predicates check them. `check_manifest` and the predicates on the files beside the manifest reach a real build through `check_output_dir`, which the contracts lane runs over the mini bundle's build and over a table diff and expects to return no errors. This directory has no fonts, index page, or sidecars, so only `check_manifest` and `check_shards` run over it directly.
- `test_fixture_sources_derive_the_checked_in_shards` in `rebuild/test_review_build.py`: `audit.load_workload` over the two sources must reproduce the shards' windows, classes, kinds, and configs, and the manifest's class order, `ledger_classes`, and per-class and total counts; its docstring states how a unit in a change group is filed and which fields derived from a unit's configs and kinds it checks. It is the only check of the manifest's `row_count`s and `totals.rows` against rows, because `check_shards` compares them only with each other.
- Each unit's `content_key`, from which the unit's id derives, so it must stay byte-identical for every recorded verdict to find its unit. `rebuild/test_carry_verdicts.py` checks it, and `carry_content_hash` in `rebuild/review/unit_cache.py` computes it. `picture_identical` is in `CARRY_PRESENTATION_KEYS` there, so changing it on a unit does not change the stamp.
- `test_fixture_duplicate_groups_and_clusters_follow_the_build_keys`, which checks every duplicate group and cluster against the whole key `build_m1` gives it, since `check_shards` checks only part of each key.
- `test_fixture_units_exercise_the_contract_branches`, which names the branches these units cover. Keep them covered when the fixture grows. One is the slim shape: a unit that takes no verdict (`audit.slim_fragment`) omits `explain`, `drafts`, and `highlight`, and its `content_key` is the hash of what it carries.
- The node tests, which load every shard the manifest lists, in manifest order. Their `the fixtures must …` assertions name the branches they need beyond the contract's, and their other assertions name unit ids, class ids, titles, and totals, so growing the fixture or re-stamping a unit means updating those literals.
- The tests that read the whole corpus (`rebuild/test_unit_index.py`, `rebuild/test_app_index.py`, `rebuild/test_rekey_verdicts.py`) read `units/` as one `units/<class id>.json` per manifest class, so nothing else goes there. The tests in `rebuild/test_rekey_verdicts.py` take the first units of `units/fixture-intended.json` in the order a shard walk visits them (`unit_index.iter_shard_fragments`, sorted by `unit_index.class_shard_key`), so a new class that keeps units must have an id that sorts after `fixture-intended`, and a new unit must go in another class's shard.

## `mini/` — the frozen mini-M1 bundle

A second fixture of a different kind: a slice of real build output, frozen so that tests of the build machinery need no live `rebuild/out/`. The module docstring of `mini/regenerate.py` says what the bundle holds, how its windows are chosen, why all of it is regenerated together, and how `pin.json` pins the spec its rows settled under. The docstrings in `mini/pin.py` say how `materialize` writes that spec out of git and how `_preserve_authored_outgoing` and `_adopt_reviewer_class_ids` adapt a pinned schema and a pinned ledger to the current loader.

Every test that needs real build output reads the bundle instead of the live `rebuild/out/`, so it runs at full xdist width. The readers are tests that build a corpus from the bundle (a mini `build_m1` takes seconds), tests that read its frozen audit rows and tables, and tests that need a real font, or a font and a spec that match each other. Each one reaches the bundle through the `mini_bundle`, `mini_corpus`, or `example_units` fixture in `rebuild/conftest.py` or through its own path to `rebuild/review/fixtures/mini/`, so this search lists every test module that reads it:

```zsh
git grep -l -E '/ "mini"|fixtures/mini|mini_bundle|mini_corpus|example_units' -- 'rebuild/test_*.py'
```

After a fresh `run_m1`, regenerate the whole bundle with:

```zsh
uv run python rebuild/review/fixtures/mini/regenerate.py
```

## Growing it

1. Add the window's rows to `fixture-audit.tsv`, one per (unit, config). Group the rows by unit for ease of editing; `load_audit` ignores row order. The dedupe key is (`codepoints`, `baseline`, `new`), so one unit's rows share a triple and no two units may share one. Keep the rows to ones `build_m1` could produce: code points in `baseline_subset.M1_ALPHABET`, baseline glyph names that are keys of `rebuild/m1-aliases.yaml`, the kinds `conform._compare_row` gives the row (`ligation` alone when the baseline's glyph count differs from the settlement's, and otherwise `cell` and `junction` as the cells and the junctions differ), and a `matched_entry` that `oracle.classify_divergence` could give it. That function gives no class to a row that drops a join and gains none, so such a unit's rows say `UNMATCHED` and the unit lands in a change group. The real `ink_identical` classes match only rows without a `junction` or `ligation` kind, and a re-routed unit's rows name the `ink_identical` class it is re-routed from. A window with a space or a ZWNJ and no `position` kind takes the no-verdict boundary class (`split-by-space-or-zwnj` in `rebuild/m1-divergences.yaml`) ahead of every other, so it is never a human unit. Two frozen units depart from these rules: `u-BLyK6Z13RtN` is a ZWNJ window in a human class whose kinds say `ligation` over two glyphs and two cells, and `u-DBug8cSj15L`'s kinds say `junction` over unchanged junctions. `KINDS_DEPARTURES` in `rebuild/test_review_build.py` exempts both from the kinds check. When the baseline names are the ones the old font (`site/AbbotsMortonSpaceportSansSenior-Regular.otf`) gives the window, give the unit a row for every manifest config under which that font gives the same names and the new cells would not differ, because rows that share a triple are one unit.
2. For a new ledger class, add an entry to `fixture-ledger.yaml` and its title, summary, status and why to the manifest's `ledger_classes`, in ledger order. It also gets a matching entry in the manifest's `classes`, with the same fields in the same order and the `section` that `audit.class_section` gives it, when some unit stays in it. A change group gets a `classes` entry with status `per-unit`, its title, summary and why from `rebuild/review/change-groups.yaml`, and no ledger entry. `classes` runs by section, then ledger order, then `CHANGE_GROUP_ORDER`.
3. Write the unit into its class shard under `units/` in the builder's output shape by copying the nearest unit and changing what differs. Give it every key `build.unit_scaffold` and `build.patch_fragment` write, in their order: `ledger_class` right after `class` (null unless the unit is re-routed), `config_classes` and `config_class_note` right after `config_gate`, and `secondary_junctions` after `boundary_marks` (null when the unit has none). The units in `fixture-intended.json`, `u-6VFDHaMNgCP`, and `u-Xp5KzYAPYK7` omit some of those keys, which `check_unit` allows. Give the drafts the shapes `drafts.Drafter` emits for the window, and give two units one duplicate group, cluster, or ink delta only where `build_m1`'s keys would: a duplicate group is one config set, judged pair, class, and ink delta, and a cluster is the same without the judged pair. A fragment carries no `batch`: its flags say whether it takes a verdict, and the manifest's `human_unit_ids` gives its place in the queue.
4. Set the unit's `content_key` to `carry_content_hash` of the unit without its `content_key` key, and give it the id `unit_id_for` derives from that key, which every `secondary_junctions` entry naming the unit as its `primary_unit` takes too. Keep each shard sorted by id.
5. Update `unit_count`, `row_count`, `machine_approved_count`, `human_unit_ids` (the human units in `audit.triage_key` order: manifest class order, group, window, id), each class's `batches` (the slices of `batch_size` its human units fall in along `human_unit_ids`), and `totals`, `duplicate_groups` included, in `manifest.json`.
6. Run `make test-rebuild`, which reruns every test that read a changed fixture file, and `node --test rebuild/review/jstests/*.test.js`.

Editing an existing unit outside `unit_cache.CARRY_PRESENTATION_KEYS` changes its `content_key` and so its id. Redo step 4 for it, redo step 5, because `human_unit_ids` and `batches` follow the triage order, which breaks ties by id, and replace the old id wherever it still appears: other units' `secondary_junctions`, and the literals in the Python and node tests. This search lists every place:

```zsh
git grep -n <old id> -- rebuild
```

Then run step 6.
