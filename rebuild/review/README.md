# Table-diff review corpus

## TL;DR

`rebuild/review/` is the source of a static review app, which the build writes to the gitignored `rebuild/out/review/`. The artifact cycle builds and serves its table-diff corpus: the accepted rebuild, as a snapshot of one run_m1 build holds it, against the working tree's build (§ Table-diff mode below). Its m1-audit corpus, which `uv run python -m rebuild.review.build` with no `--mode` still builds by hand until stage 4 of `rebuild/CUTOVER-PLAN.md` removes it, shows one review unit per distinct divergence in the divergence audit, `rebuild/out/m1/divergence-audit.tsv` (a head and its parts, read as one materialized file), sharded by kind of change: the ledger classes in `rebuild/m1-divergences.yaml` and the change groups in `rebuild/review/change_groups.py`. Each unit renders side by side in the old Senior font and the M1 font through two `@font-face` rules, with the divergent pair highlighted, the row's `font-feature-settings` applied, boundary marks, a one-line explain summary, and a note field. A verdict covers the whole unit, meaning every config in its config set. A unit whose two renderings the build shows to be equivalent is approved by machine and is not queued for review.

The sections below cover the keys, the explain panel, the triage flow, the exported files, and the mechanisms that approve or deduplicate units before a person sees them. The design record behind them is `rebuild/REVIEW-PLAN.md`: the architecture, the data model, the verdict drafters, and the contract between the build and the app.

### Commands

```sh
make review-build                                     # regenerate rebuild/out/review/, the table-diff corpus
make review-serve                                     # serve it on http://localhost:7294/
uv run python -m rebuild.review.build --mode table-diff   # the same build, run directly
uv run python -m rebuild.review.serve                 # the same server, run directly
uv run python -m rebuild.review.export verdicts.json --accepted rebuild/accepted-units.txt --out tmp/review-triage.yaml
uv run python -m rebuild.review.snapshot take        # snapshot rebuild/out/m1 under var/keep/review-snapshot/
uv run python -m rebuild.review.build --mode table-diff --out tmp/review-diff   # the current snapshot against rebuild/out/m1
make review-accept                                    # dry run of the accept; ARGS=--apply takes the snapshot and empties the store
make review-snapshot-remake                           # remake the snapshot rebuild/review-snapshot.json names on a machine without it
```

`make review` builds the scoped-anchor-selector review page, so the review app's targets are `review-build` and `review-serve`.

The build is incremental. It stamps every unit with a content key over that unit's inputs and keeps a store of per-unit results beside the manifest (`rebuild/out/review/unit-cache.ndjson.gz.head` and the base and segments it lists). The next build recomputes only the units an edit could have changed and reuses the rest from the previous corpus's shards. A fragment that comes out byte for byte as it was, reused or recomputed, stays where it is, and each changed one is appended to its class's overflow parts, deflated alone (#618's change 35), so the cost of a write is proportional to what changed: the write's route (`route::route` in `rebuild/review-rs/src/corpus/route.rs`) says when a class is written whole instead, by the share rule or a fold, deflated too, and when as a first base, plain, as a from-scratch build writes it. The share rule weighs each fragment at its plain length, whatever form its parts hold it in. The store writes only its changed records, as a segment over its base (`rebuild/pipeline/row_delta.py`). `rebuild/review/unit_cache.py`'s docstring defines what the key covers and what is reused, and `rebuild/test_unit_cache.py` checks that cached builds, and builds at any width, write the same fragments, inflated, and once materialized (`build.materialize_corpus`) the same bytes, as a from-scratch build. The build's `manifest+check` phase line reports what was reused and appended, with the plain bytes the appends inflate to and the fragments written deflated, and its `cache` phase line whether the store wrote its head alone, a segment or a new base. `--recompute-all-units` reuses no record and recomputes every unit, but still reads the prior store for each fragment's address and place, so the shards compare and append as on any pass; the artifact cycle's `--fresh` passes it through.

The review server uses port 7294, so it can run at the same time as `make serve` (`tools/serve.py`, port 7293).

## Quick start for triage

### Kerning is disabled

Both columns render with kerning off: the sample cells set `font-kerning: none`, which combines with each row's `font-feature-settings`. Every comparison the build makes (the review facts' ink-identity counts, highlight x-ranges, boundary-mark positions, pin checks) shapes with `kern: False` in both fonts (`ink.kern_neutral`). The corpus compares settlement and joins, and kerning stays out of it (rebuild/KERN-PLAN.md §4): neither font's kerning enters a before-and-after comparison, and a kern edit changes no unit of the m1-audit corpus. A table-diff corpus's kern units are the one exception (§ Table-diff mode): each shows a moved kern value, so it is shaped, compared and drawn with kerning on in both columns.

### Keyboard map

The in-app help overlay (`?`) lists every key, and `KEY_MAP`, `REJECT_MENU_MAP`, and `NEITHER_MENU_MAP` in `static/keyboard.js` define them.

The four main verdict keys are on the left home row: `a` skip, `s` reject, `d` fine either way, `f` approve. `e` records identical and `c` records neither. `a`, `d`, `e`, and `f` record the verdict and advance to the next unit. `s` and `c` open a small menu beside the row's verdict buttons, where a second key records the verdict with no comment, with a canned note, or with a custom comment, and a digit reuses a recent note. A canned note replaces whatever was in the note field. `Escape` or a click outside the menu cancels with no verdict, and the other shortcuts are off while the menu is open. `Backspace` or `Delete` clears the current unit's verdict, and pressing a unit's active verdict key again also clears it. `u` undoes the most recent verdict from anywhere. `g` approves every unverdicted unit in the cursor's group. Shortcuts are off while a note field has focus; `Escape` leaves it.

Reject means the old behavior should come back. Neither means both behaviors look wrong, so the unit needs new authoring work. Identical means the reviewer cannot see the flagged difference in the highlighted portion; that is feedback for the ink comparator and highlight tooling, not a judgment on either font.

A verdict covers every config in the unit's config set. Most units show no config badge because they diverge under every non-ss10 config. A badge such as "only when ss03 is on" marks a narrower set; hover it for the full list.

Approving a unit outlines its after sample in green, rejecting draws a red X over the after sample, either outlines both samples in green, and neither draws the red X over both. The row's recorded verdict drives these marks, so they persist through re-render and import and clear on undo.

### Reading the explain panel

Every row shows a one-line summary under the renderings: what the new pipeline chose at the primary divergence and the single record that decided it, in rune-name notation, for example "New: ·It joins ·It at the baseline (the old pipeline broke there) — decided by qsIt.yaml policy.extend[0] (join-count rank)." The Why? button, or `x`, opens the full panel:

- **Explain** is the candidate table settlement considered at each divergent position. It lists every surviving candidate with its entry, junction, and join-count, marks the winner with `->`, attributes each eliminated candidate to the rune record that eliminated it, and ends with a `decided by:` line naming the stage that separated the winner from the runner-up. `STAGE_PHRASES` in `rebuild/review-rs/src/enrich.rs` lists the stages.
- **Provenance** lists the `glyph_data/runes/*.yaml` records the outcome is attributed to. A reject's policy draft names these records.
- **Drafts** previews the three drafts (pin, policy edit, any-of) this unit's verdict would export.

### Triage flow

- The sidebar, headed "Kinds of change", lists every class by its title and summary in three sections: Open questions, Spot-check (already ruled) and a collapsed No review needed (§ Sections and statuses below). Clicking a class filters to it and opens its class header, which shows the title, pill, id, summary, any caution note, a sentence for its section and the full rationale (the ledger's `why`). Every class with units in the current batch or worklist has a light accent outline, and the class holding the cursor unit has the full cursor-blue outline; both are separate from the border that marks a clicked class filter. Within a class, units are grouped by lead-family pair (each group folds, with a button that approves its unverdicted units), ordered by code point, and paged in batches of `audit.BATCH_SIZE`; the toolbar arrows page batches, and `[` and `]` change class. A `#class=` link to an id the corpus does not have (an old id, say) toasts and clears the filter.
- The header strip starts with a chip showing the corpus's unit total. Its popover shows the generation stamp and head, how many letters have migrated, and the total split into machine-approved units (by machine check), units covered by a ruling (the no-verdict classes), and units left for human review, which is the Overall denominator. After the chip come Overall progress with per-verdict tallies, ending, once a close-out has run, in "· N since the <date> close-out", which counts every record but the accepted ones, and so also the rejects, neithers and skips the close-out left in the store, the selected class's progress when a class filter is on, and the current batch's progress. A batch can span classes and a class can span batches, but selecting a class narrows the batch list. Each sidebar entry's counts line (`classCountsLine` in `static/render.js`) depends on its section: "to review" in Open questions and "to confirm" in Spot-check, both counting blank and skipped units, then "done", with a Spot-check class's rejects named; "all N done" once nothing is left; and the unit count with "covered by a ruling" or "all machine-approved" in No review needed. Progress counts cover the human units only.
- Machine-approved units (ink-identical, picture-identical, or junior-equivalent) and units in no-verdict classes are hidden by default. The toolbar's "Show units that need no review" toggle (`machine=1` in the URL hash) shows them in collapsed folds by class below the human units. Each row has a badge (its machine check's "… — machine approved", or "no verdict needed") and disabled verdict buttons whose title says why no verdict is needed. A `#unit=` link to one of these units while the toggle is off shows that one unit until you navigate away, and leaves the toggle and the URL unchanged. Keyboard navigation, auto-advance, and `g` cover the human units only.
- View state lives in the URL hash (`STATE_KEYS` in `static/state.js`), so reloading or sharing the URL restores the view. Verdicts autosave. After every change the app POSTs the verdicts it set or cleared (an `ams-review-verdicts-delta/1` body, never the whole store) to the serve script's `/autosave` endpoint. The server keeps the store in memory (`rebuild/review/verdict_store.py`), appends each save's sets and clears to `verdicts-journal.ndjson` before it answers, and atomically rewrites `verdicts-autosave.json` at the repo root once a minute passes with no save; every other writer of the store first writes into it the saves the journal holds past its last write (`landing.locked_store`), so none of them is lost when the server stops before it writes. It applies each save under the verdict store's lock (`rebuild/review/store_lock.py`), which the close-out and the table-diff accept also hold, and answers a save made while another writer holds it with a 503. Every change is also written to the tab's outbox in localStorage (`static/outbox.js`) when it is made and stays there until the server acknowledges it. A save refused with a 503 or cut off by a network error is retried on a doubling backoff (`AUTOSAVE_RETRY_FIRST_MS` to `AUTOSAVE_RETRY_MAX_MS` in `static/app.js`), and the status bar reads "N verdicts kept in this browser, saving…" meanwhile. The save a closing tab sends is not retried, and the next page load sends what the outbox still holds (`planOutboxReplay` in `static/outbox.js` offers entries older than `REPLAY_MAX_AGE_MS`, and entries whose set the server would refuse, as a download instead, and `unsavedFiles` in `static/verdicts.js` puts the records an Import would refuse in a separate file per corpus, apart from the rest of their corpus's entries), so the hand-run writers of the store refuse to write it while the server is up. That file is outside `rebuild/out/review/`, which a pass's land replaces as a whole. On load the app restores an autosave whose stamp matches the manifest, and afterward it asks `/autosave?since=<token>` for only what other sessions changed. A reload, crash, or closed tab loses no work, and the size of a save does not grow with the number of carried verdicts in the store. Each save sends `base_at`, the `at` of the record the tab last saw the server hold. A tab loaded on an earlier corpus keeps saving: the server carries its changes onto the store by unit id, a unit's id being its content key, as long as the store is on the served corpus. A save made on the served corpus while the store is still on another one carries the store onto the served corpus by unit id and keeps the old file as its stash, and a save made on neither gets a retryable 503. A skip made on an earlier corpus is dropped, as the carry drops every skip, and the tab shows the unit blank again. A change the store cannot apply is kept in `var/verdict-orphans/<stamp>.json` and reported to the tab: a conflict (the store holds a newer record, or a newer clear) makes the tab adopt the store's record and show a "Reapply N conflicted" button, which the tab keeps in its sessionStorage across a reload, the one onto a rebuilt corpus included, and an orphan (a unit outside the served corpus's human units) is announced in a toast. The readiness banner shows the conflicts and orphans recorded since the page loaded, or since the page it moved from loaded. The outbox is kept per checkout, keyed by the repo root the server names on `/capabilities`, because every checkout's server listens on the same port. `rebuild/review/verdict_store.py` states the rules. On load the app does not restore an autosave stamped for another corpus, and says so in a toast. The warnings about unexported verdicts (the beforeunload prompt and a toast every 50 unexported verdicts) appear only when autosave is not working, for example when a server without the endpoint serves the corpus, and the beforeunload prompt appears only when the outbox cannot be written either. When autosave works, the status bar's unexported count ends in "(autosaved)".
- **Accepted units.** A close-out folds the store's approve, either and identical verdicts into the tracked `rebuild/accepted-units.txt` and leaves the rest in the store (`doc/review-cycle.md` § The accepted list and the close-out). The full GET of `/autosave` lists, in its `accepted` field, the accepted units the store holds no override for, and the tab puts each into its records with an `accepted` flag (`applyAccepted` in `static/verdicts.js`), so the counts, the queue, the duplicate fill and the row marks take it as verdicted under its mark. Its row shows the verdict's marks, an empty note, and "accepted at the <date> close-out" where a verdict's date goes. Another verdict, or a note typed on it, makes an override record in the store (`accepted.Overrides`); Clear, `Backspace` or its own verdict key again blanks it, which the server keeps as an override tombstone; and an undo back to it sends it as it was, so the server drops the override. The duplicate fill and `g` never fill or overwrite it. A sync, an Import or a conflict reply keeps the flag on an accepted record, and a record dated at or before the close-out never replaces one. A full GET or a save's reply that names another list moves the tab, as a rebuilt corpus does (`static/reload.js`). While the store and the list do not pair, or the list cannot be read, the server refuses every save under `accepted-mismatch` or `accepted-malformed`, the banner shows its message, and the outbox keeps the saves.
- **Moving onto a rebuilt corpus.** The server reloads no tab when a file changes. The cycle sends `ams:corpus/<generated_at>` or `ams:assets/<static hash>` through livereload's `/forcereload` after it changes what the server serves, and `static/reload-plugin.js` hands the path to the app. A tab also moves when a save's reply or `/status` names a corpus other than the one it loaded, or when a byte-range read finds another build's record where its index points; the readiness banner reads "Moving onto the rebuilt corpus…" meanwhile. The app sends its unsaved changes, waits while the reader has text in a focused field (and, in a hidden tab, until the tab is shown), saves the scroll position, the queue anchor, and note drafts in sessionStorage, and reloads at the same URL hash. A reload that finds the page still on the corpus it left does not try the same move again, and the banner then reads "Corpus rebuilt since this page loaded" and asks for a reload. `static/reload.js` holds the rules.
- **The queue view** (the header's Queue button, `#view=queue`; `#view=docket` opens it too) is the live queue of the blank human units in Open questions, where blank means unverdicted or skipped. It groups them by the build's `cluster` signature, which is the duplicate-group key without the judged pair, so one visual change that recurs across letter contexts is one card. The largest decisions come first: the first `TOP_CLUSTER_COUNT` clusters as cards with exemplar renderings and evidence from judged lookalikes, the remaining clusters as a compact table, singletons in chunks of `SINGLETON_CHUNK`, and every duplicate group whose recorded verdicts disagree (all in `static/queue.js`). Every button is a `#units=` worklist link that carries `queue=1` (a hash that carries `docket=1` reads the same), the key of the decision it stacks (`decision`: a cluster's signature, or `#singletons` for a singleton chunk), and the corpus's `generated_at` stamp, so judging uses the normal keyboard flow with duplicate fill. Finishing a worklist opens the next decision by itself: the first one this browser has not yet opened, so leaving a card postpones it, the last open singleton included; once every open decision has been shown, the one shown longest ago comes back (`nextQueueDecision`). The rotation is kept across corpus rebuilds, because a decision's key is its cluster signature. A tab that resumes a worklist stamped for another corpus build keeps the units the new corpus still has, since a unit's id is its content key, and goes to the live queue only when none are left (`queueResumeAction`). The view recomputes from the in-memory store as verdicts are recorded, so clusters shrink, empty, and move up with no new snapshot. Blank units in Spot-check classes are left out behind a one-line count, since a class ruling covers them; selecting such a class in the sidebar walks them as a spot-check. The view reads each class's `section` from the manifest and keeps no status list of its own. Any filter or class click leaves the view.
- Each row shows the code point string in both fonts on a checkered background. The divergent pair has an amber band drawn from x-ranges in font units that the build computes; the app never measures text. A dotted line marks each boundary token (space, namer dot, or ZWNJ). To the right of each magnified cell, which is only as wide as its run, the same run appears stacked at 22px and at 11px (two font pixels per CSS pixel, then one; on a screen with exactly two device pixels per CSS pixel the 22px line is 16.5px, three device pixels per font pixel), with no checkerboard or marks. The row also has the one-line summary, a Copy button that copies a prompt preamble for the unit, and a Why? button (or `x`) that opens the explain panel with the attribution described in `doc/rebuild-design.md` §6.3. Regions without a mark render identically in both fonts or differ only in glyph names.
- The text lines use the same amber: the notation line (·May·Oy·It·May) and the code point line (E665:E679:E670:E665) underline the divergent pair's tokens in the band's `--hot` color. The build computes the mapping (`pair_codepoints`, a span of code point positions, and `notation_tokens`, one per code point position) because ligatures make glyph positions differ from code point positions. A unit with no primary pair shows both lines unmarked. A secondary junction with no primary unit (an "only here" junction, below) gets a dashed underline on the text lines; other secondary junctions are not marked there.
- A longer unit can contain divergent junctions besides the amber primary pair. Each such secondary junction shows in both columns as a dimmer dashed band with a chip naming its primary unit, the shortest unit where the same before-and-after behavior is the primary judgment. Clicking the chip opens that unit, across batches and classes and on machine-approved units too. A chip reading "only here" means the junction has no primary unit: no other unit whose code point string lies within this unit's has that junction, with the same before-and-after behavior, as its primary pair, so judge that junction in this unit. A junction whose primary unit is ink-identical or picture-identical gets no marker, since there is nothing visible to judge. The manifest's `secondary_junctions` record counts the markers, and the §7 checker compares it with the shards.
- No chip strip lists every config a unit diverges under, because for most units (those that diverge under every non-ss10 config) it would say nothing. A unit whose config set is informative has a badge of inert chips, one per stylistic set that pins the set down. Each chip uses its set's color, is lit when the set must be on and muted when it must be off, and is glossed with the set's `feature_descriptions` entry. `build.config_badge` computes both the chips and their text: it finds the smallest conjunction of on/off constraints that selects exactly the unit's config set, and falls back to one literal "only under: …" chip when no short conjunction does. The app renders each clause's `text` as given. The badges mark the cases that matter for judgment (ss03-gated, ss03-excluded, ss10-only, and narrower two- and three-set conjunctions), which also explain the row's `font-feature-settings`. Each chip's title lists the full config set. The queue view's cluster headers show the same chips.
- Units are deduplicated by (codepoints, baseline outcome, new outcome), so every config of a unit renders the same. The build groups configs by rendered outcome into `render_groups`, and the §7 checker fails an m1-audit build with a unit of more than one group. The app can still draw extra groups, each before-and-after pair stacked below the first with its own config label and feature settings.
- A verdict always covers the whole unit. `verdicts.json` records have no `configs` field, and an import ignores one.
- _Export_ downloads `verdicts.json` (format `ams-review-verdicts/1`, notes included), which holds the store's records and leaves out the accepted units, since `rebuild/accepted-units.txt` holds those. _Import_ merges an earlier export by unit id and asks before merging a file stamped for a different manifest, so triage can span sessions. `verdicts-autosave.json` is a rolling copy for the live manifest; downloaded exports are durable copies of the verdicts recorded since the last close-out, the list in git is the durable copy of the accepted ones, and the export CLI reads both.

### What to do with each exported artifact

Run the export CLI on the downloaded file with `--accepted rebuild/accepted-units.txt`, which any file but `verdicts-autosave.json` needs, so each accepted unit the file holds no record for counts under its mark and drafts with an empty note. An Export holds no tombstones, so the CLI takes them from the `verdicts-autosave.json` beside the list, which must pair with it (`accepted.view_of_file`), and an accepted unit cleared since the close-out is left out of the triage as it is in one made from the store. The resulting `tmp/review-triage.yaml` has a `review` header with counts, a `machine_approved` section (see "Machine-approved units"), and five verdict sections:

- **`pins`** (from approvals): whole-word `data-expect` strings, each checked for syntax with the repo's `parse_expect` and for meaning against the after font. Copy each into its `suggested_home` (for example `site/the-manual.html`) as a `data-expect` or `data-expect-noncanonically` attribute; this is how an approved behavior becomes a pin (`doc/rebuild-design.md` §10, item 5). `duplicate_of` flags pins the corpus already has.
- **`policy_edits`** (from rejections): one-line `policy.prefer[+]`, `policy.refuse[+]`, or `policy.contract[+]` records, each naming the target rune file, an appendable keypath, the provenance records that decided the outcome, and the decided stage. These are _drafts_ and are never applied automatically: review each, paste it into the named `glyph_data/runes/*.yaml`, and rebuild. An entry with `no_mechanical_draft` has no one-line reversing edit; start from its `names_provenance` and the unit's explain panel.
- **`any_of`** (from fine-either-way): candidate expect strings, after-behavior first, for the any-of check, which `assert_expect_any` (`rebuild/validation/check.py`, run by `_assert_expect_any` in `test/test_calt_expectations.py`) implements until the corpus has an any-of connective. A unit whose before and after behaviors give the same whole-word string (a cell-only divergence) has one candidate.
- **`neither`** (from neither verdicts): both behaviors look wrong, so nothing is drafted. Each entry has the unit id, code points, notation, the reviewer's note, and `names_provenance`, the `glyph_data/runes/*.yaml` records the outcome is attributed to. These units need new authoring work, starting from those records and the unit's explain panel.
- **`identical`** (from identical verdicts): the reviewer cannot see the flagged difference. Nothing is drafted; each entry has the unit id, code points, notation, and the reviewer's note. These entries report a difference the ink comparator and highlight tooling flagged that no person can see; they are not judgments on either font.

## The kerning view

The header's Kerning button opens the kerning view (`#view=kern`): every pair of letters that meet at a break, drawn from the last M1 build's pixels with the kern values the rune files set, which it edits. `rebuild/KERN-PLAN.md` §6 is its contract. A value lives in the leading letter's rune file, in its `kern:` block: the view writes it there within about a second of the last press, and a value written there by hand shows at the next refresh. It shapes nothing. It draws every glyph from `kern-inventory.json`, which the M1 build writes beside the font, at the pen positions the build computed and checked against the font with `kern` off, and moves each break by its value. The review server serves the inventory and the values (`rebuild/review/kern_routes.py`) straight from `rebuild/out/m1`, so a kern-only cycle pass, which lands no corpus, reaches the view too.

- **Opening it.** The Kerning button, or a link with `#view=kern`. The hash also carries the focused pair of letters (`pair=qsNo:qsTea`) and facing pair (`facing=`), so a reload or a shared link reopens the same place. The sidebar is hidden while the view is open, and any sidebar or filter click leaves it.
- **The grid.** The leading letter runs down the side and the following letter across the top, each ligature after its first letter. A cell draws the pair's representative facing pair at its value: the shapes the two letters settle to when written alone, where they break there, or else the facing pair that covers the most glyph pairs. The value is in the cell's top left corner when it is not 0, and `×N` in its top right says the two letters have N facing pairs. A chip at the foot says when they meet only across a ZWNJ (`ZWNJ`), only under ss10 (`ss10`), or only in those two ways. A blank cell's letters never meet at a break. A dashed outline marks a cell with a value the built font does not have yet: one set or changed since the last build, which `make artifact-cycle` makes.
- **The detail panel** shows the focused cell. The facing pairs of the two letters are listed by second shape, under a line naming it when there are several (`before ·Way[half]`), so every stance of ·Ye before half ·Way stands together; only the pairs with the selected pair's second shape are listed in full, and the others take one line each, with their value, until one is selected. Each facing pair listed in full is drawn in a text whose settlement puts that pair side by side: a word from The Manual when there is one, otherwise a short text found for it. The two shapes at the junction are in color, and the line beside them gives the text's notation, the two sides' names, how many glyph pairs the facing pair covers, what reaches it (mid-word, across a ZWNJ, under ss10) and in which configurations, the closest ink across the junction (touching or overlapping ink is flagged), and the value with the record that decides it, marked when the built font has another one. A facing pair whose side mixes shapes no record can tell apart (a `mixed` side) shows each of its drawings, and its closest ink is the worst of them: a pixel both shapes ink is an overlap, and strokes that pass each other without one are named as such. A facing pair with no such text shows its two shapes alone and says so. Below them come the joined pairs of the same two letters, drawn and marked as not kerned (a join's length is `extend` and `contract`), and the words from The Manual that hold the two letters, each drawn with every value applied: first the words where the two letters break, with the closest ink at that break, then the words where they only join, each saying at what height.
- **Staleness.** Lines under the title say when the shapes are the last build's because the runes or the build code changed since, when the inventory was built over other tables, when the Manual pages changed since it was built, when a cycle pass is running, and when the rune files' `kern:` blocks do not resolve, in which case they list the errors and the view shows the built values. The view asks the server again every few seconds while it is visible and when the window regains focus, and loads the new inventory when a build has written one. A request that fails, as while the server restarts, keeps the values the view has and says they could not be refreshed, and a view whose inventory did not load, before the first build or during a restart, tries again at the next poll.
- **Editing.** The box at the top of the detail panel holds the scope a change sets, which its two buttons choose: **This shape pair**, the selected facing pair's own record, or **All unjoined ·X·Y**, the record that names only the two letters, which every facing pair of the two takes unless it has a record of its own. With the second chosen, each facing pair that moves with it is outlined, and one that keeps a value of its own says so and from which record. The box shows the scope's record as the line its rune file holds and the file's name, or says the file holds none, and the record's note. A change moves the drawings at once and is written after a third of a second with no further press, so a run of presses is one change; until the server answers, the box and the facing pair say the change is being written. The server checks the result as the next build would (the spec loader, the kern stage and the defect gate's contact check at the new offsets) before it writes anything. A value equal to the one the scope takes without a record of its own leaves no record, and the box says so. A grid cell's value is its representative's.
- **Refusals.** A change the build would refuse, an ink overlap the allow list does not bless, a kern error or a loader error, writes nothing: the drawing goes back, and the box shows the server's message with the build's first errors, which a toast repeats. A change made against a block that moved on disk since the view's last poll, as when a pass's held changes were just written, is sent once more against the block as it stands; a second conflict writes nothing either, after which the view holds the block as it stands. A change to a file whose block the editor cannot write back exactly is refused too, and the box names that block beforehand with what to fix by hand (a comment or a blank line in the block, a multi-line `why`, a record not on one line of its own, lines that do not all end alike). A value past 64 pixels either way is refused before it is sent.
- **Undo.** `u` drops the newest change not sent yet, and otherwise undoes the newest change this tab sent that the server wrote or is holding for a pass, by its number in the journal. One still waiting for a pass is cancelled. A written one is undone only while it is the newest change the server wrote, from any tab, and its block still holds what it wrote; otherwise the box says why and nothing changes. A press that changed nothing is not a change to undo, and a reload starts the tab's undo afresh. The changes live in `var/kern/journal.ndjson`, which is outside version control.
- **During a cycle pass.** While a pass reads the runes, the server holds every change and undo in the journal, and the view keeps the change in the drawings, marked as waiting, with a line under the title saying how many wait. When the pass ends they are written in order, each checked again against the file as it then stands; one that no longer applies is dropped, and a line says why.
- **Reaching the font.** A written value is in the rune file at once and in the view at once, marked as not in the built font yet. The next `make artifact-cycle` finds that only `kern:` blocks moved and runs a kern-only pass (`run_m1 --kern-only`), which recompiles the font over the tables on disk and lands no corpus; the mark goes once that pass has written the font.
- **Relatives.** Under the facing pairs, the detail panel lists the selected facing pair's relatives: the facing pairs whose junction is the same one, its mirror image (`·Ah | ·Low` and `·Llan | ·Awe`), the same junction upside down, or turned half round. A junction is every gap between the two sides' ink on one row or on neighboring rows, and two are the same when they agree on every gap less than 3 px looser than the closest one, so ink set well back, such as a ligature's second letter's stem, counts for nothing; a relative that agrees on every gap says "pixel for pixel". The relatives are grouped by the value each has, those with another value first, as tiles: each is drawn small as its two shapes alone at its value, after a tile of the selected pair drawn the same way, with its name, its relation in a word (`≈` before one that is not pixel for pixel), and `−` and `+` buttons that kern it in place as its own record. The rest is in the tile's tooltip, and a click on a tile goes to its pair. A group of relatives with more than one value is kerned inconsistently: the header line counts such groups, their cells carry `≠` at the top of the cell in the grid, and their rows say so. `r` and `w` go to the next and the previous one, `t` sets the selected facing pair to the value most of its relatives have (a group's "take" button picks a particular value), `v` gives the selected pair's value to every relative that has another, each as its own record in its own leading rune's file, and `a` marks the selected pair as kerned apart from its relatives on purpose and goes on, or takes that mark off. A pair marked apart is compared with none of its relatives, a group's "mark these apart" button marks every relative at one value, and the marks are in `var/kern/apart.json`. **Near relatives**, listed after them, are facing pairs whose junction differs by at most 3 px in all, where a value may rightly differ: they are drawn for comparison and are in no count.
- **Comparables.** Three buttons at the top of the relatives section, and `c`, choose what it compares the selected facing pair with: **Same junction**, the relatives above; **Like ·X before ·Y**, every facing pair with the same second shape whose first shape is like the selected pair's (with `·Ye[loop] | ·Way[half]` selected, the letters shaped like ·Ye before half ·Way); or **Like ·Y after ·X**, the same for the second shape. Two shapes are alike when their facing edges differ, row by row, by little more than a constant, the distance each is set from the junction: within a pixel for each row of the selected shape's edge, with 4 px for a row only one of them inks. The like ones are listed most alike first, as tiles named by the shape that differs, and a button lists the rest of that column or row of the grid. Each tile gives how far apart the pair's ink is where it is closest, rows one apart counted, in color when that differs from the selected pair's; its tooltip says how far its shape is from the selected one and how much further from the junction, or nearer to it, its ink sits. A tile's `−` and `+` buttons tighten and loosen that pair in place, as its own record, and `=` sets it to the selected pair's clearance. `t`, `v` and `a` act only while the section lists the relatives.
- **Carried over from the old font.** After the importer has run (`uv run python -m rebuild.tools.import_kerning`, a dry run that writes `var/kern/import-report.json`; `--apply` writes the rune files), every facing pair it set is marked carried over until the author has reviewed it: `old` at the foot of its grid cell and a line on its detail row, and a count in the header line. `g` in the detail panel marks the selected scope's carried-over pairs reviewed and moves to the next carried-over pair (from a scope with nothing carried over or already marked it only moves), and the **reviewed** button does the same or takes the mark off when they all have it, and changing a pair's value marks it too, a mark that undoing the change takes off; the marks live in `var/kern/reviewed.json`. `]` and `[` jump to the next and the previous pair of letters that still has one. A pair whose value moved since the import, by the editor or by hand, no longer counts. The marks name facing pairs by their sides, so when a later build splits or renames a side (·Bay becoming `qsBay[sole]` once a second edge appears), its imported and reviewed entries no longer reach a pair: the header line counts them, and a line under the title says so when `var/kern/reviewed.json` cannot be read. Running the importer again only adds records for pairs it never set and no record decides.
- **Keys.** The view opens with the detail panel focused when the selected pair of letters has a facing pair, and with the grid focused otherwise; the focused pane has an outline. The arrows move the grid's cursor (`e`, `s`, `d` and `f` move it up, left, down and right too), `-` and `=` tighten and loosen the focused pair of letters by a pixel (the **All unjoined** scope) without leaving the grid, and `Enter` moves to the detail panel. There `↑` and `↓` (or `e` and `d`) choose a facing pair, and past the last or the first one move on as `]` and `[` do, `←` and `→` (or `s` and `f`) tighten and loosen the chosen scope, `0` drops the scope's own record, `n` opens a one-line field for its record's note (`why:`, saved with `Enter`, removed by saving it empty, `Escape` cancels), and `Escape` returns to the grid. `g` marks the scope's carried-over pairs reviewed. `u` undoes in either pane, `]` and `[` find the carried-over pairs, and each key but those two has a button in the box that shows its key. `Enter` on a focused button keeps its own meaning. `/` jumps to a pair of letters typed by name (`·no·tea`, `no tea`, `·day+utter·tea`), and `?` lists every key. The verdict keys do nothing in this view. `KERN_GRID_MAP` and `KERN_DETAIL_MAP` in `static/keyboard.js` define the keys.

## Table-diff mode

The artifact cycle builds this corpus and lands it (`doc/review-cycle.md` § The table-diff accept and the snapshot), and `uv run python -m rebuild.review.build --mode table-diff --out <dir>` builds it by hand: a corpus of what changed between the current snapshot of the accepted build (`--snapshot` names another) and the run_m1 build in `rebuild/out/m1` (`--new` names another). The before column draws the snapshot's font and the after column the new build's, both with kerning off but for the kern units. `rebuild/REVIEW-PLAN.md` §2.3 is the design, and the module docstrings of `rebuild/review/snapshot.py` and `rebuild/review/diff_units.py` give the snapshot's layout and how the units are found.

- **What a unit is.** Each unit is one visible change, not one changed table row: in **Settlement**, a letter that settles to another cell than in the accepted build, whatever its left neighbor (the explain panel lists the left glyphs it was seen after), and in **Joins**, a pair of settled cells that meets differently (a pair that is gone, a new pair, or a moved junction or extension). Each unit is drawn in its shortest text that shows the change, and one unit lists every configuration that text shows it under, so its config badge says where it holds. Changes that show the same text under the same configurations are one unit: a join row that is gone, the row that takes its place and the cell change at that junction are judged once, under **Joins**, and the row key and the explain panel name each of them. A join row no text is found for is shown by its notation alone and needs a verdict. A letter whose rows changed where no text shows it drawn differently is machine-approved when every text tried draws alike, and **Provenance only** lists the letters whose rows changed only the records they credit, which take no verdict.
- **The Queue.** Units that show the same pixels share one card, whatever their configurations and whether they are joins or settlement, so one join edit is usually one card. With no unaccepted change the Queue says so, naming the snapshot's commit, and a machine with no snapshot builds a corpus with no units, whose kerning view still works.
- **Explain.** The panel names the change, the configurations, how the text was found, and the changed rows of the accepted and the new tables the unit stands for. Table-diff units carry no drafts.
- **Glyphs.** A glyph drawn differently than in the accepted build, its outline, its advance and sidebearing, or its cursive anchors, with the tables unchanged, is a unit in **Glyphs**, shown in the shortest certificate that settles to it, else its code point alone, else a kerning-inventory text that holds it, else its letters under ss10. Latin, Shavian and the other glyphs outside Quikscript are units too, in the group `non-quikscript`, shown by their code point. A letter's bare glyph, which no text draws, is a unit with no text, and such glyphs of one letter share a Queue card.
- **Kerning.** A facing pair kerned by another value than in the accepted build is a unit in **Kerning**, drawn with kerning on in the kerning inventory's text for the pair. It takes no verdict: the kerning view is where kern values are judged, and the sidebar and the Queue still count these units.
- **Verdicts across edits.** The land carries the store onto each new corpus by unit id, and a unit's id is its content key, so a verdict stays while later edits leave its unit's change as it was, and goes to `var/verdict-orphans/` once an edit changes or reverts it. The store reads no accepted list.
- **Accepting.** Once every unit needing a verdict is verdicted and none is rejected or neither, `make review-accept ARGS=--apply`, with the review server stopped, takes a snapshot of `rebuild/out/m1`, points the tracked `rebuild/review-snapshot.json` at it, which goes into the commit with the edit, and empties the verdict store, so the next corpus starts from no unaccepted change. A clone or another machine without the snapshot remakes it with `make review-snapshot-remake`, from a build of the commit that last changed the pointer. `make verdict-ready` on a table-diff corpus prints a snapshot row and a diff row that counts the unaccepted changes, and names the accept once none is open. `rebuild/review/accept.py`'s module docstring gives the refusals.
- **What it can miss.** The texts tried are every text of at most three letters around a changed letter and the certificates of its rules, so a change that only a longer context shows can be missed.

## Mechanisms

Each section below says what a mechanism does for the reviewer and names the module docstring or `rebuild/REVIEW-PLAN.md` section that has the detail.

### Machine-approved units

The build approves a unit without a person when a machine check shows that its two renderings match. There are three checks, tried in the order `MACHINE_CHECKS` in `rebuild/review/audit.py` gives, so a unit carries at most one flag. The first is ink identity: a unit is `ink_identical` when both fonts place the same outlines under every config in its set, shaped with kerning off, so only glyph names differ. The module docstring of `rebuild/review/ink.py` says how the outlines are placed and compared. The other two are picture identity and Junior equivalence, below.

A machine-approved unit takes no place in the triage index (the manifest's `human_unit_ids`), so it is in no batch, no sidebar count, and no progress denominator, and the triage flow above says how the app shows it. It is written as a slim fragment, without the explain table, the drafts, or the pair band (the comment on `SLIM_OMITTED_KEYS` in `audit.py` says why), and its explain panel says what was left out. The cross-class search covers the human units only, so a machine-approved unit is reached through a show-machine fold or a pasted `#unit=` link.

`verdicts.json` holds human verdicts only. The export drafts nothing from a verdict recorded on a machine-approved unit and counts it under `skipped_machine_approved`, and the triage YAML's `machine_approved` section lists the approved units with their counts and each check's method (REVIEW-PLAN §4.2). The manifest's `machine_approved` record holds the same totals, and `rebuild/review-facts-pins.json` records them. In table-diff mode the ink and picture checks run over each unit's text under each of its configurations, and a unit with no text stays a human unit (REVIEW-PLAN §2.1).

### Picture-identical units

The second check approves a unit whose two fonts fill the same pixel cells under every config, where the glyph-name change the audit recorded only moves ink from one glyph to a neighbor without changing the picture: a junction pixel the old font drew twice and the rebuild draws once, as at ·At·J’ai, or a stroke redrawn as part of the adjacent letter. The check fails closed: a window whose outlines or placements are off the pixel grid, or whose pictures differ under any config, is queued. `InkComparator.picture_identical` and `config_diff` in `rebuild/review/ink.py` define it. A picture-identical unit has no visible junction change, so it carries no secondary junctions, and a secondary junction whose primary unit is picture-identical gets no marker. The flag is outside the carry content key (the comment on `CARRY_PRESENTATION_KEYS` in `rebuild/review/unit_cache.py` says why), so a change in the flag changes no unit's id.

### Junior-equivalent units

The third check covers units that diverge only under ss10, the set whose ratified meaning is fully isolated letters (the Taste sets / ss10 row in `doc/rebuild-design.md`). The build's Junior oracle (`JuniorOracle` in `rebuild/review-rs/src/ink.rs`) approves such a unit when the rebuild's ss10 rendering places the same ink as the old Junior font for the same string, once Junior's letter tracking is removed. A pass means the rebuild draws the canonical isolated rendering, whatever the old Senior font draws. A unit that also diverges under any other config still goes to a person, because those configs need judgment and a verdict covers the whole unit. The oracle does not approve the `· ◊ZWNJ` windows, where Junior draws the namer dot lowered and the rebuild's ss10 run draws the plain one. `ink.junior_tracking`'s docstring states the premise the tracking rests on, which it checks before any unit is compared, and the manifest's `machine_approved.checks.junior_equivalent` record names the Junior font it used.

### No-verdict ledger classes

A ledger entry with `no_verdict: true` says a ratified rule decides the whole class (the header comment of `rebuild/m1-divergences.yaml`), so no unit in it needs its own verdict. Its units are handled like machine-approved ones: they take no place in the triage index, are hidden behind the toggle with their controls disabled, and show a "no verdict needed" badge, and the sidebar lists the class under No review needed with "covered by a ruling" in place of its progress. `needsNoVerdict` in `static/render.js` is the app's test for both kinds. The export ignores a verdict recorded on an exempt unit and counts it under `skipped_no_verdict`, so an old verdicts master cannot add pins for a class the ledger has ruled on. Exempting another class is a one-line ledger edit, and `grep -n no_verdict rebuild/m1-divergences.yaml` lists the classes that have the flag.

### Ink-duplicate unit merging

The dedupe key, (codepoints, baseline, new), compares glyph names, so a config that only renames a glyph splits one visual question into two units. For example, the old font's ss04 lookups rename word-initial ·It without moving any ink, which splits ·It·Day·Tea·No into a default unit and an "only when ss04 is on" unit. The build merges such siblings before enrichment when their ink is identical under every config (`merge_members` in `rebuild/review-rs/src/corpus/table.rs`), so the reviewer sees the window once, with the union of its configs. The merge runs before change grouping, so an ss04 half that differs only by name is decided with its default sibling and is not asked again in `only-with-ss04`. Its doc comment gives the survivor rule and when a member is kept apart, and the module docstring of `rebuild/review/unit_cache.py` describes the ink-signature store that lets an unchanged build merge without shaping anything.

### Duplicate groups — one verdict per rendered change

Different windows often show the same change: ·Pea·Day·Tea·No, ·May·Day·Tea·No, and ·It·Day·Tea·No all show the same ·Day·Tea regrouping. Every human unit carries a `duplicate_group` id keyed on its configs, judged pair, class, and pixel-level before-to-after delta, so windows whose change paints the same pixels share a group whatever letters surround it. The docstring of `InkComparator.config_diff` in `rebuild/review/ink.py` defines the delta, including why a follower that only slid and a pixel handed to a neighbor that paints it anyway do not split a group, and `duplicate_group_id` in `rebuild/review-rs/src/corpus/passes.rs` defines the id.

In the app, a unit in a group with more than one member shows a "duplicate ×N" chip; clicking it opens the group as a `#units=` worklist, stacked. Typing a group id into the cross-class search offers the same stacked group. A verdict on any member, whether from a button, a key, a canned reject or neither note, or `g`, fills the _unverdicted_ rest of the group with the same verdict and note as one undo step, and a toast reports the fill. `skip` is never copied, members that already have a verdict are never overwritten, and any member can still be overridden or cleared on its own. The store keeps one record per unit, so export, import, autosave, and carry are unaffected.

The fill fires only on verdicts recorded in the app.

The corpus build stores each unit's per-config delta digests as `ink_deltas` (`ink.delta_digest`), from which its `cluster` is made.

### The artifact cycle mechanized

`make review-cycle` rebuilds the font, builds the table-diff corpus, lands it with the verdict store carried onto it by unit id, runs the gates, and then serves the corpus when no server is up; `make artifact-cycle` is the same pass without the serve. The review server keeps running through every pass: the pass builds the corpus beside the served one (`rebuild/out/review.next`), snapshots the store, and then lands the corpus and the store together under the store's lock (`landing.py`), laying the verdicts recorded during the pass over the store it carries. A save made while the land holds the lock gets a retryable 503 and waits in the outbox, and the open tabs then move onto the new corpus by themselves. The cycle restarts a server running older code, leaves one serving another checkout alone, and stops a server from before the land protocol once (`--stop-server`, which `make review-cycle` passes; `--yes` runs beside it instead). The land serves the new corpus as soon as the build has finished, while the heavy gates may still run, so a red pass can leave the app serving a corpus no gate has passed; `make verdict-ready` and the app banner stay NOT READY until every gate has passed on those inputs: a gate the pass did not run counts as not passed unless a green record shows the same inputs already passed. A green pass ends with a `review diff` line counting the unaccepted changes, which never fails it. `doc/review-cycle.md` is the runbook, and the module docstring of `rebuild/tools/artifact_cycle.py` has the rest.

### Review-facts pins as one reviewable file

`rebuild/review-facts-pins.json` holds the review facts of the last m1-audit corpus the cycle built: what that build measured about its own corpus, in one checked-in file that a person accepts by committing it. No pass refreshes it, since the cycle builds the table-diff corpus, and it goes with the m1-audit corpus (rebuild/CUTOVER-PLAN.md stage 4). The `volatile` block's counts change with every migrated letter, and a change in the `invariant` block (which classes ship, which the build machine-approves, which are exempt, and which change groups the corpus reaches) needs an explanation. The module docstring of `rebuild/review/facts.py` defines both blocks and the `--update` command that rewrites the file from an m1-audit corpus's `review-facts.json` sidecar.

### Policy drafters

A reject's policy draft is the smallest one-line `refuse`, `contract`, or `prefer` record that would reverse the change, at the unit's first divergent position that is not a boundary token, and REVIEW-PLAN §4.3 gives the order the drafter tries them in. A name-grain divergence with no such record (post-ZWNJ locked copies, bind pullbacks, non-summing suppressed extensions) gets no draft, and the export still lists the reject in `policy_edits` with null fields, the unit's provenance, and a `no_mechanical_draft` explanation, so a rejected unit always appears in the triage YAML.

### Sections and statuses

Every class has a reviewer-facing id, a `title` and a one-line `summary`, and some a caution `note`; the ledger holds them beside each entry's `why`, and `rebuild/review/change-groups.yaml` holds the change groups'. A status says who decides the class: `by-design` (a rule of the rebuild's design), `approved` (the user ruled the change correct) or `per-unit` (no ruling covers the class, so each unit's verdict decides it). `audit.LEDGER_STATUSES` is the vocabulary and `audit.RULED_STATUSES` the ruled half; every change group is `per-unit`, and a table-diff bucket has no status. The app shows them as the pills "by design", "you approved" and "you decide", and as "machine-approved" on a class in No review needed whose every unit a machine check approves; `STATUS_LABELS` in `static/render.js` holds the wording.

`audit.class_section` puts each class in one section, once per corpus, and the manifest carries the result as `section`: No review needed when the class is no-verdict or has no human unit, whatever its status; otherwise Spot-check (already ruled) for a ruled status and Open questions for `per-unit` or no status. The build emits the classes in section order, then ledger order, then `change_groups.CHANGE_GROUP_ORDER`, before it sorts the triage index, so batches, `[` and `]`, and the first unverdicted unit follow the sidebar, and an entry never moves as verdicts land. The Queue reads `section`, and the app refuses a manifest without it. The manifest's top-level `ledger_classes` maps every ledger id, those that reach no unit included, to its title, summary, status and why, so a unit's config badge and explain panel can name and explain any class.

### Change groups

The corpus sorts the windows no ledger class matches (**UNMATCHED**) into change groups by the kind of visible change each shows, for presentation only, which leaves the oracle unchanged. Each group is a synthetic `per-unit` class, so it sits in Open questions after the ledger classes unless a machine check approves every one of its units. A difference that shows only under a stylistic set goes to that set's group; otherwise a new join decides first, then a dropped join, then a join moving up or down, then the word's width. The module docstring of `rebuild/review/change_groups.py` gives the rules, `CHANGE_GROUP_ORDER` there lists the groups, and an empty group gets no manifest entry.

A unit of an `ink_identical` ledger class whose picture changes (no machine check approves it) goes to a change group too, because the class's claim that the letters draw exactly as in the old font is false for it; it keeps the ledger id as `ledger_class`, which its explain panel names. A no-verdict class is never re-routed. So every "Looks identical" class lists only units whose picture matches the old font, and the review-facts pins count the re-routed units per ledger class.

A window can be blessed under one stylistic set and novel under the default config. The build keeps it as one unit, records every config's class in `config_classes`, and gives the unit the UNMATCHED class, so the novel behavior is what gets reviewed; the app shows both classes in a badge from the shard's `config_class_note`. `rebuild/REVIEW-PLAN.md` §2.1 gives the rule, and a unit whose rows match two different ledger classes fails the build.
