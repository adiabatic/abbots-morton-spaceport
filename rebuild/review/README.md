# Treaty-diff review surface

## TL;DR

`rebuild/review/` (committed-shape source) generates a self-contained static app under the gitignored `rebuild/out/review/`: review units covering the M1 divergence rows from `rebuild/out/m1/divergence-audit.tsv`, sharded by the ledger classes in `rebuild/m1-divergences.yaml`. Every unit renders side-by-side in the old Senior Sans and the M1 mini-font via dual `@font-face`, with the divergent pair highlighted, correct per-row `font-feature-settings`, visible ZWNJ boundary marks, an always-visible one-line explain summary, and a per-unit note field. A verdict always covers the whole unit — every config in its config set — and a unit whose two renderings are provably equivalent never reaches a human at all.

Each of those mechanisms is documented in full below: the verdict keys and the two-step reject popup under “Keyboard map”; the candidate table behind the Why? button under “Reading the explain panel”; the sidebar, the docket, autosave, secondary-seam chips, and the inert config badge under “Triage flow”; the three build-time approval channels and the class-blanket ledger exemption under “Machine-approved units”, “Picture-identical units”, “Junior-equivalent units”, and “No-verdict ledger classes”; the two grains of deduplication under “Ink-duplicate unit merging” and “Echo groups”; and the path from a downloaded `verdicts.json` to the triage YAML it exports under “What to do with each exported artifact”.

### Commands

```sh
make review-build                                     # regenerate rebuild/out/review/
make review-serve                                     # serve it on http://localhost:7294/
uv run python -m rebuild.review.build                 # the same build, spelled out
uv run python -m rebuild.review.serve                 # the same server, spelled out
uv run python -m rebuild.review.export tmp/verdicts.json --out tmp/review-triage.yaml
```

The Makefile targets are `review-build` / `review-serve` because plain `review` was already taken by the scoped-anchor-selector review page.

The build is incremental: it stamps every unit with a content key over that unit's input closure and persists a slim store beside the manifest (`rebuild/out/review/unit-cache.ndjson.gz`), so the next build re-enriches only the units an edit could have touched and serves the rest from the previous surface's shards, byte-identically — `rebuild/review/unit_cache.py`'s docstring is the contract, and `test_builds_are_byte_identical` plus `rebuild/test_unit_cache.py` are the proof. `--fresh-unit-cache` (which the artifact cycle's `--fresh` passes through) bypasses the store and recomputes everything.

Port 7294 deliberately coexists with `make serve` (`tools/serve.py`, port 7293), so both can run simultaneously. Start the server with the serve command above.

## Quick start for triage

### Kerning is disabled

Both columns render with kerning off (`font-kerning: none` on the sample cells, composing with each row’s `font-feature-settings`), and every build-side comparison — the ink-identity census, highlight x-ranges, boundary-mark positions, pin semantics — shapes with `kern: False` in both fonts. The rebuild pipeline deliberately has no kerning until the §12 milestone, so the old font’s kern feature is pure noise in before/after comparisons; kern differences get their own review when that milestone lands. This is a no-op on the after font, but the rule is explicit so it survives §12.

### Keyboard map

| Key      | Action                                                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `a`      | Skip + auto-advance                                                                                                                          |
| `s`      | Reject (want the old behavior back) — opens the follow-up popup: `s` no comment, `a` / `f` canned notes; `Escape` cancels. Then auto-advance |
| `e`      | Identical — the highlighted portion looks identical (the flagged difference is invisible) + auto-advance                                     |
| `d`      | Fine either way (any-of channel) + auto-advance                                                                                              |
| `c`      | Neither — both behaviors look wrong (follow-up) + auto-advance                                                                               |
| `f`      | Approve (the new behavior is right) + auto-advance                                                                                           |
| `u`      | Undo last verdict                                                                                                                            |
| `n`      | Focus the note input for the current unit (`Enter` saves and advances)                                                                       |
| `g`      | Approve the whole group under the cursor                                                                                                     |
| `x`      | Toggle the explain panel (same as the row’s Why? button)                                                                                     |
| `↓` `↑`  | Move cursor without verdicting                                                                                                               |
| `k` `i`  | Same as `↓` `↑` — next / previous unit                                                                                                       |
| `[` `]`  | Previous / next class (toolbar arrows page batches)                                                                                          |
| `?`      | Help overlay                                                                                                                                 |
| `Escape` | Blur input / close overlay (or cancel the reject popup)                                                                                      |

The four main verdict keys sit on the left home row: `a` skip, `s` reject, `d` fine-either-way, `f` approve. Rejecting is a two-step: `s` (or the Reject button) opens a small popup anchored to the row’s verdict buttons, and a second key records the reject — `s` with no comment, `a` with the canned note “the old way seems nicer to write out by hand”, `f` with “the new way is broken” (a canned note overwrites whatever was in the note field), `z` with “new way has a worse-looking extension/contraction”, `x` records the reject and drops you straight into the note field for a custom comment; `Escape` or a click anywhere outside cancels with no verdict, and every other shortcut is suppressed while the popup is open. To clear an erroneous verdict entirely, press `Backspace` (or `Delete`) on the unit — pressing its active verdict key again also toggles it off; `u` undoes the most recent verdict from anywhere. The fifth verdict, `c` neither, means both behaviors look wrong — the unit needs follow-up authoring work rather than a pick. The sixth, `e` identical, means the highlighted portion looks identical — the reviewer cannot see the flagged difference, which is signal for the ink-comparator and highlight tooling rather than for either font. In the verdict grid the Identical button sits in row 1’s third column with Either and Neither stacked directly below it. `k` and `i` are home-row aliases for `↓` and `↑`. Shortcuts are suppressed while a note input is focused; `Escape` gets you back out. A verdict always covers the whole unit — every config in its config set (most units show no config marker because they diverge under every non-ss10 config; when a small badge like “only when ss03 is on” is present, hover it for the full list). Approving a unit draws a green outline around its after sample; rejecting overlays a red X on it; either outlines both samples green (both are fine); neither overlays the red X on both (both are wrong) — all four visuals follow the row’s recorded verdict, so they survive re-render and import, and clear on undo.

### Reading the explain panel

Every row carries an always-visible one-line summary under the renderings — what the new pipeline chose at the primary divergence and the single deciding record, in rune-name notation, e.g. “New: ·It joins ·It at the baseline (the old pipeline broke there) — decided by qsIt.yaml policy.extend[0] (join-count rank).” When that line is not enough, the Why? button (or `x`) opens the full panel:

- **Explain** is the candidate table the settlement function considered at each divergent position: every surviving candidate with its entry/seam and join-count, `->` marking the winner, the eliminated candidates each attributed to the YAML record that eliminated them, and a `decided by:` line naming the stage that separated the winner from the runner-up (join-count rank, declaration order, a prefer, or the structural floor).
- **Provenance** lists the `glyph_data/runes/*.yaml` records the outcome was attributed to — these are the levers a reject’s policy draft will name.
- **Drafts** previews the three precomputed verdict artifacts (pin / policy edit / any-of) this unit would export.

### Triage flow

- The sidebar lists the ledger classes with the ledger’s verbatim `why`/`status` text; clicking one filters to that class. Two accent outlines keep it oriented, echoing the main pane’s cursor ring: every class with units in the current batch (or worklist) carries a lighter-shade one, and the class holding the cursor unit the full cursor blue — independent of the border marking a clicked class filter. Units within a class are grouped by family pair (fold/unfold per group), ordered by codepoints, and paged in batches of 300 (`[` / `]`). The progress counters run big-chunk → little-chunk left to right, but only the counters that move as you work stay on screen: the header strip leads with a chip carrying the whole-surface unit total, which opens a popover holding the standing facts — the generation stamp and head, then a two-column table whose header row carries how much of the alphabet has migrated (the letters this surface is built over, against all 44) opposite the `units` column heading, and whose body breaks the surface total into the machine-approved count split by channel (ink-identical + picture-identical + junior-equivalent, listing only the channels that approved something), the no-verdict-class exemptions, and the human-review remainder the other two leave behind, which is the Overall denominator — and then shows the human-workload Overall progress with its per-verdict tallies, the selected class’s progress (when a class filter is active), and the current batch — classes and batches cross-cut (a batch can span classes and a class can span batches), but selecting a class narrows the batch list, so class-then-batch is the drill-down as experienced. Each sidebar entry’s counts line follows the same order: class units, machine-approved, verdicted/human, rows. Verdict-progress numerators and denominators count the human workload only.
- Machine-approved units (ink-identical, picture-identical, or junior-equivalent) are hidden by default. The toolbar’s “Show no-verdict units” toggle (state in the URL hash as `machine=1`) reveals them, grouped by class in collapsed folds below the human units, each row carrying its channel’s inert “… — machine approved” badge and disabled verdict buttons whose title explains why no human input is meaningful (ink-identical: both fonts render the unit identically; junior-equivalent: the rebuild’s ss10 rendering is the Junior font’s isolated rendering, which is the ratified ss10 spec). Deep-linking to `#unit=<an ink-identical id>` with the toggle off reveals just that one unit transiently — the persistent toggle stays off, the URL stays clean, and navigating away hides it again. Keyboard flow, auto-advance, and `g` group-approve operate over the human workload only.
- All view state (class, batch, cursor unit) lives in the URL hash — reloading or sharing the URL restores exactly where you were. Verdicts autosave: every store mutation debounce-POSTs the full export payload to the serve script’s `/autosave` endpoint, which atomically writes `verdicts-autosave.json` at the repo root (outside `rebuild/out/review/`, so livereload’s JSON watch doesn’t turn each save into a page reload), and the app restores a stamp-matching autosave on load — a reload, crash, or closed tab no longer loses in-progress work. An autosave whose `manifest_generated_at` differs from the live manifest is never joined by unit id: the app leaves it unrestored (a toast says so), and the server stashes it aside as `verdicts-autosave-<stamp>.json` before the first overwrite, preserving pre-rebuild work for a content-keyed carry. The unexported nag (the beforeunload warning and the every-50 toast) only fires when autosave isn’t working — e.g. when the surface is served by something without the endpoint — and the status bar’s unexported count gains an “(autosaved)” suffix when it is.
- **The docket view** (the header’s Docket button, `#view=docket`) is the live work order over the blank units: it groups every blank (unverdicted or skipped) human unit by the build-emitted `cluster` signature — the echo key minus the judged pair, so one visual question recurring across letter contexts is one card — and lays out the queue largest-decision-first: a top-25 tranche of cluster cards with exemplar render pairs and evidence from judged lookalikes, later clusters as a compact table, singletons in 40-unit chunks, and every echo group whose recorded verdicts disagree. Every button is a `#units=` worklist link carrying `docket=1` and the surface's `generated_at` stamp, so judging happens in the normal keyboard flow with echo-fill, finishing a worklist restacks the next decision by itself, and a tab resumed on a worklist from another surface build (whose unit ids the rebuild reassigned) bounces to the live queue instead of rendering the stale list; the view recomputes from the in-memory store as verdicts land — clusters shrink, empty, and promote with no re-bake. Blank units in ledger-ruled classes are excluded behind a one-line count (a class-level decision or bulk-proposal import covers those), and any filter or class click exits the view. `rebuild/tools/review_docket.py <verdicts-file>` writes the same clustering frozen against a verdicts file to `tmp/docket-data.json`, the data feed for bulk-proposal authoring. Its complaint-side sibling, `rebuild/tools/complaint_docket.py` (`make complaint-docket`), clusters the open reject/neither verdicts by the rune records that decided them and writes `tmp/complaints-data.json`, with per-group park candidates (still-blank units the same records decide) and `--park` emission of `verdicts-park-*.json` skip files for the Import dialog; `parked` is a recognized note-marker kind — the frontend’s `CARRIED_PROVENANCE_PREFIX` enumerates the full set, with `_MARKER` in `rebuild/tools/verdict_notes.py` as its Python twin.
- Each row shows the codepoint string in both fonts on a checkered background, the divergent pair highlighted with an amber band (precomputed x-ranges in font units; the frontend never measures text), a visible tick on ZWNJ boundaries, a per-unit Copy button that yields a prompt preamble, the one-line summary sentence, and a Why? button (or `x`) opening the explain panel with the §6.3 attribution. Unmarked regions can be trusted: they render identically in both fonts, or differ only invisibly at name grain.
- The same amber marks the pair on the text lines: the notation line (·May·Oy·It·May) and the codepoints line (E665:E679:E670:E665) underline the divergent pair’s tokens in the band’s `--hot` color. The mapping is computed at build time (`pair_codepoints`, a codepoint-position span, plus `notation_tokens` aligned one-to-one with codepoint positions) because ligatures make glyph positions diverge from codepoint positions; units with no primary pair render both lines unmarked, and only the primary pair is marked — secondary seams stay out of the text lines.
- Longer units can contain divergent seams beyond the amber-banded primary pair. Each such secondary seam renders in both columns as a dimmer dashed band with a small chip naming its home unit — the shortest unit where the same before/after behavior is the primary judgment — and clicking the chip deep-links there (cross-batch, cross-class, machine-approved homes included). A chip reading “only here” means no shorter home exists (a genuinely context-dependent divergence at the depth-2 horizon): judge that seam in this unit. Seams whose home is ink-identical get no marker at all — the difference is an invisible name-grain rename with nothing to see. The visible-marker census is pinned by tests and recorded in the manifest.
- There is no config-chip strip listing every config a unit diverges under: it carried no information for the majority that diverge under all non-ss10 configs, so it was removed. In its place a unit whose config set is informative carries a badge of one inert chip per stylistic set that pins the set — each in that set’s own color, lit when the set has to be on and muted when it has to be off, and glossed with the set’s `feature_descriptions` entry. `build.config_badge` is the authority for both the chips and their prose (it resolves a config set to the minimal conjunction of on/off constraints selecting exactly it, falling back to a literal “only under: …” chip when no short conjunction does); the app renders each clause’s `text` verbatim and never re-derives a phrase. That surfaces the judgment-relevant cases — ss03-gated, ss03-excluded, ss10-only, and the narrower two- and three-set conjunctions — which also explain the row’s `font-feature-settings`; each chip’s title lists the full config set verbatim. The docket’s cluster headers carry the same chips.
- Units are deduplicated by (codepoints, baseline outcome, new outcome), so every config of a unit renders identically by construction; the build groups configs by rendered-outcome identity into `render_groups` and the tests pin the invariant that every M1 unit has exactly one group. If future data ever violates it, the app renders each extra group’s before/after pair stacked below the first with its own config label and feature settings — nothing is collapsed, nothing needs clicking.
- Verdicts always cover the whole unit (all of its configs); the per-config verdict scoping that the original chips offered is gone, and `verdicts.json` records carry no `configs` field (legacy files importing one have it ignored).
- _Export_ downloads `verdicts.json` (format `ams-review-verdicts/1`, includes notes); _Import_ merges a previous export back in by unit id (with a manifest-mismatch warning and a force path), so triage can span sessions. The autosave complements but doesn’t replace exports: `verdicts-autosave.json` is a rolling safety net scoped to the live manifest, while downloaded exports remain the durable masters that feed the export CLI.

### What to do with each exported artifact

Run the export CLI on the downloaded file; the resulting `tmp/review-triage.yaml` has five sections:

- **`pins`** (from approvals): whole-word `data-expect` strings, each already validated for syntax (the repo’s real `parse_expect`) and semantics against the after-font. Copy each into its `suggested_home` (e.g. `site/the-manual.html`) as a `data-expect` / `data-expect-noncanonically` attribute — this is the opinions-become-pins loop from §10 item 5. `duplicate_of` flags pins already covered.
- **`policy_edits`** (from rejections): one-line `policy.prefer[+]` / `policy.refuse[+]` / `policy.contract[+]` records naming the target rune file, an appendable keypath, the deciding provenance records, and the decided stage. These are _drafts_, never auto-applied: review each, paste into the named `glyph_data/runes/*.yaml`, and rebuild. Units with `no_mechanical_draft` have no expressible one-line counter-lever — start from `names_provenance` and the unit’s explain panel by hand.
- **`any_of`** (from fine-either-way): candidate expect strings (after-behavior first) for the any-of channel, realized as `_assert_expect_any` until the corpus connective exists. Units whose before/after behaviors are whole-word-identical (cell-only divergences) deliberately carry a single candidate.
- **`neither`** (from neither-verdicts): both the old and the new behavior look wrong, so nothing automatic is drafted — no pin, no policy edit, no any-of. Each entry carries the unit id, codepoints, notation, the reviewer’s note, and `names_provenance` (the `glyph_data/runes/*.yaml` records the outcome was attributed to — the follow-up author’s levers). These units need fresh authoring work, starting from the provenance and the unit’s explain panel.
- **`identical`** (from identical-verdicts): the reviewer cannot see the flagged difference — the highlighted portion looks identical. Nothing is drafted; each entry carries only the unit id, codepoints, notation, and the reviewer’s note. These are claims that the flagged divergence is invisible, which is signal for the ink-comparator and highlight tooling (a difference it flagged that no human can spot), not a judgment on either font’s behavior.

## Mechanisms

### Machine-approved units

`rebuild/review/ink.py` is the build-time gate: a unit is `ink_identical` iff shaping its text in both shipped fonts under **every** config in its set produces identical placed outlines (uharfbuzz shaping via the validation `Shaper`, always with `kern: False` merged into the config’s features via `ink.kern_neutral`; per-glyph `DecomposingRecordingPen` outlines translated by the cumulative `x_advance` plus `x_offset`/`y_offset`; pieces sorted and compared). These units get `batch: null`, are excluded from batches, sidebar counts, and progress denominators, and surface in the app only behind the “Show no-verdict units” toggle, badged and verdict-disabled. On every machine-approved unit, and on every unit of a no-verdict class, the fragment itself is slim: `explain`, `drafts` and `highlight` are omitted outright — keys absent, never null, so the app can tell a slim fragment from a whole record with a blank in it (`slim_fragment` and `SLIM_OMITTED_KEYS` in `audit.py`; `check_unit` holds the shape exact in both directions, so a human unit without its explain material fails the build just as a slim unit carrying any of it does). Those fields were the bulk of every shard’s bytes and largest on exactly the shards nobody opens, and the pin draft replayed a shaping per unit besides, so no draft is computed for such a unit and the enricher renders it no candidate table. A show-machine fold draws its rows from what the slim fragment carries — the window, both fonts’ cells and seams, the badge, the summary — with no pair band, and the explain panel says what was left out when it opens on one. Two of the inputs that decide the shape sit outside the content key (picture identity and the class’s exemption), so the unit cache’s store record carries a `slim` flag and serves a fragment only when it is the shape this build would write: a unit crossing into the human workload on a ledger edit is re-enriched in full, and one crossing out is re-drafted slim. The manifest records the totals (the `machine_approved` totals, the method one-liner, per-class counts), the export CLI reports them as a `machine_approved` section in the triage YAML (counts, per-class counts, method, compact unit-id ranges — never as drafted pins), and `verdicts.json` stays human-verdicts-only. The numbers are pinned by tests and must reproduce exactly on a rebuild; in table-diff mode the same comparison runs over each entry’s witness string, and a witnessless entry stays in the human workload because there is nothing to shape.

### Picture-identical units

The second machine-approval channel, asked of every unit the ink gate refused: a unit is `picture_identical` iff, under **every** config in its set, both fonts fill exactly the same cells of the pixel grid — the whole-window rendering is one picture, and the name-grain change the audit recorded is ink handed from one glyph to a neighbor without changing the union (a seam pixel the old font double-drew and the rebuild draws once, as at ·At·J’ai; a stroke re-spelled onto the adjacent letter). `InkComparator.picture_identical` in `rebuild/review/ink.py` is the authority on the reading: each placed piece's cells come from `OutlineIntern.cells` translated to its pen position, the whole run's cells are unioned per font, and the unions are compared config by config. It is taken over the whole run rather than over `config_diff`'s localized delta on purpose — the delta strips a covering neighbor as common prefix, so a delta's cells alone cannot say whether the pixels one glyph lost are still painted by the piece beside it. It fails closed: an outline that is not grid-rectilinear, an off-grid placement, or a config whose pictures differ is no claim at all, and the unit queues. Piece identity implies picture identity, so the build asks the picture question only where `ink_identical` is false, and Junior equivalence only where both are false; a unit carries at most one channel flag, with `MACHINE_CHANNELS` in `rebuild/review/audit.py` fixing that precedence and `check_unit` enforcing it. `picture_identical` flows through `audit.Unit` and the unit JSON exactly like `junior_equivalent` — `batch: null`, its own `picture-identical — machine approved` badge, counted in `machine_approved_count`, the manifest's `machine_approved.channels.picture_identical` record with its method one-liner, and the export's `machine_approved` section (a verdict landing on such a unit, as the ones judged by hand before the channel existed do, is counted under `skipped_machine_approved` and drafts nothing) — and what it approved on a given surface is in that manifest record, with the totals in `rebuild/review-census-pins.json`. Picture identity is a whole-window property, so a picture-identical unit is seam-inert exactly as an ink-identical one is: the enricher computes no secondary seams for it, a seam homed on it is suppressed, and the app draws no seam band on it. Unlike `ink_identical`, the flag is a carry-presentation key (`CARRY_PRESENTATION_KEYS` in `rebuild/review/unit_cache.py`): it is a pure function of the window and both fonts' placed glyphs, which the content key already covers, so its arrival moved no content key and stranded no carried verdict. The pre-merge ink census stays at the piece grain; picture identity, like Junior equivalence, plays no part in it.

### Junior-equivalent units

The third machine-approval channel, asked only where neither ink nor picture identity holds, for the ss10-only units whose correctness never needed a human: `ink.JuniorOracle` approves a unit divergent **only** under ss10 (the suppress-all-joins set, whose ratified meaning is fully isolated letters — see the ss10 entries in `rebuild/m1-divergences.yaml`) when the rebuild's ss10 rendering places exactly the ink the shipped Junior font places for the same string, once Junior's letter tracking is removed. The premise — Junior carries the same isolated letterforms as Senior plus exactly one pixel of extra advance on every Quikscript glyph, and no advance difference anywhere else — is verified against the shipped Senior at oracle construction, which refuses to run if the fonts drift from it. A pass means the rebuild draws the canonical isolated rendering, so the new behavior is the spec by construction regardless of what the old font did (the old font variously kept joins, formed ligatures, or kerned under ss10). Units also divergent under any other config are never oracle-approved: the other legs still need judgment, and verdicts are per unit. `junior_equivalent` flows through `audit.Unit` and the unit JSON exactly like `ink_identical` (`batch: null`, its own `junior-equivalent — machine approved` badge, counted in `machine_approved_count` and the manifest's `machine_approved.channels.junior_equivalent` record alongside the Junior font's source and sha256). The oracle refuses the `· ◊ZWNJ` boundary windows where Junior lowers the namer dot and the rebuild's ss10 run draws the plain one, so those stay in the human workload; what it approved on any given surface is in that manifest record.

### No-verdict ledger classes

The class-blanket exemption channel, which keeps units nobody should be asked about from sitting in the verdict queue with live buttons: a ledger entry may carry `no_verdict: true`, meaning a ratified rule adjudicates the whole class and no unit in it ever needs an individual verdict. The flag flows from `rebuild/m1-divergences.yaml` through `audit.LedgerClass`/`Unit` into every unit and class record; `assign_batches` gives exempt units `batch: null` exactly like machine-approved ones (the §7 checker enforces both), the app reads `batch === null` (`needsNoVerdict` in `render.js`) as “needs no verdict” (out of the cursor queue, controls disabled, hidden behind the toggle, `no verdict needed` badge, sidebar progress replaced with the badge), and `export.py` skips any verdict record landing on an exempt unit (`skipped_no_verdict` in the triage counts) so stale masters can’t smuggle boundary pins into a triage YAML. Extending the flag to another class is a one-line ledger edit; `grep -n no_verdict rebuild/m1-divergences.yaml` lists the classes carrying it.

### Ink-duplicate unit merging

The third dedup channel, which stops the surface asking the same visual question twice: a unit (e.g. ·It·Day·Tea·No, “only when ss04 is on”) can be pixel-identical to its default-config sibling in both fonts — the old font’s ss04 lookups rename word-initial ·It (`qsIt.en-y0.ex-y0.before-day` vs `qsIt.ex-y0.before-day.after-no-baseline-join`) without moving any ink, and the name-grain `(codepoints, baseline, new)` dedupe key splits the window on the label alone. `audit.merge_ink_duplicate_units` (called by `build_m1` between `load_workload` and the ink-identical census) folds sibling units of the same window whose `InkComparator.signature` — the placed-outline pair for (before, after) — is identical across every config on both sides. The earliest-config sibling survives with the union of configs, rows, kinds, and `config_classes`, keeps its own name tuples for display, re-resolves its class UNMATCHED-wins, and collapses to a single render group (ink identity is exactly render-group identity, so the one-render-group invariant survives). A fold that would put two distinct matched ledger classes on one unit is skipped — different names legitimately hit different ledger predicates. Because `assign_family` runs post-merge, the merge also pulls relabeled-only ss04 halves out of `deferred-ss04` into the default families where their real adjudication lives, so they are never re-asked in the deferred pass. The signatures themselves come from the persisted ink-signature store beside the unit cache (issue 18; `unit_cache.py`'s docstring is the contract): each (window, config) digest is keyed by the audit row's rendered names plus the window families' digests, so a steady-state build folds the whole population without shaping anything, and only the key misses are re-shaped — across a spawn pool when the pile is deep enough to amortize its startup.

Two safety consequences. First, the manifest stamp: `_generated_at` derives from input mtimes, so a code-only change that renumbers units keeps the old stamp and lets a stale autosave or export attach by id to the wrong units. `build.UNIT_ASSEMBLY_EPOCH` floors the stamp; bump it whenever a build-code change re-keys or renumbers units with no input change. Second, verdict carry: `rebuild/tools/carry_verdicts.py` takes `--source SURFACE_DIR VERDICTS_JSON` (repeatable) and `--out`, excludes `secondary_seams` from the content key (its `home` field embeds another unit’s id, which churns on every renumbering), and falls back to matching by `(codepoints, ink signature)` — the merge criterion itself — for verdicts whose pre-merge content keys no longer exist. When a merged unit’s halves carry conflicting prior verdicts (the approve-vs-neither contradictions on ink-identical siblings are the double-ask pathology this whole mechanism retires), neither is carried and the unit is reported for one fresh look.

### Echo groups — one verdict per rendered change

The dedup channel one grain above the ink-duplicate merge: different windows whose before→after change is the exact same picture. The merge handles identical whole windows; echo groups handle the far larger population where the _change_ is pixel-identical — the same pieces of ink appearing and disappearing, the same judged letter pair, the same class and config set — but the surrounding letters differ (·Pea·Day·Tea·No, ·May·Day·Tea·No, ·It·Day·Tea·No, … all showing the identical ·Day·Tea regrouping). The grain is (configs, judged pair, class, localized ink delta, follower shift): unchanged flanking ink sits outside the delta even when it slid over because the change altered the run’s advance — a follower that merely moved by the width of a dropped extension is the same question, not a new one — while a window with no followers at all lacks the slid-over aspect and keys separately (its shift is 0).

Build side: `InkComparator.config_diff` returns the per-config before→after ink delta localized to the changed region — the two shaped runs aligned glyph-by-glyph from both ends, stripping the common prefix (same ink at the same position) and the common suffix (same ink rigidly shifted by one uniform dx), then multiset-differencing the remaining middles and jointly normalizing so the delta’s leftmost point sits at x=0, returning the two piece sets plus the suffix shift; the same pass that computes `ink_identical` (a diff of `IDENTITY_DIFF` — `((), (), 0)` — under every config) stashes it, and after family promotion every human unit gets an `echo: e-NNNN` group id (exempt units carry null; the §7 checker enforces both, and `totals.echo_groups` pins the count). The same pass also persists the delta identity on every unit as `ink_deltas` — one `ink.delta_digest` (`d-` plus twelve hex digits over the diff's repr) per config whose delta is nonempty, so ink-identical configs simply have no key — which is what an `ink_deltas` rule in `rebuild/standing-approvals.yaml` matches against: a blessed delta stops queueing in every future window where it is the whole ink change, however the judged pair, class, or surroundings differ. Two standing rules can also explain one window between them — the tool's composed reading, at the rendered-pixel grain, for a window that pairs a blessed slide with a blessed extension drop — so one blessed change riding beside another never re-queues either. Echo ids and `ink_deltas` are order-derived/recomputable and excluded from the carry content key, exactly like `secondary_seams`.

App side: a unit in a multi-member group shows an “echo ×N” chip (click = the group as a `#units=` worklist, stacked), and typing a group id (`e-NNNN`) into the cross-class search offers the whole group stacked the same way. A verdict on any member — button, key, canned reject/neither note, or `g` group-approve — fills the _unverdicted_ rest of the group with the same verdict and note as one undo step, with a toast reporting the fill; `skip` never echoes, already-verdicted members are never overwritten, and any member can still be individually overridden or cleared afterward (the store records stay per-unit, so export, import, autosave, and carry are all unchanged).

Seeding and auditing: `rebuild/tools/echo_verdicts.py <verdicts-file>` emits `verdicts-echo-fill.json` (fill records for blanks in unanimously-verdicted groups) and prints every group whose recorded verdicts disagree, each with a ready `#units=` deep-link. The artifact cycle runs it against the freshly-merged autosave and lands the fill file right after its carry+merge steps, so a blank whose group already holds a unanimous carried verdict never reaches a sitting — the app’s live fill only fires on in-session verdicts, and carried verdicts would otherwise leave such blanks stranded until someone ran the tool by hand.

### The artifact cycle mechanized

The commit-time artifact cycle is one command: `make artifact-cycle` (the driver is `rebuild/tools/artifact_cycle.py`; `make review-cycle` wraps it between a review-server stop and a restart, under `SERVE=0` between the stop and a printed restart command, which lets the target terminate for a non-interactive caller, or under `SERVE=bg` between the stop and a detached restart the recipe waits to see listening, which terminates the same way while leaving the app up). It snapshots the served surface, recompiles and vets M1.otf with `run_m1`, rebuilds the surface in place, carries prior verdicts forward onto the fresh manifest, merges the carried file into the live autosave, lands the echo-prefill and standing-approval fills through the same merge, refreshes the census pins from the build's census sidecar and prints their git diff, clusters the open complaints, and runs five gates — `gate:js` (the `node --test rebuild/review/jstests/*.test.js` glob form), `gate:make-test`, `gate:rebuild-contracts` and `gate:rebuild-validators` (the rebuild suite's two lanes, split by whether a test's fixture closure reaches a live build artifact — contracts reads none and runs at full xdist width on a closure holding no build output, validators reads `rebuild/out` and the surface and takes the width `rebuild/conftest.py` derives for it), and `gate:conform` (the exhaustive font-vs-settle sweep) — printing a summary table at the end even on failure. What it prints is one digest, identical on a terminal and down a pipe: a plan block that numbers every step and marks which will run and which a green record already skips, then per step a rule line, a short description of what that step is for, its `$ argv`, and only the lines worth surfacing out of the child — the phase it opened, the phase it closed and how long that took, its counters throttled to one in a while, and every warning — and at the end the summary table followed by `Cycle complete.` Nothing is dropped to buy that: `tmp/build-logs/<stamp>-<sha>/` (with `latest` pointing at the newest run) holds `plan.txt`, a byte copy of the terminal, and one log per spawned step with both of its streams merged in arrival order, and a failed step's log is replayed verbatim under its own banner before the summary.

Four of its rules are worth knowing without opening the driver. It refuses to start while a review server is listening on port 7294 — an in-place rebuild would strand the live session’s in-tab store and orphan its autosave across the manifest restamp (`--yes` overrides with a warning). It snapshots `rebuild/out/review` to `tmp/review-pre-<short hash>` before any mutation, which is both the carry input and the only recovery copy; a second pass at the same commit takes the next free `-2`, `-3` name rather than overwriting one, and the snapshot of a cycle that never finished is spared by the retention pass because it can be the only copy of a surface that cycle had begun rewriting. Because `run_m1` exits nonzero whenever any oracle rows are UNMATCHED — always true mid-migration — it gates on the four summary JSONs instead of the exit code, aborting only on defect errors, a boundary-gate failure, a Manual-pin failure, or `multi_matched > 0`. And every pass verifies before it hands the surface back: the heavy gates run in the pass that rebuilt what they check, so the letters never come up on a surface nothing has gated. A gate the pass did not run is unproven, not waived — its skip rides into the cycle summary, which `status.py` counts against readiness, so `make verdict-ready` and the app banner both stay NOT READY until a pass runs it. What keeps the loop cheap is the green records rather than any postponement: a pass that changed nothing skips every heavy stage and costs seconds. Everything else is the driver’s own reference: which master a `--verdicts`-less run resolves to carry, how the gates are scheduled so only one heavy pytest pool ever owns the box, which stages auto-skip on a provably-unchanged input closure, and what the green-finish retention pass prunes all live in its module docstring, and `--dry-run` prints the fully resolved plan without executing anything.

### Census pins as one reviewable file

`rebuild/review-census-pins.json` is the last accepted census — what a build measured about its own surface, in one checked-in file a human accepts by committing it. Every build emits those counts as the `census-facts.json` sidecar beside the manifest — `build_m1` writes it as a by-product: the pre-merge `audit`/`ink`/`families` groups derived from the pre-merge grain it captured before the ink-duplicate fold plus its own phase-1 products (a folded sibling shares its survivor’s ink verdict; a deferred-ss* family is pure config logic over the pre-merge config classes), and the post-merge `manifest`/`built` groups from the same in-memory state the shards were written from — and every non-rehearsal artifact-cycle pass copies the sidecar’s groups into the checked-in file and prints `git diff -- rebuild/review-census-pins.json` in full. There is nothing to re-baseline and no staleness to carry: the diff _is_ the review, and reading it is part of committing, with the judgment — does every moved number match the commit’s expected scope? — intact and in one place. The file’s top-level split says how much attention a moved number deserves: the `volatile` block holds the counts that legitimately move with every migrated letter, which want a glance, while the `invariant` block hoists out the structure those counts’ own keys imply — which classes the surface ships, which of them the build machine-approves, which are exempt from individual verdicts, and which verdict families the corpus reaches — so a new class or a new exemption reads as its own hunk instead of hiding among moved totals, and movement there wants a real explanation (`census.invariant_group` is the authority for what the block carries; both blocks come from one machine emission, so they cannot drift apart). Within the volatile block the groups stay divided by source and grain — `manifest` and `built` are post-merge (the shipped surface), `audit` and `ink` are the pre-merge name grain, `families` is the triple grain (a class count there can differ from the post-merge manifest, which is the proof the manifest cannot source it). The review test modules never read the file: they assert internal consistency and invariants they derive from the checked-in sources themselves, so a failure in one is a real failure with no census amnesty behind it. `rebuild/review/census.py` keeps the manual instruments: `--check` (the default) compares the checked-in file against a surface’s sidecar and exits nonzero with a per-key report; `--update` performs the copy by hand; `--surface DIR` names an already-built surface to read, and without it the tool builds a fresh temporary surface so it can never describe a stale one; `--from-scratch` is the independent source re-derivation to compare the sidecar against; what keeps the by-product derivation honest is `census.derive_premerge`'s own asserts over the capture it writes, since a folded sibling's ink verdict is its survivor's by definition now that `InkComparator.signature` is the pair of run-order ink lists `config_diff` reads. Semantic pins deliberately stay hardcoded in their tests: the drafts worked-example window, the enrich `diff_positions` exemplar, `FAMILY_ORDER`, and the `test_surface.py` unlock lists. `build_m1` and `build_table_diff` prune orphaned `units/*.json` shards after writing the manifest, so no shard outlives the units it held and the output dir never needs clearing by hand.

- **Source layout**: `rebuild/review/` is a normal package — `audit.py` (TSV + ledger ingestion), `tablediff.py`, `enrich.py` (seams, divergent positions, highlight ranges, explain attribution, all precomputed at build time), `drafts.py` (the three verdict drafters), `build.py`, `unit_cache.py` (the persisted per-unit cache the incremental build serves from, and the shared carry content-key definition), `app_index.py` (the sidecars the app boots from), `export.py`, `serve.py`, `static/` (the ES modules + CSS + HTML shell), `jstests/`. Tests live flat as `rebuild/test_review_*.py` plus `node --test` over `jstests/`.
- **Output contract**: `rebuild/out/review/` is fully self-contained — `index.html`, app JS/CSS, `manifest.json` (format `ams-review-manifest/2`, per-class counts, per-class machine-channel splits, per-class shard-part lists, and sha256-recorded font copies), the `units/` shards, the sidecars the app boots from (`app-units.ndjson.gz`, format `ams-review-app-index/1`, and the locator pair `app-locator.ndjson.gz`, format `ams-review-app-locator/2`, over `app-locator-rows.ndjson.gz` — see the bullet below), `units-index.ndjson.gz` (format `ams-review-unit-index/1`, the verdict plumbing’s own projection) and `unit-cache.ndjson.gz` (the incremental build’s store), `census-facts.json` (format `ams-census-facts/2`, what the cycle’s pin refresh and the manual check both read), `fonts/before.otf` + `fonts/after.otf`. The frontend↔engine interface is the manifest, the shard schema (REVIEW-PLAN.md §7.2), and the app sidecars’ row projection and byte spans (§7.4); the build runs its own contract self-check over all of them. Builds are byte-identical run to run (modulo `generated_at`). The app sidecars, the per-unit index and the unit-cache store are stamped with `unit_index.manifest_sha256` — the manifest’s identity over its parsed content, with the `static` fingerprint component the copied UI assets ride projected out — which is what lets `build.py refresh-assets` rewrite that one field over a served surface without invalidating any of them.
- **What the tab holds**: the app’s resident set is the review queue, not the corpus. It boots by streaming `app-units.ndjson.gz` a line at a time — one slim row per unit awaiting a verdict, carrying exactly the fields the docket, search, echo, filter, and progress paths read across the whole queue — so the tab’s heap grows with the human workload rather than with every migrated letter. What a card draws from its own record — the sample text, the pair band, the settled cells behind the seam underline, and the explain table and drafts behind the Why? button — is not in the row: each row carries the part index, byte offset, and byte length of its record inside its class shard, and the app Range-fetches that one record out of a static file when the card renders and again (or from its cache) when the explain panel opens, with no server-side logic and no endpoint. The machine-approved and no-verdict units are addressed the same way through the locator pair: `app-locator-rows.ndjson.gz` is one address per such unit, in shard order, written as a sequence of gzip members of at most `app_index.LOCATOR_BLOCK_ROWS` rows each and never spanning a class, and `app-locator.ndjson.gz` is the table of those members — each one’s byte span, class, and first and last id. A show-machine fold reads its class’s rows one block at a time and draws them a window at a time, with a button for the next window, so opening a fold on a large class costs one window rather than the class’s shards; a deep link to a machine unit binary-searches each class’s blocks by unit number and fetches the one member per class that can hold the id. The table is the only part of the locator a tab retains — the machine workload divided by the block size — and a worklist’s own machine records stay pinned for as long as that worklist is the view. All three sidecars are stamped with that same manifest identity and with `generated_at` (the rows file through the table, which records its byte length), so a tab holding an index written for another build refuses it rather than reading byte offsets into rewritten shards; the index and the table are gzipped on disk, served with `Content-Encoding: gzip` by `serve.py` and decompressed by the app itself when some other static file server hands them over undecoded, so an archived surface under `tmp/review-pre-*` still opens, and a block of the rows file is one whole gzip member either way. One accepted consequence: the cross-class search covers the human surface only — a machine-approved unit is reachable by id through a pasted `#unit=` link, not by searching for it.
- **Future migrations**: `build.py --mode table-diff --baseline <dir> --new <dir>` plus the `snapshot` subcommand generalize beyond the M1 audit TSV, so M2+ reviews reuse the same app unchanged.
- **At cutover**: the app moves out of `rebuild/out/` and (probably) the serve script merges into `tools/serve.py`’s livereload. The user-sanctioned `review-build` / `review-serve` Makefile targets already exist (plain `review` was taken); no `site/` changes, no existing pipeline files touched.
- **Known leftovers, not blocking**: a `{"type":"module"}` `package.json` is copied verbatim from `static/` into the output (harmless); `rebuild/review/fixtures/` and `rebuild/review/jstests/fixtures/` are divergent copies that should converge on one source of truth before cutover.

### Policy drafters

`drafts.py` picks one of four counter-levers per rejected unit:

- **`policy.contract[+]`** — a `contract by: N` lever, drafted only when the gained extension rides a join both fonts share, with the `when` window following the extension’s side.
- **`policy.refuse[+]`** — when the divergence includes a join the baseline didn’t have, a `contract` cannot restore the old break, so the drafter detects the new-join side against the baseline seam and refuses the anchor reaching across that gap, scoped to that neighbor (e.g. `{exit: x-height, when: {right: {family: [qsIt]}}, …}`).
- **`policy.prefer[+]` with `mode: absolute`** — on seam-identical units, where a refuse would break joins both fonts share; it pins the baseline cell (or stance) over the new anchors.
- **`no_mechanical_draft`** — adjustment-grain units (post-ZWNJ locked twins, bind pullbacks, non-summing-suppressed extensions) have no expressible one-line counter-lever and carry no policy draft; `export.py` still emits them in `policy_edits` with null fields, the unit’s provenance, and a `no_mechanical_draft` explanation, so rejected units never vanish from the triage YAML.

### Verdict families (UNMATCHED presentation)

The surface presents the **UNMATCHED** verdict windows as presentation-only families, which leaves the oracle untouched until those families are adjudicated.

- **Per-config class.** A render triple `(codepoints, baseline, new)` no longer maps to one ledger class: a window can be blessed under one stylistic set yet novel under the default config. `audit.py` keeps the window as one unit, records every config’s class in `config_classes`, and adjudicates the novel (default) behavior (UNMATCHED-wins); the shard carries a `config_class_note` blessed/novel strip the app renders as a badge. A two-_matched_-class triple still raises as a real bug.
- **Verdict families.** `families.py` groups the UNMATCHED triples into presentation-only synthetic classes (`status: unmatched`), appended after the ledger classes so they sort last and clean-unit ids stay stable. The grouper reads the before/after settled seams from `enrich` — a gain (`break → yN` or a raised seam) names a family by the joining pair (the seam is the left cell’s exit, i.e. a ligature’s trailing component, joining the right cell’s entry); every loss pools into `seam-loss-withdrawal`; an unchanged-seam/changed-cell window is `extension-non-summing`; anything else is the `unmatched-misc` catch-all (the grouper is total). Stylistic-set-only windows are parked in `deferred-ss04` / `deferred-ss10` / `deferred-ss03`, sorted last.
- **`after_cells` provenance.** `after_cells` is the re-derived settled cells, not the audit `new` column — the `kern-channel-out-of-scope` position-only rows carry per-slot diagnostics there, not cell tokens, so reading the audit column breaks the `after_seams`-parallel-`after_cells` contract over the full audit.
