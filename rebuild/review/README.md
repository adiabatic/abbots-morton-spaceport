# Treaty-diff review surface

## TL;DR

`rebuild/review/` is the source of a static review app, which the build writes to the gitignored `rebuild/out/review/`. The app shows one review unit per distinct divergence in `rebuild/out/m1/divergence-audit.tsv`, sharded by the ledger classes in `rebuild/m1-divergences.yaml`. Each unit renders side by side in the old Senior font and the M1 font through two `@font-face` rules, with the divergent pair highlighted, the row's `font-feature-settings` applied, boundary marks, a one-line explain summary, and a note field. A verdict covers the whole unit, meaning every config in its config set. A unit whose two renderings the build shows to be equivalent is approved by machine and is not queued for review.

The sections below cover the keys, the explain panel, the triage flow, the exported files, and the mechanisms that approve or deduplicate units before a person sees them.

### Commands

```sh
make review-build                                     # regenerate rebuild/out/review/
make review-serve                                     # serve it on http://localhost:7294/
uv run python -m rebuild.review.build                 # the same build, run directly
uv run python -m rebuild.review.serve                 # the same server, run directly
uv run python -m rebuild.review.export verdicts.json --out tmp/review-triage.yaml
```

`make review` builds the scoped-anchor-selector review page, so the review app's targets are `review-build` and `review-serve`.

The build is incremental. It stamps every unit with a content key over that unit's inputs and keeps a store of per-unit results beside the manifest (`rebuild/out/review/unit-cache.ndjson.gz`). The next build recomputes only the units an edit could have changed and copies the rest from the previous surface's shards byte for byte, so the cost of a write is proportional to what changed. `rebuild/review/unit_cache.py`'s docstring defines what the key covers and what is copied unchanged, and `rebuild/test_unit_cache.py` checks that served, pooled, and serial builds write identical bytes. The build's `manifest+check` and `cache` phase lines report how much was copied unchanged. `--fresh-unit-cache` ignores the store and recomputes every unit; the artifact cycle's `--fresh` passes it through.

The review server uses port 7294, so it can run at the same time as `make serve` (`tools/serve.py`, port 7293).

## Quick start for triage

### Kerning is disabled

Both columns render with kerning off: the sample cells set `font-kerning: none`, which combines with each row's `font-feature-settings`. Every comparison the build makes (the ink-identity census, highlight x-ranges, boundary-mark positions, pin checks) shapes with `kern: False` in both fonts (`ink.kern_neutral`). The rebuild emits no kerning until the kerning milestone (`doc/rebuild-design.md` §12), so the old font's kern feature would only add noise to before-and-after comparisons. Kern differences get their own review at that milestone. Turning kerning off changes nothing in the after font today; the setting is explicit so that it still applies after §12.

### Keyboard map

The in-app help overlay (`?`) lists every key, and `KEY_MAP`, `REJECT_MENU_MAP`, and `NEITHER_MENU_MAP` in `static/keyboard.js` define them.

The four main verdict keys are on the left home row: `a` skip, `s` reject, `d` fine either way, `f` approve. `e` records identical and `c` records neither. `a`, `d`, `e`, and `f` record the verdict and advance to the next unit. `s` and `c` open a small menu beside the row's verdict buttons, where a second key records the verdict with no comment, with a canned note, or with a custom comment, and a digit reuses a recent note. A canned note replaces whatever was in the note field. `Escape` or a click outside the menu cancels with no verdict, and the other shortcuts are off while the menu is open. `Backspace` or `Delete` clears the current unit's verdict, and pressing a unit's active verdict key again also clears it. `u` undoes the most recent verdict from anywhere. `g` approves every unverdicted unit in the cursor's group. Shortcuts are off while a note field has focus; `Escape` leaves it.

Reject means the old behavior should come back. Neither means both behaviors look wrong, so the unit needs new authoring work. Identical means the reviewer cannot see the flagged difference in the highlighted portion; that is feedback for the ink comparator and highlight tooling, not a judgment on either font.

A verdict covers every config in the unit's config set. Most units show no config badge because they diverge under every non-ss10 config. A badge such as "only when ss03 is on" marks a narrower set; hover it for the full list.

Approving a unit outlines its after sample in green, rejecting draws a red X over the after sample, either outlines both samples in green, and neither draws the red X over both. The row's recorded verdict drives these marks, so they persist through re-render and import and clear on undo.

### Reading the explain panel

Every row shows a one-line summary under the renderings: what the new pipeline chose at the primary divergence and the single record that decided it, in rune-name notation, for example "New: ·It joins ·It at the baseline (the old pipeline broke there) — decided by qsIt.yaml policy.extend[0] (join-count rank)." The Why? button, or `x`, opens the full panel:

- **Explain** is the candidate table settlement considered at each divergent position. It lists every surviving candidate with its entry, seam, and join-count, marks the winner with `->`, attributes each eliminated candidate to the rune record that eliminated it, and ends with a `decided by:` line naming the stage that separated the winner from the runner-up. `_STAGE_PHRASES` in `enrich.py` lists the stages.
- **Provenance** lists the `glyph_data/runes/*.yaml` records the outcome is attributed to. A reject's policy draft names these records.
- **Drafts** previews the three drafts (pin, policy edit, any-of) this unit's verdict would export.

### Triage flow

- The sidebar lists the ledger classes with the ledger's `why` and `status` text, and clicking a class filters to it. Every class with units in the current batch or worklist has a light accent outline, and the class holding the cursor unit has the full cursor-blue outline; both are separate from the border that marks a clicked class filter. Within a class, units are grouped by lead-family pair (each group folds), ordered by code point, and paged in batches of `audit.BATCH_SIZE`; the toolbar arrows page batches, and `[` and `]` change class.
- The header strip starts with a chip showing the surface's unit total. Its popover shows the generation stamp and head, how many letters have migrated, and the total split into machine-approved units (by channel), units in no-verdict classes, and units left for human review, which is the Overall denominator. After the chip come Overall progress with per-verdict tallies, the selected class's progress when a class filter is on, and the current batch's progress. A batch can span classes and a class can span batches, but selecting a class narrows the batch list. Each sidebar entry's counts line (`classCountsLine` in `static/render.js`) reads: class units, machine-approved, verdicted out of human, rows. Progress counts cover the human workload only.
- Machine-approved units (ink-identical, picture-identical, or junior-equivalent) and units in no-verdict classes are hidden by default. The toolbar's "Show no-verdict units" toggle (`machine=1` in the URL hash) shows them in collapsed folds by class below the human units. Each row has a badge (its channel's "… — machine approved", or "no verdict needed") and disabled verdict buttons whose title says why no verdict is needed. A `#unit=` link to one of these units while the toggle is off shows that one unit until you navigate away, and leaves the toggle and the URL unchanged. Keyboard navigation, auto-advance, and `g` cover the human workload only.
- View state lives in the URL hash (`STATE_KEYS` in `static/state.js`), so reloading or sharing the URL restores the view. Verdicts autosave. After every change the app POSTs the verdicts it set or cleared (an `ams-review-verdicts-delta/1` body, never the whole store) to the serve script's `/autosave` endpoint. The server keeps the store in memory (`rebuild/review/verdict_store.py`) and atomically rewrites `verdicts-autosave.json` at the repo root. That file is outside `rebuild/out/review/` so that livereload's JSON watch does not reload the page on every save. On load the app restores an autosave whose stamp matches the manifest, and afterward it asks `/autosave?since=<token>` for only what other sessions changed. A reload, crash, or closed tab loses no work, and the size of a save does not grow with the number of carried verdicts in the store. An autosave whose `manifest_generated_at` differs from the live manifest is never joined by unit id: the app does not restore it and shows a toast, and before the server writes the new store it moves the old file aside as `verdicts-autosave-<stamp>.json`, which keeps the pre-rebuild work for a carry. The warnings about unexported verdicts (the beforeunload prompt and a toast every 50 unexported verdicts) appear only when autosave is not working, for example when a server without the endpoint serves the surface. When autosave works, the status bar's unexported count ends in "(autosaved)".
- **The docket view** (the header's Docket button, `#view=docket`) is the live queue of blank human units, where blank means unverdicted or skipped. It groups them by the build's `cluster` signature, which is the echo key without the judged pair, so one visual change that recurs across letter contexts is one card. The largest decisions come first: the first `TRANCHE_SIZE` clusters as cards with exemplar renderings and evidence from judged lookalikes, the remaining clusters as a compact table, singletons in chunks of `SINGLETON_CHUNK`, and every echo group whose recorded verdicts disagree (all in `static/docket.js`). Every button is a `#units=` worklist link that carries `docket=1` and the surface's `generated_at` stamp, so judging uses the normal keyboard flow with echo fill. Finishing a worklist opens the next decision by itself: the first one this sitting has not yet opened, so leaving a card postpones it; once every open decision has been shown, the one shown longest ago comes back (`nextDocketDecision`). A tab that resumes a worklist stamped for another surface build goes to the live queue instead of rendering the old id list, because a unit whose content changed has a new id. The view recomputes from the in-memory store as verdicts are recorded, so clusters shrink, empty, and move up with no re-bake. Blank units in classes the ledger has already ruled on (`RULED_STATUSES`) are left out behind a one-line count, since a class-level decision or a bulk-proposal import covers them. Any filter or class click leaves the view.
- `rebuild/tools/review_docket.py <verdicts-file>` writes the same clustering, fixed against one verdicts file, to `tmp/docket-data.json` as input for bulk proposals. `rebuild/tools/complaint_docket.py` (`make complaint-docket`) clusters the open reject and neither verdicts by the rune records that decided them and writes `tmp/complaints-data.json`. For each group it lists park candidates (blank units the same records decide), and `--park` writes `verdicts-park-*.json` skip files for the Import dialog. `parked` is one of the note-marker kinds; `CARRIED_PROVENANCE_PREFIX` in `static/verdicts.js` and `_MARKER` in `rebuild/tools/verdict_notes.py` list the same set.
- Each row shows the code point string in both fonts on a checkered background. The divergent pair has an amber band drawn from x-ranges in font units that the build computes; the app never measures text. A dotted line marks each boundary token (space, namer dot, or ZWNJ). The row also has the one-line summary, a Copy button that copies a prompt preamble for the unit, and a Why? button (or `x`) that opens the explain panel with the attribution described in `doc/rebuild-design.md` §6.3. Regions without a mark render identically in both fonts or differ only in glyph names.
- The text lines use the same amber: the notation line (·May·Oy·It·May) and the code point line (E665:E679:E670:E665) underline the divergent pair's tokens in the band's `--hot` color. The build computes the mapping (`pair_codepoints`, a span of code point positions, and `notation_tokens`, one per code point position) because ligatures make glyph positions differ from code point positions. A unit with no primary pair shows both lines unmarked. A secondary seam with no home unit (an "only here" seam, below) gets a dashed underline on the text lines; other secondary seams are not marked there.
- A longer unit can contain divergent seams besides the amber primary pair. Each such secondary seam shows in both columns as a dimmer dashed band with a chip naming its home unit, the shortest unit where the same before-and-after behavior is the primary judgment. Clicking the chip opens that unit, across batches and classes and on machine-approved units too. A chip reading "only here" means no shorter home unit exists (a context-dependent divergence at the depth-2 horizon), so judge that seam in this unit. A seam whose home unit is ink-identical or picture-identical gets no marker, since there is nothing visible to judge. The manifest's `secondary_seams` record counts the markers, and the §7 checker compares it with the shards.
- No chip strip lists every config a unit diverges under, because for most units (those that diverge under every non-ss10 config) it would say nothing. A unit whose config set is informative has a badge of inert chips, one per stylistic set that pins the set down. Each chip uses its set's color, is lit when the set must be on and muted when it must be off, and is glossed with the set's `feature_descriptions` entry. `build.config_badge` computes both the chips and their text: it finds the smallest conjunction of on/off constraints that selects exactly the unit's config set, and falls back to one literal "only under: …" chip when no short conjunction does. The app renders each clause's `text` as given. The badges mark the cases that matter for judgment (ss03-gated, ss03-excluded, ss10-only, and narrower two- and three-set conjunctions), which also explain the row's `font-feature-settings`. Each chip's title lists the full config set. The docket's cluster headers show the same chips.
- Units are deduplicated by (codepoints, baseline outcome, new outcome), so every config of a unit renders the same. The build groups configs by rendered outcome into `render_groups`, and the §7 checker fails an m1-audit build with a unit of more than one group. The app can still draw extra groups, each before-and-after pair stacked below the first with its own config label and feature settings.
- A verdict always covers the whole unit. `verdicts.json` records have no `configs` field, and an import ignores one.
- _Export_ downloads `verdicts.json` (format `ams-review-verdicts/1`, notes included). _Import_ merges an earlier export by unit id and asks before merging a file stamped for a different manifest, so triage can span sessions. `verdicts-autosave.json` is a rolling copy for the live manifest; downloaded exports are the durable masters the export CLI reads.

### What to do with each exported artifact

Run the export CLI on the downloaded file. The resulting `tmp/review-triage.yaml` has a `review` header with counts, a `machine_approved` section (see "Machine-approved units"), and five verdict sections:

- **`pins`** (from approvals): whole-word `data-expect` strings, each checked for syntax with the repo's `parse_expect` and for meaning against the after font. Copy each into its `suggested_home` (for example `site/the-manual.html`) as a `data-expect` or `data-expect-noncanonically` attribute; this is how an approved behavior becomes a pin (`doc/rebuild-design.md` §10, item 5). `duplicate_of` flags pins the corpus already has.
- **`policy_edits`** (from rejections): one-line `policy.prefer[+]`, `policy.refuse[+]`, or `policy.contract[+]` records, each naming the target rune file, an appendable keypath, the provenance records that decided the outcome, and the decided stage. These are _drafts_ and are never applied automatically: review each, paste it into the named `glyph_data/runes/*.yaml`, and rebuild. An entry with `no_mechanical_draft` has no one-line counter-lever; start from its `names_provenance` and the unit's explain panel.
- **`any_of`** (from fine-either-way): candidate expect strings, after-behavior first, for the any-of check, which `_assert_expect_any` (`test/quikscript_shaping_helpers.py`) implements until the corpus has an any-of connective. A unit whose before and after behaviors give the same whole-word string (a cell-only divergence) has one candidate.
- **`neither`** (from neither verdicts): both behaviors look wrong, so nothing is drafted. Each entry has the unit id, code points, notation, the reviewer's note, and `names_provenance`, the `glyph_data/runes/*.yaml` records the outcome is attributed to. These units need new authoring work, starting from those records and the unit's explain panel.
- **`identical`** (from identical verdicts): the reviewer cannot see the flagged difference. Nothing is drafted; each entry has the unit id, code points, notation, and the reviewer's note. These entries report a difference the ink comparator and highlight tooling flagged that no person can see; they are not judgments on either font.

## Mechanisms

### Machine-approved units

`rebuild/review/ink.py` decides ink identity at build time. A unit is `ink_identical` when shaping its text in both shipped fonts under every config in its set places identical outlines. Shaping uses uharfbuzz through the validation `Shaper`, always with `kern: False` added to the config's features (`ink.kern_neutral`). Each glyph's `DecomposingRecordingPen` outline is placed at the cumulative `x_advance` plus its `x_offset` and `y_offset`, and the sorted pieces are compared.

Machine-approved units take no place in the triage index (the manifest's `human_unit_ids`), so they are in no batch, no sidebar count, and no progress denominator. The app shows them only behind the "Show no-verdict units" toggle, with a badge and disabled verdict buttons.

Every machine-approved unit, and every unit of a no-verdict class, is written as a slim fragment: `explain`, `drafts`, and `highlight` are absent, not null, so the app can tell a slim fragment from a full record with an empty field (`slim_fragment` and `SLIM_OMITTED_KEYS` in `audit.py`). `build.check_unit` checks the shape both ways: a human unit missing its explain material fails the build, and so does a slim unit that carries any of it. These fields were most of every shard's bytes, and the pin draft ran one shaping per unit, so the build drafts nothing for these units and writes no candidate table. A show-machine fold draws its rows from what the slim fragment has (the window, both fonts' cells and seams, the badge, the summary) with no pair band, and the explain panel says what was left out. Two of the inputs that decide the shape are outside the content key (picture identity and the class's exemption), so the unit cache's store record has a `slim` flag and serves a fragment only when it has the shape this build would write. A unit that joins the human workload after a ledger edit is enriched in full, and one that leaves it is redrafted slim.

The manifest's `machine_approved` record holds the totals, each channel's method one-liner, and per-class counts. The export CLI reports them as the triage YAML's `machine_approved` section: counts, per-class counts, method, and the sorted unit ids, never drafted pins. `verdicts.json` holds human verdicts only. The census pins (`rebuild/review-census-pins.json`) record the totals. In table-diff mode the same comparisons run over each entry's witness string, and an entry with no witness stays in the human workload because there is nothing to shape.

### Picture-identical units

The second machine-approval channel runs on every unit the ink check did not approve. A unit is `picture_identical` when, under every config in its set, both fonts fill the same cells of the pixel grid. The whole window renders as one picture, and the glyph-name change the audit recorded only moves ink from one glyph to a neighbor without changing the union: for example, a seam pixel the old font drew twice and the rebuild draws once, as at ·At·J’ai, or a stroke redrawn as part of the adjacent letter. `InkComparator.picture_identical` in `rebuild/review/ink.py` defines the check: `config_diff` returns `IDENTITY_DIFF` under every config. `config_diff` reads the whole run: each placed piece's cells from `OutlineIntern.cells` are moved to the piece's pen position, unioned per font, and subtracted both ways. So the flag and the stored `ink_deltas` come from one computation, and a picture-identical unit has empty `ink_deltas`, as an ink-identical one does. The check fails closed: an outline that is not grid-rectilinear, an off-grid placement, or a config whose pictures differ approves nothing, and the unit is queued.

Ink identity implies picture identity, so the build asks the picture question only where `ink_identical` is false, and asks about Junior equivalence only where both are false. A unit carries at most one channel flag; `MACHINE_CHANNELS` in `rebuild/review/audit.py` sets that precedence and `check_unit` enforces it. `picture_identical` is handled like `junior_equivalent`: the unit takes no place in the triage index, has its own "picture-identical — machine approved" badge, counts toward `machine_approved_count`, and appears in the manifest's `machine_approved.channels.picture_identical` record with its method one-liner and in the export's `machine_approved` section. A verdict recorded on such a unit is counted under `skipped_machine_approved` and drafts nothing. That manifest record lists what the channel approved on a given surface, and the totals are in `rebuild/review-census-pins.json`. Picture identity is a property of the whole window, so a picture-identical unit has no visible seam change, as an ink-identical one has none: it carries no secondary seams (the §7 checker enforces this), a secondary seam whose home unit is picture-identical is suppressed, and the app draws no seam band on it.

Unlike `ink_identical`, `picture_identical` is in `CARRY_PRESENTATION_KEYS` (`rebuild/review/unit_cache.py`), so it is not part of the content key. The flag depends only on the window and both fonts' placed glyphs, which the key already covers, so leaving it out changes no key and strands no carried verdict. The pre-merge ink census counts ink identity only; picture identity and Junior equivalence play no part in it.

### Junior-equivalent units

The third machine-approval channel runs only where neither ink nor picture identity holds, and covers ss10-only units whose correctness needs no person. `ink.JuniorOracle` approves a unit that diverges **only** under ss10 (the set that suppresses all joins, whose ratified meaning is fully isolated letters; see the ss10 entries in `rebuild/m1-divergences.yaml`) when the rebuild's ss10 rendering places the same ink as the shipped Junior font for the same string, once Junior's letter tracking is removed. The oracle assumes that Junior has the same isolated letterforms as Senior plus one constant extra advance on every Quikscript glyph and no advance difference anywhere else. Its constructor checks the advance part of this against the shipped Senior, takes the tracking from it, and raises `ValueError` if it does not hold. A pass means the rebuild draws the canonical isolated rendering, so the new behavior matches the specification whatever the old font did (under ss10 the old font variously kept joins, formed ligatures, or kerned). A unit that also diverges under any other config is never approved by the oracle, because those configs still need judgment and a verdict covers the whole unit. `junior_equivalent` is handled like `ink_identical`: the unit takes no place in the triage index, has its own "junior-equivalent — machine approved" badge, and counts toward `machine_approved_count` and the manifest's `machine_approved.channels.junior_equivalent` record, which also records the Junior font's source and sha256. The oracle does not approve the `· ◊ZWNJ` boundary windows: Junior draws the namer dot lowered and the rebuild's ss10 run draws the plain one, so the ink differs and those units stay in the human workload. That manifest record lists what the channel approved on a given surface.

### No-verdict ledger classes

This channel exempts whole classes, so units nobody needs to judge do not sit in the verdict queue with live buttons. A ledger entry with `no_verdict: true` says a ratified rule decides the whole class, so no unit in it needs its own verdict. The flag goes from `rebuild/m1-divergences.yaml` through `audit.LedgerClass` and `Unit` onto every unit and class record. `assign_batches` gives exempt units no place in the triage index, as it does machine-approved ones. The app's `needsNoVerdict` (`static/render.js`) reads a fragment's flags (`no_verdict` or any machine channel), and a unit it matches is out of the cursor queue, has its controls disabled, is hidden behind the toggle, and shows a "no verdict needed" badge; the sidebar shows the badge in place of the class's progress. `export.py` skips any verdict recorded on an exempt unit (`skipped_no_verdict` in the triage counts), so an old verdicts master cannot add boundary pins to a triage YAML. Adding the flag to another class is a one-line ledger edit; `grep -n no_verdict rebuild/m1-divergences.yaml` lists the classes that have it.

### Ink-duplicate unit merging

This merge keeps the surface from asking the same visual question twice. A unit (for example ·It·Day·Tea·No, "only when ss04 is on") can be pixel-identical in both fonts to its default-config sibling: the old font's ss04 lookups rename word-initial ·It (`qsIt.en-y0.ex-y0.before-day` against `qsIt.ex-y0.before-day.after-no-baseline-join`) without moving any ink, and the `(codepoints, baseline, new)` dedupe key compares names, so it splits the window on the name alone. `audit.merge_ink_duplicate_units`, which `build_m1` calls after `load_workload` and before enrichment, folds sibling units of the same window whose `InkComparator.signature` (the placed-outline pair for before and after) is identical under every config on both sides. The earliest-config sibling survives with the union of the configs, rows, kinds, and `config_classes`, keeps its own name tuples for display, re-resolves its class with UNMATCHED winning, and collapses to one render group, since ink identity is render-group identity. A fold that would put two different matched ledger classes on one unit is skipped, because different names can match different ledger predicates. `assign_family` runs after the merge, so the merge also moves ss04 halves that differ only by name out of `deferred-ss04` into the default families where they are decided, and they are not asked again in the deferred pass.

The signatures come from the ink-signature store beside the unit cache (`ink-signatures.tsv.gz`; `unit_cache.py`'s docstring describes it). Each (window, config) digest is keyed by the audit row's rendered names plus the digests of the window's families, so a build with nothing changed folds every unit without shaping anything. Only key misses are shaped, across a spawn pool when there are enough of them to cover the pool's startup cost, at a width set by the machine's cores (`--signature-jobs`, `artifact_cycle.signature_job_budget`) instead of the build's memory-derived `--jobs`.

Two safety rules follow from unit ids being content keys. First, the manifest stamp: `_generated_at` derives from input mtimes, so a code-only change that re-keys units (moving their content keys and so their ids) would keep the old stamp and let a stale autosave or export attach by id to the wrong units. `build.UNIT_ASSEMBLY_EPOCH` sets a minimum for the stamp; bump it whenever a build-code change re-keys units with no input change. Second, the verdict carry: `rebuild/tools/carry_verdicts.py` takes `--verdicts VERDICTS_JSON` (repeatable) and `--out`, and writes each verdict onto the current unit with the same content id without opening any other surface. A verdict whose unit is no longer on the surface is stranded; the carry's `carry figures:` line says how many were, and the cycle records that line on its run line in the timings journal. The content key leaves out `secondary_seams` (listed in `unit_cache.CARRY_PRESENTATION_KEYS`), because its `home` field holds another unit's id, which is a relation between units and not a fact about this one.

### Echo groups — one verdict per rendered change

Echo groups deduplicate one level above the ink-duplicate merge: different windows whose before-to-after change is the same picture. The merge handles identical whole windows. Echo groups handle the much larger set of windows where the _change_ is pixel-identical (the same pixels appear and disappear, with the same judged letter pair, class, and config set) but the surrounding letters differ, as in ·Pea·Day·Tea·No, ·May·Day·Tea·No, and ·It·Day·Tea·No, which all show the same ·Day·Tea regrouping. The key is (configs, judged pair, class, localized pixel delta, follower shift). Unchanged flanking ink is outside the delta even when it moved because the change altered the run's advance, so a follower that only moved by the width of a dropped extension is the same question. A window with no followers has no moved ink and keys separately, with a shift of 0. The key compares the rendered picture, not the glyph pieces. A change that paints no different pixel (·At giving up a crown pixel that ·J’ai paints anyway, or an overlap removed at a seam) is not a change. On its own, such a window is picture-identical and is never queued. Beside a real change, the window gets the same key as the windows that have only the real change, and a verdict on them covers it. The same ink moved at a seam that the neighbor no longer reaches paints a real hole and stays in the delta.

Build side: `InkComparator.config_diff` returns each config's before-to-after delta at the picture grain, localized to the changed region: the cells only one font paints, shifted so the delta starts at column 0, plus the follower shift. The `rebuild/review/ink.py` module docstring describes how it is computed. The same pass computes `ink_identical` (the sorted placed pieces are equal under every config) and `picture_identical` (a diff equal to `IDENTITY_DIFF`, `((), (), 0)`, under every config, asked only where `ink_identical` is false). After family promotion every human unit gets an `echo` group id, `e-` followed by eleven base58 symbols derived from the key (`unit_cache.echo_id_for`), and every unit outside the human workload has `echo: null`; the §7 checker enforces both, and the manifest's `totals.echo_groups` gives the count.

The same pass stores each unit's delta identities as `ink_deltas`: one `ink.delta_digest` (`d-` plus twelve hex digits over the diff's repr) per config whose delta is not `IDENTITY_DIFF`, so ink- and picture-identical configs have no entry. An `ink_deltas` rule in `rebuild/standing-approvals.yaml` matches against these digests. A blessed delta stops queueing in every future window where it is the whole visible change, whatever the judged pair, class, or surrounding letters. When the delta's shape changes, the rule's digest is re-derived from the standing probe's family line, never edited by hand. Two or more standing rules can also cover one window together: the composed reading in `rebuild/tools/standing_verdicts.py`, at the same rendered-pixel grain, covers a window that combines a blessed slide with a blessed extension drop, so a blessed change that appears beside another is not queued again. Echo ids and `ink_deltas` can be recomputed and are left out of the carry content key, as `secondary_seams` is.

App side: a unit in a group with more than one member shows an "echo ×N" chip; clicking it opens the group as a `#units=` worklist, stacked. Typing a group id into the cross-class search offers the same stacked group. A verdict on any member, whether from a button, a key, a canned reject or neither note, or `g`, fills the _unverdicted_ rest of the group with the same verdict and note as one undo step, and a toast reports the fill. `skip` never echoes, members that already have a verdict are never overwritten, and any member can still be overridden or cleared on its own. The store keeps one record per unit, so export, import, autosave, and carry are unaffected.

Seeding and auditing: `rebuild/tools/echo_verdicts.py <verdicts-file>` writes `verdicts-echo-fill.json` (fill records for the blank members of groups whose recorded verdicts agree) and prints every group whose recorded verdicts disagree, each with a `#units=` link. The artifact cycle runs it on the freshly merged autosave and merges the fill file right after its carry and merge steps. The app's live fill fires only on verdicts recorded in the app, so without this step a blank whose group already has an agreed carried verdict would reach a sitting and stay blank until someone ran the tool by hand.

### The artifact cycle mechanized

`make artifact-cycle` runs the commit-time cycle; `rebuild/tools/artifact_cycle.py` is the driver. It recompiles and checks M1.otf with `run_m1` and judges that step from its summary JSONs (the `run_m1` gate, below). It then rebuilds the surface in place and runs the verdict plumbing: it carries prior verdicts onto the new manifest, merges the carried file into the live autosave, applies the echo and standing-approval fills through the same merge, and clusters the open complaints. Next it refreshes the census pins from the build's census sidecar and prints their git diff, and runs four gate steps: `gate:js` (`node --test` over `rebuild/review/jstests/*.test.js`), `gate:make-test`, `gate:rebuild-contracts` (the rebuild suite, which reads no live build artifact), and `gate:conform` (the exhaustive font-versus-settlement sweep). It prints a summary table at the end, even on failure. `make review-cycle` runs the same pass and then serves the surface; the driver decides whether the pass has to stop the review server (`--stop-server`), and `SERVE=0` or `SERVE=bg` let the target exit (the Makefile comments above the target describe both). The terminal shows a digest of each step, and `var/build-logs/<stamp>-<sha>/` (`latest` points at the newest run) keeps `plan.txt`, a byte copy of the terminal, and one full log per step. `doc/review-cycle.md` is the runbook.

Three rules are worth knowing without reading the driver. When a pass would rewrite the surface or the verdict store while a review server listens on port 7294, it refuses to start, because an in-place rebuild would leave the open tab's store and its autosave stamped for the old manifest. `--stop-server` lets it stop the server instead, and `--yes` overrides the refusal with a warning. `run_m1` exits nonzero whenever any oracle rows are UNMATCHED, which is always true mid-migration, so the cycle judges it from its three summary JSONs instead of its exit code and fails only on defect errors, a Manual-pin failure, or `multi_matched > 0`. And every pass runs the heavy gates on what it rebuilt before the surface is served, so the app never serves a surface that no gate has checked. A gate the pass did not run counts as not passed unless a matching green record shows that the same inputs already passed; the cycle summary records each skip, `rebuild/review/status.py` counts it against readiness, and `make verdict-ready` and the app banner stay NOT READY until a pass runs the gate. The green records keep the loop fast: a pass after verdict-only changes skips every heavy stage and takes seconds. The driver's module docstring covers the rest: which master a run without `--verdicts` carries, how the gates are scheduled so that only one heavy pytest pool runs at a time, which stages skip on an unchanged input closure, and what the retention pass after a green finish prunes. `--dry-run` prints the resolved plan without running anything.

### Census pins as one reviewable file

`rebuild/review-census-pins.json` is the last accepted census: what a build measured about its own surface, in one checked-in file that a person accepts by committing it. `build_m1` writes the same counts as the `census-facts.json` sidecar beside the manifest. It derives the pre-merge `audit`, `ink`, and `families` groups from the pre-merge state it captured before the ink-duplicate fold plus its own phase-1 products (a folded sibling shares its survivor's ink verdict, and a deferred-ss* family depends only on the pre-merge config classes), and the post-merge `manifest` and `built` groups from the in-memory state the shards were written from. Every non-rehearsal artifact-cycle pass copies the sidecar's groups into the checked-in file and compares the result with the git index copy. Nothing has to be re-baselined: committing the rewritten file is the acceptance, and the cycle summary's `census pins` line says what is being accepted.

The file has two top-level blocks so that the line can say what kind of change a pass made. The `volatile` block holds the counts that change with every migrated letter; when only it changed, the line reads `invariant unchanged` and nothing is printed (the surface's totals are in `rebuild/out/cycle_summary.json`). The `invariant` block holds the structure that the volatile counts' own keys imply: which classes the surface ships, which of them the build machine-approves, which are exempt from verdicts, and which verdict families the corpus reaches. When it changed, the line names the change class by class (`census.invariant_delta`), and the block's own diff is printed under the census banner without the volatile hunks (`census.invariant_diff`). A change there needs an explanation. `census.invariant_group` defines what the block holds, and both blocks come from one machine emission, so they cannot disagree. The summary's `census reach` line beside it reports the one census fact recorded nowhere else. Machine approval is emergent, because a class is machine-approved when the build approved at least one of its units through any channel, so `census.reach` compares the ledger's `ink_identical` and `no_verdict` declarations with the classes the corpus reached and machine-approved, in both directions, and `cycle_summary.json` stores the sets under `census_reach_sets`. Within the volatile block the groups stay separated by source and grain: `manifest` and `built` are post-merge (the shipped surface), `audit`, `ink`, and `families` count pre-merge units, the (codepoints, baseline, new) triples before the ink-duplicate fold, so a class count there can differ from the post-merge manifest's.

The review test modules never read the file. They check internal consistency and invariants they derive from the checked-in sources, so a failing test is a real failure. `rebuild/review/census.py` is the manual tool: `--check` (the default) compares the checked-in file with a surface's sidecar and exits nonzero with a per-key report; `--update` does the copy by hand; `--surface DIR` reads an already-built surface, and without it the tool builds a fresh temporary surface so it never describes a stale one; `--from-scratch` recomputes the `audit`, `ink`, and `families` groups from the source inputs instead of reading them from the sidecar, which shapes and enriches the corpus again, and `--check` or `--update` then uses the result. `census.derive_premerge` checks the sidecar's pre-merge derivation with assertions over the capture it reads. Some expected values stay hardcoded where they are used: the drafts worked-example window, the enrich `diff_positions` exemplar, `FAMILY_ORDER`, and the unlock lists in `rebuild/test_surface.py`. `build_m1` and `build_table_diff` delete `units/*.json` shards the new manifest no longer references, after writing it, so no shard outlives its units and the output directory never needs clearing by hand.

- **Source layout**: `rebuild/review/` is a Python package, and each module's docstring says what it does (`rebuild/REVIEW-PLAN.md` §1.1 describes the layout). `static/` holds the app's ES modules, CSS, and HTML shell, and `jstests/` holds its `node --test` tests. The Python tests are `rebuild/test_review_*.py` and their neighbors under `rebuild/`.
- **Output contract**: `rebuild/out/review/` is self-contained. It holds `index.html` and the app's JS and CSS; `manifest.json` (format `ams-review-manifest/2`, with per-class counts, per-class machine-channel splits, per-class shard-part lists, and font copies with their sha256); the `units/` shards; the app sidecars (`app-units.ndjson.gz`, format `ams-review-app-index/1`, and the locator pair, `app-locator.ndjson.gz`, format `ams-review-app-locator/2`, over `app-locator-rows.ndjson.gz`; see the next item); `units-index.ndjson.gz` (format `ams-review-unit-index/1`, the verdict plumbing's projection); `unit-cache.ndjson.gz` and `ink-signatures.tsv.gz` (the incremental build's stores); `census-facts.json` (format `ams-census-facts/2`, read by the cycle's pin refresh and by the manual check); and `fonts/before.otf` and `fonts/after.otf`. The interface between the build and the app is the manifest, the shard schema (`REVIEW-PLAN.md` §7.2), and the app sidecars' rows and byte spans (§7.4); the build checks its output against all of them. Builds are byte-identical run to run (except `generated_at`). The app sidecars, the per-unit index, and the unit-cache store are stamped with `unit_index.manifest_sha256`, the manifest's identity over its parsed content with the `static` fingerprint component (the copied UI assets) left out. That is why `build.py refresh-assets` can rewrite that one field on a served surface without invalidating any of them.
- **What the tab holds**: the app keeps the review queue in memory, not the corpus. It boots by streaming `app-units.ndjson.gz` one line at a time: one slim row per unit awaiting a verdict, with the fields the docket, search, echo, filter, and progress code read across the whole queue. So the tab's memory grows with the human workload, not with every migrated letter. What a card draws from its own record (the sample text, the pair band, the settled cells, and the explain table and drafts) is not in the row. Each row has its record's part, byte offset, and byte length in its class shard, and the app fetches that one record from the static file with a Range request when the card renders or the explain panel opens. Machine-approved and no-verdict units are reached the same way through the locator pair: `app-locator-rows.ndjson.gz` holds one address per such unit in blocks of at most `app_index.LOCATOR_BLOCK_ROWS` rows, each block a separate gzip member within one class, and `app-locator.ndjson.gz` is the table of those blocks. A show-machine fold reads its class one block at a time, and a deep link binary-searches each class's blocks by id, so neither loads a whole class. A tab keeps the table and a few decoded blocks (`BLOCK_CACHE_CAP` in `static/slim.js`). `rebuild/review/app_index.py` and `REVIEW-PLAN.md` §7.4 describe the format. All three sidecars are stamped with the same manifest identity and with `generated_at` (the rows file through the table, which records its byte length), so a tab holding an index written for another build rejects it instead of reading byte offsets into rewritten shards. The index and the table are gzipped on disk; `serve.py` sends them with `Content-Encoding: gzip`, and the app decompresses them itself when another static file server sends them undecoded, so an archived surface still opens. A block of the rows file is one whole gzip member either way. One accepted limitation: the cross-class search covers the human workload only, so a machine-approved unit is reachable by id through a pasted `#unit=` link but not by search.
- **Future migrations**: `build.py --mode table-diff --baseline <dir> --new <dir>` and the `snapshot` subcommand work beyond the M1 audit TSV, so M2 and later reviews can use the same app unchanged.
- **At cutover**: the app moves out of `rebuild/out/`, and the serve script will probably merge into `tools/serve.py`'s livereload. The `review-build` and `review-serve` Makefile targets exist already; the move needs no `site/` changes and touches no existing pipeline files.
- **Known leftovers, not blocking**: a `{"type":"module"}` `package.json` is copied verbatim from `static/` into the output (harmless); `rebuild/review/fixtures/` and `rebuild/review/jstests/fixtures/` are divergent copies that should converge on one source of truth before cutover.

### Policy drafters

`Drafter.draft_policy` in `drafts.py` picks one counter-lever per rejected unit, at the unit's first divergent position that is not a boundary token. It tries these in order:

- **`policy.refuse[+]` on the new join**: when the new behavior joins a gap the baseline left as a break and the unit has provenance, a `contract` cannot restore the break, so the drafter refuses the anchor that reaches across that gap, scoped to the neighbor on that side (for example `{exit: x-height, when: {right: {family: [qsIt]}}, …}`).
- **`policy.contract[+]`**: when the cell gained an extension the baseline glyph lacks and the provenance includes a `policy.extend` record, a `contract` record with `by: N` on that side, with its `when` window on the extension's side.
- **`policy.prefer[+]` with `mode: absolute`**: on seam-identical units with provenance, where a refuse would break joins both fonts share, a prefer that pins the baseline cell's differing anchors (or its stance) over the new ones.
- **`policy.refuse[+]` on the settled cell**: any other unit with provenance gets a refuse of the cell's exit, or of its stance when it has no exit.
- **`policy.prefer[+]` of the baseline exit**: a unit with no provenance gets a prefer for the baseline's exit at that position.

A seam-identical unit whose baseline cell differs from the new cell only at adjustment grain (post-ZWNJ locked twins, bind pullbacks, non-summing suppressed extensions) has no one-line counter-lever and gets no policy draft. `export.py` still lists it in `policy_edits` with null fields, the unit's provenance, and a `no_mechanical_draft` explanation, so a rejected unit always appears in the triage YAML.

### Verdict families (UNMATCHED presentation)

The surface groups the **UNMATCHED** verdict windows into families for presentation only, which leaves the oracle unchanged until those families are adjudicated.

- **Per-config class.** A render triple `(codepoints, baseline, new)` can match a different ledger class under each config: a window can be blessed under one stylistic set and novel under the default config. `audit.py` keeps the window as one unit, records every config's class in `config_classes`, and gives the unit the novel (UNMATCHED) class, since UNMATCHED wins. The shard carries a `config_class_note` that states both, which the app shows as a badge. A triple that matches two different ledger classes raises an error.
- **Verdict families.** `families.py` groups the UNMATCHED triples into synthetic classes (`status: unmatched`) placed after the ledger classes, so they sort last. The grouper reads the before and after settled seams from `enrich`. A gained join (`break → yN` or a raised seam) names a family by the joining pair, where the seam is the left cell's exit (for a ligature, its trailing component) joining the right cell's entry; `FAMILY_ORDER` lists the named families, and a gain with no named family goes to `unmatched-misc`. Every lost join goes to `seam-loss-withdrawal`. A window with no changed seam, or whose seam and cell counts do not line up (as when a ligature forms or splits), goes to `extension-non-summing`. A changed seam that is neither a gain nor a loss goes to `unmatched-misc`, so every unit gets a family. Windows novel only under a stylistic set go to `deferred-ss04`, `deferred-ss10`, or `deferred-ss03` (which also holds the ss02 and ss05 windows), sorted last.
- **`after_cells` provenance.** `after_cells` holds the re-derived settled cells, not the audit's `new` column. For the position-only `kern-channel-out-of-scope` rows that column holds per-slot diagnostics instead of cell tokens, so reading it would break the requirement that `after_cells` parallel `after_seams` across the whole audit.
