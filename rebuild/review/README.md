# Table-diff review corpus

## TL;DR

`rebuild/review/` is the source of a static review app, which the build writes to the gitignored `rebuild/out/review/`. The app shows one review unit per distinct divergence in `rebuild/out/m1/divergence-audit.tsv`, sharded by the ledger classes in `rebuild/m1-divergences.yaml`. Each unit renders side by side in the old Senior font and the M1 font through two `@font-face` rules, with the divergent pair highlighted, the row's `font-feature-settings` applied, boundary marks, a one-line explain summary, and a note field. A verdict covers the whole unit, meaning every config in its config set. A unit whose two renderings the build shows to be equivalent is approved by machine and is not queued for review.

The sections below cover the keys, the explain panel, the triage flow, the exported files, and the mechanisms that approve or deduplicate units before a person sees them. The design record behind them is `rebuild/REVIEW-PLAN.md`: the architecture, the data model, the verdict drafters, and the contract between the build and the app.

### Commands

```sh
make review-build                                     # regenerate rebuild/out/review/
make review-serve                                     # serve it on http://localhost:7294/
uv run python -m rebuild.review.build                 # the same build, run directly
uv run python -m rebuild.review.serve                 # the same server, run directly
uv run python -m rebuild.review.export verdicts.json --out tmp/review-triage.yaml
```

`make review` builds the scoped-anchor-selector review page, so the review app's targets are `review-build` and `review-serve`.

The build is incremental. It stamps every unit with a content key over that unit's inputs and keeps a store of per-unit results beside the manifest (`rebuild/out/review/unit-cache.ndjson.gz`). The next build recomputes only the units an edit could have changed and copies the rest from the previous corpus's shards byte for byte, so the cost of a write is proportional to what changed. `rebuild/review/unit_cache.py`'s docstring defines what the key covers and what is copied unchanged, and `rebuild/test_unit_cache.py` checks that cached, pooled, and serial builds write identical bytes. The build's `manifest+check` and `cache` phase lines report how much was copied unchanged. `--recompute-all-units` ignores the store and recomputes every unit; the artifact cycle's `--fresh` passes it through.

The review server uses port 7294, so it can run at the same time as `make serve` (`tools/serve.py`, port 7293).

## Quick start for triage

### Kerning is disabled

Both columns render with kerning off: the sample cells set `font-kerning: none`, which combines with each row's `font-feature-settings`. Every comparison the build makes (the review facts' ink-identity counts, highlight x-ranges, boundary-mark positions, pin checks) shapes with `kern: False` in both fonts (`ink.kern_neutral`). The rebuild emits no kerning until the kerning milestone (`doc/rebuild-design.md` §12), so the old font's kern feature would only add noise to before-and-after comparisons. Kern differences get their own review at that milestone. Turning kerning off changes nothing in the after font today; the setting is explicit so that it still applies after §12.

### Keyboard map

The in-app help overlay (`?`) lists every key, and `KEY_MAP`, `REJECT_MENU_MAP`, and `NEITHER_MENU_MAP` in `static/keyboard.js` define them.

The four main verdict keys are on the left home row: `a` skip, `s` reject, `d` fine either way, `f` approve. `e` records identical and `c` records neither. `a`, `d`, `e`, and `f` record the verdict and advance to the next unit. `s` and `c` open a small menu beside the row's verdict buttons, where a second key records the verdict with no comment, with a canned note, or with a custom comment, and a digit reuses a recent note. A canned note replaces whatever was in the note field. `Escape` or a click outside the menu cancels with no verdict, and the other shortcuts are off while the menu is open. `Backspace` or `Delete` clears the current unit's verdict, and pressing a unit's active verdict key again also clears it. `u` undoes the most recent verdict from anywhere. `g` approves every unverdicted unit in the cursor's group. Shortcuts are off while a note field has focus; `Escape` leaves it.

Reject means the old behavior should come back. Neither means both behaviors look wrong, so the unit needs new authoring work. Identical means the reviewer cannot see the flagged difference in the highlighted portion; that is feedback for the ink comparator and highlight tooling, not a judgment on either font.

A verdict covers every config in the unit's config set. Most units show no config badge because they diverge under every non-ss10 config. A badge such as "only when ss03 is on" marks a narrower set; hover it for the full list.

Approving a unit outlines its after sample in green, rejecting draws a red X over the after sample, either outlines both samples in green, and neither draws the red X over both. The row's recorded verdict drives these marks, so they persist through re-render and import and clear on undo.

### Reading the explain panel

Every row shows a one-line summary under the renderings: what the new pipeline chose at the primary divergence and the single record that decided it, in rune-name notation, for example "New: ·It joins ·It at the baseline (the old pipeline broke there) — decided by qsIt.yaml policy.extend[0] (join-count rank)." The Why? button, or `x`, opens the full panel:

- **Explain** is the candidate table settlement considered at each divergent position. It lists every surviving candidate with its entry, junction, and join-count, marks the winner with `->`, attributes each eliminated candidate to the rune record that eliminated it, and ends with a `decided by:` line naming the stage that separated the winner from the runner-up. `_STAGE_PHRASES` in `enrich.py` lists the stages.
- **Provenance** lists the `glyph_data/runes/*.yaml` records the outcome is attributed to. A reject's policy draft names these records.
- **Drafts** previews the three drafts (pin, policy edit, any-of) this unit's verdict would export.

### Triage flow

- The sidebar lists the ledger classes with the ledger's `why` and `status` text, and clicking a class filters to it. Every class with units in the current batch or worklist has a light accent outline, and the class holding the cursor unit has the full cursor-blue outline; both are separate from the border that marks a clicked class filter. Within a class, units are grouped by lead-family pair (each group folds, with a button that approves its unverdicted units), ordered by code point, and paged in batches of `audit.BATCH_SIZE`; the toolbar arrows page batches, and `[` and `]` change class.
- The header strip starts with a chip showing the corpus's unit total. Its popover shows the generation stamp and head, how many letters have migrated, and the total split into machine-approved units (by machine check), units in no-verdict classes, and units left for human review, which is the Overall denominator. After the chip come Overall progress with per-verdict tallies, the selected class's progress when a class filter is on, and the current batch's progress. A batch can span classes and a class can span batches, but selecting a class narrows the batch list. Each sidebar entry's counts line (`classCountsLine` in `static/render.js`) reads: class units, machine-approved, verdicted out of human, rows. Progress counts cover the human units only.
- Machine-approved units (ink-identical, picture-identical, or junior-equivalent) and units in no-verdict classes are hidden by default. The toolbar's "Show no-verdict units" toggle (`machine=1` in the URL hash) shows them in collapsed folds by class below the human units. Each row has a badge (its machine check's "… — machine approved", or "no verdict needed") and disabled verdict buttons whose title says why no verdict is needed. A `#unit=` link to one of these units while the toggle is off shows that one unit until you navigate away, and leaves the toggle and the URL unchanged. Keyboard navigation, auto-advance, and `g` cover the human units only.
- View state lives in the URL hash (`STATE_KEYS` in `static/state.js`), so reloading or sharing the URL restores the view. Verdicts autosave. After every change the app POSTs the verdicts it set or cleared (an `ams-review-verdicts-delta/1` body, never the whole store) to the serve script's `/autosave` endpoint. The server keeps the store in memory (`rebuild/review/verdict_store.py`) and atomically rewrites `verdicts-autosave.json` at the repo root. It applies each save under the verdict store's lock (`rebuild/review/store_lock.py`), which `merge_verdicts` and `rekey_verdicts` also hold, and answers a save made while another writer holds it with a 503. Every change is also written to the tab's outbox in localStorage (`static/outbox.js`) when it is made and stays there until the server acknowledges it. A save refused with a 503 or cut off by a network error is retried on a doubling backoff (`AUTOSAVE_RETRY_FIRST_MS` to `AUTOSAVE_RETRY_MAX_MS` in `static/app.js`), and the status bar reads "N verdicts kept in this browser, saving…" meanwhile. The save a closing tab sends is not retried, and the next page load sends what the outbox still holds (entries older than `REPLAY_MAX_AGE_MS` in `static/outbox.js` are offered as a download instead), so those tools refuse to write the live store while the server is up unless given `--yes`. That file is outside `rebuild/out/review/`, which a pass's land replaces as a whole. On load the app restores an autosave whose stamp matches the manifest, and afterward it asks `/autosave?since=<token>` for only what other sessions changed. A reload, crash, or closed tab loses no work, and the size of a save does not grow with the number of carried verdicts in the store. Each save sends `base_at`, the `at` of the record the tab last saw the server hold. A tab loaded on an earlier corpus keeps saving: the server carries its changes onto the store by unit id, a unit's id being its content key, as long as the store is on the served corpus. A save made on the served corpus while the store is still on another one carries the store onto the served corpus by unit id and keeps the old file as its stash, and a save made on neither gets a retryable 503. A skip made on an earlier corpus is dropped, as the carry drops every skip, and the tab shows the unit blank again. A change the store cannot apply is kept in `var/verdict-orphans/<stamp>.json` and reported to the tab: a conflict (the store holds a newer record, or a newer clear) makes the tab adopt the store's record and show a "Reapply N conflicted" button, which the tab keeps in its sessionStorage across a reload, the one onto a rebuilt corpus included, and an orphan (a unit the served corpus does not have) is announced in a toast. The readiness banner shows the conflicts and orphans recorded since the page loaded, or since the page it moved from loaded. The outbox is kept per checkout, keyed by the repo root the server names on `/capabilities`, because every checkout's server listens on the same port. `rebuild/review/verdict_store.py` states the rules. On load the app does not restore an autosave stamped for another corpus, and says so in a toast. The warnings about unexported verdicts (the beforeunload prompt and a toast every 50 unexported verdicts) appear only when autosave is not working, for example when a server without the endpoint serves the corpus, and the beforeunload prompt appears only when the outbox cannot be written either. When autosave works, the status bar's unexported count ends in "(autosaved)".
- **Moving onto a rebuilt corpus.** The server reloads no tab when a file changes. The cycle sends `ams:corpus/<generated_at>` or `ams:assets/<static hash>` through livereload's `/forcereload` after it changes what the server serves, and `static/reload-plugin.js` hands the path to the app. A tab also moves when a save's reply or `/status` names a corpus other than the one it loaded, or when a byte-range read finds another build's record where its index points; the readiness banner reads "Moving onto the rebuilt corpus…" meanwhile. The app sends its unsaved changes, waits while the reader has text in a focused field (and, in a hidden tab, until the tab is shown), saves the scroll position, the queue anchor, and note drafts in sessionStorage, and reloads at the same URL hash. A reload that finds the page still on the corpus it left does not try the same move again, and the banner then reads "Corpus rebuilt since this page loaded" and asks for a reload. `static/reload.js` holds the rules.
- **The queue view** (the header's Queue button, `#view=queue`; `#view=docket` opens it too) is the live queue of blank human units, where blank means unverdicted or skipped. It groups them by the build's `cluster` signature, which is the duplicate-group key without the judged pair, so one visual change that recurs across letter contexts is one card. The largest decisions come first: the first `TOP_CLUSTER_COUNT` clusters as cards with exemplar renderings and evidence from judged lookalikes, the remaining clusters as a compact table, singletons in chunks of `SINGLETON_CHUNK`, and every duplicate group whose recorded verdicts disagree (all in `static/queue.js`). Every button is a `#units=` worklist link that carries `queue=1` (a hash that carries `docket=1` reads the same), the key of the decision it stacks (`decision`: a cluster's signature, or `#singletons` for a singleton chunk), and the corpus's `generated_at` stamp, so judging uses the normal keyboard flow with duplicate fill. Finishing a worklist opens the next decision by itself: the first one this browser has not yet opened, so leaving a card postpones it, the last open singleton included; once every open decision has been shown, the one shown longest ago comes back (`nextQueueDecision`). The rotation is kept across corpus rebuilds, because a decision's key is its cluster signature. A tab that resumes a worklist stamped for another corpus build keeps the units the new corpus still has, since a unit's id is its content key, and goes to the live queue only when none are left (`queueResumeAction`). The view recomputes from the in-memory store as verdicts are recorded, so clusters shrink, empty, and move up with no new snapshot. Blank units in classes the ledger has already ruled on (`RULED_STATUSES`) are left out behind a one-line count, since a class-level decision or a bulk-proposal import covers them. Any filter or class click leaves the view.
- `rebuild/tools/review_queue.py <verdicts-file>` writes the same clustering, fixed against one verdicts file, to `tmp/queue-data.json` as input for bulk proposals. `rebuild/tools/complaint_list.py` (`make complaint-list`) clusters the open reject and neither verdicts by the rune records that decided them and writes `tmp/complaints-data.json`. For each group it lists defer candidates (blank units the same records decide), and `--defer` writes `verdicts-deferred-*.json` skip files for the Import dialog. `deferred` is one of the note-marker kinds, and so is `parked`, which older defer files carry; `CARRIED_PROVENANCE_PREFIX` in `static/verdicts.js` and `_MARKER` in `rebuild/tools/verdict_notes.py` list the same set.
- Each row shows the code point string in both fonts on a checkered background. The divergent pair has an amber band drawn from x-ranges in font units that the build computes; the app never measures text. A dotted line marks each boundary token (space, namer dot, or ZWNJ). The row also has the one-line summary, a Copy button that copies a prompt preamble for the unit, and a Why? button (or `x`) that opens the explain panel with the attribution described in `doc/rebuild-design.md` §6.3. Regions without a mark render identically in both fonts or differ only in glyph names.
- The text lines use the same amber: the notation line (·May·Oy·It·May) and the code point line (E665:E679:E670:E665) underline the divergent pair's tokens in the band's `--hot` color. The build computes the mapping (`pair_codepoints`, a span of code point positions, and `notation_tokens`, one per code point position) because ligatures make glyph positions differ from code point positions. A unit with no primary pair shows both lines unmarked. A secondary junction with no primary unit (an "only here" junction, below) gets a dashed underline on the text lines; other secondary junctions are not marked there.
- A longer unit can contain divergent junctions besides the amber primary pair. Each such secondary junction shows in both columns as a dimmer dashed band with a chip naming its primary unit, the shortest unit where the same before-and-after behavior is the primary judgment. Clicking the chip opens that unit, across batches and classes and on machine-approved units too. A chip reading "only here" means the junction has no primary unit: no other unit whose code point string lies within this unit's has that junction, with the same before-and-after behavior, as its primary pair, so judge that junction in this unit. A junction whose primary unit is ink-identical or picture-identical gets no marker, since there is nothing visible to judge. The manifest's `secondary_junctions` record counts the markers, and the §7 checker compares it with the shards.
- No chip strip lists every config a unit diverges under, because for most units (those that diverge under every non-ss10 config) it would say nothing. A unit whose config set is informative has a badge of inert chips, one per stylistic set that pins the set down. Each chip uses its set's color, is lit when the set must be on and muted when it must be off, and is glossed with the set's `feature_descriptions` entry. `build.config_badge` computes both the chips and their text: it finds the smallest conjunction of on/off constraints that selects exactly the unit's config set, and falls back to one literal "only under: …" chip when no short conjunction does. The app renders each clause's `text` as given. The badges mark the cases that matter for judgment (ss03-gated, ss03-excluded, ss10-only, and narrower two- and three-set conjunctions), which also explain the row's `font-feature-settings`. Each chip's title lists the full config set. The queue view's cluster headers show the same chips.
- Units are deduplicated by (codepoints, baseline outcome, new outcome), so every config of a unit renders the same. The build groups configs by rendered outcome into `render_groups`, and the §7 checker fails an m1-audit build with a unit of more than one group. The app can still draw extra groups, each before-and-after pair stacked below the first with its own config label and feature settings.
- A verdict always covers the whole unit. `verdicts.json` records have no `configs` field, and an import ignores one.
- _Export_ downloads `verdicts.json` (format `ams-review-verdicts/1`, notes included). _Import_ merges an earlier export by unit id and asks before merging a file stamped for a different manifest, so triage can span sessions. `verdicts-autosave.json` is a rolling copy for the live manifest; downloaded exports are the durable masters the export CLI reads.

### What to do with each exported artifact

Run the export CLI on the downloaded file. The resulting `tmp/review-triage.yaml` has a `review` header with counts, a `machine_approved` section (see "Machine-approved units"), and five verdict sections:

- **`pins`** (from approvals): whole-word `data-expect` strings, each checked for syntax with the repo's `parse_expect` and for meaning against the after font. Copy each into its `suggested_home` (for example `site/the-manual.html`) as a `data-expect` or `data-expect-noncanonically` attribute; this is how an approved behavior becomes a pin (`doc/rebuild-design.md` §10, item 5). `duplicate_of` flags pins the corpus already has.
- **`policy_edits`** (from rejections): one-line `policy.prefer[+]`, `policy.refuse[+]`, or `policy.contract[+]` records, each naming the target rune file, an appendable keypath, the provenance records that decided the outcome, and the decided stage. These are _drafts_ and are never applied automatically: review each, paste it into the named `glyph_data/runes/*.yaml`, and rebuild. An entry with `no_mechanical_draft` has no one-line reversing edit; start from its `names_provenance` and the unit's explain panel.
- **`any_of`** (from fine-either-way): candidate expect strings, after-behavior first, for the any-of check, which `_assert_expect_any` (`test/quikscript_shaping_helpers.py`) implements until the corpus has an any-of connective. A unit whose before and after behaviors give the same whole-word string (a cell-only divergence) has one candidate.
- **`neither`** (from neither verdicts): both behaviors look wrong, so nothing is drafted. Each entry has the unit id, code points, notation, the reviewer's note, and `names_provenance`, the `glyph_data/runes/*.yaml` records the outcome is attributed to. These units need new authoring work, starting from those records and the unit's explain panel.
- **`identical`** (from identical verdicts): the reviewer cannot see the flagged difference. Nothing is drafted; each entry has the unit id, code points, notation, and the reviewer's note. These entries report a difference the ink comparator and highlight tooling flagged that no person can see; they are not judgments on either font.

## Mechanisms

Each section below says what a mechanism does for the reviewer and names the module docstring or `rebuild/REVIEW-PLAN.md` section that has the detail.

### Machine-approved units

The build approves a unit without a person when a machine check shows that its two renderings match. There are three checks, tried in the order `MACHINE_CHECKS` in `rebuild/review/audit.py` gives, so a unit carries at most one flag. The first is ink identity: a unit is `ink_identical` when both fonts place the same outlines under every config in its set, shaped with kerning off, so only glyph names differ. The module docstring of `rebuild/review/ink.py` says how the outlines are placed and compared. The other two are picture identity and Junior equivalence, below.

A machine-approved unit takes no place in the triage index (the manifest's `human_unit_ids`), so it is in no batch, no sidebar count, and no progress denominator, and the triage flow above says how the app shows it. It is written as a slim fragment, without the explain table, the drafts, or the pair band (the comment on `SLIM_OMITTED_KEYS` in `audit.py` says why), and its explain panel says what was left out. The cross-class search covers the human units only, so a machine-approved unit is reached through a show-machine fold or a pasted `#unit=` link.

`verdicts.json` holds human verdicts only. The export drafts nothing from a verdict recorded on a machine-approved unit and counts it under `skipped_machine_approved`, and the triage YAML's `machine_approved` section lists the approved units with their counts and each check's method (REVIEW-PLAN §4.2). The manifest's `machine_approved` record holds the same totals, and `rebuild/review-facts-pins.json` records them. In table-diff mode the same checks run over each entry's example text, and an entry with no example text stays a human unit (REVIEW-PLAN §2.1).

### Picture-identical units

The second check approves a unit whose two fonts fill the same pixel cells under every config, where the glyph-name change the audit recorded only moves ink from one glyph to a neighbor without changing the picture: a junction pixel the old font drew twice and the rebuild draws once, as at ·At·J’ai, or a stroke redrawn as part of the adjacent letter. The check fails closed: a window whose outlines or placements are off the pixel grid, or whose pictures differ under any config, is queued. `InkComparator.picture_identical` and `config_diff` in `rebuild/review/ink.py` define it. A picture-identical unit has no visible junction change, so it carries no secondary junctions, and a secondary junction whose primary unit is picture-identical gets no marker. The flag is outside the carry content key (the comment on `CARRY_PRESENTATION_KEYS` in `rebuild/review/unit_cache.py` says why), so a change in the flag changes no unit's id.

### Junior-equivalent units

The third check covers units that diverge only under ss10, the set whose ratified meaning is fully isolated letters (the Taste sets / ss10 row in `doc/rebuild-design.md`). `ink.JuniorOracle` approves such a unit when the rebuild's ss10 rendering places the same ink as the old Junior font for the same string, once Junior's letter tracking is removed. A pass means the rebuild draws the canonical isolated rendering, whatever the old Senior font draws. A unit that also diverges under any other config still goes to a person, because those configs need judgment and a verdict covers the whole unit. The oracle does not approve the `· ◊ZWNJ` windows, where Junior draws the namer dot lowered and the rebuild's ss10 run draws the plain one. The class docstring states the premise its constructor checks, and the manifest's `machine_approved.checks.junior_equivalent` record names the Junior font it used.

### No-verdict ledger classes

A ledger entry with `no_verdict: true` says a ratified rule decides the whole class (the header comment of `rebuild/m1-divergences.yaml`), so no unit in it needs its own verdict. Its units are handled like machine-approved ones: they take no place in the triage index, are hidden behind the toggle with their controls disabled, and show a "no verdict needed" badge, which the sidebar shows in place of the class's progress. `needsNoVerdict` in `static/render.js` is the app's test for both kinds. The export ignores a verdict recorded on an exempt unit and counts it under `skipped_no_verdict`, so an old verdicts master cannot add pins for a class the ledger has ruled on. Exempting another class is a one-line ledger edit, and `grep -n no_verdict rebuild/m1-divergences.yaml` lists the classes that have the flag.

### Ink-duplicate unit merging

The dedupe key, (codepoints, baseline, new), compares glyph names, so a config that only renames a glyph splits one visual question into two units. For example, the old font's ss04 lookups rename word-initial ·It without moving any ink, which splits ·It·Day·Tea·No into a default unit and an "only when ss04 is on" unit. `audit.merge_ink_duplicate_units` merges such siblings before enrichment when their ink is identical under every config, so the reviewer sees the window once, with the union of its configs. The merge runs before unmatched grouping, so an ss04 half that differs only by name is decided in the default groups and is not asked again in `deferred-ss04`. The function's docstring gives the survivor rule and when a merge is skipped, and the module docstring of `rebuild/review/unit_cache.py` describes the ink-signature store that lets an unchanged build merge without shaping anything.

### Duplicate groups — one verdict per rendered change

Different windows often show the same change: ·Pea·Day·Tea·No, ·May·Day·Tea·No, and ·It·Day·Tea·No all show the same ·Day·Tea regrouping. Every human unit carries a `duplicate_group` id keyed on its configs, judged pair, class, and pixel-level before-to-after delta, so windows whose change paints the same pixels share a group whatever letters surround it. The docstring of `InkComparator.config_diff` in `rebuild/review/ink.py` defines the delta, including why a follower that only slid and a pixel handed to a neighbor that paints it anyway do not split a group, and `unit_cache.duplicate_group_id_for` defines the id.

In the app, a unit in a group with more than one member shows a "duplicate ×N" chip; clicking it opens the group as a `#units=` worklist, stacked. Typing a group id into the cross-class search offers the same stacked group. A verdict on any member, whether from a button, a key, a canned reject or neither note, or `g`, fills the _unverdicted_ rest of the group with the same verdict and note as one undo step, and a toast reports the fill. `skip` is never copied, members that already have a verdict are never overwritten, and any member can still be overridden or cleared on its own. The store keeps one record per unit, so export, import, autosave, and carry are unaffected.

The app's fill fires only on verdicts recorded in the app. For carried verdicts, the artifact cycle's verdict update runs `rebuild/tools/duplicate_verdicts.py`, which fills the blank members of every group whose recorded verdicts agree and prints every group whose verdicts disagree, so a blank whose group already has an agreed carried verdict is filled before the corpus is served.

The corpus build stores each unit's per-config delta digests as `ink_deltas` (`ink.delta_digest`). An `ink_deltas` rule in `rebuild/standing-approvals.yaml` matches them, so a blessed change never waits for review again in any window where it is the whole visible change, and the combined match in `rebuild/tools/standing_verdicts.py` covers a window that combines two or more blessed changes. When a blessed delta changes shape, re-derive the rule's digest from the `deltas` that `rebuild/tools/standing_probe.py` prints for a unit showing it; never edit a digest by hand.

### The artifact cycle mechanized

`make review-cycle` rebuilds the font and the corpus, carries and fills the verdicts, runs the gates, and then serves the corpus when no server is up; `make artifact-cycle` is the same pass without the serve. The review server keeps running through every pass: the pass builds the corpus beside the served one (`rebuild/out/review.next`), carries and fills the verdicts into a copy of the store, and then lands the corpus and the store together under the store's lock (`landing.py`), laying the verdicts recorded during the pass over the copy. A save made while the land holds the lock gets a retryable 503 and waits in the outbox, and the open tabs then move onto the new corpus by themselves. The cycle restarts a server running older code, leaves one serving another checkout alone, and stops a server from before the land protocol once (`--stop-server`, which `make review-cycle` passes; `--yes` runs beside it instead). The land serves the new corpus as soon as the verdict update has finished, while the heavy gates may still run, so a red pass can leave the app serving a corpus no gate has passed; `make verdict-ready` and the app banner stay NOT READY until every gate has passed on those inputs: a gate the pass did not run counts as not passed unless a green record shows the same inputs already passed. `doc/review-cycle.md` is the runbook, and the module docstring of `rebuild/tools/artifact_cycle.py` has the rest.

### Review-facts pins as one reviewable file

`rebuild/review-facts-pins.json` holds the last accepted review facts: what a build measured about its own corpus, in one checked-in file that a person accepts by committing it. Every non-staging artifact-cycle pass rewrites it from the build's `review-facts.json` sidecar, and the cycle summary's `review facts` line says what the commit would accept. The `volatile` block's counts change with every migrated letter, and a change in the `invariant` block (which classes ship, which the build machine-approves, which are exempt, and which unmatched groups the corpus reaches) needs an explanation. `doc/review-cycle.md` § The review facts says how to read the summary lines, and the module docstring of `rebuild/review/facts.py` defines both blocks and the manual `--check` and `--update` tool.

### Policy drafters

A reject's policy draft is the smallest one-line `refuse`, `contract`, or `prefer` record that would reverse the change, at the unit's first divergent position that is not a boundary token, and REVIEW-PLAN §4.3 gives the order the drafter tries them in. A name-grain divergence with no such record (post-ZWNJ locked copies, bind pullbacks, non-summing suppressed extensions) gets no draft, and the export still lists the reject in `policy_edits` with null fields, the unit's provenance, and a `no_mechanical_draft` explanation, so a rejected unit always appears in the triage YAML.

### Unmatched groups (UNMATCHED presentation)

The corpus groups the **UNMATCHED** windows, which no ledger class matches, into unmatched groups for presentation only, which leaves the oracle unchanged until those groups are adjudicated. Each group is a synthetic class (`status: unmatched`) placed after the ledger classes. A gained join goes to its joining pair's named group when one exists, every lost join goes to `junction-loss-unjoined`, a window with no changed junction goes to `extension-non-summing`, and `unmatched-misc` catches the rest; windows novel only under a stylistic set go to `deferred-ss04`, `deferred-ss10`, or `deferred-ss03`, which sort last. The module docstring of `rebuild/review/unmatched_groups.py` says which window goes to which group, and `UNMATCHED_GROUP_ORDER` there lists the groups.

A window can be blessed under one stylistic set and novel under the default config. The build keeps it as one unit, records every config's class in `config_classes`, and gives the unit the UNMATCHED class, so the novel behavior is what gets reviewed; the app shows both classes in a badge from the shard's `config_class_note`. The docstring of `audit.load_table` gives the rule, and a unit whose rows match two different ledger classes fails the build.
