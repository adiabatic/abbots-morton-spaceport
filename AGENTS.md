# Instructions for agents

## Roadmap and open decisions

- WHATNEXT.md is the forward-looking punch list — what ought to happen next, and the open forks in the road. Read it when you need that context. When work lands, keep it current by editing the live state in place and deleting what it supersedes — WHATNEXT records the live frontier, never a running log of what happened (see its “Keeping this file honest” block, and the note-taking rules below).

## Note-taking and the rebuild logs

The rebuild tends to generate far more notes than a forward-working agent ever reads. The governing principle: **git already holds the history, so a checked-in note earns its place only by recording the live frontier, a durable design fact, or the user’s rationale — never a play-by-play of what already landed.**

- **Milestones get a forward PLAN, not an after-the-fact REPORT.** A `*-PLAN.md` under `rebuild/` is a design spec and stays. When a milestone lands, its record is the commit history plus the runes’ `why:` fields — don’t write a standalone `*-REPORT.md` that re-narrates counts, gate tallies, and edits git already preserves. A durable design fact that emerges during the work belongs in the PLAN or in `doc/rebuild-design.md`, not a report.
- **An in-flight batch keeps at most one scratch progress file, and it stays bounded.** It may hold only: what’s parked and why, recorded design overrides, the verification recipe, and the resume commands — never a list of landed commits, which is git’s job. Per-commit narration goes in the commit body (multiline messages are fine in this repo), and the batch’s commit set needs no bookkeeping: the progress file’s own creation commit bounds it in `git log`. It must not accumulate a per-change verification paragraph — exact row/window counts, per-config diffs, gate-pass tallies — because that detail lives in the commit the change landed under. Delete the progress file when its batch closes, first lifting any surviving forward-pointer into WHATNEXT.
- **A count in prose names the artifact that reports it, never the number.** The rebuild measures itself on every cycle, so a tally written into a note is stale by the next one — and when a fact has both a prose copy and a machine copy, it is always the prose that rots while the machine copy stays true. Drifting state has homes already: `rebuild/out/cycle_summary.json` and the per-gate summaries beside it under `rebuild/out/m1/`, `rebuild/out/review/manifest.json` for surface totals, `rebuild/review-census-pins.json` for the last accepted census, and `make verdict-ready` for whether a sitting can start. Point at those rather than transcribing them, and prefer the qualitative shape — "the sweep is exact", "read-back's GSUB headroom is inside its floor", "the unmatched rows are verdict-gated, not failing" — to a figure. Definitional numbers are not counts and stay: Tall/Deep/Short as 9/9/6 rows, the depth-4 chain cap, the dev-server ports, a hash that _is_ a byte-identity contract, and a frozen fact about the old shipped font. The same goes for a commit-stamped filename — write `verdicts-carried-<sha>.json`, not this cycle's hash.
- **When a fact has both a prose home and an executable one, the executable one is binding and the prose says so.** A field list a validator already enforces, a gate's exempt-tree list, a keyboard map the frontend binds, a class list a ledger already carries — restating any of these in a note creates a second copy that can only drift out of agreement, and the note is the copy nothing checks. Name the authority (`build.check_manifest`, `make_test_exempt`, `keyboard.js`, `rebuild/m1-divergences.yaml`) and describe the shape; don't maintain a parallel specification alongside it.
- **Reconnaissance is scratch.** Pre-work fact-finding that grounds a PLAN is consumed once; after the PLAN exists it belongs in git history, not a checked-in `recon/` file that outlives the decision it informed.
- **Checked-in evidence lives only as long as its decision is open.** Once a triage/audit/lever-hunt conclusion lands in the runes or a ledger and commits, delete the evidence dump — git preserves it. Keep evidence only when it is the proof pile for a _still-open_ fork or a live build input (the archived surfaces `carry_verdicts.py` reads).
- **When a note has drifted into a changelog, collapse it to present tense.** Dated `Update (…)` / `(2026-…)` stamps inside a note are the tell; rewrite the current state in place rather than appending another dated correction.
- **Docstrings and code comments say what the code does, never what it used to do.** The same principle reaches the source: a docstring that opens on the shape it replaced — "these used to be tests that swept the live shards", "the entry used to be an `Rc`", "the seven separate steps used to append" — is a changelog entry parked in the code, and it rots the way a note does, because nothing checks it and the reader it is written for never saw the old shape. State the present design and the reason for it. When the reason is a measurement or a failure mode of an alternative, describe the alternative as an alternative ("an `Rc` per entry is four allocations behind every slot"; "a row filled from seconds would read `ok` for a failed step"), not as the past; when the reason is that the work lives elsewhere, name where it lives, not where it moved from. The tells are "used to", "no longer", "now" paired with a past tense, "retired", "moved here from", and an issue number cited as a date ("since issue #78"). The commit message is where the before-and-after belongs; a PLAN's decision record may keep the argument that settled it, but a disposal ledger or a "landed" paragraph inside one collapses to what exists and what is in git history.

## General

- Always ask clarifying questions when there are multiple valid ways to do something.
- Never write a `why:` explanation yourself in `glyph_data/runes/qs*.yaml`. There, `why:` is the user’s recorded rationale for a design decision, in the user’s voice. It is also the durable home for that rationale: log and progress files may point at a `why:`, but must not re-narrate it — don’t copy a design rationale into a rebuild log, where it only drifts from the rune. **That rule is exactly that scoped, and does not generalize.** The other two YAMLs that carry `why:` fields — `rebuild/m1-contact-allow.yaml` and `rebuild/m1-divergences.yaml` — are agent-written: write their prose yourself, in the surrounding section’s idiom, and don’t park a blessing on the user or ask them to sign off on the wording. “Human-reviewed” in those files’ headers means the user decides whether the entry belongs, not who drafts its sentence, and rewording one is free — both files hash prose-blind, so a `why:` edit re-runs no gate — which leaves no reason to keep a sentence worse than it should be.
- When a request mentions a letter by name (e.g., “after ·Pea”, “before ·Tea”) and that family has multiple variants (half/full, alt, en-y6, ex-y0, etc.), don’t silently default to a bare `{family: qsX}` selector. Before editing, look up the family in `glyph_data/quikscript.yaml`, enumerate its variants (and the relevant axis — half vs. full, exit Y, traits, etc.), and present them as a clarifying question so the user can pick the intended subset without needing the YAML in front of him.
- Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning." Instead of "this point still matters," they write "this point earns its keep." The phrases exist to display the writer, not to convey the idea, and readers can tell. That is why mannered prose irritates: it makes the reader work harder so the writer can perform. It is also imprecise. Metaphors drag in connotations the writer did not choose and cannot control. The fix is to say what you mean. When a literal phrase is available, use it.
- After any glyph or code changes, run `make test` to make sure nothing is broken. It self-skips in about a second when nothing it checks has changed since its last green run — a change outside its input closure (`make_test_exempt` in `rebuild/tools/artifact_cycle.py` is the authority: the exempt trees and files, Markdown, and the Makefile beyond what `make -n all` and `make -n test` print) cannot move it, and those are the rebuild suite's and artifact cycle's job to gate, so don't force a run for them. `make test FORCE=1` overrides the skip. `make test-rebuild` is the rebuild suite's own gate and runs it in two lanes with a green record each: contracts (no live build artifact, full xdist width) first, then validators, and a hard contracts failure stops before validators starts. Neither lane runs the slow-marked tests; `make test-rebuild-slow` is what does. A rebuild test that reads a live build artifact — `rebuild/out`, the review surface — must request the `live_artifacts` fixture, which is what puts it in the validators lane; an audit guard in `rebuild/conftest.py` (the authority on the split) fails it otherwise. The validators lane is small — the per-configuration rule-witness arms and nothing else, at the narrow width `rebuild/conftest.py` derives for it, with `make cycle-timings ARGS='--by-step'` the record of what it costs — because everything the build can prove per unit is proven in the build (`check_unit` / `check_shards` in `rebuild/review/build.py` — `check_unit` over the units this build computed, a cache-served one held instead by the content-key stamp its store record and the shard fragment on disk must agree on, and every cross-unit predicate over all of them either way — plus the enricher's audit mismatches as errors, the drafter and the enricher refusing at production what no later re-read could repair, and the served-vs-recomputed sample) and everything whose subject is the code runs in the contracts lane over the checked-in fixtures, the hermetic mini bundle under `rebuild/review/fixtures/mini/` included. The validators lane fails fast on stale build artifacts rather than rebuilding anything in-process, and the first refusal comes before the lane does: `make test-rebuild` declines to spawn it at all while the tables on disk are not stamped with the current sources, so a stale stamp fails in a second rather than after a lane's worth of collection. Past that the arms refuse for themselves: `rebuild/test_rule_witnesses.py` refuses a window enumeration stamped from other sources than the ones on disk, so after a rune or pipeline edit, run `run_m1` (or a `make review-cycle` pass) before expecting that lane green. The review surface's worked examples are in the contracts lane, over the frozen mini bundle under `rebuild/review/fixtures/mini/`, and read no live artifact at all.
- **Codex's macOS sandbox blocks the Darwin memory-size oracle.** Inside the sandbox, `sysctl -n hw.memsize` exits with `Operation not permitted`, so `rebuild/test_memory_budget.py::TestTheLiveProbe::test_the_portable_probe_is_byte_identical_to_hw_memsize_on_darwin` fails even when the portable probe is correct. If that is the contracts lane's only failure, rerun the named test — or `make test-rebuild` when its green record needs refreshing — outside the sandbox. Do not weaken the probe or the test to accommodate the sandbox.
- **The long steps outrun a sandboxed shell's patience — detach them.** A bare `run_m1` build is minutes now rather than the better part of a quarter-hour and a review-cycle pass's heavy gates (the rebuild suite plus the conform sweep) a few minutes more, but a full `make artifact-cycle` pass still outgrows a ten-minute window, and an agent harness's backgrounded shell is typically killed at about ten minutes regardless of progress, stranding the cycle mid-gate. Run any pass that includes the heavy gates detached from the tool's lifecycle (`nohup … > tmp/cycle-pass.log 2>&1 &`), with `caffeinate -i` as cheap insurance against idle sleep. That redirect is still worth having, but it is no longer where the detail lives: every cycle opens a run directory under `tmp/build-logs/`, with `tmp/build-logs/latest` pointing at the newest one, holding `plan.txt`, `terminal.log` as a byte copy of what the terminal saw, and one `<nn>-<step>.log` per spawned step whose stdout and stderr are merged in arrival order with the stderr lines tagged. So watch `tmp/build-logs/latest/terminal.log` for the completion banner — the summary table, then `Cycle complete.` on a green pass or a `CYCLE FAILED:` block of reasons on a red one — and open the step's own log beside it when one goes red or falls quiet. Two hung-run traps, both survived once: the pytest controller legitimately sits at 0% CPU while its xdist workers grind, and the workers are execnet children whose argv contains no "pytest" — so judge liveness by summing CPU over the controller's process tree (`pgrep -P`), never by grepping process names, or a healthy suite reads as a deadlock and gets killed mid-run. A third trap is the mirror image: a watcher loop polling `pgrep -f <pattern>` matches its own command line and reports a finished run as live forever — record the pid at launch and poll `kill -0 <pid>` instead (or bracket a pattern character, `pgrep -f "artifact_cycl[e]"`). `make cycle-timings` (`ARGS='--by-step'` for per-machine medians) is the live record of what each step actually costs here; read it before deciding a run is hung, and before picking any watcher's timeout.
- The M1 table build runs in Rust: `rebuild/kernel-rs/` is the engine of record (issues #40 and #48) and, since issue #78, the only fixpoint there is — `cargo` is a hard prerequisite alongside `uv` for anything that builds tables, the rebuild test suite included, and a box without it cannot build the M1 artifacts at all. The seam is `rebuild/pipeline/kernel_exec.py` (`build_table_files` for a configuration’s three artifacts and its contract digest, `build_tables` for one configuration’s two tables in memory, `guard_sweep` for the formation verdicts, `settle_cases` / `settle_windows` / `settle_sequences` for batched settlement, `enumerate_transitions` for the raw product at the enumeration’s own grain — which no build stage and no tool asks for, the rebuild suite alone keeping that path exercised; `run_m1.build_tables` is the persisting fan-out), and since the crate grew its `build-tables` verb it enumerates _and_ folds — `rebuild/pipeline/table.py` folds nothing any more and is the data model, the artifact readers and the digests, with `rebuild/test_table.py` replaying the crate’s rules against the crate’s rows on the mini fixture as the one independent check on the fold. Settlement has one home too: the crate ranks candidates, fires refusals, orders specificity, estimates prospect and answers the late-formation guard, and `rebuild/pipeline/settle.py` is the Python side’s vocabulary alone — the tokens and boundary cells, `tokens_from_codepoints`, and `form_ligatures`, which stages formation ahead of settlement off the verdicts `kernel_exec.guard_sweep` hands back. Every Python consumer settles through the crate: `gate:conform` re-settles each swept text window by window through `settle-cases`, `emit_gsub` reads the guard sweep directly, and the review surface, explain CLI, and probe read the settle-cases trace. So a change to settlement semantics is written once, in `rebuild/kernel-rs/`; what still has to stay paired is the spec contract the crate ingests — `rebuild/pipeline/model.py` and `kernel_io.py` — which the contracts lane holds byte-aligned on every `make test-rebuild` (`rebuild/test_kernel_io.py` echoes the live dump through the crate’s `spec-echo` and requires the bytes back identical). No cycle gate runs the crate’s own suite, so run `make kernel-gate` around any kernel-semantics change: it is the crate’s fmt/clippy/test gate (`make kernel-check`, where settlement’s whole regression budget is spent), seconds once the crate is built — while `gate:conform` remains the every-cycle end-to-end check, HarfBuzz shaping the compiled font against a re-settle whose memo is keyed on the raw window, which keeps it independent of the crate’s enumeration and fold, and since the standalone boundary gate retired it also carries the split-buffer check on every splitter-bearing text at horizon 4 (`make conform-deep` carries it deeper), while read-back proves the boundary glyphs inert on the font bytes themselves — no substituted position of any lookup admits `uni200C` or `space`, the ZWNJ carries no advance, and neither draws an outline. `run_m1 --gates-only` re-runs the defect gate, the Manual-pin gate and the oracle over the tables and font already on disk, refusing a stale stamp; the artifact cycle takes that route itself when everything that moved since the last green build is comparison-side (`comparison_side_label` in `rebuild/tools/artifact_cycle.py` is the roster) and the tables on disk still carry their stamp, and the green that pass records lets the next one skip run_m1 outright. The crate's `--cache-census` flag on `enumerate` / `enumerate-configs` prints what each memo holds per configuration; it is the instrument for any memory argument about the kernel, whose per-configuration peak is what caps the fan-out width.
- Never commit without explicit user approval. Show the changes and wait for the go-ahead before committing.
- When the work reaches a natural commit point, don’t just offer to commit — spawn a fresh sub-agent to draft commit-message suggestions, then present those for approval.
- In this repository only, it’s OK to have multiline commit messages, although by no means mandatory.
- In this repository only, don’t use worktrees unless explicitly asked.
- Prefer commit messages that either:
  - describe the change in author/reader experience — what the YAML/HTML/code now lets you skip writing, or what now looks right. For example: “Make tables.html store state in the URL, not localStorage”.
  - describe how the font’s letters will look different (“Reduce the half-·He extension at the x-height”, “Don’t join ·Way·Thaw ever”)
- Contrariwise, messages that describe the mechanism are anti-preferred.

## Prose style

- While there are significant parts of this project that are in British English (like The Manual), use American English for all code and comments.
- Capitalize **Tall**, **Deep**, and **Short** wherever they name the height classes of letters (Tall = 9 rows; Deep = 9 rows with `y_offset: -3`; Short = 6 rows) — everywhere, not just sentence-initially — so they read as the defined classes. Lowercase them only in an ordinary, non-class sense.
- Don’t use “iso” (in any casing — “iso”, “Iso”, “ISO”) as a shorthand for “isolation” / “isolated”, whether in prose, identifier names, dataclass fields, or YAML keys. Spell it out: `isolated_form`, `isolated_left` / `isolated_right`, “isolated shaping”, “the isolated form”, “in isolation”, “isolated pair”, etc.
- Don’t hard-wrap comments or docstrings. Let each paragraph be a single long line and rely on the editor’s soft-wrap.
- Joins between letter names are written in the `data-expect` notation and no other: `~b~` for a baseline join, `~x~` for an x-height join, `|` for a break, `+` for a ligature (`·Tea+Oy`), with stance suffixes hanging off the letter (`·It ~b~ ·Day.half`). `parse_expect` in `test/test_shaping.py` is the authority for the full grammar, the rarer heights and the `|?|` / `?` operators included. **A bare `~` is not an operator** — it asserts a join while dropping the very height `~b~` / `~x~` exist to carry — so never write `·Tea~·Utter`. Spell the height out when the context fixes it; when the sentence only means the pair or the seam, say that in plain prose (“the ·Tea·Utter seam”, “the ·Roe·May pair”) rather than inventing a heightless join.

## Performance

The Python and Rust in this repository run against hard CPU and RAM limits, not comfortable headroom. The M1 table build holds a whole configuration's working set in memory until its artifacts are written, the review-surface build holds the whole corpus in its parent at any width, and every fan-out width in the repo is a division of the box's memory by a measured per-unit peak (`rebuild/tools/memory_budget.py`, and the `*_BYTES` constants at each call site). On the CPU side, a full artifact cycle already outgrows a ten-minute shell window; `make cycle-timings` is the record of what each step costs, host-tagged against the machines listed in `doc/fleet.md`. So a routine that is a little slower or holds a little more per unit is not a rounding error here: it moves a per-unit peak, which narrows a fan-out, which lengthens every cycle after it.

Write Python and Rust with that in mind, and not necessarily the first way that comes to mind:

- **Think about the working set before the algorithm.** Ask what the code holds live at its peak and for how long, and whether that is the whole corpus, one configuration, one unit, or one row. Stream and iterate where a list would materialize; release a large structure as soon as its last reader is done rather than at function exit; prefer one pass that folds over several that each re-read.
- **Price the hot path in the units it runs at.** A cost that is negligible per call becomes the build when the call runs per window, per candidate, or per row. Move invariant work out of the loop, memoize on the key the caller actually varies, and avoid building intermediate strings, dicts, or `Vec`s that the next line only takes apart.
- **In Python, reach for the idiom that stays in C.** Comprehensions, `dict`/`set` lookups, `bytes`/`memoryview`, tuple keys, and the standard library's compiled paths over a hand-rolled loop; and when a Python-side pass is still the bottleneck, the answer is usually the crate, not a cleverer loop.
- **In Rust, mind allocation and cloning as much as asymptotics.** Borrow where you would `.clone()`, size a `Vec` or map up front when the count is known, keep per-entry structures flat, and prefer iterators that fuse over collecting between stages.
- **Measure, and let the measurement drive the width.** `make cycle-timings ARGS='--by-step'` and the kernel's `--cache-census` are the instruments; a change that moves a per-unit peak must revise the `*_BYTES` constant and the docstring that argues it at the same call site, because the widths derive from those numbers and nothing else checks them.

Clarity still wins ties, and a performance change with no measurement behind it is a guess. But a routine that is correct and simple and materially increases a peak is not done.

## Python

IMPORTANT: Always use `uv run` instead of `python` or `python3` directly. The project pins `cache-dir = ".uv-cache"` under `[tool.uv]` in `pyproject.toml` so the cache stays inside the repo, which is needed in sandboxed environments where the default `uv` cache (`~/.cache/uv` or `~/Library/Caches/uv`) isn’t writable. For example:

- `uv run pytest` not `pytest`

IMPORTANT: Never single-thread the test suite. `make test` runs `uv run pytest test/ site/ -n auto --dist worksteal` for a reason: single-threaded (`-p no:xdist`) the full suite ran ≈20 minutes back when the full-width pool ran ≈3, and even at the width a cycle holds gate:make-test's pool to — `make_test_pool_width` in `rebuild/tools/artifact_cycle.py` resolves it, under `MAKE_TEST_POOL_WORKERS` and the cores this process may actually run on — the worksteal pool stays ahead of `-n 0`. Run the whole suite with `make test`, and any multi-file gate with `uv run pytest <targets> -n auto --dist worksteal`. Reserve `-n 0` for a single test id or a tiny handful where you want a clean, unscrambled traceback — never for a broad run, and never spell it `-p no:xdist`: the root `conftest.py` defines xdist hooks (`pytest_testnodedown`), so disabling the plugin kills collection with a `PluginValidationError` before any test runs. When you delegate test runs to sub-agents, tell them this explicitly: the instinct to single-thread for readable output is a large time tax.

IMPORTANT: The parallelism defaults come from measured per-worker peaks rather than core counts, and every width that divides a box by one of those peaks derives itself from the box in hand instead of shipping the answer one machine's memory once gave: `rebuild/tools/memory_budget.py` is the authority on that arithmetic and on the policy behind it — how many of a thing fit, total memory clamped by any cgroup limit and less a stated reserve, never free or available memory — while each per-unit cost stays at its own call site in the docstring that already has to argue the width, so a number and the argument for it are never in different files. Only three fan-outs are genuinely memory-bound. The Rust kernel's configuration fan-out is priced at `CONFIG_PEAK_BYTES` in `rebuild/pipeline/kernel_exec.py`, because a live configuration holds its whole working set until it has written its artifacts, and resolves through `kernel_threads_default` — as `KERNEL_THREADS_DEFAULT` for the solo width a bare `run_m1` gets, while a cycle names its own through `kernel_threads_budget` in `rebuild/tools/artifact_cycle.py`, which takes gate:make-test's pytest pool off the box before the division so the width answers for the machine the fan-out will actually run on. The rebuild suite's validators lane is the second: `VALIDATORS_WORKER_BYTES` in `rebuild/conftest.py` (the authority on the lane split) is what one of its workers holds, `VALIDATORS_LANE_CAP` beside it is the short-run bound the arithmetic cannot supply, and `VALIDATORS_WORKERS` is the one division over the pair; that same per-worker figure prices any run whose composition the root hook cannot narrow by inspection — a lane-less `uv run pytest rebuild/`, a single rebuild test file, a mixed or straddling collection — since a worksteal pool cannot keep a validators test off any slot it starts; the root `conftest.py` restates it as `HEAVIEST_WORKER_BYTES` rather than importing it (a check in `rebuild/test_memory_budget.py` holds the two equal) and divides it into the box under a cap of the cores this process may actually run on. The review-surface build is the third, and the one whose flat half is as large as its divided half, so its call site in `rebuild/tools/artifact_cycle.py` names two constants: `SURFACE_PARENT_BYTES` is the parent that holds the whole corpus at any width, subtracted from the box before the division — beside gate:make-test's co-resident pool under a gated cycle, whose bytes come off the box as its two cores come off the cap — and `SURFACE_WORKER_BYTES` is what one worker holds, with `surface_job_budget` the one division over the pair, stopped at `SURFACE_JOBS_CAP` where the build stops scaling; a box the pooled shape does not fit floors at one, which is the serial build rather than a refusal. Everything else is bound by something other than memory: the post-build sweeps are data-capped at one process per acceptance configuration, which is all `run_m1._spawn_pool` will start (`sweep_job_budget`); and font-suite workers are cheap enough — `FONT_SUITE_WORKER_BYTES` in the root `conftest.py`, whose `pytest_xdist_auto_num_workers` hook answers for them — that cores bind the pool long before memory does, so their `-n auto` is a plain clamp to `memory_budget.usable_cores()`, the cores this process may actually run on with the affinity mask and any cgroup CPU quota included, which `os.cpu_count()` reads straight past, and the contracts lane takes that same clamp because it reads no live artifact at all. Where a width is stated rather than derived, the statement carries its reason: `make test-rebuild-slow` states its own narrow width because the marker deselects nearly everything its workers have already collected, so a slot the selection cannot fill buys no parallelism while costing a whole collection; and under a cycle gate:make-test's pool runs at the width the cycle states through `PYTEST_XDIST_AUTO_NUM_WORKERS` on that one child, so the pool that runs is the pool the cycle reserved for rather than one sized as though nothing else were on the box. A deliberately wider one-off run overrides all of this in the environment, never by editing the checked-in values — `PYTEST_XDIST_AUTO_NUM_WORKERS` for any `-n auto` pool and `AMS_KERNEL_THREADS` for the kernel fan-out, both winning ahead of everything derived, and `AMS_TOTAL_MEMORY_BYTES` overriding the probe rather than the policy, so a roomy box can reproduce a small one's widths and junk in it is ignored rather than raised on. The machines all of this actually runs on — chips, P/E core splits, RAM — are recorded in `doc/fleet.md`, the reference for the host-tagged output `make cycle-timings` and `make job-costs` print.

IMPORTANT: After any Python changes, run `make prettier` to format the code.

Pyright covers the whole Python tree, `rebuild/` included, and every invocation is a bare `uv run pyright` — `[tool.pyright] include` in `pyproject.toml` is the single authority for what gets checked, so never pass paths on the command line. `make test` gates the main tree and `make test-rebuild` gates `rebuild/` (a rebuild-only edit cannot move `make test`'s fingerprint, so it can never be the gate for one). Suppress with `# pyright: ignore[reportSpecificRule]`, always naming the rule; never `# type: ignore[...]`, which pyright reads as a blanket whole-line suppression that silently hides neighboring errors.

## General background information

- “Orthodox” is Quikscript-speak for “English written in the Latin script”.
- Quikscript letters, when they’re being referred to as letters, are prefixed with `·`.

## Specific background information

- Tall letters have a height of 9 pixels (9 entries in `bitmap`).
- Short letters have a height of 6 pixels (6 entries in `bitmap`).
- Deep letters have a height of 9 pixels (9 entries in `bitmap`) and a `y_offset` of -3.
- See @doc/glyph-names.md for the canonical map between Quikscript letters’ names (·Pea), PostScript family names (qsPea), and code points (U+E650).

## Adding glyphs

- Whenever a glyph is added to any YAML file under `glyph_data/`, ensure it also has an entry in postscript_glyph_names.yaml if it uses a standard PostScript name (not a `uniXXXX` name).
- Keep all glyphs alphabetized by code point (`uniXXXX`).
- “Ink” is a filled bitmap pixel — a `#` cell, as opposed to a space. The font’s strokes are made of ink. The cursive-attachment tooling talks about a row’s “leftmost-ink column” (the leftmost `#` in that row), “no ink at y=N” (the row at glyph-space y=N is all spaces), and `exit_ink_y` (the fallback row to scan when the exit anchor’s own Y has no ink).
- For bitmap data, use double-quoted row strings. Add bare trailing `#` comment markers on the rows whose glyph-space `y` values are 5 and 0; which bitmap rows those are depends on `y_offset`.

## Locations of things

- Quikscript source data lives under `glyph_families` in `glyph_data/quikscript.yaml`, with separate `mono`, `prop`, `shapes`, and `stances` records. Put `entry` / `exit` anchors (under an `anchors:` mapping) in the proportional record or stance that should compile into the proportional font; mono-only records do not carry `curs` anchors.
- Shared Quikscript bitmaps belong under a family’s `shapes`, and contextual/alternate stances belong under `stances` with `anchors`, `select`, `derive`, `traits`, and `modifiers`. Preserve `traits: [alt]` and `traits: [half]` when those concepts are real; other suffixes belong under ordered `modifiers`.

## Dev-server URLs

- `make serve` runs `tools/serve.py`, which serves the `site/` directory on `http://localhost:7293/`.
- `make review-serve` serves the rebuild review surface on `http://localhost:7294/`. When the user asks whether everything is ready to verdict, don't reason it out from the git log — run `make verdict-ready` (surface freshness by input fingerprint and against the M1 font under the served letters, gate greenness, verdict-store alignment, server, blanks remaining); the app shows the same status as a banner. The fingerprints the table build is keyed on are prose-blind toward the rune files: YAML comments, reformatting, and every documentation field — `ductus`, `notes`, and `why` everywhere, refuse records included — sit outside them, with `rebuild/pipeline/fingerprint.rune_file_digest` the authority, so editing prose never rebuilds the tables, re-runs the conform sweep, or re-runs either suite lane. The one rationale anything downstream reads is a refuse record's `why`, which the surface's explain panel quotes, and it has homes of its own instead: the Stage B `explain_prose` fingerprint component the surface stamps itself with, and the review unit cache's family keys (`fingerprint.rune_explain_digest`). So rewording one re-stamps the surface and re-enriches the windows that quote it, which a review-cycle pass does with run_m1, the conform sweep, and both suite lanes skipping on their greens. The three human-reviewed ledgers are hashed the same way — `rebuild/m1-divergences.yaml`, `rebuild/m1-contact-allow.yaml` and `rebuild/standing-approvals.yaml` go through a projection before they are hashed, with `fingerprint.divergence_ledger_digest`, `fingerprint.contact_allow_digest` and `fingerprint.standing_approvals_digest` the authorities — so a comment, a reformatting, or a reworded `why:` or `note:` leaves the table build, the conform sweep and both suite lanes alone, and only an edit to what an entry structurally says moves them. Each ledger's prose still lands wherever something actually reads it: a divergence entry's `why` is written into the surface manifest's class list, so it rides the same Stage B `explain_prose` component a refuse record's `why` does, and rewording one re-stamps the surface and nothing else; the contact allow-list's `why` reaches nothing downstream at all, so wording a bless is free; and a standing rule's `note` is quoted verbatim into every fill it lands, so it stays inside the verdict plumbing's key alone.
- `make review-cycle` is the hands-off loop: run the artifact cycle — whose plumbing step (`rebuild.tools.verdict_chain`: the carry, then `merge_verdicts`, the app's newer-`at`-wins import union, headless and never-shrinking, then the echo and standing fills run to their fixpoint and the complaint docket, all in one process over the surface's slim `units-index.ndjson.gz` rather than four parses of the shards) lands the carried verdicts in `verdicts-autosave.json` with no browser import — and serve the surface at the end. Whether the review server has to come down for a pass is the cycle's decision, not the recipe's, because only the resolved plan knows: two of the things a cycle writes belong to the running app — the surface it serves, where a restamped manifest orphans the open tab's store, and the verdict store, which `merge_verdicts` refuses to touch under a live server anyway — so a pass that rebuilds the surface or moves the store stops the server first (`--stop-server` is the recipe's permission to; a bare `make artifact-cycle` still refuses and says how), while a pass that writes neither leaves it up and the letters stay on screen for the whole run. That second shape is the pass whose artifact work a green record already proved, so the verification runs underneath the letters rather than in place of them. An edit confined to `rebuild/review/static/` is the one surface input a pass refreshes in place rather than rebuilding for — the `assets-refresh` step, which is `rebuild.review.build refresh-assets`: the served copy is overwritten and only the manifest's `static` component restamped, so no shard, no sidecar and no `generated_at` moves, the tab's store stays aligned, the server stays up and livereload reloads it onto the new shell; that tree is out of the validators lane's closure too, so an app JS/CSS/HTML edit costs seconds plus the contracts lane rather than a surface build. Serving in the foreground is what an interactive caller wants and what makes the target hands-off, but it also means the recipe never exits: run it from anywhere that waits on a command and the cycle summary never lands as a completed run. `make review-cycle SERVE=0` is the form for those callers — same cycle, but it prints the `make review-serve` command instead of serving, so the target terminates; a pass that wrote neither the surface nor the store costs them nothing, since the server it never stopped is still up, and the recipe says so instead. `make review-cycle SERVE=bg` also terminates, but when the pass brought the server down it restarts it detached and waits for the port to answer before exiting, so the letters are back on screen and a `make verdict-ready` on the next line reads a server that is up rather than one still starting. One knock-on: while a server is up the retention pass leaves the journal and the stash sweep that indexes off it alone, because the app appends to that journal as you verdict and a compaction rewrites it around a read. After that merge the cycle also lands the echo prefill and the standing approvals: `rebuild/standing-approvals.yaml` holds checked-in once-and-for-all pattern rules (applied by `rebuild/tools/standing_verdicts.py`; a rule's `except_left` families still queue, any human verdict outranks a standing fill on merge, and two rules can explain one window between them at the rendered-pixel grain when neither reaches it alone), so a delta shape the user has blessed forever never reaches the docket again. Every store write (app autosaves included) is journaled in `verdicts-journal.ndjson`; `merge_verdicts --restore-as-of <time> --apply` rolls the store back to any recorded moment, and `--list` shows the history. A green cycle ends with a retention pass over the regenerable piles: only this cycle's `tmp/review-pre-*` snapshot and the stamp-aligned `verdicts-carried-*.json` survive, `verdicts-autosave-*` stashes older than the journal's last base event go (the journal replays them), the run directories under `tmp/build-logs/` beyond the last 10 go, and the journal is compacted to a 7-day restore floor — `ARGS='--keep-history'` skips the pass, and the tracked copy under `rebuild/evidence/` is never touched. One pass verifies everything it cannot prove unchanged and then serves, so the letters are never on screen under a NOT READY banner waiting on a verification nobody ran: after a rune edit the heavy gates run before the letters come up, and what comes up is sitting-ready. The green records are what keep that from costing anything twice — a pass that changed nothing still costs seconds, because every heavy stage skips on its record and the verdict plumbing skips too (the whole chain rides one green record keyed on the surface, the verdicts master, the store, `standing-approvals.yaml` and the chain's own import closure, so a pass that changed none of them re-derives nothing, and a pass whose surface did not move merges its master straight in without a snapshot or a carry). A gate that did not run is unverified, not waived, so `make verdict-ready` stays NOT READY until one does. Nothing prompts you to run that command after a pass: a green cycle closes its summary on the same checklist — `make artifact-cycle` with the server row, `make review-cycle` without it, since the recipe answers the server question on the line after — so `make verdict-ready` is the form for asking on its own, and the app's banner is the same status again. The census is never one of those skips: every non-rehearsal pass rewrites `rebuild/review-census-pins.json` from the census sidecar the surface build already emitted — milliseconds, no recompute — and prints `git diff -- rebuild/review-census-pins.json` in full. That file is the last accepted census and committing the diff is the acceptance, so reading it belongs to the commit: the `volatile` block holds the totals that legitimately move with every migrated letter and wants a glance, while anything moving in the `invariant` block — which classes the surface ships, which the build machine-approves, which are exempt from individual verdicts, which verdict families the corpus reaches — wants real attention. `make artifact-cycle` is that same verification without the serve, which is the form for commit time. Every cycle also appends per-step wall times and peak RSS — host-tagged, with each child's inner `[t]` phase lines — to `rebuild/out/cycle-timings.ndjson`, and every judged check invocation files its verdict there too, interactive `make test` / `make test-rebuild` / `run_m1` runs included; `make cycle-timings` summarizes recent runs, `ARGS='--by-step'` compares step medians across machines, and `ARGS='--by-outcome'` reports each check's green/red/skipped history with a histogram of the test ids it has failed on. That `[t]` line is one of four an in-house child prints for the cycle to read back, on stdout or stderr alike: `[t]` for a label that has just finished and the seconds it took, `[phase]` for one it has just opened, `[progress]` for how far a counted pool has got, and `[warn]` for a line that must reach the terminal whatever else is being throttled. `rebuild/tools/console.py` is the authority on both halves of that — the producers a child calls and the digest that renders the cycle's terminal out of what they print — and a third-party child (pytest, node) reaches the same events through a per-step adapter there rather than by printing the protocol itself.

## YAML files

- Quikscript stance keys (`alt_reaches_way_back`, `entry_xheight`) are local labels — compiled glyph identity and compatibility metadata come from each stance’s explicit `traits` and `modifiers`. Structured selectors in `select` / `derive` can combine all three, e.g. `{family: qsUtter, traits: [alt], modifiers: [reaches-way-back]}`.
- Within `select` / `derive` lists and `context_sets`, keep `{family: qsX}` entries in code-point order (qsPea, qsBay, qsTea, …, qsOoze — see postscript_glyph_names.yaml). For ligatures, sort by the lead family’s code point, with the bare lead before any ligature that starts with it.
- When multiple Quikscript stances share the same selector or anchor scaffolding, prefer `inherits` over copying the whole stance, and clear inherited nested keys with `null` when a child stance needs to drop them.

### Ductus

`ductus` describes how a letter is drawn by hand (pen direction, stroke order, where the stroke enters and exits). It exists to clarify the strokes to readers — including agents — who aren’t drawing the letters themselves. Keep it separate from `notes`, which records join _constraints_ (“·Fee cannot join both to and from at the x-height on the same letter”) rather than how-to-draw.

- **Put the canonical `ductus` at the family level**, as a sibling of `mono` / `prop` / `shapes` / `stances` (see `qsIt`, `qsFee`, `qsMay`, `qsNo`). It describes the abstract stroke and so covers both `mono` and `prop` at once — even when their bitmaps differ (as with `qsPea` and `qsTea`), because the drawing motion is the same. Don’t hang the default `ductus` off the `mono` record.
- **When one bitmap supports several valid drawing orders** (e.g. `qsTea` is written top-to-bottom _or_ bottom-to-top), keep them in the single family-level block scalar as `-` bullets rather than duplicating anything. See `qsIt`.
- **Give a `shapes:` or `stances:` entry its own `ductus` only when it is genuinely drawn differently** from the family default (see `qsFee.shapes.connect_from_short_height` and `continues_stroke_from_top`, which loop the opposite way and enter at a different height). A variant’s `ductus` **fully replaces** the family default for stances built on that shape, so write it as a complete stroke description, not a delta. A variant with no `ductus` inherits the family one.

### Formatting

- When rewriting `glyph_data/quikscript.yaml`, keep anchor coordinate pairs inline as `[x, y]`. Keep short `traits`, `modifiers`, and `select` / `derive` reference lists inline too, and only fall back to block lists when entries are genuinely long enough that inline formatting hurts readability.
- The width rule that decides flow-vs-block in `glyph_data/quikscript.yaml`: **keep a mapping or list inline (flow style) as long as the whole line stays within 100 columns; when it doesn’t, break the _outermost_ flow collection on that line into block style and re-apply the rule to the resulting lines.** Four consequences to honor:
  - It’s recursive to a fixpoint — breaking the outer collection just moves its children onto their own lines, and any of those still over 100 break again.
  - The 100-column target is best-effort, not a guarantee — a long scalar (`ductus`, a paragraph-length `why:`) can’t be broken and is left long, matching the no-hard-wrap prose rule.
  - **A collection whose subtree carries comments must stay block regardless of width** — flow style can’t hold per-item line comments, so inlining a `bitmap:` list would silently destroy its `#` row markers.
  - YAML forbids a block collection nested inside a flow one, which is _why_ the break is at the outermost collection — once any child must be block, its whole map goes block, so short scalar siblings (`{x: 0, stroke: horizontal}`) get their own lines too.
- The rune files under `glyph_data/runes/` do **not** use the width rule. They use a structural rule instead, so that a collection’s style never flips because an edit changed its line length: **every mapping and list is block style, except three leaf shapes that stay flow — an empty collection (`{}` / `[]`), a single-key mapping whose value is a scalar (`{family: qsDay_qsUtter}`, `{exit: x-height}`), and a pair of numbers (`[1, 1]`).** A single-key mapping whose value is a collection goes block, as does a single-item list (`require:` followed by `- entry`, not `require: [entry]`). Multi-line scalars are emitted in `|` literal style, and the comment invariant above applies here too.
- Both policies are mechanized by `tools/reflow_yaml.py` (ruamel round-trip, so comments and block scalars survive, and idempotent so re-running is a no-op); it picks the policy by path. Run `uv run python tools/reflow_yaml.py` to reflow `quikscript.yaml` plus every `glyph_data/runes/*.yaml`, or pass explicit paths.

### Selectors

- For “every letter that has an anchor at y=N” use `{exit_y: N}` / `{entry_y: N}` selectors instead of hand-curating a `context_set`. Add `except: [{family: …}, …]` to drop specific families from the resolved set (e.g., `{exit_y: 0, except: [{family: qsYe}, {family: qsPea}, {family: qsTea}]}` skips ·Ye/·Pea/·Tea even though they exit at y=0).
- For “this family, but only variants with a compatible anchor at y=N” use family-scoped anchor selectors such as `{family: qsMay, exit_y: 5}` in `after` lists or `{family: qsTea, entry_y: 0}` in `before` lists. These mirror normal family selector behavior, including compatible ligature/component expansion, then apply the anchor-Y filter. Use `tools/suggest_scoped_anchor_selectors.py` to find candidates, but do not replace a broad family selector unless generated Senior FEA or focused shaping tests prove the change is equivalent.
- Family-scoped anchor selectors may still compile to include the bare scoped glyph when that bare glyph is the pre-lookup stance for an unrestricted entry/exit upgrade at the requested Y; this lets cyclic joins like ·They·May use `{family: qsMay, entry_y: 0}` instead of widening back to `{family: qsMay}`.
- Don’t mechanically replace long family lists with `{entry_y: …}` / `{exit_y: …}` just because the list is long. Anchor selectors expand to every matching variant, so a shorter source list can still change generated FEA or create join warnings; prove equivalence with the generated Senior feature code or the shaping tests before committing such a cleanup.
- To prove a scoped-anchor narrowing (`{family: qsX}` → `{family: qsX, entry_y: N}` / `exit_y: N`) is a pure source cleanup, run `make check-html-before` first, make the change, run `make all`, then `diff site/before/AbbotsMortonSpaceportSansSenior-Regular.fea site/AbbotsMortonSpaceportSansSenior-Regular.fea` (or sha1sum the six OTFs in each directory). Byte-identical means the change is equivalent and `make test` + `make review` is enough; any divergence is a real shaping change — surface the diff for review instead of treating it as a cleanup.
- When a narrow `after:` selector competes with a broad fallback like a `context_set`, make sure the narrow selector wins first.

### Anchors

- The standard x-value for an `exit` anchor is one pixel to the right of the stroke (`exit.x = max_ink_x_at_exit_y + 1`). Usually this places the anchor just past the bitmap’s right edge, but sometimes the anchor falls inside the bitmap — as with ·He, ·Ye, and `qsThey.ex-y5` — because the stroke exits from the left or middle of the glyph.
- Symmetrically, the standard x-value for an `entry` anchor sits **on** the leftmost ink at the entry’s row (`entry.x = min_ink_x_at_entry_y`). Wide letters whose entry attaches to an already-inset stroke land at the actual leftmost ink, not at `x = 0` — e.g. `qsBay.en-y5` at `(3, 5)` over `"   # "`, `qsThaw.prop` at `(2, 0)` over `"  #  "`. Derived `*.en-ext-1` / `*.en-con-1` / `*.en-trim-N` variants intentionally diverge from this; see `tools/audit_anchor_geometry.py`’s docstring for which buckets are expected anomalies.

### Miscellaneous

- When the right glyph is about to be consumed into a ligature with no matching entry, the left glyph must not keep a now-false exit. `·Excite·Tea·Oy` is the worked example: `qsTea_qsOy` has no baseline entry, so `qsExcite.ex-y0.before-vertical` must surrender its exit. Extend `_PENDING_LIGA_ENTRY_GUARDS` in `tools/quikscript_join_analysis.py` rather than broadening the plain pair-guard machinery.
- When you’d otherwise author a near-duplicate `before:` stance so an entryless forward-exit stance can displace its entry-bearing siblings, reach for `strip_entry_before: true` instead; see `qsAt.entry_nowhere_exit_baseline` for the worked example, and the JSON schema description for the full rules.
- In `calt` selectors, ZWNJ is the literal `uni200C` glyph — list it alongside `space` in `after` / `not_after` when blocking word boundaries.
- Two-glyph ligatures inherit their entry anchor from the lead automatically (see `_inherit_ligature_entries_from_lead`); the build emits `LigatureEntryInheritanceWarning` for any redundant or mismatched explicit declaration. Keep an explicit entry only when the lead’s inheritable stance is context-restricted (e.g. `qsThey.en-y5`) or the ligature’s bitmap doesn’t share the lead’s leftmost-ink column at the entry’s Y.
- The mirror image holds for the exit side: `_iter_related_extension_targets` propagates the trailing component’s `extend_exit_before` / `contract_exit_before` onto a `qsX_qsY` ligature, and `calt_liga` routes `(qsX, qsY.<exit-modifier>)` through to `qsX_qsY.<exit-modifier>`. Don’t restate trailing-component exit rules on a ligature — unless it declares its own `noentry_after`, which skips the propagation (currently true for `qsThey_qsUtter`); in that case, carry the exit rules on the ligature in YAML.
- Don’t hand-list ligature names (e.g. `qsJay_qsUtter`) in `select.after` / `select.before`; the `expand_selectors_for_ligatures` IR pass adds them automatically from the trailing/lead component. See its docstring for edge cases.
- A ligature opts out of all left-side joins by declaring `entry: null` on its `prop.anchors` (see `entry_explicitly_none` in `tools/quikscript_ir.py`). The FEA emitter reverts predecessors automatically, and `expand_selectors_for_ligatures` naturally suppresses the forward-expansion path because the ligature has no entry Ys to satisfy; the backward direction still fires so `after: [trailing_component]` selectors on followers continue to pick up the ligature post-liga. Don’t hand-author `not_before: [qsX_qsY]` clauses on predecessor variants to compensate.
- When a `noentry_after` ligature leaves a predecessor’s bare bitmap with unsupported exit-side ink, add an explicit `.ex-noentry` stance with no exit anchor and the trimmed bitmap. Two flavors exist:
  - **Entryless** (`qsMay.ex-noentry`): no entry either; the post-liga cleanup chooses this when the predecessor’s selected variant has no entry anchor (typical when nothing exits at the matching Y).
  - **Entry-preserving** (`qsMay.en-y0.ex-noentry`, authored via `inherits: entry_baseline` plus `anchors.exit: null` and a `[ex-noentry]` modifier): the entry side is kept so the join with the predecessor still attaches. Authoring this also opts the family out of the calt_cycle guard that `_propagate_noentry_after_to_not_before` would otherwise emit, so the matching entry-bearing stance (e.g. `qsMay.en-y0`) is picked pre-liga and `·Roe·May` joins at the baseline whether or not the entryless ligature follows.
  The `_exit_noentry_fallback` in `tools/quikscript_fea.py` matches the input variant’s entry side and modifier set when picking the replacement, so each input variant routes to the closest sibling. The second pass, `calt_post_liga_left_cleanup_pred`, only fires when the replacement is entryless: any pre-predecessor whose `select.before` clause was triggered by the now-demoted family is reverted to its bare base, so a glyph like `qsRoe.ex-y0` doesn’t keep extending toward an entry that no longer exists.
- When an entry-preserving `ex-noentry` stance is used as a `before:` forward-pair override to match split shaping across a non-joining break, scope its left context to predecessors whose isolated left half already chooses the same entry stance. Use an anchor selector with `except` for the positive predecessor set, and add a `trailing_demote_overrides` entry when the follower may already have taken a backward upgrade that must return to the isolated right-half stance (e.g. `qsIt.en-y0.ex-noentry.before-day-exam` demotes `qsDay.half` back to `qsDay`).

## How to do simple changes

Most one-line cursive-attachment tweaks fit one of the patterns below. Don’t reach for a new stance before checking these first.

### Make ·X·Y use Y’s `<shape>` shape

Add `{family: qsX}` to the `select.after` list of the qsY stance that uses that shape. If qsY’s `prop.derive.extend_entry_after.targets` mirrors the same `select.after` list, add `{family: qsX}` there too to keep them in lockstep. Example: making ·Jay·Roe use Roe’s `shortened_top` shape adds `{family: qsJay}` to both `qsRoe.stances.entry_extended_at_baseline.select.after` and `qsRoe.prop.derive.extend_entry_after.targets`.

### Extend the ·X·Y connection by N pixels

Add `{family: qsY}` to qsX’s family-level `derive.extend_exit_before.targets` (creating the dict with `by: N` if it doesn’t exist). The build widens X’s exit stroke and shifts the exit anchor by the same amount, so the receiver moves right and the connecting stroke gains N pixels of ink. Example: extending ·Jay·Exam by a pixel adds `{family: qsExam}` to `qsJay.derive.extend_exit_before.targets`.

When the same stance needs to extend by different amounts for different followers, `extend_exit_before` also accepts a list of `{by, targets}` rules instead of a single dict — add a second rule with the different `by` rather than authoring a sibling stance. Reach for a sibling stance only when other fields (selectors, anchors, bitmap) also differ. The same list shape works on `extend_entry_after`: add a second `{by, targets}` rule to the existing stance instead of cloning it when only the extension distance changes.

### Contract (opposite-of-extend) the ·X·Y connection by N pixels

Add `contract_entry_after: {by: N, targets: [{family: qsX}]}` to qsY’s joining stance’s `derive` (typically `entry_xheight` for xheight joins, `entry_baseline` for baseline joins). Don’t make a new stance, even when qsY already has an `extend_entry_after` whose targets implicitly include qsX (e.g., through `halves_exit_xheight`) — the narrow contract rule (a single family) wins over the broad extend rule because the build orders narrower selectors first. Example: contracting ·He·Jay by a pixel adds `contract_entry_after: {by: 1, targets: [{family: qsHe}]}` to `qsJay.stances.entry_xheight.derive`, alongside the existing `extend_entry_after`. If the directive on that side already has a different `by`, put the rule on the other side of the join instead.

### Mix `before:` and `not_before:` on a single stance

When a stance needs both a forced positive trigger and a broad anchor-class fallback, declare both `before:` and `not_before:` on the same stance rather than splitting into two near-duplicates. The symmetric pair `after:` / `not_after:` works the same way. See `qsGay.stances.exit_baseline` for the canonical example.

## Bumping the version number

1. Update `version` in `glyph_data/metadata.yaml` (e.g., `3.000`)
2. Update `version` in `pyproject.toml` (e.g., `3.0.0`)
3. Run `uv sync` to update `uv.lock`
4. Add a `### X.YYY` changelog entry for the new version under the `## Changelog` heading in `FONTLOG.md` if one doesn’t already exist; leave it empty if there’s nothing to record yet

## Visual before/after diffs

- `site/check.html` is a side-by-side rendering harness for eyeballing glyph changes. On the baseline branch, run `make check-html-before` to capture the “before” OTFs into `site/before/` (gitignored); make your changes on a branch, run `make check-html-after`, and reload. The whole file is regenerated by `tools/build_check_html.py` (called from the `check-html-after` target) — both auto-generated sections (corpus render diffs and isolation leaks) plus the surrounding chrome — so don’t hand-edit it. The file itself documents the workflow in more detail.

## Markdown-document style

- Use sentence case for titles, not title case.
- Do not hard-wrap lines. Let each paragraph or list item be a single long line.
- Ensure that Markdown tables are nicely formatted for humans and have nicely lined-up columns.
- Make sure `markdownlint-cli2` doesn’t have anything to complain about.
