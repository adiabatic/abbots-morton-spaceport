# Testing

This file maps each kind of change to the gate that checks it, and says what each gate fails on. Each rule names its executable authority; read that for the details.

## Which gate to run

| Change                                                                                                                  | Gate                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Glyph data or code in the main tree                                                                                     | `make test`                                                                                                                               |
| Anything under `engine/`                                                                                                | `make test-engine`                                                                                                                        |
| Settlement or proof-fold semantics in `engine/kernel-rs/`                                                               | `make kernel-gate`, then `make test-engine`                                                                                               |
| The table-diff corpus or its snapshot (`engine/review/diff_units.py`, `snapshot.py`, `tablediff.py`)                    | `make test-engine`, then `make artifact-cycle`, which builds and lands it beside the served corpus                                        |
| The table-diff accept or remake (`engine/review/accept.py`, `engine/tools/store_guards.py`)                             | `make test-engine`, then `make review-accept` (a dry run, which writes nothing)                                                           |
| A review-app module in `engine/review/static/`                                                                          | `node --test engine/review/jstests/*.test.js` (the cycle's `gate:js`)                                                                     |
| The contract fixture in `engine/review/fixtures/`                                                                       | `make test-engine`, then `node --test engine/review/jstests/*.test.js` (the cycle's `gate:js`)                                            |
| The review server, the verdict store, or the land                                                                       | `uv run pytest engine/test_landing.py engine/test_review_autosave.py -n auto --dist worksteal`, then `make test-engine`                   |
| A rune or pipeline edit, to rebuild and recheck the tables                                                              | `uv run python -m engine.pipeline.run_build` (or a `make review-cycle` pass)                                                              |
| A rune's `kern:` block, or the font's non-Quikscript data, alone                                                        | `uv run python -m engine.pipeline.run_build --kern-only` (a cycle pass plans it)                                                          |
| Mono and Junior, or the six-font publish (`build_family`, `build_fonts`)                                                | `make test-engine`, then `make all`                                                                                                       |
| The release upload and the workflow that publishes it (`engine/tools/release_fonts.py`, `.github/workflows/deploy.yml`) | `make test-engine`, then `make draft-release` (a dry run, which writes nothing); `uvx --from actionlint-py actionlint` lints the workflow |
| A `data-expect` pin, or the grammar, collector or checker (`engine/validation/expect.py`, `corpus.py`, `check.py`)      | `make test`, which checks the pins against the published fonts; `make test-engine` for the checker's own tests                            |
| Commit time                                                                                                             | `make artifact-cycle`; `make review-cycle` when a review session follows                                                                  |
| Is it ready for review?                                                                                                 | `make verdict-ready`                                                                                                                      |
| A change meant to shorten edit-to-READY (tracking issue #584)                                                           | `make cycle-timings ARGS='--by-step'`, before and after on matched pass shapes (`doc/perf-check.md`)                                      |
| Periodic, by hand or overnight                                                                                          | `make test-engine-slow`, `make conform-deep`, `make replay-deep`                                                                          |

Never single-thread a broad run; `doc/parallelism.md` has the width rules. Run anything that includes the heavy gates detached; `doc/running-long-steps.md` has the recipe.

## `make test`

- Skips in a few seconds when nothing it reads has changed since its last passing run. `make_test_exempt` in `engine/tools/artifact_cycle.py` defines what is outside its input closure. A change there cannot affect this gate; the engine suite or the artifact cycle checks it, so don't force a run for one.
- `make test FORCE=1` runs it regardless.
- The session first publishes the six fonts into `site/` through `engine/tools/build_fonts.py`'s command, the one `make all` runs, and fails with its message, which names the build command, while the build's Senior is stale; a test session never starts the Senior's build. Every test reads the fonts there. The `data-expect` pins on the three site pages and the any-of regression checks (`test/test_calt_expectations.py`) are checked against Senior and Junior by `engine/validation/check.py`, the checker the build's pin gate runs, with the Senior's glyph-facts sidecar read beside the build under `engine/out/build/`.
  - The key covers the published fonts by what they are published from (`make_test_font_lines`): the Senior under `engine/out/build/` with its glyph-facts sidecar and whether it is current, and Mono's and Junior's code and data. So a rune or pipeline edit reruns the suite once run_build has rebuilt the Senior, and the artifact cycle starts gate:make-test only once the build gate passes.
  - A pin the engine disagrees with, pending the author's ruling, is an expected failure, and a pending pin that passes fails (`doc/data-expect.md` § Pending pins).
- Pyright runs in the same invocation over the whole tree. `[tool.pyright] include` in `pyproject.toml` defines what it checks, so every invocation is a bare `uv run pyright` with no paths.
  - Pyright skips on its own green record (`engine/out/pyright-green.json`) when nothing it can read has changed since its last passing run; `engine/tools/pyright_gate.py` defines that closure. A dependency change reruns it, and so does a version bump, which rewrites `pyproject.toml`.
  - `FORCE=1` runs pyright along with the suite.

## `make test-engine`

- Runs the contracts suite through `engine/tools/engine_gate.py`, with one green record (`engine/out/engine-contracts-green.json`) shared with the artifact cycle's gate:engine-contracts; `engine/tools/contracts_closure.py` owns the run lifecycle both entry points share. `make test-engine FORCE=1` runs the whole suite regardless.
- No test under `engine/` reads live build output. `engine/conftest.py`'s audit guard fails a test that reads a live tree (`engine/out/`, `tmp/`, `var/`, the root verdict stores) with `ContractsLaneViolation`. Write a new test against a synthetic root or `tmp_path`. A check on a live artifact belongs in the build that makes the artifact.
- The suite reads only checked-in inputs, including the hermetic mini bundle under `engine/review/fixtures/mini/`, a frozen font and two of its tables, and runs at full width.
- A bare engine-suite collection and a mixed font and engine collection use the root conftest's worker-sizing hook.
- The suite usually runs only the tests whose recorded input closure contains a changed file, and prints what it left out, as the artifact cycle's plan does for `gate:engine-contracts`; the module docstring of `engine/tools/contracts_closure.py` says what a closure holds and which tests always run.
- A narrowed run still pays the suite's fixed startup cost, because every worker collects the whole suite before the selection deselects anything. Selection saves only the test time above that cost; `make cycle-timings ARGS='--by-step'` shows it.
- Neither conftest's import closure reaches `engine/pipeline/` or `engine/review/`; the module docstring of `engine/tools/cycle_paths.py` says why, and `TestTheConftestsStayLeaves` in `engine/test_contracts_closure.py` checks that and pins their direct imports (`CONFTEST_EDGES`).
  - Fixtures that need the review tree load it through `announced_import` in `engine/conftest.py`.
- The build checks everything it can about its own artifacts, so the suite does not:
  - The review corpus's per-unit checks, `check_unit` and `check_shards` in `engine/review/build.py`. A build runs `check_unit` in the worker that drafts a fragment and again in the process that writes it, each time over the fields settled by then, and runs `check_shards` over the corpus read back from disk.
  - The rule certificates the crate writes beside every table's rules. `run_build`'s witness stage (`run_rule_witnesses`) settles each certificate and asserts that its rule is the first to match at some position in it. It runs on the table-only branch beside the glyph chain, which is joined before the build gate is decided. `engine/test_rule_witnesses.py` tests the witness code on the mini fixture, and `engine/test_run_build_tail.py` tests the branch's join and its error order.
  - The order the settlement lookup ships its rules in. The shipped-order walk on the same branch replays it against every configuration's rows (`run_emitted_order`, over the crate's `replay-emitted` subcommand); `engine/test_emitted_order.py` tests it on the same fixture.
  - Every ligature stance's declared outgoing mapping, settled against the formed rune before the tables are built (`run_build.run_ligature_outgoing` over `engine/pipeline/ligature_outgoing_check.py`). `engine/test_ligature_outgoing_check.py` tests it on the synthetic fixture, and `engine/test_ligature_outgoing.py` tests the loader's inheritance rules. A ligature-local record that loses or moves a join its trailing letter permits fails the build instead of showing up in a review session.
- No suite test can fail on a stale artifact, because none reads one. After a rune or pipeline edit, run the build to recheck the tables.
- `make test-engine` is also the pyright gate for `engine/`: `make_test_exempt` exempts that tree but for the font suite's checker (`MAKE_TEST_ENGINE_FILES`), so `make test` does not run for an edit anywhere else in it.
  - Pyright skips on the same record as under `make test`; when it runs, a type error fails the run after the tests finish (`engine/tools/pyright_gate.py`).
- Test collection under `engine/` skips the two crates and the build output (`collect_ignore` in `engine/conftest.py`). No test file lives in any of them, and their trees are nearly everything the collection would otherwise visit in every worker.
- The suite skips slow-marked tests. `make test-engine-slow` runs them, at `-n auto`.
- A ligature stance's `outgoing` declaration names policy records and exit unlocks by their index in a list (`policy.prefer[0]`, `surface.unlocks[0]`). Each policy or unlock key of `outgoing.exceptions`, and each key of `outgoing.replacements`, indexes the trailing letter's lists, and each `outgoing.replacements` value indexes the ligature's own policy lists: in `glyph_data/runes/qsTea_qsOy.yaml`'s `{'policy.prefer[0]': 'policy.prefer[0]'}`, the key names ·Oy's first preference and the value names the ligature's first. An exit-row exception key such as `surface.exits.x-height` names the row by its height. `glyph_data/runes/qsThey_qsUtter.yaml` carries exception keys into ·Utter's `policy.extend`, and `_inherit_ligature_outgoing` in `engine/pipeline/spec_load.py` reads both sides. An edit that changes a named record's position in its list (inserting or deleting a record ahead of it, or reordering the list) moves the path onto a different record. Loading fails when the path then names nothing applicable. Otherwise the build's ligature-outgoing check reads the same paths: a key that lands on another applicable record can change what the ligature inherits without failing either, and a value that lands on another applicable local record of the same kind changes which record the check substitutes for the excepted one. Update the paths in the same edit that inserts, deletes, or reorders the records: the keys for an edit to the trailing letter's lists, and the replacement values for an edit to the ligature's own policy lists.
- Codex's macOS sandbox blocks `sysctl -n hw.memsize`, so `engine/test_memory_budget.py::TestTheLiveProbe::test_the_portable_probe_is_byte_identical_to_hw_memsize_on_darwin` fails there even when the probe is correct. If it is the suite's only failure, rerun it outside the sandbox, and rerun `make test-engine` there so the gate records the result. Never weaken the probe or the test.

## Rerunning the gates without a build

The comparison-side inputs (the contact allow-list and the code `fingerprint.COMPARISON_CODE_MODULES` names) are not part of the tables' stamp, so a change to one of them needs no new enumeration:

```zsh
uv run python -m engine.pipeline.run_build --gates-only
```

That reruns the defect gate and the pin gate (`manual_pins`, over all three site pages) over the tables and font already on disk, and fails if the tables' stamp is stale. The artifact cycle plans this gates-only rerun itself when everything that changed since the last passing build is comparison-side (`comparison_side_label` in `engine/tools/artifact_cycle.py` lists what counts), and the green record it writes lets the next pass skip the build entirely.

## The settle memo

The settle memo that `gate:conform` and the witness stage share is keyed per family (`engine/pipeline/settle_memo_keys.py`), and each of its parts records the stamp and family keys it was settled under. It is held as a base and segments under a head (`engine/pipeline/row_delta.py`, merged by probe). The string replay fills it on every full replay, from the window memo each configuration's walk writes into a pipe it inherits from its absorb worker, which reads it as it arrives (`run_build.replay_and_absorb`, through `kernel_exec.replay_memo_walk`, over `conform.read_replay_memo`), comparing the refill with the standing memo and writing a segment of what differs, or the head alone when nothing does (`conform.compare_replay`), and commits each head only once every walk has passed. The conformance sweep's absorbs each write a segment of their fresh windows, and each writer's route, a segment or a whole base, is decided before any writer of its step writes (`conform.plan_settle_memos`). A rune edit therefore re-settles only the windows naming an edited family in the sweep, and a cold pass (a code or crate edit that changes the memo stamp) is cold in the replay, not in the sweep. The witness stage only reads the memo, so it also settles again on every pass the certificate windows that no replay text reaches. The docstrings of `conform._write_settle_memo`, `conform._settle_memo_segment`, `conform._MemoStore`, `conform.absorb_settle_memo` and `conform.materialize_settle_memo` describe the memo: the whole file's layout, which every base is and every segment repeats before its Bloom filter and dead bitmaps, the read-only mapping every walk shares, the one absorb that writes the fresh windows of the walks that may not write it, and the materialized form, which the `cmp` tests in `engine/test_conform.py` hold to today's writer's file. `run_build.run_rule_witnesses` says why the witness stage reads the memo and writes nothing to it.

The run's log reports what each pass served:

- The `[t] settle_memo` lines report what each pass of the conformance sweep served, retired, and pruned, one a configuration (`conform.settle_memo_line`).
- The witness stage's walk loads only the rows its certificate texts can ask for (`conform._SettledWindowWalk.load_only_asked_by`). Its `[t] rule_witnesses[<config>]` line carries `served=`, `unasked=`, and `fresh=`, and `witness_summary.json` records the same three per configuration. `served=` counts the rows the load kept, including stale rows: rows that name a family whose key changed, which the walk never serves. `unasked=` counts the rows the load dropped.

## Kern edits

A rune's `kern:` block reaches no table or settlement, so it is in none of their keys (`fingerprint.rune_file_digest` leaves it out). It reaches the run_build skip key through one line per rune (`fingerprint.kern_lines`), and when only those lines moved since the last green build and the Stage A record under `engine/out/build` matches the sources, the artifact cycle runs `run_build --kern-only` (`artifact_cycle.kern_only_rebuild`). That run reads the tables on disk, runs the kern stage, the defect gates with every kerned break at its kerned offset, the GSUB and GPOS emission, the compile and read-back beside the build, replaces the font, `kern.tsv`, `kern-classes.json` and the pipeline summary only once read-back passes, and keeps the Manual-pin summary and the Stage A record. A kern error or a read-back divergence leaves the build as it was, so the pass that fixes the record is a kern-only rebuild too; without a matching Stage A record the cycle rebuilds in full (`run_build.kern_only_run` says why). The string replay, the witness stage, the shipped-order walk and the Manual-pin gate do not run, the cycle rebuilds the review corpus, whose kerning units show the moved values (`artifact_cycle.corpus_build_skippable` compares its after font with `Senior-Regular.otf` byte for byte), and `gate:conform` skips unless the kern lookup's rule shapes (its behavior classes) moved. Read-back checks the values on every build; the conformance sweep checks every shaped break against `kern-classes.json` when it runs (`conform.check_break_advances`). The engine suite still reruns the tests whose closure holds the rune file, which it hashes whole (`fingerprint.rune_document_digest`).

An edit to the font's non-Quikscript data takes the same route. The Latin, Shavian, punctuation and symbol glyph files, `glyph_data/metadata.yaml`, the Latin kern rules in `glyph_data/opentype-features.yaml` and `postscript_glyph_names.yaml` reach the run_build skip key through one line per file (`fingerprint.font_data_lines`) and no other build key, and when only those lines and kern lines moved, the cycle runs `run_build --kern-only` (`artifact_cycle.font_only_label`). `glyph_data/punctuation.yaml` is the exception: the namer dot's glyphs come from it, so it is in the tables' stamp and an edit to it, the angle parentheses and `space` among its records, rebuilds.

## The kernel's own gate

No cycle gate runs the crate's test suite, so run `make kernel-gate` around any change to kernel semantics. It is the crate's fmt, clippy, and test gate (`make kernel-check`), and takes seconds once the crate is built. GitHub Actions runs `make kernel-check` and `make kernel-proofs` on a push to `master` or a pull request that touches `engine/kernel-rs/` (`.github/workflows/kernel.yml`); it runs nothing else, since every other gate is sized to a fleet machine.

- The proof-fold tests compare the production successor search with the per-producer breadth-first reference for identical parents and distances. They compare the indexed outcome partition with the string reference for identical winning rule positions, retained rows, refusal text, and certificates. Both references compile only in tests; certificate tail completion keeps the production string matcher as its independent check. [The issue comment on the `fold.prefixes` and `fold.partition` phases](https://github.com/adiabatic/abbots-morton-spaceport/issues/303#issuecomment-5785733925) maps the acceptance evidence.
- The hash wrapper's tests compare whole and fragmented application messages with independently computed Python `hashlib` digests. `engine/test_kernel_exec.py` checks every settlement configuration's returned table digest and deep-class tokens against `table.table_digest` and `table.deep_class_id` on the mini fixture, reading that synthetic build's retained windows because the returned tables hold only their heads.
- The gate checks the trace memo's byte identity (`engine/kernel-rs/src/memo.rs`). A configuration enumerated as a delta over `default`'s memo must write the same tables and digests as a from-scratch enumeration, and so must every schedule of deltas started from scratch beside `default`, the one where every delta does and `default` keeps no memo among them. The crate's own tests check this, and so does `tests/cli.rs` through the binary. `engine/test_kernel_exec.py` checks the same identity on the mini fixture through `kernel_exec.build_table_files`. A delta served `default`'s liveness verdicts, which reruns only the probe asks naming its unlocking runes, must also write the tables and digests a build with `--no-verdict-sharing` writes; the crate's fan-out width test, `tests/cli.rs` and `engine/test_kernel_exec.py` check it. A build whose engines clear their prospect and candidate memos at a ceiling (`fixpoint::TABLE_MEMO_CEILINGS`) must write the tables and digests of one that never clears them: the engine's ceiling test checks it window by window, and `tests/cli.rs` checks it through the binary by comparing a build at eight-bucket ceilings with one at the default ceilings, which the fixture never reaches. Every other table build that `tests/cli.rs` compares with another build's files runs at eight-bucket ceilings too. A delta reads `default`'s snapshot packed in sorted blocks through a cache of decoded blocks (`memo::SnapshotEntries`), and must read the same entries at any cache size and under any packing. `memo.rs`'s store test checks every key and its near neighbors at caches of 0, 1, 2 and 455 blocks, with the filter on and off and with restart points inside a block, and `tests/cli.rs`'s snapshot packing test checks that builds with no cache, with restart points, with no filter and at the default cache write the tables and digests of a build at a cache of two blocks. Every other byte-identity test in which a delta reads the snapshot reads it through a cache of two blocks, fewer than the fixture's snapshot holds, so a fence search, the filter's absent answer, a decode and an eviction run in each of those lanes: the fan-out width test, the delta parity test in `fixpoint.rs`, and every other table build `tests/cli.rs` compares with another's files (`SMALL_SNAPSHOT_CACHE`). `engine.rs`'s ranking test packs its few records one to a block so that the same paths run there. A build whose engines hold their trace memos to a ceiling (`fixpoint::TABLE_TRACE_CEILING`), clearing or half-dropping a full shard and storing no window with a concrete third slot and a known fourth, must write the tables and digests of one whose trace memos keep every window: the engine's trace ceiling test checks it window by window under both evictions, with the windows whose first slot alone is known surviving every eviction, `hash.rs`'s ceiling test checks that no shard outgrows its table, and `tests/cli.rs` checks it through the binary at the smallest ceiling, with `ss03` both as a delta reading `default`'s whole memo and from scratch beside it.
- The gate checks the grouped fourth-slot sweep's byte identity (`engine/kernel-rs/src/liveness.rs`); `build-tables` groups its sweeps unless given `--no-grouped-sweeps`. A build whose fourth-slot prospect probes answer an ask from the transcript of an earlier ask whose questions its token answers alike must write the tables and digests of an ungrouped build. `liveness.rs`'s grouped-sweep test checks it on the liveness fixtures, product, cited provenance and every memo length and count of the cache stats but the prospect memo's, which holds no entry for an ask a transcript answered, with every match also checked against the full ask, and requires that some ask was answered by a transcript, some by the transcript of an ask that took the candidacy estimate, and some probe found its slot live after one was; its check-mode test feeds the sweep a wrong transcript and requires the raise. `token.rs`'s tests check that a swept token compares, orders, hashes and keys as the plain one, and what the recorder records, ignores and is poisoned by. `tests/cli.rs` checks the identity through the binary against a `--no-grouped-sweeps` build in the delta schedule with verdict sharing on and in the from-scratch schedule, and that `--check-grouped-sweeps` passes there.
- The argument that a grouped sweep ends where the full sweep ends and fires what it fires is also written as Lean proofs over a model of the sweep (`engine/kernel-rs/proofs/`, whose `README.md` states the theorems and what the model assumes). `make kernel-proofs` checks them, by hand: it is in no local gate, and nothing else needs Lean installed. `engine/kernel-rs/proofs/modeled-sources.tsv` pins a digest of each Rust item the model stands for most directly, and `token.rs`'s `the_modeled_sources_match_their_pinned_digests`, part of this gate, fails when one of those items changes or a function of `engine.rs` calls `token::enter` without a pin, so the model is read against the new code before the digest is replaced.
- The memo lives only inside the `build-tables` process: no build reads or writes a memo file, so every build that runs the crate enumerates cold.
- A bare run_build runs the crate only when its input has moved since the last green run. The table-reuse record a green run leaves under `engine/out/build` keys the tables on the spec dump, the built binary, the crate and the roster (`run_build.memo_structure_stamp`), the table build's driver in `run_build.py` (`run_build.table_driver_digest`), the configurations and the mode flags (`run_build.table_reuse_lines`). On a match whose table files all still have the raw digests it records, the build re-stamps each head file with the run's sources and writes the tables the crate would, byte for byte; a build deletes the record before it writes anything, so a red, killed or torn build leaves none and the next run builds. `--fresh-tables`, which the cycle passes under `--fresh`, runs the crate regardless. `engine/test_kernel_exec.py` checks the byte identity against a forced build and that a red or killed crate followed by a revert builds again.

Three more checks compare the crate's tables with the rest of the build:

- The string replay checks the crate's tables against the crate's engine on every build, right after the tables are written or reused (`run_build.run_replay_strings` over the crate's `replay-strings` subcommand). It walks the persisted rules over every text up to `run_build.REPLAY_MAX_LENGTH` and compares each result with a fresh settlement keyed on the raw window.
  - It walks every text after a code or structure change or when the tables' imported windows move (`run_build.imports_digest`; `doc/engine-design.md` §10), and only the texts naming an edited family after a rune edit.
  - It also walks every text whenever a configuration's settle memo is missing, does not read, or has a part recording another stamp (`conform.settle_memo_standing`), because the walks' window memos fill `engine/out/build/settle-memo-<config>.bin`, its head and parts, for the witness stage and `gate:conform` to map, and only a full replay refills them.
  - `engine/out/build/replay_summary.json` is the record the next build computes its delta against.
- The shipped-order walk (`run_build.run_emitted_order` over the crate's `replay-emitted` subcommand) checks the emitter's one shipped lookup against the crate's tables. On every build, over the tables the crate just wrote or the ones the build reused, it tries every configuration's rows, first match wins, against the order the lookup ships, reading a `#NA` after a letter as every label in that slot and every later one, so it checks each continuation of an open slot, and `uni200C` as a literal label. Before it, the emitter checks each table's copy of that order, which the crate's cross-configuration exchange decided its imports by (`emit_gsub._fold_rules`).
- `gate:conform` checks the tables against the font: a HarfBuzz sweep of the compiled font against the same fresh settlement. `make conform-deep` is its periodic deeper form. The ss10 overlay case sweeps texts of up to two letters, relies on read-back's isolation check, and never goes deeper. Each cosmetic configuration (`conform.COSMETIC_CONFIGS`, ss06) sweeps texts of up to three letters against its settlement configuration's stream with the cosmetic copies substituted, relies on read-back's cosmetic checks and spec_load's rule that no condition names a cosmetic set, and never goes deeper.
  - `make conform-deep ARGS='--targeted'` runs the same checks, in minutes, over the texts the `settle:bk1-la4` rules give: each rule's certificate and every text whose six positions take a family from the rule's six classes, alone and after each symbol. No text at maximum length 5 can fire such a rule. `deep_sweep.targeted_lines` keys its green record, and `ARGS='--targeted --status'` asks whether it is due; the cycle neither runs nor reports it.

`make replay-deep` (`engine/tools/deep_replay.py`) extends the replay one letter past the build's maximum length: the same `replay-strings` subcommand at maximum length 5, over the texts naming the runes whose content changed since its last recorded walk. It is the cheaper form of the deep sweep's check: only it and a `make conform-deep` at maximum length 5 or more see a fault confined to the deep lookahead slots. It checks rune edits and the edits that move its structure stamp (`artifact_cycle.deep_replay_structure_stamp`: the crate, the semantics tokens, the cross-rune structure and the capability features), and is never a cycle gate. The artifact cycle reports its status beside the deep sweep's (`artifact_cycle.deep_replay_status`), and the tool's module docstring states the cost that keeps it off the per-edit path and which texts a walk covers. A passing `make conform-deep` at maximum length 5 or more also refreshes its record (`engine/tools/deep_sweep.py` says when), and `artifact_cycle.record_deep_replay_green` decides the maximum length the record holds after a walk or a refresh.

`doc/engine-design.md` §10 describes the test tiers and has the fault-coverage table, which records which of these gates failed for each injected fault. `engine/perf/faults.yaml` holds the rows some gate catches as patches against the current head, each with the gates that catch it, and `engine/tools/fault_kit.py` re-injects them. §14.1 describes the crate.
