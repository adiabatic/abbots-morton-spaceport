# The review cycle

This is the operator's guide to the artifact cycle: what a pass does, what it skips, what it writes while the review app is running, and what it leaves on disk. The module docstring of `rebuild/tools/artifact_cycle.py` is the authority on the plan a pass resolves, the Makefile comment above a target named here, where it has one, describes that target and any Make variable other than `ARGS` that it reads (such as review-cycle's `SERVE`), and the tool behind each target that takes `ARGS` lists its flags under `--help`. The corpus a pass builds and serves is the table-diff corpus, the accepted snapshot of the build against the working tree's: the review app's Queue shows its unaccepted changes, and `make review-accept ARGS=--apply` accepts them (§ The table-diff accept and the snapshot).

## The commands

```sh
make artifact-cycle # the verification alone; the form to run at commit time
make review-cycle # the same pass, then serve the corpus
make review-cycle SERVE=0 # same pass; prints the serve command instead of serving, so the target terminates
make review-cycle SERVE=bg # same pass; starts the server detached if it is not running, and waits for the port
make verdict-ready # the readiness checklist; the app's banner shows the same status
make review-serve # serve rebuild/out/review/ on http://localhost:7294/
make close-out # the close-out's dry run; it refuses on a table-diff corpus and retires with the m1-audit one
make review-accept # a table-diff corpus's accept, a dry run; ARGS=--apply takes the snapshot and empties the store
make review-snapshot-remake # remake the accepted snapshot rebuild/review-snapshot.json names on a machine without it
make cycle-timings # what each step and check costs on this machine; ARGS=--help lists its flags
```

Flags are passed to the cycle through `ARGS`. `--fresh` runs every stage, and has run_m1 run the crate's table build where it would reuse the tables on disk (`--fresh-tables`), `--force-make-test` forces that one gate, `--skip-gates` and `--skip-conform` narrow a pass, `--review-out <dir>` stages the corpus elsewhere and lands nothing, `--keep-history` skips retention, and `--stop-server` (which `make review-cycle` passes) permits the pass to stop a review server from before the land protocol, which is the only kind a pass ever stops.

`make review-cycle` serves in the foreground and never exits, so a caller that waits for the command to finish, such as an agent harness, uses `SERVE=0` or `SERVE=bg`. Stop a detached server the way the cycle does:

```sh
pkill -f 'rebuild\.review\.serve'
```

## What a pass does

- It rebuilds the M1 font and tables, builds the table-diff corpus beside the served one, snapshots the verdict store, lands the corpus with the store carried onto it by unit id, runs the gates, and compares the checked-in per-unit memory peaks with what this machine measured. On a green finish it prunes the regenerable outputs.
- The corpus build runs in Python (`rebuild.review.build --mode table-diff`, `rebuild/review/README.md` § Table-diff mode): the accepted snapshot that `rebuild/review-snapshot.json` names, under `var/keep/review-snapshot/`, against `rebuild/out/m1`.
- Every heavy stage is skipped when its green record shows its inputs are unchanged since its last green run, so a pass over unchanged inputs takes seconds. A gate that did not run is unverified, not waived: `make verdict-ready` reports NOT READY until it runs.
- A green pass ends by running the readiness checklist, so nothing needs to run after it, and above it a `review diff` line counts the unaccepted changes since the snapshot (`verdict_ready.diff_summary_line`). The diff is a row of the checklist and a line, never a red gate: a pass whose corpus holds unaccepted changes ends green and READY. `make verdict-ready` runs the same checklist on its own.
- When only comparison-side inputs changed, the pass re-runs the gates over the artifacts already on disk instead of rebuilding them. `doc/testing.md` § Rerunning the gates without a build gives the recipe and lists those inputs.
- When only runes' `kern:` blocks moved since the last green build, the pass runs `run_m1 --kern-only`, which recompiles the font over the tables on disk and reruns nothing the kern blocks do not feed, and it rebuilds the corpus and lands it: the corpus's after font is the new M1.otf, byte for byte, and its kerning units read the new `kern.tsv` (`artifact_cycle.corpus_build_skippable`). The review app's kerning view reads `rebuild/out/m1` through the server (`rebuild/review/kern_routes.py`), so it shows the new values as soon as the font is written, and the kern inventory it draws from stays as the last full build wrote it. A kern edit made in the view while a pass holds the pass lock waits in `var/kern/journal.ndjson` and is written once the pass ends, so the pass reads the rune files as they stood when it began, and the edit reaches the font at the next pass.
- When run_m1 runs but nothing its table build reads or runs has moved since its last green run, as after an edit to an emitter, read-back or the spec loader that leaves the spec dump as it was, the build re-stamps the tables on disk instead of running the crate, and every stage after it runs as on a build (`run_m1.build_tables`; `doc/testing.md` § The kernel's own gate says what keys the reuse).
- One pass runs at a time. A pass holds `var/cycle/pass.lock` from before it plans until it ends, and a second pass prints the holder's pid and waits for it; Ctrl-C stops the wait. Each pass gets a scratch directory under `var/cycle/` and deletes it when it ends, and the next pass deletes any a killed pass left. A staging pass (`--review-out`) holds the lock too, because a live pass's land can promote the corpus a staging pass writes, but it gets no scratch directory. A `--dry-run` takes the lock without waiting; when another pass holds it, the dry run skips the superseded-corpus recovery and plans against the corpus on disk. The close-out and the table-diff accept take the lock without waiting too, and refuse while a pass holds it, so no pass runs across either.

The cycle owns publication and invalidation of its M1 and conformance green records; its `run_m1` children leave those records alone when `CYCLE_RUN_ENV` is set. Standalone full, gates-only, and conform-only runs own their records, using the same finalization rule in `rebuild/tools/green_record.py::settle_green`: success records only an unchanged input fingerprint, and failure deletes only a matching record. A launched M1 child must exit zero and pass its summary gates before corpus work starts. A skipped build re-evaluates the verified summaries without publishing another green. Gates-only publication also requires a prior green, a matching tables stamp, and changes confined to comparison-side inputs (`gates_only_rerun` and `m1_tables_stamped` in `rebuild/tools/artifact_cycle.py`).

The cycle and `make test-rebuild` prepare and complete contracts runs through `rebuild/tools/contracts_closure.py`. The roster fingerprint keys the green record; a separate digest projection covers extra paths the recorded tests read. Both must match for a skip, and both are checked for drift before publication, including on a forced run. The cycle refreshes its selection after any gate queue wait, immediately before spawning. The shared lifecycle removes stale sidecars before a run and merges the run's closures with those of collected tests it skipped. Scheduling, worker budgets, timings, and terminal output belong to each entry point.

## Which hashes ignore prose

The fingerprints for the table build, the conform sweep, and the contracts suite ignore prose in rune files and ledgers, so rewording those triggers no heavy rebuild. The other data files' prose and code-file prose are covered in the last two items below. `rebuild/pipeline/fingerprint.py` is the authority. In outline:

- Rune files under `glyph_data/runes/` are hashed by `rune_file_digest`, which ignores YAML comments, formatting, and the documentation fields (`ductus`, `notes`, and every `why`, including those on refuse records).
- A refuse record's `why` is the only rune prose any later step reads: the corpus's explain panel quotes it. It is hashed into `rune_explain_digest` and the corpus's Stage B `explain_prose` component, so rewording one restamps the corpus and re-enriches only the windows that quote it.
- The two human-reviewed ledgers are hashed through projections (`divergence_ledger_digest`, `contact_allow_digest`), so only a structural edit to an entry re-runs a gate. A divergence entry's `why`, `title`, `summary` and `note` (`fingerprint.LEDGER_PROSE_KEYS`) are copied into the corpus manifest and are hashed into `explain_prose` in the same way, and so is the change groups' copy in `rebuild/review/change-groups.yaml`, which is in no other component. A contact-allow `why` is read by nothing downstream.
- The schemas under `rebuild/schema/` are hashed without their `title` and `description` annotations, which are the editor's hover text and which the schema checker skips (`schema_file_digest`). `rebuild/script.yaml`, `glyph_data/punctuation.yaml`, `rebuild/m1-aliases.yaml` and the kern sidecar are hashed as their parsed documents, without comments or formatting (`yaml_data_digest`). Key order stays in both, so a reorder still counts as an edit. Rewording a hover or a comment in these files leaves the run_m1 skip key, the tables' stamp, the trace-memo and replay stamps, the oracle row cache and settle memo, and the review unit store unchanged. The oracle's position stamp still hashes the kern sidecar's bytes, so after a comment edit there the next pass that runs the oracle re-shapes every position. `gate:rebuild-contracts` still re-runs the tests whose closure holds the file, because that closure hashes them raw, and a comment edit to `glyph_data/punctuation.yaml` or the kern sidecar still runs `gate:make-test`, whose closure hashes both raw because `make all` reads them.
- Code files that reach `fingerprint.path_lines` are hashed through a projection too (`code_file_digest`). A Python docstring or a whole-line Rust comment does not affect it, so rewording either leaves these unchanged: the tables' stamp, the run_m1 skip key, the trace-memo and replay stamps, the oracle row cache and settle memo, both corpus stores, and the conform and deep-sweep keys, whose compile modules (`artifact_cycle.COMPILE_CODE_FILES`) go through `path_lines` as well. `gate:rebuild-contracts` and `gate:make-test` still run after such an edit, because their closures hash code files raw: test fixtures read source text, and a `# pyright: ignore` comment changes the result being checked.

## The server and the pass

The review server keeps running through every pass, and the open tabs keep working: nobody stops, restarts, or exports anything. `rebuild/review/landing.py` and the module docstring of `rebuild/tools/artifact_cycle.py` are the authorities; in outline:

- A pass never writes the served corpus or the live verdict store in place. A pass that changes the corpus empties `rebuild/out/review.next` and builds the table-diff corpus there (`corpus-build --out`). Once the build has finished it links the live store's file into its scratch directory, `var/cycle/<run>/`, under the store's lock as the snapshot (`store-snapshot`). Every writer of the store and the snapshot replaces its file by rename, so a write to one never reaches the other, and the link moves nothing the server checks the store for.
- The `land` step then moves the corpus into place and carries the store onto it in one short section under the store's lock, with no prepared store and with `--allow-orphans`: on a stamp change it starts from the snapshot carried onto the new corpus by unit id (`landing.carry_snapshot`), so a verdict whose unit the new corpus still has, its content and so its id unchanged, stays, a skip is dropped, leaving a tombstone on a unit the new corpus has, and a verdict off the new corpus's human units goes to `var/verdict-orphans/<stamp>.json`, which no pass refuses over. It holds no store whole: before it takes the lock it checks the snapshot and the prepared store a record at a time and walks them, with the snapshot in the live store's place, as streams merged by unit, and under the lock it walks them again beside the live store only when the live store is no longer the snapshot's bytes, as after a save the server made during the pass, which the lock first writes into the live store, or when the walk before the lock had to stamp a tombstone with the time of day, which the land takes under the lock. Under the lock it lays every save the server applied since the snapshot over the prepared store, writing the result once as the prepared store's records stream past, swaps `review.next` in with one rename, links the old store to its stash name on a stamp change, renames the result over the store, and journals the move, splicing each set line from the result's line for its unit. A store whose records are out of unit order makes the land read every store whole instead, which lands the same bytes, and its log names the store and why. A verdict or a clear saved since the snapshot beats whatever the carry prepared for its unit, and the prepared store's verdict or tombstone for a unit wins over a tombstone the store already held at the snapshot. A save made during that section gets a retryable 503 and waits in the tab's outbox. On a stamp change a verdict saved on a unit outside the new corpus's human units goes to `var/verdict-orphans/<stamp>.json`, a clear on such a unit is dropped, and a skip made during the pass on one of the new corpus's human units is dropped, as the carry drops every skip: its unit keeps no verdict, only a tombstone, so it is asked again. The `store-snapshot` step refuses a live store holding a verdict record the carry refuses (`verdict_store.well_formed`), naming the store and the first such record, so the pass stops there, and the land refuses a live store, snapshot or prepared store holding one the same way, before it writes anything, so the `land` step fails and the store and both corpora stay as they were. It aborts the same way, keeping the staged tree, when the live store does not pair with the accepted list, or the snapshot or the prepared store does not because the list changed during the pass (§ The accepted list and the close-out). The land runs as its own child in its own session: a Ctrl-C or a signal to the pass's process group does not reach it, and the pass waits for it to finish. After the land the pass sends `ams:corpus/<generated_at>`, and the open tabs save, wait while the reader types, and reload onto the new corpus. The land lands after the corpus build, while the gates may still run.
- A pass whose corpus did not change lands nothing.
- A land killed inside its locked section (only `kill -9` of the land itself can do that) leaves `var/cycle/land.json`. The next holder of the store's lock finishes or drops that land before anything else: the review server on its next request, the next pass at its start, or a merge. Nobody runs a command.
- When a staging pass, or an earlier pass stopped after its build, has already built the corpus the current inputs produce, byte for byte, the land swaps that directory in instead of a rebuild (`promotable_corpus` checks the preconditions, `review.next` first, then `plan.review_out` in the last `cycle_summary.json`, then `var/staged-review`). A complete `review.next` that the inputs have moved past since, because a rune changed, is deleted by the next build, which starts from an empty directory. A `review.next` a build did not finish is deleted at the next pass's start. If the land's three-rename fallback is interrupted, a `rebuild/out/review.superseded` tree is left; the next pass renames a lone one back to be the live corpus and deletes one beside a live corpus. A `--dry-run` deletes neither.
- An edit confined to `rebuild/review/static/` is refreshed in place (the `assets-refresh` step, `rebuild.review.build refresh-assets`). Each served file whose bytes changed is replaced by a `.partial` copy renamed into place, so a tab never loads a truncated file, an unchanged one is left in place, and only the manifest's `static` component is restamped, so the tab's store stays aligned. Once every file is in place, the pass sends `ams:assets/<static hash>` to the server's livereload `/forcereload`, and the open tab reloads onto the new app files. An edit to the app's JS, CSS, or HTML therefore costs a few seconds plus the contracts tests whose recorded closure includes the edited file (the module docstring of `rebuild/tools/contracts_closure.py` describes the per-test closure).
- The review server reloads no tab when a file changes (`register_dormant_watch` in `rebuild/review/serve.py`). Besides the cycle's `ams:` reloads, a tab moves onto a changed corpus by itself when a save's reply or `/status` names a corpus other than the one it loaded, or when a byte-range read finds another build's record. It sends its unsaved changes, waits while the reader has text in a focused field or while the tab is hidden, and reloads at the same URL hash, keeping the scroll position, the queue anchor, and note drafts. A queue worklist keeps the units the new corpus still has, and postponed queue decisions stay postponed. `rebuild/review/static/reload.js` describes the move.
- Before a pass the cycle asks the server's `/capabilities` which checkout it serves and the digest of its land-protocol and freshness code (`landing.code_digest`). A server from this checkout on the working tree's code keeps running. One on other code (started before a pull, or from an intermediate commit) is restarted on the tree's code, detached as `SERVE=bg` starts it, by the first pass that writes the corpus or the store, and its tabs retry their saves until it answers; a pass that writes neither leaves it running. One that serves another checkout is left alone and sent no reload; while it holds the port, the `server` row of `make verdict-ready` fails, and `make review-cycle` names that checkout after its pass and exits non-zero unless `SERVE=0`. A server from before the land protocol, which answers `/capabilities` with a 404, is stopped once, with `--stop-server`, when the pass writes the corpus or the store; after that the server started from this checkout keeps running. A listener that gives no answer after a few tries (`CAPABILITIES_ATTEMPTS`) is never stopped: a pass that writes neither the corpus nor the store runs beside it, any other pass refuses, and a re-run once the server answers goes ahead.
- While a pass holds the pass lock, the app's banner and `make verdict-ready` tell the reader to wait for that pass, by the pid the lock records, where they would otherwise name `make artifact-cycle`.
- `make review-build` refuses while the review server listens, because it builds into the served corpus in place; `make artifact-cycle` builds beside it.

## The verdict store

A table-diff corpus's store reads no accepted list (`verdict_store.accepted_path_for`, which the review server's store asks again at each reload, so it stops reading the list once a land swaps a table-diff corpus in), and the land carries it onto each new corpus by unit id. The paragraphs below on the accepted list and on overrides describe what stays until stage 4 of `rebuild/CUTOVER-PLAN.md` removes it.

The supported review app saves changes as deltas; `/autosave` accepts only `ams-review-verdicts-delta/1` POST bodies. A whole-store replacement can overwrite verdicts another tab or writer saved, so an `ams-review-verdicts/1` POST gets HTTP 400 with `reason: whole-store-post-unsupported`, recovery instructions, and no store or journal write. Historical clients keep their records after an ordinary autosave failure and can export them; the refusal uses neither HTTP 409, which tells legacy readers to reload rather than download pending verdicts, nor `corpus_stamp`, which can prompt newer clients to reload automatically. The full-store format is the file, export, import, and GET format, and the external-file refresh path operates on it. A store file holding a verdict record the carry refuses (`verdict_store.well_formed`) is read as an unreadable one is, so the server serves no verdict from it, but it is never written over: until another writer replaces the file, a GET gets HTTP 404 and every delta `parse_delta_payload` accepts HTTP 422, both with `reason: store-malformed` and an error naming the file and the first such record, which the app shows the reader, and nothing is written. The readiness check (the app's banner and `make verdict-ready`) fails on such a store, naming the same record. These readers refuse one this way before they compare its records' `at` values (`verdict_store.read_store_document`): the server, the readiness check, a pass's `store-snapshot` step and land, and the recovery of a land whose holder died (below).

For a historical tab whose save is refused, export/download its verdicts or copy pending verdicts before closing or reloading it, and note pending clears and note edits. Then open/reload the current app and import the saved file, or reapply the copied verdicts. Manually reapply pending clears and note edits: historical exports hold only extant records, and importing or merging an export merges its records without treating omitted verdicts as clears. A historical note-only edit can retain its record's `at`, and import keeps the server record when the imported record has a tied or older timestamp. The exported file preserves that pending note; keep it until all pending verdicts, clears, and note edits are verified in the current app.

- Every writer of the store and the journal holds the store's lock, an exclusive `flock` on `verdicts-autosave.json.lock` (`rebuild/review/store_lock.py`): the review server for each save, for its idle write and while it loads the store at boot, the close-out, the table-diff accept, a pass's store snapshot and land, and retention. Every writer but the server's saves and idle write takes it through `landing.locked_store`, which first finishes a land whose holder died and then writes into the store the saves the server journaled and has not written (`landing.catch_up`); a store or land result holding a verdict record the carry refuses stops that recovery, naming the file and the record, and so does a land whose result and old corpus are both gone. The land's intent then stays, so each such writer refuses with the recovery's message until a person acts on the file it names, as the message says, by deleting a land result holding such a record (the next recovery then treats the land as one whose run directory is gone), replacing a store holding one, or restoring the result or old corpus of a land that lost both: the close-out and the accept print it and exit 1, a pass stops with it before its first step or fails its `land` step with it, and the server stops at boot with it, or, already running, answers every `/autosave` and `/status` request with it under `reason: store-malformed` or `reason: land-unrecoverable` (a GET of `/autosave` as a 404, the others as a 422), which the app shows the reader, keeping its outbox. The server never waits for it: a save made while another writer holds it gets a 503. A debounced save stays in the tab's outbox and is retried with backoff, but the save a closing tab sends is sent again only when the app is next opened, so a hand-run writer of the live store (the close-out, the accept) refuses while this checkout's server listens (`store_guards.serves`). A pass holds the lock beside a running server only for its catch-up at its start, its snapshot, its land, and retention's journal tail. A dry run and a run refused because a server listens take no lock, and a writer that must wait for the lock says so once and waits.
- The app sends each change with `base_at`, the `at` of the record it last saw the server hold for the unit, and keeps it in its outbox (`rebuild/review/static/outbox.js`, in the browser's localStorage) until the server acknowledges it. A save stamped for another corpus than the store's is carried onto the store by unit id when the store is on the served corpus: it applies where the store has no record and no newer tombstone, where the store's record has the `at` the save names as `base_at`, or where the save is newer. The store keeps a tombstone for each cleared unit (a top-level `cleared` list in `verdicts-autosave.json`), so a stale save cannot bring back a verdict another tab cleared. What the store cannot apply goes to `var/verdict-orphans/<stamp>.json`: `reason: conflict` for a save that lost to a newer record, which the tab adopts and offers to reapply, and `reason: orphan` for a save on a unit outside the served corpus's human units. The tab reports both and keeps its offer to reapply a conflict across a reload, and the readiness banner shows those recorded since the page loaded, or since the page it moved from loaded when it reloaded onto a rebuilt corpus. A skip stamped for another corpus is dropped, clearing the store's record for its unit under the same tests and leaving a tombstone on an accepted unit, so the unit is asked again. A save stamped for the served corpus while the store is on another corpus (a first pass after `rebuild/out/review` was deleted builds it in place and lands no store) carries the store onto the served corpus by unit id: the old file is kept as `verdicts-autosave-<stamp>.json`, and the store keeps its verdicts on the served corpus's human units, less its skips, each of which leaves a tombstone at its `at`, before it applies the save. A save made on neither corpus gets a retryable 503 and stays in the outbox. `rebuild/review/verdict_store.py` is the authority on the rules.
- Every store write is logged in `verdicts-journal.ndjson`, and the app's autosaves are logged before the store is written: the review server appends a save's sets and clears and answers, and writes the whole store once a minute passes with no save, and every other holder of the store's lock first writes into the store the journal's events at or after the store's `exported_at` (`landing.catch_up`), the server at its boot and a pass at its start among them, so each reads every save whether the server still runs or was stopped before it wrote them. A tail that changes nothing writes nothing, and a tail holding a base event torn short of its set lines is applied from the events after it, since its writer wrote the store before it began the base. Every holder after a land reads that land's own event again, its time being after the store's `exported_at`, and streams the store once to compare it, writing nothing; the cycle's driver runs each of its catch-ups in a short child. A store copied in from a backup outside the tools takes the journal's events at or after its `exported_at`; Each append holds a `flock` on the journal and first ends the file on a newline, cutting off a final line that a crashed append left unparseable. A land records the journal's length before it appends, and the recovery of a land that died mid-append cuts the journal back to that length, the start of the land's event line, before it journals the landed store again as a base event. A base event holds the whole store, its tombstones included, and each clear line names the tombstone, if any, the store keeps for its unit, so a replay (`journal.replay_store`) gives back the store's records and its tombstones as of the moment it replays to. Journal lines without those fields replay by fallbacks that can differ from the store, among them these: a clear line with no `at` takes its event's time, which can lay a tombstone the store never held for a record a land dropped, and a base event with no `cleared` list holds no tombstones, so a replay from it on lacks the tombstones of the clears made before it. The land writes a base event for a stamp change only when it replaces no store, the journal does not exist yet, `base_due` says one is due (the marker below exists, the journal holds no base, or its last base is torn, holds no `cleared` list, or is at least `BASE_INTERVAL` old), or its sets and clears would reach the result's record count; otherwise it journals the change as the sets and clears from the store it replaced, since a unit's id names the same unit on either stamp. Every other writer writes one at each stamp change. The land's report and the cycle's `land` row say whether it journaled a base or how many sets and clears. Those sets and clears replay right only while the journal replays to the store they replace, so `var/cycle/unjournaled.json` marks a store write the journal may lack: the review server writes it, and then the whole store at once, when a save's append fails, and leaves it, and writes it before each store write it makes ahead of that write's append (a move onto the served corpus, the empty store at boot, and every save while the marker exists) and removes it once that append succeeds unless it was already there, so an append that failed, was cut short, or never ran leaves it. While it exists no lock holder catches the store up with the journal and every server save writes the whole store at once, so none waits in the journal (#618's decision 82), and the next land that moves the stamp writes a base and removes it. A base event followed by fewer set lines than it names is torn, and the store from it until the next complete base is unknown: a replay refuses a moment in that span and names where it ends, and compaction never starts the journal at a torn base. `rebuild/review/journal.py` is the authority.

## The accepted list and the close-out

The close-out refuses every form on a table-diff corpus, whose store reads no list (`close_out.TABLE_DIFF_REFUSAL`); it and the list retire with the m1-audit corpus. The m1-audit store, its journal and stashes, and the last close-out's archive are kept as found under `var/keep/m1-audit-final/`.

`rebuild/accepted-units.txt` is tracked. It holds the human units whose verdict a close-out accepted, approve, either or identical, one `u-` id a line with its verdict's mark, under a header that names the last close-out's time, `closed_at`. The store holds what that close-out left, its rejects, neithers, skips and tombstones, and every verdict recorded since. The module docstring of `rebuild/review/accepted.py` is the authority on the list's format, its refusals and the rule below, and that of `rebuild/tools/close_out.py` on the close-out. In outline:

- Every reader of the store reads a unit through the list (`accepted.verdict_of`): the store's record for it when there is one, otherwise blank when the store holds a tombstone for it, otherwise its accepted record when the list names it (its mark, an empty note, and `closed_at` as its `at`), otherwise blank. The review server and the app, the land, the triage export and `make verdict-ready` all read it so, and the readiness check counts the store's accepted units among its effective verdicts, so no root verdicts file outranks the store. A listed id that is not on the corpus a reader reads is ignored by that reader, so no pass writes the list; only the close-out does.
- A verdict on an accepted unit is an override, a record in the store's override section (`overrides`, apart from its own `verdicts` and `cleared`, which name no accepted unit), and no writer drops one until the next close-out consumes it: it folds an accepting override into the list, and a reject, neither, skip or tombstone takes the id out. A clear on an accepted unit leaves an override tombstone, which blanks it, and an undo back to its accepted record, a set of its accepted verdict with an empty note dated `closed_at`, removes the override and any tombstone, also when the land lays it over a pass's prepared store; the accepted verdict picked again at any other time is an override like any other verdict, so every tab adopts it. When the server judges a save on an accepted unit, the accepted record, dated `closed_at`, is the unit's record, so an outbox replay or a save from another corpus that was made before the close-out and differs from it is a conflict, whose reply hands back the accepted record. The merge and the carry keep out another file's record on an accepted unit the store holds no override for when it equals the accepted record or is dated at or before `closed_at` (`Accepted.keeps_out`), so an export, a bulk file or a download made before the close-out brings back no folded verdict, while a note typed on an accepted unit since survives.
- The store names the list it was folded against in its `accepted` field, the list's sha256 and `closed_at`, which every writer of the store carries forward. Every reader refuses a store that names another list, or a list beside a store that holds verdicts, tombstones or overrides and names none, as `accepted-mismatch`, and a list it cannot read as `accepted-malformed`, naming the files and the remedy: the review server serves no verdict and refuses every save, which the tabs keep in their outboxes, a pass stops before its land, the tools exit, and the verdict-store row of `make verdict-ready` fails. A `git checkout`, stash, branch switch or revert that changes the list under the store does this until the list the store names is put back; a close-out is undone with `make close-out ARGS=--undo`, never by reverting its list. A store with no record, no tombstone, no override and no field pairs with whatever list the tree holds, and when no store file exists beside a list the review server writes an empty store stamped for the served corpus at boot, so a fresh clone needs no step. On a machine that makes no verdicts, such as the M4 Pro Mac mini, the remedy after pulling a close-out is to stop its review server, delete its store and journal by hand, and start the server again, since it writes the empty store only at boot.
- A tool run on `verdicts-autosave.json` reads the list beside it, and one run on a store under any other name takes `--accepted PATH`, which the cycle passes for its prepared store, so a run on a copy in a temporary directory never reads the live list. The empty store a `--no-merge` or `--no-carry` pass lands names the list too and keeps the store's override section whole, so its units stay accepted and an accepted unit rejected or cleared since the close-out keeps that answer.
- The full GET of `/autosave` lists the store's overrides with its own records and tombstones, as one store, and carries the accepted units the store holds no override for in an `accepted` field, and every save's reply names the list, so a tab that finds another list moves onto it as it moves onto a rebuilt corpus. `rebuild/review/README.md` § Triage flow says how the app shows an accepted unit.

`make close-out` is a dry run: it prints the report and every refusal and writes nothing. `make close-out ARGS=--apply` folds. It runs by hand, from the `close-out` skill, never in a pass, and refuses while a pass holds `var/cycle/pass.lock`, while this checkout's review server listens, while `make verdict-ready`'s blocking checks fail, while the list differs from `HEAD`'s or from the store's field, and while the store holds a record the carry refuses (`verdict_store.well_formed`). With nothing to fold it says so and writes nothing. The apply:

- writes the new list: each listed id still a human unit of the served corpus with no override, and each human unit whose record, its own or its override, is approve, either or identical, with that record's mark, so a reject, neither, skip or tombstone on a listed id takes it out, and a listed id off the corpus's human units drops out;
- writes the store with its rejects, neithers and skips and its tombstones on human units, stamped for the served corpus, its field naming the new list;
- starts a new journal at one base event of that store, removes the unjournaled marker and the journal's scan state, and deletes the root's `verdicts-autosave-*.json` stashes, which no event in the new journal names, reporting the other root verdicts files, which it leaves;
- keeps the store it found and the lists before and after, gzipped, under `var/keep/close-outs/<closed_at>/`, and deletes every older archive, so the notes and provenance markers of the folded verdicts, and each one's own time, survive only there, until the next close-out.

The new list goes into the "Close the ·X batch" commit. A close-out killed between renaming the list and renaming the store leaves every reader refusing on the pairing with `make close-out ARGS=--apply` as the remedy, and that apply finishes it from its intent file, `var/cycle/close-out.json`, or drops one killed before it renamed the list. `make close-out ARGS=--undo`, under the same locks and with the server stopped, puts back the archive's list and lays the live store's records and tombstones over the archive's store, so the verdicts made since the close-out survive; the list it puts back is a tracked change to commit, never to revert, since the store then names it (when the close-out's commit was never made, the tree already matches `HEAD`).

## The table-diff accept and the snapshot

The cycle builds and serves the table-diff corpus (`rebuild/REVIEW-PLAN.md` §2.3), which compares a snapshot of the accepted build, under `var/keep/review-snapshot/`, with `rebuild/out/m1`, and `rebuild/review/accept.py`'s module docstring is the authority on its accept and remake. In outline:

- The tracked pointer, `rebuild/review-snapshot.json`, names the accepted snapshot by digest and records no commit; the commit the snapshot stands for is the last commit that changed the pointer.
- `make verdict-ready` and the app's banner choose their rows by the served corpus's mode. On a table-diff corpus they check its `fingerprint.TABLE_DIFF_COMPONENTS` and its after font byte for byte, add a `snapshot` row, which fails while the current snapshot is not the one the pointer names (remedy `make review-snapshot-remake`), and a `diff` row, which never fails and counts the unaccepted changes, `N` of them since the pointer's commit, `H` needing a verdict (`B` blank, `R` rejected or neither), `M` machine-approved and `K` needing none, and print no fullest-verdicts or journal row.
- The corpus build skips only when the served corpus is a table-diff corpus that a build would reproduce byte for byte, its after font among it (`artifact_cycle.corpus_build_skippable`), and the land carries the store onto each new corpus by unit id, so a verdict made before a second edit stays on every unit that edit leaves unchanged.
- `make review-accept ARGS=--apply` takes the snapshot of `rebuild/out/m1`, writes the pointer and empties the store, starting its journal again at one base event, and keeps the store it found under `var/keep/review-accept/`. It refuses on an m1-audit corpus, so it never clears the store the close-out folds, while `make verdict-ready`'s blocking checks fail or the corpus does not show `rebuild/out/m1`, while a pass holds the pass lock or this checkout's review server listens, and while a human unit is blank, skipped, rejected or neither. `ARGS='--apply --retake'` takes the snapshot over the verdict, readiness and corpus refusals, for a snapshot-format bump or a snapshot no build remakes.
- `make review-snapshot-remake` exports the pointer's commit with `git archive` into `var/cycle/snapshot-remake/`, which a pass deletes, runs that commit's own table build, glyph chain and snapshot there, holding the pass lock, and installs the snapshot once its digest is the pointer's. It runs the whole table build, so it never runs beside a pass or a gate.

## Retention

A green pass ends with a retention pass over the regenerable outputs. `--keep-history` skips it. The autosave stashes and the journal are at the repository root, and the build logs are under `var/`, the gitignored tree for output that outlives a run. `tmp/` holds only scratch and is safe to wipe between change sets.

- `verdicts-autosave-*` stashes that no journal event since the last stamp change or base event refers to are deleted; the journal can replay their state.
- The journal is compacted to start at the newest complete base event older than `HISTORY_DAYS` days (`rebuild/review/journal.py`), which is the earliest moment a replay reaches. A journal that already starts at that base, or holds no complete base event that old, is left as it is, and the retention block's journal line says which. A close-out starts the journal again at one base event, so while close-outs come less than `HISTORY_DAYS` days apart no base is that old and compaction never copies the journal. On an m1-audit corpus, once the journal's first event is `CLOSE_OUT_DUE_DAYS` days old, `make verdict-ready` adds a `journal` warning naming the day compaction can first copy the journal and `make close-out` (`journal.close_out_due`); an accept starts the table-diff store's journal again. The stash sweep and the compaction share one scan of the journal, made without the store's lock, and take the lock only to re-read the tail appended since, delete the stashes, or copy that tail and replace the journal; the review server answers a save made in that window with a retryable 503, as during a land, and a lock that stays held for `RETENTION_LOCK_TIMEOUT_S` leaves that part for a later pass. Beside a listening server from before the land protocol, which writes without the lock, both are left for a later pass. The scan resumes from the state the last pass saved in `var/cycle/journal-scan.json`, rebased onto the compacted file when that pass compacted, so a pass parses only the lines appended since. It resumes only when the journal has the same inode, is at least as long, and still holds the bytes just before where the state ends and every event line the state recorded, each at its offset (`_holds` in `rebuild/review/journal.py`); otherwise it reads from the start. That catches a journal replaced, and one cut shorter and regrown, because a land recovery cuts it back to the start of an event line and the next append writes its own event line there with a later `at`, even when the bytes before the old end come out the same. Run directories under `var/build-logs/` beyond the newest `BUILD_LOGS_KEEP` are deleted (`rebuild/tools/cycle_paths.py`, which defines every path the cycle writes to).

## Logs and timings

- `console.CycleConsole` numbers steps in the order their opening banners appear, parallel gates included. The plan lists the work without numbers, and skipped or unstarted steps get no number. Log filenames and the closing table use the same numbers, with the unnumbered rows after the steps that started.
- Every pass appends host-tagged per-step wall times, peak RSS and bytes written to `rebuild/out/cycle-timings.ndjson`, and its run line carries a `written` block with what the whole pass wrote and its write class, and, in its `outputs` block, what the writes through `rebuild/pipeline/output_sink.py`'s helper wrote and what they left in place because it came out the same; `rebuild/tools/cycle_timings.py`'s module docstring lists the fields. Every evaluated check run also writes its outcome there, including interactive `make test`, `make test-rebuild`, and `run_m1` runs. `make cycle-timings` reads the file, `ARGS='--writes'` groups the passes by host and write class, and `doc/fleet.md` explains how to tell which machine wrote a row.
- The write meter (`rebuild/tools/write_meter.py`) reads the pass's resource coalition, which holds every process the pass starts, so a child's writes still count after it exits. A pass started from a terminal shares its coalition with the terminal's other processes, so its figure is an upper bound: the `shared` basis, less what the other processes it can read wrote. When the coalition read fails its self-check, the figure is the device's machine-wide count, the `device` basis, and a `[warn]` line says why. A reading never fails the pass.
- The closing table's `written` column is the meter's figure for each step's window, from its spawn to its reap, marked `+` where another step's window overlapped it, so that figure holds the other step's writes too; the line under the table says so. The `written` line below the table gives the pass's figure with its basis, the review server's own writes, which the figure leaves out, the device's and swap's machine-wide counts, and the pass's write class with that class's ceiling. A pass over its class's ceiling prints a `[warn]` line and a `write ceiling` line and still passes (`cycle_timings.PASS_WRITE_CEILING_BYTES`).
- `doc/running-long-steps.md` covers running a pass detached, where the per-step logs are written, how to tell whether a run is hung, and how to stop a whole pass.
