# Rebuild design: stance surfaces, riders, and the settled pipeline

This is the design for the rebuild whose requirements are in [core-idea.md](core-idea.md). Core-idea says _what the system is for_; this document says _what the YAML looks like and what the code does_. It combines four candidate designs (join-surface-first, rider-conditions, negotiation-protocol, and a conservative-reform control) that were scored against core-idea's requirements and then reviewed adversarially. The structure is the join-surface-first design, with specific mechanisms taken from the other three where the scoring found them better.

## 0. Two findings that frame everything

**The convergence finding.** All four candidate designs, written independently, arrived at the same architecture: form ligatures first, pick each position's stance in a small settlement function over a `[resolved-left, self, raw-right, raw-right²]` window (§3.4 widens the lookahead to four raw slots), and emit only final, positive substitutions to OpenType. All four also had one `curs` lookup per height, class-based pair kerning, specificity precedence that refuses to guess between incomparable conflicts, and recorded tie-breaks that can be promoted to named case groups. That shared core is settled. The designs differed only in the authoring format.

**The control finding.** The conservative-reform candidate asked for the smallest change to the old format that meets the requirements. Its answer was that even the smallest change needs an upstream resolver and must drop the emit-then-repair model, because the demote oracles, guard walls, name-healing layer, and `_PENDING_BK_ENTRY_GUARDS` cannot be rehoused in place. The derived-demote feasibility study and the leak-cleanup history (`doc/history/2026-06-03--leak-cleanup/`) each record a failed attempt. So the choice was only which vocabulary to write the rebuild in, and the conservative vocabulary would have kept the old format's familiar surface together with the structure that let rules accumulate one patch at a time.

## 1. The architecture: settle in the kernel, transcribe to OpenType

**A note on “today.”** In this document _today_ means the shipped Senior engine: the pipeline under `tools/` and the FEA it emits. It never means the rebuild's progress. §13.6 archives that pipeline to `doc/graveyard/` at cutover, so every _today_ below describes that archive and stays true after the move.

Today the meaning of the YAML is whatever the emitted chain of contextual substitutions happens to do. The old pipeline models that chain three times without computing it: ignore-guards to prevent its failures, demote tables to repair them, and the leak contract to detect them. The rebuild reverses this:

- The Rust kernel's **settlement function** is the engine of record. Given a rune sequence and an active stylistic-set configuration, it computes ligation, the stance and join-surface cell of every position, every join height, and every extension amount. It works deterministically, left to right, and can explain each decision. It is the only implementation of these. The conformance sweep, the witness stage, the baseline oracle, the review surface, the explain CLI, and the probe reach it through `kernel_exec`'s `settle-cases` and `guard-sweep` subcommands. `rebuild/pipeline/settle.py` keeps only the vocabulary a caller needs to state a window: tokens, boundary cells, and the guarded ligature formation that runs before settlement.
- The FEA emitter is a **transcription** of the settlement function's decision table. Every emitted rule is a final, positive substitution whose context is already settled when the rule runs. No rule is committed and later repaired, because there are no later repair rules.
- Conformance is **empirical**: the compiled font is shaped through HarfBuzz over a generated set of example sequences and compared with the settlement function, transition by transition. The pipeline never predicts what a chain of substitutions will do by reading the emitted FEA. Read-back (`rebuild/pipeline/readback.py`) is a different kind of check. After compilation the build re-parses the written font and compares every lookup, the feature and script registrations, the lookup order, and the lookup flags with the emitters' plan. On the same bytes it checks `pack_gsub`'s repack of the settlement lookup and reads the GSUB's uint16 subtable-offset headroom. Read-back predicts nothing about shaping, so it adds to the empirical gate and does not replace it.

This gives the two-part definition of “broken” that core-idea asks for, and it says where the fault lies. A **spec defect** is the settlement function's own output violating a structural invariant, which can be checked exhaustively against bitmaps and anchors with no font built. A **compiler defect** is HarfBuzz disagreeing with the settlement function, which is always a pipeline bug and never an authoring problem.

These old-engine mechanisms have no counterpart in the rebuild: `restore_isolated_form_overrides`, `predecessor_demote_overrides`, `trailing_demote_overrides`, `_PENDING_BK_ENTRY_GUARDS`, the three verbatim `calt_pred_demote` passes, the `ignore sub` guard walls, `calt_cycle`, the post-liga repair layer, the reflip layer, the `.noentry` variant glyphs, the name-healing layer, `strip_entry_before`, `terminal_default`, `preferred_over`, `reverse_upgrade_from`, `extend_exit_when_entered`, `noentry_after`, and file-scope context sets. Settled emission makes each one unnecessary, or it is re-expressed as one of the concepts below. There is one exception. A few follower-preference families, with ·He as the worked case, hold real taste decisions that today live in complement lists. §5.9 shows the cell-grain preference that expresses them, and an author who prefers the literal list migrates it as a refuse with a `why:`.

## 2. File layout

There is one file per rune, so a pair can be read in two editor panes, as core-idea asks (“one rune per editor pane, two panes”).

```text
glyph_data/
  runes/qsPea.yaml … qsOoze.yaml      one file per letter and ligature
  script.yaml                          registries only, never policy: heights, boundary tokens, feature registry, predicate classes
  senior_quikscript_kerning.yaml       the flat kerning sidecar (the one exception to locality)
```

Until cutover the registry lives at `rebuild/script.yaml`, because the old build reads every `glyph_data/*.yaml` and would take a `glyph_data/script.yaml` for a Senior kerning rule (`rebuild/M1-PLAN.md` §1).

`script.yaml` holds:

- The closed height table (`baseline: 0`, `x-height: 5`, `y6: 6`, `top: 8`). Adding a height is a language change.
- The boundary tokens (`space`, `zwnj`, `namer-dot`), each declaring whether it splits runs for word-position derivation. `space` and `zwnj` split runs. `namer-dot` does not, but a condition can still name it (§3.4).
- The stylistic-set registry. Every `ssNN` declares a user-facing description and a `kind: capability | taste`, and `interactions:` lists the combinations of sets that are declared.
- **Predicate classes**, the only cross-rune sets. Each is defined by a computable expression over surfaces and bitmap geometry (`can_enter_at: baseline`, `can_exit_at: x-height`, `trait: half`, `height_class: tall`, `stroke_at: {exit: vertical}`), combined with `all:` and `union:`. The schema (`rebuild/schema/script.schema.json`) gives no way to list members by hand. Any condition can name a class (§3.4). Membership does not depend on stylistic sets: `spec_load._evaluate_predicate_classes` reads a stance's declared rows and never its unlocks, and `rebuild/test_spec_load.py` checks that applying the active unlocks under every configuration derives the same classes. So a class means the same set whichever stylistic sets are on. Classes keep today's most-shared sets from turning into per-rune copies: `halves_exit_xheight` is referenced from many families, and the `talls` context set drives ·Thaw's after-Tall stance.

Anything that is one rune's private trigger list lives in that rune's `policy.groups`. `spec_load._flag_duplicate_groups` warns when rune-local groups in two or more rune files have identical membership, since they are candidates for a predicate class.

To understand a pair, open the two rune files; there is no third place to look. A derived class's membership is computed from its expression, and no generated report lists it yet.

## 3. The rune file

```yaml
rune: qsMay
codepoint: 0xE665            # ligatures declare `sequence: [qsOut, qsTea]` instead
ductus:                      # the closed set of motions, each with its drawing prose; every motion needs a stance
  loop: |
    Written clockwise from the leftmost pixel at the baseline, looping under the baseline, ending at the x-height on the right.
  grounded-loop: |
    Written counterclockwise from the rightmost pixel at the x-height, down past the baseline, ending on the baseline at the right.
notes: |                     # optional prose that changes no output (join constraints are pairings data, not sentences)
mono: {bitmap: [...], y_offset: -3}
stances: { ... }             # §3.1–3.2
policy: { ... }              # §3.3
```

### 3.1 Stances and ductus parity

A stance is one motion the hand makes to write the rune: a `motion:` reference into the ductus, exactly one hand-drawn base bitmap, and a complete join surface. Stance IDs name the pen motion (`loop`, `half`, `flipped`, `grounded-loop`), never a neighbor, boundary, or feature: `spec_load.FORBIDDEN_ID_PATTERN` rejects stance IDs and motion names that match `(before|after|noentry|noexit|nonjoining|ss[0-9])`. A rune with exactly one stance names that stance and its one ductus motion `hapax`, a reserved name meaning “occurs once”, and the stance's `motion:` points at that `hapax` key. The pen-motion label (`loop`, `bar`, …) appears only in the ductus prose. `spec_load` reports an error when a lone stance or a single-motion ductus uses any other name, and when `hapax` appears among two or more stances or two or more motions.

```yaml
stances:
  loop:
    motion: loop             # build error if missing or not in the ductus; every ductus motion must have a stance
    traits: [ ]              # the closed set `half` / `alt`, kept for data-expect compatibility
    bitmap:                  # the isolated drawing; double-quoted rows, trailing # markers at y=5 and y=0, as in quikscript.yaml
    - "   ##"  #
    - "  #  "
    - "  #  "
    - " #   "
    - " #   "
    - "#### "  #
    - " #  #"
    - " #  #"
    - "  ## "
    y_offset: -3
    bitmaps:                 # optional named hand-drawn siblings, referenced by cell/anchor bindings below
      pulled-back-stubless: {bitmap: [...], y_offset: -3}
    surface: { ... }
```

**Ductus parity** makes the closed set of motions mechanical: every stance names a motion in the ductus, and every ductus motion has a stance (`spec_load` checks both). Ductus values are prose strings, so a motion that is not drawn yet cannot be listed. A rune cannot be written in this format until its ductus is written. This departs from core-idea, as §15 records. Core-idea says to finish all of the ductus prose before starting the rewrite, and this design instead makes each rune's migration wait on its own ductus. The reason is that unenforced prose written up front produced today's defective entries: in `glyph_data/quikscript.yaml`, qsPea's ductus stops mid-sentence, and qsMay's omits the counterclockwise motion that core-idea names. This change of order needs the author's sign-off.

### 3.2 The surface

The surface is the stance's complete join capability, written as data.

```yaml
surface:                                      # a composite: the rows above cells: are qsMay's loop, the cells: rows are qsUtter's alternate
  entries:
    baseline:  {x: 0, stroke: horizontal}
    x-height:  {x: 3, stroke: horizontal, joined: pulled-back-stubless, joined_x: 2}
  exits:
    x-height:  {x: 5, stroke: horizontal}
  pairings:
    never:
      - {entry: x-height, exit: x-height}     # qsMay's prose note about the x-height, as checkable data
  cells:
    - {entry: x-height, exit: baseline, bitmap: reaches-way-back, exit_x: 6}             # per-cell anchor override: the exit moves with the joined form
  unlocks: []                                 # ss capability rows; each may carry a narrowing when:
  require: []                                 # [entry] / [exit] for join-born stances that only exist joined
```

Key by key:

- **`entries` / `exits`**: maps keyed by height name. `x:` is the anchor's x pixel, and y is implied by the height. The E-ANCHOR check (`defects._check_anchors`) enforces the conventions `entry.x = min_ink_x_at_entry_y` and `exit.x = max_ink_x_at_exit_y + 1` against the drawing each realized glyph uses, cell bindings included (see below). `x_off_convention: true` exempts one side from the check; no migrated rune sets it. `ink_y:` on an exit row carries today's `exit_ink_y`, and `selectable: false` on an entry row carries today's `entry_curs_only`. A stance may declare several entries: ·Roe's entry at two heights is two rows, not a special list form.
- **`stroke:`**: `horizontal | vertical | diagonal`, the stroke's orientation at the attachment. Conditions read it as axis 4 (§3.4). It is also the designed input to the collision and orientation-mismatch flags, which are not built (§9).
- **`toward:` / `from:`**: an optional positive neighbor scope on an exit or entry row. A row with `toward: [{family: qsMay}]` produces joining cells only against the named set, written with the §3.4 conditions, predicate classes included. This is where today's positive allowlists go, one line each: ·They's tuck exists only toward ·May, and ·Roe's baseline exit joins only a named list of families. Migration depends on it (§13.3). Without it, every allowlist would have to be inverted into complement refusals, and join-count ranking would join hundreds of pairs that today's font leaves unjoined. The dead-policy check (`defects._check_dead_policy`) lists a scope that never admits a join in `pipeline_summary.json`, but it does not fail the build.
- **`stub:`**: columns of ink on this anchor's row that appear or disappear with this side's join state. A stub declares which state inks it (`stub: {cols: [0], inks_when: joined}` or `inks_when: withdrawn`), because the data needs both. ·Pea's x-height entry adds a pixel at column 0 only when a letter joins there, while ·May's grounded loop has a column-3 pixel in its base drawing that is removed when its x-height entry joins. A stub edits only its own row and is checked against the resolved per-cell bitmap. A difference across rows needs a hand-drawn shape.
- **`joined:` / `withdrawal:`**: bindings to hand-drawn sibling bitmaps. `joined:`, on an entry row, names the drawing used when that entry is live, for redraws beyond a same-row stub, and `joined_x:` gives that drawing's entry x. `withdrawal:`, on an exit row, names the drawing used when the exit is declined mid-word or the cell exits at another height. It can instead be `safe` when the build can verify that the isolated ink has no connector reaching out on that row. A declined side whose ink would dangle and that binds no withdrawal drawing is the error `E-DANGLE`. This replaces all of today's authored `.ex-noentry`, `.noentry`, and `noexit` stances with one checkable requirement: today's two ·May `ex-noentry` stances become cells, ·Utter's `alternate` stance requires its exit and so has no declined-exit drawing at all, and nothing is named after a context.
- **`cells:`**: explicit per-cell bindings. The side bindings (`stub`, `joined`, `withdrawal`) are checked shorthand that resolves to a drawing for each cell. When a cell needs a combination the shorthand cannot give, such as an entry-live, exit-declined cell whose entry binding names one drawing and whose decline wants another, a `cells:` row binds the cell to one hand-drawn bitmap. The row may also override the anchors (`entry_x:`, `exit_x:`) where the anchor moves with the drawing: ·Utter's `alternate` exit moves to x=6 with its `reaches-way-back` entry drawing, and ·Oy's `open-on-the-left` loop moves its baseline exit to x=5. The resolution order is an explicit cell binding, then the side bindings, then the base bitmap (`rebuild/pipeline/surface.py`). Two side bindings that disagree on a cell with no `cells:` row are a build error naming the cell. The stub, withdrawal-safety, anchor, and gap checks all run against the resolved per-cell bitmap.
- **`pairings`**: constraints over two-sided cells, either `never:` (the usual case) or `only:` (when the allowed set is smaller than its complement, as for ·It). One-sided and isolated cells always exist unless `require` removes them.
- **`unlocks`**: stylistic-set rows that add an entry, an exit, or a pairing under a feature, each with an optional narrowing `when:`. The narrowing is needed in practice. Every one of today's stylistic-set stances is context-scoped (ss05's ·Tea both-baseline form only after ·Et, ss02's ·Tea x-height entry only after ·I), and an unlock without its context would widen behavior without anyone noticing. A context-free unlock is the exception.
- **`require`**: the stance exists only when joined on the named sides. ·Fee's `reversed-loop` stance declares `require: [entry]`. The ductus decides between a required stance and a binding. ·Fee's joined form is a different pen motion (it loops the other way), so it is a stance with `require`. ·Gay's joined baseline entry is the same motion redrawn, so it is a `joined:` binding (`reachable-at-the-baseline`) on its `hapax` stance's baseline entry row. Only a stance may carry a requirement, per core-idea.

**Cells.** A stance's cells are the (entry state, exit state) pairs over its declared rows plus `none`, filtered by `pairings`, `unlocks`, `require`, and row scopes. The compiler mints one glyph per cell _reachable under settlement_. The cell is what everything else refers to: selection picks cells, extensions adjust cells, kerning is designed to key on cells, and defect detection enumerates cell pairs. A cell's identity is the tuple `(rune, stance, entry, exit, adjustments)` (`model.CellId`). Its display name, such as `qsMay.grounded-loop.en-y5.ex-y0`, is generated by `geometry.display_name` and capped at 63 bytes, with a hash replacing the overflow. Rune files never contain display names, so there is nothing for a name-healing layer to heal, and the name grammar has no syntax for a context.

**The derived view.** The derived view is a designed, generated, diffable report of each rune's complete capability matrix (entries × exits × pairings × unlocks × row scopes, per stylistic-set configuration). It is the join surface that core-idea says is “derived from the stance set and shown to the author”, and it is meant to be the first thing a reader or agent consults. No target generates it yet. The pipeline generates the settlement and treaty tables of §8, and the emitted FEA comments each settlement rule with the records that shaped it.

### 3.3 Policy: five rider kinds

All contextual behavior is attached to existing stances or to the rune through five rider kinds: `refuse`, `prefer`, `extend`, `contract`, and `resolve`. Two more policy keys are not riders: `order:`, the rune's stance preference list, and `groups:`, rune-local named sets. None of them adds a stance. A rider names its target with optional keys (`stance:`, `cell:`, or `entry:`/`exit:` with a height) and its context with a `when:` condition from the closed vocabulary of §3.4. `when:` is required on refuse, extend, and contract records and optional on prefer and resolve records. The stance-target key is always `stance:`.

```yaml
policy:
  order: [loop, grounded-loop]    # stance preference; defaults to declaration order; replaces name-sort and terminal_default
  refuse:
    - {when: {right: {family: qsThaw}}, why: Joined ·Way·Thaw is ugly and awkward to write by hand.}     # whole-join grain
    - {exit: baseline, when: {right: {class: can-enter-at-baseline, except: [{family: qsNo}]}}}          # surface-row grain
    - {stance: flipped, when: {left: {family: qsZoo}, right: {family: qsEt}}}                            # stance grain
  prefer:
    - {stance: flipped, when: {left: {family: [qsIt, qsVie], joined_at: baseline}}}                      # mode defaults to yields-to-joins
    - {stance: smaller-loop, mode: absolute, when: {left: {family: qsPea, joined_at: baseline}}, why: This is what the join looks like, not a taste call.}
    - {cell: {exit: baseline}, over: {entry: baseline}, why: ·He joins the follower, not the predecessor, when both baseline joins are open.}   # cell grain, §5.9
  extend:
    - {exit: x-height, by: 1, ok: [1, 2], when: {right: {family: [qsDay, qsFee, qsJai, qsJay, qsRoe, qsIt]}}}           # no stance: — only one qsMay stance exits at the x-height
    - {entry: baseline, by: 2, bind: shortened-top, when: {left: {family: qsYe, bitmap: climbing-loop}}}   # hand-drawn bound form (qsRoe's record, shown for the grammar)
  contract:
    - {stance: loop, entry: x-height, by: 1, when: {left: {family: qsHe}}, why: ·He's bare downstroke already sits flush.}
  resolve: []                     # recorded tie-breaks and case-groups, §5.8
  groups:
    low-setups: {union: [{family: qsDay}, {family: qsExam}], minus: [{family: qsDay, trait: half}]}
```

(The block above combines records from several runes to show every grammar form in one place. No single rune has all of them.)

- **`refuse`**: a veto applied before ranking and never negotiated, at three grains: the whole join, one surface row toward a context, or one stance in a context. Each refusal is one line, and group set algebra and predicate classes cover many neighbors at once. A refusal on either rune removes the join. A refuse record's `when.right` may not use `then:` (the schema and `spec_load._lint_refuse_window_rule` both check this), so a refusal can be decided one position to the left of the rune it constrains. That keeps the lookahead closure (§6.1) inside the window.
- **`prefer`**: ranking among the surviving candidates, at stance grain or **cell grain** (`cell: {…}, over: {…}`, needed wherever one stance's cells compete, §5.9). `mode: yields-to-joins`, the default, suspends the preference whenever the candidates' window join counts differ. That makes core-idea's “prefer X in isolation, but switch to Y when Y gives a better neighbor join” the default meaning of every preference. `mode: absolute` outranks join count and requires a `why:`. It is the rare, explicit case where taste overrides joining. Prefers from **both** runes of a seam take part in that seam's ranking (§6.1).
- **`extend` / `contract`**: the parametric connector layer. The target side and height are required. `stance:` is also required whenever more than one stance offers that side and height, and `spec_load` reports an error otherwise; where only one stance does, the stance name is left off. With the required targets, this rules out extensions that apply to the wrong stance. `by:` is the author's amount. `ok: [lo, hi]` is the tolerance band the extension-band check (§9) accepts, and it defaults to `[by, by]`. `split:` is parsed but reserved: no rune sets it and the build does not read it. `trim: N` is a contract option that blanks N pixels of ink on the targeted row and leaves the anchor in place (today's `en-trim`). **`bind:`** names one of the stance's hand-drawn `bitmaps:` siblings as the drawing to use, and the anchors move to the conventional positions on that drawing. A `by:` amount on the same record still lengthens or shortens the connector on the bound drawing. It is for neighbor-conditioned junction ink that is more than a longer connector: ·Roe's `shortened-top` drawing after the climbing-loop ·Ye (an extend) and ·Out's `raked` drawing after ·See (a contract). §4's designed per-rune counts include bound shapes. At most one extend record and one contract record apply to each side of a cell, the most specific under §6.2, and records on the same side never add up. Across a seam, the follower's entry extension is suppressed when the predecessor's exit extension already draws the connector (`Engine::commit` in `rebuild/kernel-rs/src/engine.rs`). Different amounts for different followers are separate records on the same stance, never sibling stances.
- **`resolve`**: a recorded resolution of a conflict. Two shapes are designed: against a named record (`{against: {rune: qsGay, id: plant-word-initial}, when: …, pick: …, why: …}`) and against the structural floor (`{at: {right: {family: qsX}}, pick: …, why: …}`, which overrides the deterministic default of §6.1 for a named window class). Case groups are promoted with set expressions using union and subtraction. A designed subsumption linter flags individual resolves that a promoted group makes deletable, and a group that overlaps a remaining individual resolve is a build error. `why:` is required on every resolve and every `mode: absolute` prefer, and encouraged everywhere else.

  Only the against-a-named-record shape is implemented. A record takes an optional kebab-case `id:`, unique within its rune, for `against:` to name, and `spec_load` checks the reference. When two runes' prefers collide at incomparable specificity, the engine (`Engine::apply_resolution` in `rebuild/kernel-rs/src/engine.rs`) checks both runes' resolves before raising an error, applies the matching resolve's `pick:` to the stage's survivors, and adds its provenance to the explain notes and the fired set. qsTea_qsOy's resolve against qsIt's `withhold-before-no-after-oy` is a live example. `spec_load` rejects a resolve without `against:` (the floor form and case groups) and a resolve with a `self:` condition at load time, and the subsumption linter is not built. The `E-INCOMPARABLE` message includes an example window and a resolve stub ready to paste.
- **`groups`**: rune-local named sets with union and subtraction over family literals, traits, and predicate classes.

### 3.4 Conditions: the closed vocabulary

A `when:` object admits only the keys below. The schema sets `additionalProperties: false`, so adding an eighth axis is a language change.

```yaml
when:
  left:                        # the RESOLVED left neighbor — settlement runs left to right, so this is settled fact
    family: [qsIt, qsVie]      # axis 1; ligature runes are ordinary values here, and left-facing lists are ligature-transparent (see below); group/class references legal
    class: can-exit-at-baseline    # a predicate class (§2) or rune-local group
    stance: flipped            # axis 2 — the neighbor's resolved stance
    bitmap: climbing-loop      # axis 2 spelled as the drawing; the loader resolves it to `stance` (see below)
    joined_at: baseline        # axis 3 — the height of the join being decided (none = the seam did not join)
    stroke: vertical           # axis 4 — orientation at the facing attachment
    is: boundary               # axis 6 — boundary | namer-dot (see below)
    except: [{family: qsIng}]  # negation/carve-out, legal in every condition object
  right:                       # the RAW right neighbor — static facts only, never resolved state
    family: [qsDay]
    class: can-enter-at-baseline
    stroke: horizontal
    is: boundary
    except: [{family: qsMay}]
    then: {family: [qsExam], class: can-enter-at-x-height}    # a static hop; may nest two further thens, and an except entry may carry its own chain — capped three hops out
  self: {entry: live}          # this position's own cell state — live | none per side (replaces extend_exit_when_entered)
  word: final                  # axis 5 — initial | medial | final | isolated (derived from run-splitting boundaries)
  feature: ss04                # axis 7 — active stylistic set(s)
```

`bitmap:` on a left condition names the `stance` axis by its drawing, for a record whose reason is the shape beside it rather than the motion. The engine records a settled left as its rune, stance, and seam, never as the sibling drawing its cell used. So the loader (`spec_load._resolve_left_bitmaps`) rewrites the key to `stance:` before the kernel sees it, and only when the name is a stance of every family the condition names and that stance has no `bitmaps:` siblings. Adding a sibling to such a stance later fails the build at the record. The two forms hash the same, because the kernel's spec carries only the resolved `stance`.

Left-facing family lists are ligature-transparent. A family named in a `left.family`, an entry row's `from:` scope, or the family atoms of a rune-local group union also matches every modeled ligature rune whose `sequence` ends in that family (`spec_load._expand_ligature_lefts`, the rebuild's equivalent of the shipped font's `expand_selectors_for_ligatures`). Without it, each new ligature would need an edit to the `from:` scope of every follower its trailing component already reaches, and a missed edit would lose the join without any error. Naming a ligature explicitly stays legal, and a condition that names only the ligature is more specific under §6.2's extensional order. The expansion only adds: `except:` entries and group `minus` atoms stay literal, so excluding a ligature means naming it. Right-facing lists (`toward:` scopes, `when.right` and its `then:` chains) are not expanded, so a letter that joins into a ligature names the ligature in its `toward:` scope (·Gay's baseline exit lists `qsDay_qsUtter` and `qsOut_qsTea`). Whether a right-facing list should match a ligature by its lead component is an open question.

Boundary semantics: `boundary` matches the edge of the run or any registered boundary token, and `namer-dot` matches only the namer dot. `space` and `zwnj` split runs and so determine word position: `initial` means the left context is the edge, a space, or a ZWNJ. A condition cannot name `space` or `zwnj` on its own (`boundaryValue` in `rebuild/schema/rune.schema.json`), so no record can treat a letter beside one differently from the same letter at a text edge. `namer-dot` does not split runs, and a condition can name it with `is: namer-dot`. The shipped font needs that distinction, because ·Excite guards against the namer dot and ·Utter does not. A letter after a ZWNJ is therefore word-initial by definition. The shipped font keeps that alignment by hand and incompletely. The oracle gives every divergent row whose window contains a space or ZWNJ the `boundary-echo` class (`oracle.classify_divergence`, `rebuild/m1-divergences.yaml`), and the belt's split-buffer check (`conform.check_split_buffer`) checks that each text containing a run-splitting boundary shapes the same as its segments shaped alone.

The difference between the two directions bounds the lookahead depth. `left` may read resolved state, because the left neighbor is already settled, and it stands for all the context further left; it is the system's only memory. `right` may read only static capability plus a static `then:` chain. A `then` may nest two further `then`s, and an `except:` entry inside a right condition may carry its own chain over the same raw slots. Each hop reads one more raw token, and spec_load caps every chain at `model.RIGHT_CHAIN_CAP` hops past the immediate right neighbor: three, for the four-slot window `model.RIGHT_WINDOW_SLOTS`. There is no `left2`, no `right.stance`, and no `right.offers`. Forward viability is handled by the settlement algorithm's built-in lookahead, and no record can state it.

The grammar reads no further than the fourth raw token, so verification to depth 4 covers every rule that can exist. The deep tokens reach only readers that stay inside that window:

- A rune's own `prefer` and `resolve` records read them directly.
- A follower's prefer, voting at the position one to the left of its own rune (§5.9), reads them shifted by one slot. Its `then:` chains therefore match the raw tokens the emitted rule will see, instead of matching optimistically against an unknown slot.
- The join count's third term replays the follower's own transition over the shifted window (§6.1 step 4.2) and treats slots past the window edge as unknown.

Refuse records stay decidable one position to the left (§3.3). The lookahead closure, refusals, and unlocks treat their deep slots as unknown and match optimistically. The §5.7 guard's engines bind every slot past a verdict's two to the window edge, so neither the vote shift nor the simulated prospect can change a formation verdict.

The window grew past the original depth-2 bound because of the orphaned-·Tea windows. In ·Day·Tea·Utter·Low and ·Oy·Tea·Utter·Low, the predecessor's yield has to see the ·Low that makes qsUtter veto ·Tea's entry, and no record-level scope can express that. Depth 4 is needed for the same reason: in ·Day·Tea·Utter·Tea·X, the yield has to read the fourth raw token to keep the middle ·Utter from being left joined on neither side.

The table has a slot for every token the grammar can read. `Transition` and `Rule` carry a fourth right slot, and `table._assert_window_arity` checks at import that their slot count equals `model.RIGHT_WINDOW_SLOTS`, from which `RIGHT_CHAIN_CAP` is derived. Raising the cap without widening the table therefore fails at import instead of emitting records that read past the window. The crate's fixpoint (`rebuild/kernel-rs/src/fixpoint.rs`) enumerates the third and fourth slots, the transducer emits a fourth lookahead class, and the witness replay reads the fourth slot.

The crate splits a window by a deep token only where that token can still change the outcome. Two slot filters decide this: the chain branch in `census.rs` and the liveness branch in `liveness.rs`. The third slot is live where an own-rune chain, a shifted follower-vote chain, or the simulated prospect is still undecided over the nearer slots, and the fourth slot likewise one slot deeper. Where every deep reader has already resolved, the table leaves the slot at `#NA`. Almost every (right1, right2) window resolves its deep readers without the third token, so the number of deep rows follows the records that read the slots, not the size of the alphabet. The simulated prospect can make the fourth token decisive behind a settled third, so the third-slot filter is also live wherever the fourth slot alone could still decide, and no live fourth slot sits behind an unenumerated third. Conform's replay does not use the filters: it keys on all four raw slots (`conform._window_rights`), and a rule that dropped a slot matches any token there.

Within a live window, the deep slots are enumerated at class grain (`kernel_exec.class_grain`, on whenever the simulated prospect or the vote slots are on). The crate partitions a slot's option letters into fibers, sets of letters that settle identically there, by probing each member on the build's own engine over every collapsed left class and a bounded set of coordinates. The fiber key is the full row-visible trace record, the fourth-slot verdict, and the computed fourth-slot option list (`rebuild/kernel-rs/src/fiber.rs`). The table keeps one row per (base, fiber pair), holding a content-addressed member set, so the deep rows per live base grow with the number of fibers, not with the alphabet. Everything downstream of the enumeration reads the expanded label-grain stream (`table.DecisionTable.expanded_transitions`), so the fold, the joint flags, the treaty, and the emitted rules are the same as a label-grain build would produce. The class map is stored in the serialized enumeration for the witness replay, which maps the raw third and fourth slots to the table's class tokens (`conform._DeepTokenIndex`). Conform's sweep walk stays at raw label grain and reads no table.

Reading resolved right state, or reading past the fourth token, would be a schema change and needs a design review.

## 4. The stance-vs-accretion line

Core-idea calls this line the central question of the rebuild: **a stance is a motion the hand makes to write the rune; everything that varies with the neighbors instead of with the hand belongs to the surface, the parametric layer, or policy.** Four checks enforce it:

1. **Ductus parity**: every stance draws a named motion, and every realized motion has a stance (`spec_load` lints both). A stance cannot be added until the motion it draws is written in the ductus.
2. **One unique hand-drawn bitmap**: the comparison runs anchor-normalized over all of a rune's hand-drawn bitmaps, `bitmaps:` siblings included. Two drawings whose ink differs only by connector or stub pixels at declared attachment rows are a build error that names the mechanism already expressing the difference (a surface row, an extension, or a stub), which keeps bound shapes from becoming free-form. No build check implements this yet.
3. **Context-free identity**: stance IDs and motion names contain no neighbor, boundary, or feature reference (`spec_load.FORBIDDEN_ID_PATTERN`). The triggering context lives in policy records that reference the stance.
4. **Complete in itself**: the surface states everything the stance can do, so reading the stance answers "what can this motion do?" with nothing outside the rune's own policy block.

For migration triage, the five-step decision procedure from the reform design classifies any existing record:

1. It differs only in which neighbors summon it: a `prefer`, a `refuse`, or a row scope.
2. It differs only in which anchors are live: a cell.
3. Its ink differs only as a join-local consequence of an anchor being live or declined: a `stub`, `joined`, `withdrawal`, or `cells:` binding.
4. Its ink differs as reach toward one specific neighbor: an `extend`, parametric, or bound with `bind:` when the redraw exceeds connector arithmetic.
5. Otherwise the pen moves differently: a stance, named after the motion.

The discriminator between steps 3 and 5 is the ductus: a join-summoned redraw of the same motion is a binding, and a different motion (·Fee's reversed loop) is a stance.

Applied to the shipped font's 114 stances, the design-time projection was: 36 SHAPE and 1 TASTE stances survive with context stripped from their names; 33 ANCHOR stances become cells; 13 SUPPRESS stances become refusals; 10 CONTEXT stances become prefers, row scopes, or nothing (most are emergent; see ·No below); 10 SS stances become unlock rows with their contexts intact; and 11 EXT stances become extend records, parametric or bound. Each migrated rune's file shows what it actually uses. The readability test still applies: entries may be long, but every line is one of a fixed set of explainable kinds, scatter is impossible because there is no third place, and `why:` one-liners explain what structure alone cannot.

Prefers, bound junction shapes, refusals, and resolves are the channels through which rules could accumulate again. The derived view is designed to show per-rune counts of each, with `migrated:` resolves counted separately so the bulk-accepted migration debt stays visible and the subsumption linter can reduce it, and a linter is designed to flag pileups. These add visibility on top of the structural checks. Neither is built yet (§3.2).

### 5.1 ·May: motions, and surrender with one authored line

·May has two motions: `loop`, which exits at the x-height, and `grounded-loop`, which exits at the baseline.

```yaml
stances:
  loop:
    motion: loop
    bitmap: [...]                          # today's mono drawing
    bitmaps:
      pulled-back-stubless: {bitmap: [...]}    # today's pulled_back…without_stubbie, the form every x-height arriver gets
    surface:
      entries:
        baseline: {x: 0, stroke: horizontal}
        x-height: {x: 3, stroke: horizontal, joined: pulled-back-stubless, joined_x: 2}   # the entry anchor moves with the bound form
      exits:
        x-height: {x: 5, stroke: horizontal}
      pairings:
        never: [{entry: x-height, exit: x-height}]
  grounded-loop:
    motion: grounded-loop
    bitmap: [...]                          # today's exits_at_baseline
    surface:
      entries:
        x-height: {x: 2, stroke: horizontal, stub: {cols: [3], inks_when: withdrawn}}   # the base drawing's connector pixel retracts on the join
      exits:   {baseline: {x: 4, stroke: horizontal}}
policy:
  contract:                                # illustrative only — see below
    - {stance: loop, entry: x-height, bind: pulled-back-stubless, when: {left: {family: qsFee}}, why: ·Fee's long reach-over absorbs the baseline stubbie; the redraw spans rows, so it is a bound shape, not arithmetic.}
```

Neither stance needs a `cells:` row, because each binds only one side and the sugar has nothing to compose. The loop swaps in a hand-drawn sibling when its x-height entry is live, and the grounded loop retracts the column-3 pixel of its y=5 row when its entry joins. The `contract:` record shows the `bind:` grammar on an after-·Fee stubless entry. It is illustrative only: ·May's x-height entry row binds `pulled-back-stubless` for every arriver, so a per-left contract has nothing to add, and the record exists only in the M1 fixture spec (`rebuild/pipeline/fixtures.py`). A decline that redraws across rows is named on a `cells:` row under the `-withdrawn` exit token instead. No migrated rune has one: ·Utter's alternate, the one candidate, requires its exit. In `·May·They+Utter`, where the ligature's entry row does not accept ·May, settlement sees before committing anything that the seam offers no entry, so ·May settles in its (baseline-entry, exit-none) or (none, exit-none) cell. Cell semantics replace the shipped font's two authored `ex-noentry` stances, its `_exit_noentry_fallback` scorer, and its post-liga left-cleanup pass. ·May's hand-drawn variants and context-named stances reduce to two motions, one binding, and one stub, and nothing is named after a context.

### 5.2 ·No after ·It/·Vie: the canonical accretion stance, dissolved

·No has two stances: `loop` (x-height entry and exit) and `flipped` (`traits: [alt]`, baseline entry and exit). No record covers the ·It/·Vie case. When ·It settles with a baseline exit, `flipped` is the only ·No stance with a baseline entry, so capability matching decides. The condition "·It and ·Vie exit at the baseline only sometimes" is not written anywhere, because settlement reads the left neighbor's resolved seam (axis 3, `joined_at`). The shipped font's `qsNo.alt_after_it_and_vie` exists only because its format had no such read. Where an author does want to name the resolved fact (in a kern or a refusal scope), the condition is `when: {left: {family: qsIt, joined_at: baseline}}`.

### 5.3 ·It·No: contextual preference that yields

One record on qsNo: `- {stance: flipped, when: {left: {family: qsIt, joined_at: baseline}}}`, in the default mode, which yields to joins. Settlement at ·It's position ranks pair candidates (§6.1), and ·No's prefer takes part from the right side of the seam. In isolation, both seam heights score one join with no onward prospect, so the prefer breaks the tie and `flipped` wins. In ·It·No·Owe, the x-height path scores two (the seam plus ·No's x-height exit into ·Owe, which the baseline path rules out), so `loop` wins before the prefer is consulted. When ·It's left neighbor joins it at the baseline, ·It's pairings leave only an x-height exit, so only `loop` can join: capability decides, not preference. One line gives three behaviors, and `rebuild/pipeline/explain.py` prints each of them.

### 5.4 ·Utter·Gay·Low·It (“ugly”): priority over the intersection

·Gay's (x-height-entry, baseline-exit) cell, with its x-height stub retracted by the join, is the only candidate whose entry matches ·Utter's resolved x-height exit. It joins ·Low's baseline entry, so it beats the exit-declined cell on window join count. Settlement evaluates candidates against both neighbors at once: it picks the highest-ranked member of (left-compatible ∩ right-compatible).

### 5.5 ·Tea: the stylistic-set capability matrix

·Tea's `full` stance declares baseline and top entries, a baseline exit, `never: [{entry: baseline, exit: baseline}]`, and two context-scoped unlocks: `{pairing: {entry: baseline, exit: baseline}, feature: ss05, when: {left: {family: qsEt}}}` and `{entry: x-height, feature: ss03, when: {left: {family: [qsFee, qsMay, …]}}}`. The contexts migrate with the unlocks, because widening ss05 from "after ·Et" to "after any baseline exit" would change behavior silently in don't-care windows. No stance is named after a set. The derived view is designed to render the matrix per configuration, showing what is allowed as a function of (left, right, active sets); it is not yet emitted (§3.2). The Manual's one ss05 use is checked by its data-expect pin under `data-stylistic-set="05"`.

### 5.6 ·Way·Thaw: the unilateral veto

One rune-level line on the lead: `refuse: [{when: {right: {family: qsThaw}}, why: ...}]`. Settlement never produces a joining candidate for the pair, so no FEA rule proposes one, and the refusal compiles to no `ignore sub` statements.

### 5.7 ·Out+Tea, the ·Excite·Tea·Oy guard, and ligature formation

`qsOut_qsTea` is a rune (`sequence: [qsOut, qsTea]`) with its own ductus, stances, and a surface with no exits; `qsTea_qsOy` has an exit and no entries. Because formation runs before stance selection, ·Excite's widened baseline-exit motion (whose row is scoped toward baseline enterers) sees the entryless ·Tea·Oy ligature as its right neighbor, has no candidate that can join it, and settles in a plain cell, keeping any left join it already made. The shipped font's `_PENDING_BK_ENTRY_GUARDS` table and `qsExcite.*.before-vertical` stances are unnecessary, because a declared join must be physically realizable before it is committed.

In the model, formation is a settlement decision, and a guarded one. A ligature yields to its components in a window when the trailing component, left unformed, would join the follower and the formed ligature could not join it under any capability configuration. The case that requires this is ·Day·Utter·Low, whose Manual pin is `·Day | ·Utter.alt ·Low`: the ligature exits only at the x-height, ·Low enters only at the baseline, and forming would lose the seam the unformed alternate ·Utter carries.

The verdict is computed only in the crate (`guard::GuardState::formation_blocked`). `kernel_exec.guard_sweep` runs it once per spec, `emit_gsub` compiles it, and `settle.form_ligatures` reads it through `settle.guard_blocks`. The trailing component is settled at ranking grain, as a full transition with the lead's default stance, unjoined, as its left, so refusals, follower votes, and the runes' prefers all count. ·Day·Utter·See·Low needs ranking grain: there ·See's grounded prefer withholds the unformed ·Utter's reach, and the shipped font forms the ligature. The ligature side is checked at candidacy grain, which allows more joins. The guard's engines bind every slot past the verdict's two to the window edge instead of treating them as unknown, so only a vote that fires definitely inside the window can change a verdict.

Formation runs before the stylistic-set markers and cannot see the configuration, so the verdict is quantified over the powerset of capability-unlock features and blocks only where every configuration blocks. `guard-sweep --config=` computes the same surface under one configuration, and `rebuild/test_settle.py` checks how the two relate. Every configuration with ss03 on sweeps the quantified surface. Every configuration without it sweeps one stricter surface, which also blocks the `(X_qsUtter, ·Tea, r2)` windows where the ss03 x-height entry into full ·Tea is the ligature's only join toward its follower. ss04, ss05, and ss10 change no verdict.

The verdict's two slots are the raw tokens after the sequence, which are the slots the emitted lookup reads, so the guard never depends on state that formation cannot see. When those two slots themselves form a ligature, the guard tests against that ligature instead of the bare first slot, because the pair's own formation consumes the entry the raw reading would reach for. In ·Day·Utter·See·Utter the shipped font forms both ligatures, and a raw-slot reading would un-form the first for a join that cannot happen. Either way, the verdict is a function of the two raw slots only.

The decision is made before forming, and there is no un-form-and-repair pass. It restates the shipped font's variant-keyed formation as a derivation: the shipped `calt_liga` forms `qsDay_qsUtter` from ·Utter's `reaches-way-back` and `before-may` variants but not from the plain baseline-reaching alternate, which amounts to "form unless the unformed trail reaches a follower the ligature cannot serve." Because the guard derives from the runes' join surfaces, a newly migrated letter that only the unformed rendering can reach extends the guard with no per-ligature data, and The Manual stays satisfied. Seams on the left side are exempt: formation may still cost the predecessor its join (`qsTea_qsOy`, above), as it does in the shipped font.

Compiled shape: `emit_gsub` reads the crate's `guard-sweep` result once. A ligature the result ever blocks moves to a chaining-context lookup, `m1_formation_guarded`, first in `calt`, whose generated `ignore sub` rows implement the guard over one or two raw lookahead slots, with ZWNJ-explicit forming rows ahead of them. Unguarded ligatures stay in the plain type-4 lookup. A verdict that blocks at every boundary second slot but releases specific letters there compiles the other way round: explicit two-slot forming rows for the released letters, after a ZWNJ-explicit ignore and before a one-slot ignore that matches anything, text edge included. ·Day·Utter·See·Low and ·Day·Utter·See·Utter need this. A verdict that blocks at some boundary second slots but not others cannot be expressed in the pre-marker lookup and raises `EmitError` (`emit_gsub._formation_lines`); §15.8 covers it.

#### Preserved outgoing strokes

A ligature stance's `outgoing.stance` maps it to the final sequence component's stance. The mapping defaults only when that component has a single stance; a component with several stances requires an explicit choice. The mapped stance supplies outgoing permissions and applicable exit policy by default. The ligature supplies its own exit rows, anchors, withdrawal drawings, stubs, and bitmap bindings. A missing mapped exit is an error unless `outgoing.exceptions` names `surface.exits.<height>` with a reason; the same exception permits a local `toward` scope that differs from the source. `outgoing: {exception: ...}` opts a drawing out entirely, as for the exitless ·Out·Tea ligature.

`spec_load.outgoing_policy_record` decides which of the component's records apply. Exit-only refusals, refusals naming neither side (which veto the only seam an entryless ligature has), cell preferences, extensions, and contractions follow the mapped stroke, including right-side chains and feature conditions. Incoming behavior, word-position and internal-left conditions, stance-choice preferences, and mixed-side votes stay with the component. Exit-only unlocks follow the same context restriction and derive their anchors from the ligature's own bitmap. A bound adjustment requires an exception whose `outgoing.replacements` entry names the local replacement, because component bitmap names do not identify ligature drawings; loading fails without it. A combined `stance` and `cell` preference filters cells within that stance and leaves other stances neutral, so several ligature stances can preserve the same exit policy without voting against one another. Source-local groups keep their source membership under namespaced names.

Local policies coexist with inherited ones under the ordinary specificity order. To replace an inherited record, an exception names its source path (`policy.prefer[0]`, for example), and `outgoing.replacements` maps that path to the local record of the same kind that replaces it. The build checks that replacement even when its condition differs from the source. An exception without a replacement removes the source record. Exit-unlock exceptions name `surface.unlocks[index]`. An exception path must name applicable source behavior, so a stale exception fails loading. The runes' `outgoing` declarations record each mapping and its intended differences. `spec_load.rune_closure` includes the trailing component, so a change to its permissions or policy invalidates cached results for the formed ligature.

The formation guard still protects alternative component stances that the ligature does not preserve. It does not show that a mapped stroke is preserved: an internal-left refusal on unformed ·Zoo after ·They can suppress the guard's first probe. Loading checks inherited exit coverage separately and merges the inherited records into the ligature, so the M1 build's `ligature_outgoing_check` tests what the ligature adds on its own. It settles each mapped stance twice over feature configurations, boundaries, and contextual continuations: once carrying only the inherited exits and policies (with declared replacements standing in for their excepted sources), and once as the formed ligature with its local records. It fails on any window where the seam's height or the yield differs. So a local record that drops a join, moves it to another height, or joins where the source yields needs an exception, while a local extension or contraction, which moves no seam, coexists under the ordinary specificity order. The check drops incoming constraints so that it tests each declared outgoing stroke, join-born stances included; conformance checks the built font's actual settlement. The ss10 overlay pre-empts formation and stays subject to read-back's isolation check.

### 5.8 An incomparable conflict, recorded and promoted

Suppose ·Way's half declares a word-final prefer (axis 5) and ·Roe declares a before-·Tea prefer (axis 1), and the two demand different heights at the (·Way, ·Roe) seam. Neither condition's match set contains the other, so the build fails with `E-INCOMPARABLE`, an example window, and a paste-ready resolve stub. The author records a `resolve` on one of the two runes. When the same conflict recurs with ·Why, the author promotes it to a case-group whose membership is a set expression with union and subtraction (with word-final ·Way carved back out to keep its flourish). The subsumption linter flags individual resolves that a promoted group makes deletable, and a group overlapping a surviving individual resolve is a build error, so promotion reduces the number of resolves instead of moving them. Case-group promotion and the subsumption linter are designed and not yet implemented (§3.3).

### 5.9 ·He: follower preference at cell grain

·He's entry-baseline and exit-baseline forms are the same drawing, so they are cells of one stance with a `never` pairing. The shipped font's rule, "·He joins on the left here or on the right elsewhere, never both, and prefers the follower", is enforced by a 31-family complement list. In the new format it is one cell-grain prefer on qsHe: `{cell: {exit: baseline}, over: {entry: baseline}}`. Under §6.1, the record takes part in the predecessor's seam ranking and votes to withhold the predecessor's exit whenever ·He's own forward join can be realized after refusals, which is decidable inside the window. In ·Day·He·Day both assignments score one window join, and ·He's cell prefer breaks the tie toward the forward join. In ·Day·He·-ing, ·-ing refuses entries after ·He (a refuse on qsIng), so the forward prospect scores zero and ·Day·He joins. A refuse based only on static capability would get this case wrong. One line with a `why:` replaces the complement list.

## 6. Selection semantics

### 6.1 The settlement function

Settlement runs per run (boundary to boundary), after formation, left to right. At position i, the unit being ranked is the **pair candidate**: a cell of rune i together with the seam state toward i+1, which is a height or none.

1. **Entry binding.** A committed seam is bilateral and final. If position i−1 committed an exit at height h, only entry-h cells of rune i are candidates; entry-none cells are candidates only when the left seam committed no join. The follower cannot decline a committed seam, and an acceptor always exists, because step 2's lookahead closure at position i−1 found one.
2. **Lookahead closure.** A pair candidate with seam height h is admissible only if some cell of rune i+1 survives all of: its own pairings, `require`, unlocks, row scopes, and every refuse or availability record decidable within the window, evaluated with rune i's candidate as i+1's resolved left and rune i+2's raw surface as its right. §3.3 restricts refuse records to window-decidable conditions, so this closure is total. An exit with no acceptor after refusals is never a candidate, so a join toward a neighbor that will not accept it cannot be represented. If settlement still meets a committed exit with no acceptor cell at the next position, it raises `E-STRANDED`, naming the committed cell, the seam height, and the follower, and the table build fails.
3. **Refusals.** Any matching `refuse` on either side eliminates a candidate. Refusals are absolute and unranked.
4. **Ranking**, strictly lexicographic:
   1. Absolute prefers from both seam runes, most specific first (§6.2).
   2. **Window join count**: [left seam realized] + [own seam realized] + [the (i+1, i+2) seam under i+1's own simulated choice given this candidate]. The third term replays i+1's full transition (candidates, refusals, both prefer stages, order, and floor) over the window shifted one slot right, so it scores the seam the follower will realize, not the best seam some surviving cell could. Past the window edge the recursion treats slots as unknown, so the term is exact inside the window and neutral beyond it. The table builder compares every row's scored prospect with i+1's settled choice in the enumerated table and flags rows where they differ as `joint`; those are the windows whose outcome a token beyond the enumeration could still decide. Under class-grain deep slots the comparison runs over the expanded label-grain stream, and a class row's flag is the OR over its members, which the fiber key makes uniform.
   3. Yielding prefers from both seam runes, most specific first. A follower's stance- or cell-grain prefer is evaluated per enumerated continuation (per class row at the deep slots, uniform across members by the fiber key), with `joined_at` bound to the candidate's seam height. Prefers that demand different outcomes at non-nested specificity raise `E-INCOMPARABLE` when they belong to two runes and `E-AMBIGUOUS` when they belong to one.
   4. The runes' declared `order:`.
   5. **The structural floor**: a deterministic default for ties no record decides, so don't-care windows never become build errors. It prefers a candidate that realizes its seam toward i+1 over one that declines it, then the lower seam height, then the exit row's declaration order (`floor_key` in `rebuild/kernel-rs/src/engine.rs`). When the floor decides between a joining and a non-joining candidate, the row is also flagged `joint`. Ties settled here show up as treaty-diff rows, which keeps core-idea's "don't-care is the default, discovered not declared."
5. **Commitment.** The cell and seam state are final, and settlement moves to the next position. There is no revisiting and no repair pass.

Word position follows from run-splitting boundaries (§3.4). Word-final winners are the rows that match when the right is a boundary, so `terminal_default` needs no replacement. Withdrawal is part of candidate semantics: a stance's cells form a lattice (both-sided, one-sided, isolated), settlement picks the cell the seams support, and that cell is drawn with the bound bitmaps of §3.2.

### 6.2 Specificity, formally — and extensionally

A record's specificity is computed **extensionally**: every constrained axis expands to its concrete match set over the finite registry (families × stances × cells × heights × features × boundary values). Record A outranks B when A's match set is a subset of B's on every axis B constrains, and a strict subset on at least one. Within one axis, narrowness is set inclusion after expansion: a literal `[qsExam]` is narrower than `[qsYe, qsExam, qsI]`, a singleton group ranks by what it denotes, and mixed literal-plus-class conditions need no special case. A syntactic rank (resolved cell before stance before family) would disagree with extensional inclusion on real records and is undefined for mixed conditions.

Nested conflicts resolve silently: the narrow single-family contract beats the broad list-authored extend by membership. Crossing conflicts raise one of two hard errors, `E-INCOMPARABLE` or `E-AMBIGUOUS`, each of which needs a recorded `resolve`. Migrated idiom pairs that are incomparable under the extensional order are resolved by §13.5's triage with `migrated:` provenance, so the outcome is recorded instead of being an accident of ranking. There is no axis-priority order, no modifier-count sort, and no name sort. Because specificity feeds the settlement it orders, evaluation is stratified (capability first, then policy) so that the computation is well founded.

A bug in this order would look like a change of taste rather than a failure, so the order has extra tests. `rebuild/kernel-rs/src/specificity.rs`'s `mod tests` holds the two named regression cases as synthetic analogs on a fixture spec: the decline-discriminator window (an x-height-exiting predecessor + ·It + ·They) and the qsJay contract-versus-extend overlap. `rebuild/test_spec_load.py` checks the shapes the real runes present.

### 6.3 Explainability and the emergence compensation

Emergent behavior has no authored line: reading qsNo.yaml does not say "flipped fires after a baseline-exiting ·It." All three judges raised this criticism, and the design answers it with three compensations:

- (a) `uv run python -m rebuild.pipeline.explain SEQUENCE [--features ssNN]` replays settlement with the full candidate table, every elimination attributed to a file and record, and the ranking stage that chose the winner.
- (b) Every emitted settlement rule carries a comment naming the rune records that shaped it, so reading the FEA leads back to one explainable decision.
- (c) The derived per-rune report cross-references policy on the other rune of every pair, so reading both sides of a pair does not depend on memory. It is not yet written (§3.2).

Separately, approving a unit in the review tool drafts a whole-word data-expect pin for it (`rebuild/review/drafts.py`), which turns an emergent outcome the author cares about into a cheap assertion.

## 7. Compilation to OpenType

Everything below uses only shapes that the shipped font's 30,838-line FEA already shows are reachable. The difference is that the settlement function is computed first and then transcribed.

| Format construct | OpenType realization |
| ---------------------------- | -------------------- |
| Cells (+ adjustments) | One compiled glyph per cell reachable under settlement; identity is the structured tuple; names are generated and display-only |
| Attachment heights | Four `curs` lookups, one per height (`emit_gpos.CURS_HEIGHT_YS`), with NULL anchors for cross-height glyphs, the shipped font's encoding; a height mismatch cannot occur at the GPOS level |
| Formation | Plain GSUB type-4 over bare runes for unguarded ligatures, preceded by a chaining-context lookup holding the generated late-formation guard rows (`ignore sub` over one or two raw lookahead slots, ZWNJ-explicit forming rows first) for any ligature the crate's `guard-sweep` ever blocks (§5.7) |
| ZWNJ / boundaries | The chokepoint (`sub uni200C @m1_entry_live' by @m1_entry_locked`) plus the generated default-ignorable coverage transform, which must cover ZWNJ at **every** slot of the settlement rule shape (backtrack, first, and second lookahead): the table's boundary-outcome rows name `uni200C` explicitly in the class at the boundary slot and are ordered ahead of any join row that could match across a skipped ZWNJ. Generated per-lookup guard statements are the fallback if positive ordering proves insufficient. Emitter invariant: locked twins and chokepoint outputs appear in no raw lookahead class, family-keyed classes included. The only `ignore sub` rows are the namer-dot ZWNJ guard and the late-formation guard rows (§5.7) |
| Settlement | The decision table transcribed as chained-context single substitutions: backtrack matches _settled_ classes (GSUB backtrack sees post-substitution glyphs), lookahead matches _raw_ classes, as `sub <settled-left class> <rune>' lookup <outcome lookup> <raw class> <raw class>;`. Each row names one plain single-substitution lookup per distinct (input glyph, outcome glyph) pair, defined between the chokepoint and the settlement lookup, because feaLib resolves a named lookup through a dict while an inline `by` makes it rescan the rules for every row (`rebuild/pipeline/emit_gsub.py`). Positive rules only, no selection-semantics `ignore sub`, and classes throughout via outcome-partition (DFA-style) compression |
| Word position | Fallback-row ordering for word-final defaults; the substitute-then-revert lookup pair is kept in reserve for positive `word: final` records |
| Capability unlocks | `ssNN` marker substitutions staged **after formation and before settlement**, so enabling a set cannot un-form a ligature; ligature runes carry their own markers for unlocks they declare. Settlement tables include marker glyphs as raw inputs. Runes with several applicable sets get generated composite markers (union semantics). Conformance runs each set alone and the multi-set configuration ss03+ss05 (`conform.SETTLEMENT_CONFIGS`) |
| Taste sets / ss10 | A single-substitution pre-empt staged ahead of formation: every letter's cmap glyph to its anchor-free `.ss10` twin, which is in no formation sequence, marker line, chokepoint class, or settlement input and has no anchor (read-back checks all of this on every build). Under ss10 nothing forms, settles, or attaches, and no settlement table is built for the configuration (`conform.OVERLAY_CONFIGS`) |
| `refuse` / `prefer` / `resolve` | Not compiled: they shape the decision table, and the FEA contains only final substitutions |
| Extensions / stubs / trims / bound shapes | Part of the settled cell's identity (`CellId.adjustments`), so each adjusted cell is its own glyph, drawn at mint time, and the settlement lookup substitutes it directly |
| Kerning | One class-based PairPos format-2 lookup (global row + pair rows) plus GPOS type-8 contextual kerns. The M1 font emits no kerning yet: `compile_font` passes an empty kerning table |
| Namer dot | A final `calt` lookup, `m1_namer_dot_word_start`, which `emit_gsub` writes itself: the dot lowers before a Short letter, and an explicit `ignore sub` keeps it from lowering across a ZWNJ |

**The sound factorization is subtables, never per-family lookups.** The transducer encoding is one settlement lookup, optionally split into per-family **subtables** for size. Subtables share the lookup's single left-to-right pass, so backtrack still sees settled neighbors; the shaping spec defines this within-lookup behavior, and the shipped font already relies on it. Per-family **lookups** are unsound: each lookup finishes the whole buffer before the next starts, so a rune whose family's lookup runs first would see a raw left neighbor, and because left adjacency between families is cyclic, no lookup order fixes this. The only sound multi-lookup factorization is the two-strata fallback below.

The kill criterion is emitted size. Read-back measures it from the written GSUB bytes and fails the build when the subtable-offset headroom is below `readback.SUBTABLE_OFFSET_HEADROOM_FLOOR` (`checked.gsub_budget` in `rebuild/out/m1/readback_summary.json`). The cross-shaper smoke tests (`rebuild/pipeline/coretext_smoke.py`) check within-lookup sequential substitution, ZWNJ-interleaved cases included, under HarfBuzz and CoreText; the designed DirectWrite leg has not been run.

The subtable split is required, not an optimization. feaLib builds each ruleset in every chained-context format it can and keeps the smallest, and where a ruleset's class sets do not fit shared ClassDefs it writes one format-3 subtable per rule. At current rule counts the unpacked lookup can overflow its uint16 subtable-offset array, which fontTools cannot save (`rebuild/pipeline/compile_font.py`). So `pack_gsub` regroups the compiled lookup in memory into shared-ClassDef format-2 subtables, keeping format 3, in its original position, for rules whose class sets one ClassDef cannot express. The regrouping preserves rule order, and read-back checks it by re-deriving every rule from the packed form on disk. The module docstring of `rebuild/pipeline/pack_gsub.py` describes how rules are grouped and placed.

The designed fallback is two-strata staged-wave emission: stratum 1 over raw facts and stratum 2 keyed on stratum-1 output classes, always two passes and never an empirical fixpoint. Chains within a stratum still rely on within-lookup sequencing, so the last-resort fallback is one wave per dependency rank, bounded by the longest settled chain. In every case the guard, demote, and repair categories stay deleted, and only emitted size is at stake. The design-time forecast for the primary path was ≈950 `curs` statements unchanged, settlement in the low thousands of rules, and 3–6k lines of FEA in total against the shipped font's 30.8k. The `gsub_budget` block of `rebuild/out/m1/readback_summary.json` reports the actual GSUB bytes, lookup and subtable counts, and offset headroom.

## 8. Generated artifacts

The build writes two diff-stable tables per settlement configuration under `rebuild/out/m1/`, so a change in the font's behavior shows up as a table diff. `rebuild/out/` is gitignored and every build rewrites these files, so a hand edit does not survive a build.

- **The settlement table** (`settlement-<config>.tsv`, one per configuration in `conform.SETTLEMENT_CONFIGS`; the ss10 overlay settles nothing and has none). Each row is one rule: an input rune, a class of settled left glyphs, four raw lookahead classes, the outcome cell, a `joint` flag, and provenance pointers to the YAML records that shaped it. Its diff is the diff of the font's settlement behavior.
- **The treaty table** (`treaties-<config>.tsv`): one row per reachable pair of adjacent cells, with the join height or `break`, the summed extension, and a kern. The §9 defect gates and the review surface's table diff read it. The crate writes `kern` as 0 on every row, because the rebuild emits no kerning yet (§12).
- **The capability matrices**, one per rune and configuration, are the §3.2 derived view. They are designed but not emitted. The settlement table's `joint` flag already marks the rows where the left's choice depends on the right context (§6.1).

## 10. Testing and pinning

Five tiers, cheapest first. The first two need no font.

1. **Spec validation.** `spec_load` checks the schema, ductus parity and the naming lints when it loads the runes.
2. **The font-free enumeration.** The crate's fixpoint settles every reachable window over the alphabet and the boundaries, and the §9 defect gates read the result. A settlement error in a reachable window (`E-STRANDED`, `E-INCOMPARABLE`, `E-AMBIGUOUS` and the rest of the `E-` family) stops the table build. This tier takes minutes and is the agent's inner loop.
3. **Transcription and reachability, checked on every build.**
   - Read-back (`rebuild/pipeline/readback.py`) parses the compiled font's bytes and compares every GSUB stage, feature registration, LookupList order and `curs` anchor with the emitters' plan. On the same bytes it checks that the ss10 overlay is isolated: the pre-empt covers every letter's cmap glyph, and the twins have no cmap entry, appear at no position of any other stage, and carry no anchor. That is why the overlay configuration needs no table, certificate, settle memo or oracle settlement.
   - The crate's fold tallies the first-matching rule of every replayed row and refuses a table in which some rule is never first. A rule that other rules hide in every window fails the build here.
   - The witness stage (`run_m1.run_rule_witnesses`) settles, for every settlement rule, the certificate the crate wrote beside it, and checks that the rule fires. A certificate is a string built from the shortest chain of rows that produces a row the rule first-matches, plus that row's own slots and a bounded closure of the formation guard's open tail (`rebuild/kernel-rs/src/certificate.rs`). The stage costs O(rules) settles and no search. Settling a certificate also checks the fixpoint's pins, since a certificate whose prefix settles to a different left state fires a different rule. The walk uses the per-family settle memo that the belt and the oracle also use, so a window settled since the runes it names last changed costs one lookup. By the window-locality theorem below, a rune edit re-settles only the certificates that name an edited family.
   - `emit_gsub._assert_fold_sources` checks at emit time that every table rule folds into exactly one emitted row, so a witnessed table rule is a witnessed shipped row. The order the rows ship in is the fold of every configuration into one lookup, which no per-configuration check reads. The shipped-order walk (`run_m1.run_emitted_order`, over the crate's `replay-emitted` subcommand in `rebuild/kernel-rs/src/shipped_order.rs`) replays that order against every row of every configuration's enumeration. It renames each row into its configuration's stream and checks that the first emitted rule of its input that admits the row produces the row's outcome. Where an emitted lookahead class admits only part of a row's deep class, it checks the row member by member. It costs O(rows) and settles nothing. It runs on the tables the build just folded, so it never reads a stale artifact.

   A rule missing from the font fails read-back, and a rule no string can realize fails the fold or the witness stage. Neither check depends on a sweep horizon, so the sweeps carry no coverage obligation. Where the deep slots are enumerated at class grain, a witnessed row stands for a fiber of label windows, and the build checks that the fiber's members settle alike (the partition, echo and fiber checks) instead of assuming it.
4. **The string replay, then the HarfBuzz sweeps.**
   - **The string replay.** On every build, `run_m1` runs the crate's `replay-strings` subcommand (`replay.rs`) as soon as the tables are written. It walks every text up to `run_m1.REPLAY_HORIZON`, the belt's horizon, window by window. It applies the stored rules first-match with the settled left fed forward, and checks each window's rule outcome against the engine's own settlement of that window. It is keyed on the raw window and shares nothing with the fixpoint's verdicts. A live window that the enumeration left at `#NA` or never reached is matched by a broader rule, and the walk fails wherever that rule's outcome differs from settlement, so every build checks that the six-slot window abstraction is sufficient for these texts. A disagreement fails the build and names the configuration, the window and the text. The comment on `REPLAY_HORIZON` explains why a deeper walk belongs to the periodic sweep.

     Under the window-locality theorem below, a rune edit walks only the texts that name an edited family or a rune whose records read one, and a code or structure change walks the whole universe. `rebuild/out/m1/replay_summary.json` records the last walk, and the next build computes its delta against it.

     The walk's window memo is the build's settle memo. On every whole-universe walk the subcommand writes the memo it held for each configuration in the crate's own format. `conform.absorb_replay_memo` converts it into the file that the witness stage, the oracle and the belt map read-only (`conform.settle_memo_files`; one `mmap` layout per configuration, written whole and replaced atomically by `conform._write_settle_memo`). Each of them then reuses what the replay settled and settles only the windows a rune edit invalidated. The memo stamp covers comparison-side modules that the replay's own stamp does not, so the walk also widens to the whole universe whenever a configuration's memo file is missing or its stamp has changed.
   - **The belt**, run per edit: an exhaustive comparison of the font against settlement at horizon 4 over every settlement configuration. It adds no witness texts and makes no coverage claim. It runs the split-buffer check on every text that contains a run-splitting boundary. Beside it, the ss10 overlay's own case at `conform.OVERLAY_HORIZON` checks that every letter maps to its twin and every pair is unformed, unjoined and unmoved, each slot at zero offset with its `hmtx` advance. With read-back's isolation check this is complete, since a twin that no pair attaches is attached by no text. The deep sweep carries these checks past horizon 4, and read-back's static boundary-glyphs stage checks the ZWNJ glyph itself (zero advance, no ink). What only the belt can test is HarfBuzz's application semantics over the rule shapes the emitted lookup contains: lookup interaction across features, backtrack seeing settled glyphs across subtable breaks, default-ignorable skipping, class matching, and Extension indirection.

     The belt is keyed like the deep sweep (`artifact_cycle.conform_skip_fingerprint`, built from the deep sweep's arming lines): the behavior classes enumerated from the emitted lookup (`emit_gsub.behavior_classes`), the font-compilation code and the tools/ closure it runs, the uharfbuzz version, and the horizon. The key leaves out the runes, the tables' stamp and the font's bytes. A rune edit that adds no new rule shape therefore skips the belt, because the replay has already checked its tables against the engine over the same texts. The trade-off is that a disagreement only HarfBuzz can see waits for the next code change or deep sweep instead of the next rune edit.
   - **The deep sweep** (`make conform-deep`): the same sweep at horizon 5 or deeper, run by hand or overnight. Its green record is keyed on the same lines without the horizon. It also settles every text it shapes, so it checks completeness past the belt's depth along with the split-buffer check. A rune edit that adds no new rule shape never makes it stale, and `emit_gsub.behavior_classes` fails the build on a rule shape it cannot classify, so a new shape always arms it.
   - **The deep replay** (`make replay-deep`, `rebuild/tools/deep_replay.py`), the deep sweep's cheap form: the crate's `replay-strings` walk at horizon 5 over the texts naming the runes whose content changed since its last recorded walk. Its green record (`cycle_paths.DEEP_REPLAY_GREEN`) holds every rune's prose-blind digest, and the changed set is closed under `rune_closure` as in the build's own replay. It is the only check that can see a fault confined to the deep slots behind a letter left, at the cost of a per-family settle instead of a whole-universe HarfBuzz sweep. It is kept out of the per-edit path by measurement: on the live alphabet, one family's texts at horizon 5 cost each configuration several times the whole-universe horizon-4 replay (`make cycle-timings ARGS='--by-step'` records every walk under `replay-deep`). The cycle arms it on a rune edit and reports its status beside the deep sweep's. A green deep sweep at horizon 5 or deeper refreshes it, since the deep sweep settles every text it shapes. A walk that finds a disagreement withdraws the record's claim for the runes it walked: after a family walk the status reports those runes armed, and after a whole-universe walk it deletes the record, so the status reports `never-run`. A later walk over those runes that passes, or a green deep sweep at horizon 5 or deeper, restores the claim. A code or structure change never widens its walk; that is the whole-universe deep sweep's job. The walk caps its memos at a window ceiling so that every configuration can walk at once; `rebuild/tools/deep_replay.py` states the ceiling, the per-walk peak the machine's memory is divided by, and how both were measured.

   Compared with shaping every edit through HarfBuzz, this arrangement checks transcription on every build and reaches deeper texts, and it samples shaper interactions less often: an interaction visible only at length 5 waits for the deep sweep instead of the next cycle.
5. **Pins.** The data-expect notation and the Manual corpus carry over unchanged: glyph tokens, `~x~`/`~b~`/`~t~`/`~6~`, `|` with the break-isolation invariant, `+?`/`+|`, `.∅`, and `.half`/`.alt`, which the Manual-pin gate (`rebuild/pipeline/manual_pins.py`) resolves against the stances' declared traits. That gate skips and counts the compat-only variant assertions (`en-y0`, `noentry`, `extended`). Planned backward-compatible additions: an any-of connective in the corpus (its current form is the test helper `_assert_expect_any`), in-string stylistic-set scoping for single connections, a word-position scope marker, and an optional extension-band assertion. Whole-word assertions remain the preferred cheap check.

**Window locality** is the theorem the per-edit checks depend on. For one configuration, the engine's result for a window (the settled left, the input and its four raw right slots) is a function of these inputs and nothing else:

- the crate and `rebuild/script.yaml`;
- the rune files of the families the window names, including every ligature rune whose `sequence` is a contiguous run of the raw tokens;
- their closure under `spec_load.rune_closure`, which adds a ligature's trailing component and the transitive `resolve.against` targets;
- the cross-rune structure that `spec_load.spec_structure_digest` and `capability_features` state.

It holds because the condition vocabulary is closed (§3.4), the engine reads no slot beyond the four raw slots a case line carries (`Engine::cond_matches_right` returns `None` for a condition that needs a slot outside the window, and `census.rs` relies on that), refusals are decidable one position to the left, and the formation guard is a pure function of the ligature and its two raw slots.

There are two exceptions, and both are computable:

- **Class-ranked specificity.** `specificity::outranks` orders records by match-set inclusion, so a rune joining or leaving a predicate class re-ranks every record that names the class, including in windows that name neither rune. That is why class and group membership are part of the structure digest the string replay is keyed on, so a membership change walks the whole universe there. The trace memo across builds instead invalidates by the classes each window's settlement read (§14.1).
- **Reachability.** An edit can make a cell of another rune unreachable or newly reachable. This changes which windows exist and not what any window settles to, and every window that exists only after an edit is reached by a text naming the edited rune.

`run_m1.replay_structure_stamp` is the whole-store half of the replay's key: the non-rune data, the build-side code and the crate, the semantics tokens, the structure digest, the capability features and the horizon. While it is unchanged, a build walks only the texts naming a rune whose digest changed, closed under `rune_closure`. The oracle row cache, the review unit cache and the settle memo's key depend on the same theorem, so a counterexample would be a bug in all of them. The configuration corollary: under a given configuration, a window that names no rune with an unlock or a `feature:`-conditioned record under that configuration settles identically to `default`.

Without the walk, only the belt would check the shipped first-match order, and the belt's key does not change on a rune edit. The walk replays `ordered_fold`'s order against every configuration's rows on every build, keyed on the same inputs as the tables, so an ordering fault that a rune edit exposes without adding a behavior class fails that build instead of waiting for the next code change or deep sweep. The one subtlety is the deep classes: a rule folded from another configuration's fiber partition can admit part of a class of this one, and the walk checks such a row member by member instead of through a representative. `rebuild/out/m1/emitted_order_summary.json` reports how many rows each configuration expanded this way. On the shaper side (rows 11 and 12), neither fault changes any shaping, and each one changes the arming key, which is what the tier-4 design requires.

No sweep reads the settlement table's `joint` flag: the belt and the string replay cover every text up to horizon 4 whatever the flag says. For pure refactors of the emitter, byte identity of its output is the check. Across spec changes, behavioral equivalence is the settlement-table diff.

## 11. The review surface

`make review-build` regenerates the review surface under `rebuild/out/review/`, `make review-serve` serves it on port 7294, and `make review-cycle` runs the whole loop. `rebuild.review.build --mode table-diff` builds the table-to-table diff against an accepted baseline. Each changed settlement or treaty entry is rendered in the live font following the tester-page conventions: a checkered background, the pair under review highlighted, before and after side by side through two `@font-face` rules, one-key home-row verdicts with auto-advance, and per-unit notes. The app autosaves verdicts to the server, and the artifact cycle merges them with `rebuild.tools.merge_verdicts`, where the newer `at` wins and the merged set never shrinks, so no step goes through the clipboard. The build drafts an export for every unit (`rebuild/review/drafts.py`): an approval drafts a whole-word data-expect pin covering the unit, a rejection drafts the one-line refuse, contract or prefer edit naming the provenance records, and “fine either way” records both behaviors in the any-of channel. Every behavioral change becomes a unit, including a changed mid-word join outside the corpus, which the old font's tooling does not show anywhere.

## 12. Kerning

This section is a design: the rebuild emits no kerning yet. `emit_gpos` writes only cursive attachment, the treaty table's `kern` column is always 0, and the old font's sidecar `glyph_data/senior_quikscript_kerning.yaml` keeps its name-prefix keys. The oracle reads that sidecar to add the old font's kerns back before it compares positions (`rebuild/pipeline/oracle_positions.py`).

The designed sidecar stays flat, `---`-separated, and editable in a textarea (the one exception to locality), with structured keys instead of name prefixes:

```yaml
---
global: {value: -1}                                   # the 1px tightening for all of Senior; exactly one such record
---
left: {rune: qsNo, stance: flipped}                   # keyed by resolved stance: the ·No.alt·Pea case
right: {rune: qsPea}
value: -2
---
left: {rune: qsWay}                                   # keyed by cell: the old font's qsWay × qsGay.ex-y0 rule
right: {rune: qsGay, ex: baseline}
value: -1
---
left: {rune: qsHe}
right: {boundary: zwnj}                               # the contextual kern, GPOS type 8
value: -3
```

Each side is a structured reference: a rune, an optional stance, and an optional cell pattern (`en:` or `ex:` with a height). Sides resolve against the reachable-cell inventory at build time, and a key that matches nothing is a build error; in the old font a stale prefix kerns nothing without an error. Because GSUB resolves fully before GPOS, keys on resolved pairs are context-aware at no extra cost: `qsNo.flipped × qsTea.half` encodes the ·It that caused the half. The treaty table's reachability data is meant to drive the hidden-junction drill-downs in `site/kerning.html` (today `tools/build_kerning_hardcases.py` computes them from the old font) and a standing corpus check for a resolved pair that wants two different kerns, which would detect the contextual-kern counterexample core-idea leaves open. Compilation: one class-based PairPos format-2 lookup plus the type-8 contextual rows, replacing the old font's one lookup per sidecar rule.

## 13. Migration

Migration is gated per rune on ductus, checked against black-box extraction from the old font, and deletes the old patch layers once the baseline shows their behavior is preserved. Each letter is migrated as one `Add ·X` commit by the add-a-new-letter skill.

1. **Baseline extraction, built first.** The depth-2 basis is shaped through the old font and every window's resolved outcome is recorded as a baseline table (`rebuild/BASELINE-PLAN.md`). This is black-box shaping with no reading of the old pipeline. The baseline is the migration oracle ("done" means the new table matches except where a reviewed row says otherwise) and the review surface's first workload. Rows whose window contains a space or ZWNJ take the `boundary-echo` class, because the belt's split-buffer check covers post-ZWNJ ≡ word-initial (§3.4).
2. **Ductus, per rune.** Every stance must name a motion (`motion:` is required by `rebuild/schema/rune.schema.json`), so a rune's ductus entries are written when migration reaches it. The design's `unrealized: true` marker for an enumerated but undrawn motion does not exist: `ductus` values are prose strings. The census's per-family bitmap and stance inventories are the worklist. Every existing bitmap must end up under some motion, as a stance's base or a bound sibling, or be dropped.
3. **Record conversion.** Each old-font record maps to rune records by its census label: ANCHOR stances → surface rows and cells; SUPPRESS → refusals; CONTEXT → prefers, row scopes, or nothing at all (tried as nothing first, since most should emerge from settlement); SS → unlocks with their contexts intact; EXT → extend records (parametric or `bind:`-bound); `derive` directives → extend or contract records with required targets. **Allowlist polarity is preserved**: every old positive `select.before`/`after` gate on an exit or entry stance becomes a `toward:`/`from:` row scope, one to one. Without this step, join-count ranking would flip every pair absent from an allowlist (·Roe·It and its hundreds of siblings) from unjoined to joined, which is a systematic inversion and not incidental drift. Context sets become predicate classes (geometric) or rune-local groups (private); kerning keys go through an alias table (`qsNo.alt → qsNo.flipped`); bitmaps, anchors, traits, ligature sequences and the corpus HTML carry over unchanged. The design called for a converter script driven by the census labels. None exists: the add-a-new-letter skill authors each rune from the output of its bundled evidence tool.
4. **Deleted on evidence.** The rows of the old font's three override tables (`restore_isolated_form_overrides`, `predecessor_demote_overrides`, `trailing_demote_overrides`), `_PENDING_BK_ENTRY_GUARDS`, and the guard, demote and reflip passes are never converted. The baseline table shows that their behaviors are preserved, or surfaces the divergence for triage, where each one becomes an explicit refuse, prefer or resolve with a written reason.
5. **Arbitration triage.** Where the old font's outcome rests on modifier-count and emission-order accidents, the new build raises `E-INCOMPARABLE` or `E-AMBIGUOUS`. The design has a tool propose the resolve that reproduces the baseline row, with `migrated: matches pre-rebuild behavior` provenance (the `migrated` field on policy records), for the author to accept in bulk and re-judge later; the tool is not built. The number of migrated resolves is a visible §4 count that the designed subsumption linter is expected to reduce as case groups emerge.
6. **Order and acceptance.** The letters with the most old-font stances (qsIt, qsTea, qsPea, qsMay) come first, and the families without stances come last. Acceptance: the Manual corpus passes under its recorded ss configurations, the conformance gate passes, the treaty-diff triage is empty, the leak gate is at or below the old font's backlog, and the kerning hard cases are re-recorded. Byte identity with the old font is not a target. Cutover archives the old pipeline and adds the demote-oracle and guard-table chapters to `doc/graveyard/`.

### 14.1 The kernel crate: design facts from the port

`settle`'s engine and `table`'s fold live in `rebuild/kernel-rs/`, the engine of record. These are the facts measured during the port that the crate's structure follows from.

- **Packed keys give the speedup, not the language.** CPython beats both Rust and Go at inserting a ten-slot _string_ key, because it caches string hashes. The same insert on a packed integer key is an order of magnitude faster. That is why `model.rs` interns every vocabulary string to a `Sym` and every number to an `i64`, and keeps only prose as an owned `String`; a port that kept string keys would lose most of the gain. A fast non-cryptographic hasher without a finalizer measured _far slower_ than SipHash on these keys: its last multiply carries each bit only upward, so the low bits that pick a table's bucket cannot see the high bits of the last word written. A finalized hasher measured _far faster_, and every map and set in the crate uses it (`rebuild/kernel-rs/src/hash.rs`).
- **Rust, not Go.** Rust's speedup stayed flat as the problem grew, while Go's shrank as its garbage collector scanned a larger live heap. A memoized fixpoint whose whole working set stays live until the build ends is the worst case for a tracing collector and the best case for an arena.
- **Window rows stay packed through artifact emission.** `stream::LabelPool` holds a configuration's window labels, including boundary tokens and locked-input suffixes that are outside the spec's symbol vocabulary. `TransitionRow` holds pool-local label ids and indexes of the settled and provenance records; its outcome resolves through a label table indexed by settled record. The fixpoint drains directly into the final row vector and sorts it by lexical ranks, so sorting needs no second full row vector. `FixpointProduct` passes the pool and the outcome table to `fold::DecisionTable`, where the windows writer and the digest resolve them. The row-layout test in `fixpoint.rs` checks the compact width. The stream and artifact formats stay text.
- **The boundary is a file, and `rebuild/pipeline/kernel_io.py` is its contract.** The kernel reads an `ams-m1-spec/1` dump: canonical JSON of the whole `ResolvedSpec`, with collection order preserved because settlement depends on it. `rebuild/test_kernel_io.py`'s spec-echo test checks that the two sides agree byte for byte on every `make test-rebuild`. PyO3 is worse on every count: its only advantage over a file is saving a serialization measured at a small fraction of the build, and passing Python objects across the boundary rebuilds the object graph the packing exists to remove. `spec_load.py` is outside the runtime closure and is not ported.
- **The rule fold runs beside the enumeration, and its ordering is what needs checking.** Producing each input's ordered rules is cheap. The expensive checking is the prefix search and the outcome partition, which `build-tables --timings` reports as `fold.prefixes[<config>]` and `fold.partition[<config>]` beside the aggregate fold. The partition compiles each rule's classes into product-local label ids, keeping the row pool's ids and using newly interned ids only as membership keys. It then walks the rows in their original order, so it keeps the same winning rules and certificate candidates as the string matcher. The full string partition remains as a test-only reference, and the crate's proof-fold test compares exact winners, retained rows, refusal text and certificates. The string replay and the witness stage check each configuration's own order. The order the font ships, `emit_gsub._ordered_settle_rules`' fold of the configurations into one lookup, is checked on every build by the shipped-order walk (`run_m1.run_emitted_order`, the crate's `replay-emitted` subcommand in `shipped_order.rs`) and by the belt after it (§10's fault table, row 6), since read-back compares the font to that plan and not the plan to the tables. The acceptance protocol and evidence map are in [the proof-search issue comment](https://github.com/adiabatic/abbots-morton-spaceport/issues/303#issuecomment-5785733925).
- **A rule's realizing string is read off the rows, never searched for by settling.** Each row determines its successors: a successor has the row's right1 as input, its outcome as left, and its right slots shifted one place. One breadth-first pass over the rows in key order (`certificate::Prefixes`, whose docs describe how repeated successor queries are searched only once) gives every row its shortest chain from a seed row, whose left is a boundary. A test-only reference searches every producer, and the crate compares its exact distances and parents with the production pass. `certificate.rs` closes that chain plus the row's own slots over the formation guard's open tail into one string per rule, written into the windows head beside the rules, and `run_m1`'s witness stage settles each one back through the engine. Settling it checks the pins: a chain the fixpoint pinned wrongly settles to a different left and fires a different rule. The worklist's own parent links are not used because the worklist is a depth-first stack: its chains run to thousands of letters, each of which the witness stage would settle wave by wave. The fold takes the enumeration's own `WindowOptions`, whose guard verdict memo is already filled, so the realizability check costs O(rules) settles on the tables the build just folded, and no test lane has to read `rebuild/out/` afterwards.
- **The risk concentrates in the liveness probe** (`liveness.rs`). Most of the runtime is in this one module, and it is the hottest, the subtlest and the easiest to get wrong without noticing: a liveness verdict that opens too little omits windows, and the font is then wrong in a way no per-row assertion can see. The check for this is the `replay-strings` subcommand (`replay.rs`), which `run_m1` runs on every build (§10, tier 4): a window the enumeration left at `#NA` or never reached is matched by a broader rule, and the walk fails wherever that rule's outcome differs from the engine's settlement. The belt keys its settle memo on the raw window for the same reason, and what it adds beyond the replay is the shaper itself. That memo comes from the replay. `Replay::write_window_memo` writes the walk's memo per configuration in the crate's format: raw labels, the locked input after a ZWNJ, and an index into the record table for a settled left, since `cell_label` and `geometry.display_name` are two formats of one function of the cell. The Python side converts it into the belt's format, marker fold included (`conform.absorb_replay_memo`), so the crate never needs a configuration's marker names.
- **No Python twin.** There is no Python settlement engine. Keeping one for independent verification meant writing every settlement change twice, which was the port's largest real cost. Correctness is checked by gate:conform, which shapes the compiled font through HarfBuzz and compares it with a re-settle, and by the string replay. The author-facing tools (`explain`, `probe`, the review surface) reach the same crate through `settle-cases`, so reproducing any build or explanation needs both `uv` and `cargo`.
- **The trace memo is the unit of sharing across configurations and of persistence across builds** (`rebuild/kernel-rs/src/memo.rs`). An entry is a pure function of the raw window: the collapsed left, the input and the four raw slots. By the window-locality theorem (§10) it holds wherever the runes its key names are unchanged, and by the configuration corollary a `default` entry holds under another configuration unless the key names one of that configuration's unlocking runes or the entry's evaluation read one (`memo::unlocking_runes`: a rune with an unlock or a `feature:`-gated record under it). One `build-tables` process enumerates `default` first and keeps its memo. Every other configuration runs the same worklist from the same seeds, reads that memo except for the entries the exclusion refuses (`memo::Exclusion::admits`), and traces only what it cannot read. Each configuration's finished memo is written beside its tables as `memo-<config>.tsv.gz`, and the next build reads it, excluding the runes whose resolved, prose-blind content changed (`run_m1.memo_stamp` and `memo_seed` decide, with `rune_content_digests` giving the per-rune digests). The worklist itself is not seeded: reachability is re-derived on every build, so a cell that one configuration reaches first, or reaches only there, never breaks the theorem. The fired journal survives because every entry stores the delta its evaluation journaled, and a hit replays it.

  Which base entries a lookup refuses depends on what the entry's evaluation read. While a capture is open, the index's accessors journal every rune whose resolved content and every predicate class whose membership they return (`rebuild/kernel-rs/src/index.rs`). The entry keeps that set beside its delta, and an exclusion naming runes and classes refuses the entries that read one of them. This makes the class-ranked specificity exception mechanical: `run_m1.memo_stamp` records every class's membership and names the changed classes instead of refusing the whole store, and a window whose deep slots name a rune its settlement never consulted stays usable when that rune changes. The six runes a key names are refused as well, as a second check behind the journal.

  The file is at the memo's own grain, not the rows': it holds the probe windows that the liveness and fiber derivations trace, including virtual lefts and unknown coordinates. A derivation that quantifies over every letter as a deep token is re-run on every build and served from the base wherever its probe names no edited rune. This is the exact form of persisting verdicts across builds, since a verdict at context grain aggregates over the whole alphabet and no per-family rule can invalidate it soundly.

  Byte identity is the acceptance test and the standing gate: a seeded product equals the from-scratch one in the crate's own tests and in `rebuild/test_kernel_exec.py` over the mini fixture. The fold's output does not depend on traversal order at either grain, because a class-grain row is traced at its fiber's least member instead of at whichever member reached it first. The measurement (`--cache-census`'s `memo_base_hits` beside `trace_cache`) shows that the wall-clock time of a delta or a seeded build is spent not on the traces it skips but on the memo hits it still performs and the per-context derivations it re-runs. Most of what memo sharing and persistence gained is memory, and a cheaper hit path is the next thing to optimize.
- **Persisted memo loading drops keys naming edited runes** (the callers of `fanout::load_seed`), including in single-configuration builds and builds with `--config-seed-off`. A delta's own previous memo also keeps only the keys that name its unlocking runes. This filter preserves table and memo bytes because every base reader refuses those edited keys and `memo::write_memo` leaves them out of the carried union. It is not the full read-journal exclusion: surviving entries can still depend on edited runes or changed predicate classes, and lookup and writing check those reads. The previous default memo stays shared through the delta wave beside the fresh default snapshot, because it serves unaffected windows missing from that snapshot. `--cache-census` reports `memo_base_hits seat=N count=N` for each base in lookup order beside the aggregate `memo_base_hits count=N`, which shows which retained base serves the worklist.
- **Finished trace memos have immutable storage.** `memo::SnapshotEntries` stores full key and entry records in a compact array, partitioned by a `FastHasher` prefix and sorted by key within each partition; a small offset table bounds each lookup before the full-key comparison. The live engine's trace memo is a growing hash map. `Engine::take_memo` releases that map before indexing the collected records, and `read_memo` builds the same immutable form from accepted TSV records. Construction keeps source order as temporary positions, so a duplicate key keeps the last accepted record even when partitioning or symbol resolution reorders them. The TSV format and the writer's key order are independent of the lookup layout. The snapshots and their pools are shared through `Arc` across the delta wave. Compact storage removes bucket slack but still grows with the number of windows held. The memory allowances beside `DEFAULT_MEMO_BYTES` and `TABLE_BUILD_PEAK_BYTES` in `rebuild/pipeline/kernel_exec.py` account for both the retained snapshots and construction's temporary storage.
- **What a port does not fix.** At the full alphabet the conformance sweep is Θ(alphabet^horizon), and no change of language touches that exponent. `--conform-horizon` and the old font's calt sweep's `max_chars_after` are coverage settings that change numbers a rewrite cannot reach, and the memo across builds above is the other change of this kind. The fixpoint's cost grows steeply with the alphabet, and the target is all 44 letters. `rebuild/tools/scaling_sweep.py` is the migration's early warning. It is re-run after every letter batch (a step in the add-a-new-letter skill's checklist; `rebuild/scaling-ladder.txt` holds the last run), and its docstring states the threshold in both units, runes and letters. A port changes the constant and not the exponent, so a steepening ladder means work avoidance is due whatever the language. Two caveats when reading the ladder. The nested subsets stop adding ligatures partway up, so there the letter count grows faster than the rune count, while the migration does the reverse. And the class-grain deep slots reduce the row count but not the run time, because per-window cost rises by almost exactly the reduction factor, so their benefit is what fewer rows save downstream, not seconds.

## 15. Honest weaknesses and open questions

1. **The settlement emitter carries the most risk.** It is built and shipping: one `useExtension` settlement lookup whose compiled subtables `pack_gsub` regroups into shared-ClassDef format-2 form before the font is written, which keeps the lookup inside its 64K offset space at current rule counts. The remaining risk is emitted size, not feasibility. The two-strata fallback of §7 stays designed and unbuilt as the deeper reserve; §7 notes that it still relies on sequencing within a lookup. The module docstring of `rebuild/pipeline/pack_gsub.py` describes how rules are grouped and ordered. The packing favors subtable-offset headroom; read-back checks the serialized per-glyph rule order and enforces `readback.SUBTABLE_OFFSET_HEADROOM_FLOOR`.
2. **Emergent behavior lives off the page.** Two of the three §6.3 compensations exist: the explain CLI and the per-rule provenance comments. The review surface also drafts a data-expect pin for each approved unit. The cross-referencing per-rune report is not written, so until it is, reading both sides of a pair depends on running `explain` one sequence at a time.
3. **Cells could become the new sprawl.** The number of minted cells is bounded by the real join states, which OpenType has to store anyway, but the readability claim depends on the derived matrices staying small. The per-rune surface report is the designed check.
4. **Greedy left-to-right settlement will disagree with the old font in don't-care spots.** The systematic source, allowlist polarity, is handled by §13.3's `toward:`/`from:` migration. The remaining cases are incidental drift, triaged in the review app. Some old emergent outcomes the author preferred without saying so will still be rediscovered slowly.
5. **The specificity order fails quietly if it fails.** Hence extensional semantics, stratified evaluation, and a regression suite with named cases. This is the one component with a budget for extra testing, spent in `rebuild/kernel-rs/src/specificity.rs`'s `mod tests` and the real-YAML pins in `rebuild/test_spec_load.py`.
6. **Prefers, bound shapes, and resolves are the soft channels through which patch-by-patch rules could return.** Required targets and required `why:` fields make that growth visible, and the designed pileup lints and per-rune counts (§4, including the migrated-resolve count) would add to that; neither is built. None of these prevents the growth.
7. **Stylistic-set composition is sampled, not proven.** The model defines behavior for every combination (unlock rows compose by union). Conformance checks each capability set alone, each combination the registry declares under `interactions:` in `rebuild/script.yaml` (`conform.SETTLEMENT_CONFIGS` lists them), and the Manual's configurations. Undeclared combinations ship best-effort and documented: they are not a build error, because the font is user-facing, and they are not silent.
8. **Ligature formation depends on resolved context, and one kind of guard verdict cannot be expressed.** The §5.7 late-formation guard decides formation per window from the runes' join surfaces. It is configuration-blind and derived, not authored (·Day·Utter·Low is the worked counterexample). A verdict that blocks at every boundary second slot while releasing specific letter seconds compiles through §5.7's forming-rows-first inversion; ·Day·Utter·See·Low and ·Day·Utter·See·Utter need it. A verdict that blocks at some boundary second slots but not all cannot be expressed in the pre-marker formation lookup and is a hard emitter error. A verdict that differs across capability configurations is not an error: `rebuild/kernel-rs/src/guard.rs` quantifies the verdict over the powerset of capability features and blocks only where every configuration agrees.
9. **The orientation vocabulary is coarse** (`horizontal|vertical|diagonal`). Its values are author judgments with no ground truth but the eye, and wrong values would produce confidently wrong flags. Suggestions from bitmap gradients could help seed it.
10. **The ductus gate is resequenced from core-idea’s stated want.** Core-idea says to finish all ductus before the rewrite; this design gates per rune instead (§3.1), giving up the global up-front pass in exchange for mechanical enforcement per rune. Residual risk: motions with neither bitmap nor prose are caught by neither order, and writing the hardest enumerations under conversion pressure may bias the prose toward the bitmaps. This departs from a recorded author decision and is pending sign-off.
11. **Deleted knowledge can be lost without notice in corners no gate reaches** (the archive documents real depth-5-only regressions). Read-back and the witness stage close the transcription-and-reachability half of this by construction. Where the deep slots are class-grain they do so per equivalence class, which detects a dead class but not a dead label combination inside a live class. The build's check that every member of a fiber settles the same way keeps that narrowing sound. The per-edit depth-4 belt covers shaper semantics, and the periodic deep sweep (`make conform-deep`) looks at depth 5 and beyond at an affordable cost. It is outside the per-edit budget, so it can go as deep as an overnight run allows, and it arms whenever the emitted lookup gains a new behavior class. The accepted remaining cases: an interaction visible only at depth 5 or more waits for the deep sweep instead of the next cycle, and some taste will still be rediscovered by eye later.

Open questions left for implementation: whether the locked-twins ZWNJ optimization ever replaces the chokepoint-plus-coverage-transform, and the namer-dot Chrome itemization issue, which stays in the graveyard.
