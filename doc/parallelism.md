# Parallelism and memory budgets

Every fan-out width in this repository is computed from the machine it runs on: total physical memory, clamped by any cgroup limit, minus a reserve, divided by a measured per-unit peak, capped by any non-memory bound, and floored at one. `rebuild/tools/memory_budget.py` implements that arithmetic and documents the policy, including why the budget never reads free or available memory. Each per-unit cost is a named `*_BYTES` constant at the call site that uses it, and the comment or docstring there records the measurements behind it and explains the width it implies, so a number and its justification stay in one file. `doc/fleet.md` lists the machines and is the key for reading host-tagged output.

## The memory-bound fan-outs

Each fan-out below defines its per-unit cost where its width is computed.

- The kernel's table build: one `build-tables` process over every settlement configuration (`conform.SETTLEMENT_CONFIGS`; the ss10 overlay settles and enumerates nothing).
  - `default` enumerates first and alone and keeps its trace memo. The other configurations then run as deltas over that memo, `--threads` at a time, heaviest first by unlocking-rune count (`fanout::delta_worklist` in the crate). `default`'s fold preparation (its expansion, row chains and first rules) takes one of the `--threads` slots.
  - Where memory has room, each configuration's memo file is written on a thread of its own beside the rest of the build (the crate's `--overlap-memo-writes`, `fanout::run_configs_tables`): `default`'s from its release point, so the wave starts as soon as `default`'s enumeration ends, and each delta's beside its drain, sort and fold, which holds the delta's memo until the write ends. The files are the same bytes either way.
  - Otherwise `default` writes its memo file before the wave, so the `memo[default]` timing line is time the wave waits for and the rows the writer holds are never resident beside a delta at its peak, and each delta writes its own file when its enumeration finishes and holds no memo through its drain, sort, or fold.
  - `kernel_exec.memo_writes_overlap` chooses the writes beside the wave when the build's booking at its width, with `MEMO_WRITE_OVERLAP_BYTES` added for those writers, still fits, so a machine whose width memory sets keeps them ahead unless what that width leaves over holds the term. A bare `run_m1` decides it with nothing beside the build; the artifact cycle decides it with gate:make-test's pytest pool off the machine, as it sizes the width (`memo_writes_overlap_budget`), and passes run_m1 `--overlap-memo-writes` or `--no-overlap-memo-writes`.
  - Every configuration runs on one thread from its enumeration to its files (`fanout::run_configs_tables`), because its product holds `Rc`s, and its prepared product (the class rows, their label-grain expansion, the row chains, and the window options) stays parked from its preparation until the cross-configuration exchange ends (`rebuild/kernel-rs/src/crossconfig.rs`). The exchange holds no slot and adds little beside what is parked; each configuration then finishes its fold, writes its files, and frees everything inside a slot again. So at the end of the delta wave every configuration's parked product is resident at once, beside the last delta's enumeration.
  - Each width the build might take has a booking (`table_build_booking_bytes`), built from constants in `rebuild/pipeline/kernel_exec.py`: `DEFAULT_MEMO_BYTES` for the fresh `default` memo snapshot that stays alive for the wave, plus the filtered previous-build `default` memo when one is present; `PARKED_FOLD_BYTES` for each configuration's parked product; `DELTA_SLOT_BYTES` for each delta in flight, what one more delta adds to the wave beyond its own parked product, measured on the whole wave rather than on one configuration alone; and, at a width above the delta count, `FOLD_PREPARATION_BYTES` for the slot that runs only `default`'s fold preparation; a build that writes its memo files beside the wave adds `MEMO_WRITE_OVERLAP_BYTES`. The width is the widest, up to the configuration count, whose booking fits the machine's memory less the reserve. Below the whole wave that is the memory less the memo and the parked products, divided by `DELTA_SLOT_BYTES` and capped at the delta count, since there the preparation's slot passes to a delta once the preparation ends.
  - A build in which every configuration enumerates from scratch (a narrowed `rebuild/tools/scratch_build.py` set without `default`, or `default_memo_sharing=False`) books each slot at `SCRATCH_PEAK_BYTES`, one configuration enumerated from scratch and alone, less its parked product.
  - The terms are chosen together so that the 48 GiB machines (`doc/fleet.md`) run the whole wave, every delta and `default`'s preparation at once, with the memo files written beside it, alone and under a gated cycle. A wave that takes a second round, on a machine whose width is below the delta count, holds every finished configuration's parked product beside the deltas still enumerating, which is the parked term. The `DELTA_SLOT_BYTES` comment has the readings, the margin, and the recipe each letter batch re-measures them by.
  - `TABLE_BUILD_PEAK_BYTES` is the booking at the configuration count with the memo files written beside the wave; `make job-costs` compares every run_m1 step since the constant's commit against it.
  - `kernel_threads_default` computes the width for a bare `run_m1`, for the configurations the build names. `kernel_threads_budget` in `rebuild/tools/artifact_cycle.py` computes a cycle's width and also subtracts gate:make-test's pytest pool before the division. A narrow `AMS_KERNEL_THREADS` still parks every configuration's product, so even a width of one holds them all at the exchange. `run_m1._table_build_threads` caps either at the configuration count and the cores. The cycle's budget applies the same cap itself, as `replay_threads_budget` does, so the plan line and the argv show the width the wave runs at.
  - The window packing behind the build and the shipped-order walks on the same branch are sized by the cores, not by this width; see "Everything else".
- The string replay that follows the table build (`run_m1.run_replay_strings`, on run_m1's table-only branch): one crate process over every settlement configuration at maximum length 4.
  - `REPLAY_PEAK_BYTES` in `rebuild/pipeline/kernel_exec.py` is what one configuration's walk holds: the trace memo over the windows its texts reach, plus the window memo's inverse label map and block buffer. The constant's comment has the measurements.
  - A walk that answers records the crate process's own peak, divided by the walks it ran at once, as the `replay-walk` pool (`run_m1._record_replay_walk`), which the replay-walk row of `make job-costs` checks against the constant.
  - Nothing is subtracted before the division, because the replay's engines are built after the table build's process has exited and none of its memos survive.
  - `replay_threads_default` divides the machine's memory by it for a bare `run_m1`. `replay_threads_budget` in `rebuild/tools/artifact_cycle.py` computes a cycle's width after subtracting gate:make-test's pytest pool. `run_m1._replay_threads` caps either at the configuration count and the cores, and the cycle's budget applies the same cap, as the kernel's does. The constant is chosen so both fleet machines replay every configuration in one wave.
  - After a full replay, the settle-memo absorbs (`run_m1._absorb_replay_memo`, one spawn process per walked configuration, each holding one configuration's dump, columns, and probe index) run at the same width once the crate has exited, because each holds a fraction of `REPLAY_PEAK_BYTES`.
- The deep replay (`make replay-deep`, `rebuild/tools/deep_replay.py`): one crate process per unit, at maximum length 5. A unit is one settlement configuration over the texts that end in one alphabet symbol (`deep_replay.walk_units`, the deep sweep's settlement units), walked on one thread, and each configuration's units merge back into the counts one walk over all its texts gives.
  - Each unit's walk holds at most `DEEP_REPLAY_MEMO_WINDOWS` windows in its walk memo. Before any text that could push the memo past that limit, the walk releases the walk memo and its engine's memos (the crate's `--memo-windows`). What a walk holds therefore does not grow with the corpus, apart from the settled records and labels it keeps, which grow with the number of distinct records.
  - `DEEP_REPLAY_PEAK_BYTES` in that module is one walk's peak at that limit, and `replay_threads` divides the machine's memory by it, capped at the cores. `AMS_DEEP_REPLAY_THREADS` sets a width instead. Either is capped at the unit count.
  - A walk at that limit records each configuration's highest unit peak as the `deep-replay-walk` pool beside its check line (`deep_replay.record_walk_peaks`), which the deep-replay-walk row of `make job-costs` checks. No cycle runs the deep replay, so the row moves only when someone runs it.
  - A memo limit set above the checked-in one has no memory estimate, so set `AMS_DEEP_REPLAY_THREADS` with it.
- The deep sweep (`make conform-deep`, `rebuild/tools/deep_sweep.py`): one spawn process per unit, at maximum length 5 or more. A unit is the ss10 overlay whole, at its own maximum length, or one settlement configuration over the texts that end in one alphabet symbol (`run_m1.sweep_units`, shared with gate:conform's pooled sweep), and each configuration's units merge back into the result one walk over all its texts gives. A configuration whose features rename a few runes (`conform.renamed_runes`) shapes only the texts that name one of them, so its units shape fewer texts than `default`'s; `deep_sweep.sweep_triggers` decides which configurations do.
  - A settlement unit shares no settle memo at this depth and keeps every distinct window it settles except the pinned ones (`conform._SettledWindowWalk`, `horizon`), so below the window ceiling the next item describes its windows grow through its walk, and its footprint peaks at the window dict's last doubling late in the walk, when it briefly holds the old and new tables together.
  - Each unit's walk holds at most `DEEP_SWEEP_MEMO_WINDOWS` windows. Before a wave of settles that could push them past that ceiling, the walk empties its window dict and continues (`max_windows`), settling again the windows it meets after that. The ceiling is the most windows a dict holds before it doubles, so a walk at the ceiling fills one table and never doubles past it. `AMS_DEEP_SWEEP_MEMO_WINDOWS` states another ceiling, and the price below follows it.
  - The width is fixed before anything is spawned, not from a live reading: it prices the smaller of the windows the heaviest unit could hold at the end of its walk and the ceiling at a per-window cost that covers that peak, as every settlement unit's need.
  - `window_bound` counts in closed form, from the alphabet, the ligature runes and the symbols each ends in, the boundaries, and the glyph inventory's cells per family, an upper bound on the windows the unit whose texts end in one symbol holds at the requested maximum length: the asks whose last token ends in that symbol and the asks a boundary cuts short, less the pinned windows. Its docstring has the argument. `unit_window_bounds` bounds every symbol's unit in every configuration, since nothing `window_bound` counts from depends on the configuration: the inventory spans every configuration's tables, and the renaming maps labels one to one. A unit that skips texts shapes a subset of the texts of its own configuration's unit over every text that ends in its symbol, so it holds a subset of that unit's windows and the same bound covers it. `settlement_worker_bytes` prices the smaller of the heaviest bound and the ceiling at `DEEP_SWEEP_WINDOW_BYTES` a window beside `DEEP_SWEEP_BASE_BYTES`, the worker before its walk holds anything, which is also all the ss10 overlay holds. At maximum length 5 every bound is below the ceiling, so the bound sets the width; it grows with the alphabet, so a new letter needs no new measurement. At maximum length 6 every settlement unit is priced at the ceiling, so a unit's price, and with it the width, does not depend on the alphabet: every fleet machine sweeps as many units at once as it has cores. The constants' comments have the measurements they are set from and hold the first full run at maximum length 5 and the one-unit runs at maximum length 6 against them.
  - `sweep_width` divides the machine's memory, less the overlay worker, by the settlement unit's need, capped at the cores and the unit count. The overlay runs first in one of those slots, which then takes settlement units. The plan line prints the heaviest unit, its bound, the ceiling, and the arithmetic. When even one settlement unit exceeds the memory less the reserve, the width is floored at one and `memory_shortfall` warns; when it exceeds the machine's memory in all, the sweep refuses to start. Under the checked-in ceiling neither happens on a fleet machine at any length. `AMS_DEEP_SWEEP_JOBS` sets a width instead, and `--jobs` overrides both, for debugging; a stated width also starts a run that would otherwise be refused, with the warning.
  - Each run writes a `conform-deep` check line to the cycle-timings journal with each configuration's highest unit peak footprint (`peak_rss.peak_footprint_bytes`) beside its estimate.
  - `--targeted` runs units of one settlement configuration over a slice of at least `TARGETED_UNIT_TEXTS` of the texts the `settle:bk1-la4` rules give (`deep_sweep.targeted_units`), with no overlay unit. A unit's walk holds at most one window per character of its texts, so `settlement_worker_bytes` prices the heaviest unit's character count, capped at the ceiling, and `sweep_width` divides the memory by that with nothing subtracted for an overlay. The constant's comment has the measurement it is set from.
  - While it runs, the parent prints a progress report every 20 minutes: texts shaped, rates, an estimated finish, every running unit's footprint, and the swap in use, in total and per configuration over its units. The workers report their counts to it through shared memory and print nothing. `AMS_DEEP_SWEEP_REPORT_SECONDS` sets the interval in seconds, so a short debugging run can report every few seconds. The module docstring describes the report and how the finish is estimated.
- The review-corpus build, in `rebuild/tools/artifact_cycle.py`.
  - `CORPUS_PARENT_BYTES` is the parent process. It holds the whole corpus at any width, as columns over the unit's ordinal (`audit.UnitTable` and `unit_store.UnitStore` in `rebuild/review/`), and materializes a unit as a record only for the reader that needs one. It is subtracted before the division.
  - `CORPUS_WORKER_BYTES` is what one worker holds, and `corpus_job_budget` does the division. Its cap is a count of cores less the parent: every usable core for a hand build and under `--skip-gates`, and the build lane's share under a gated cycle (`memory_budget.split_cores`), which leaves the gate lane to gate:make-test's pool or, when that gate skips, to the other gates.
  - A machine the pooled build does not fit gets width one, which is the serial build.
- The standing fill's refill pool (`_prefill` in `rebuild/tools/standing_verdicts.py`), which decides across a spawn pool the units the memo cannot serve: every unit when the memo was dropped, or the units a changed standing rule can reach.
  - A worker holds its interpreter, a `SlideContext` over the corpus's font pair, and one chunk of units with that chunk's memos, which it releases after each chunk.
  - The verdict update's process, the pool's parent, keeps ids, decisions, and memo entries, writes pool misses to a temporary gzipped spool, and submits at most one wave of chunks (the pool width times `_STANDING_POOL_CHUNK` units) at a time. Its memory grows with ids and decisions, not with the full human corpus; the docstrings of `_prefill` and `rebuild/tools/verdict_update.py` have the details. The standing daemon holds its own corpus outside this budget.
  - In `rebuild/tools/artifact_cycle.py`, `STANDING_FILL_PARENT_BYTES` is what the verdict update's process holds and is subtracted before the division, `STANDING_FILL_WORKER_BYTES` is what one worker holds, and `standing_fill_jobs` does the division, capped by the cores.
  - The fill computes no width of its own, and without one it runs serially. The cycle passes one on the verdict update's command line (`--standing-fill-jobs`, forwarded as the fill's `--jobs`). A hand run over the whole domain, such as the dont-bug-me-about-this-ever-again skill's final pass, passes the width the cycle's plan prints (`make artifact-cycle ARGS='--dry-run'`, the `verdict-update --standing-fill-jobs` line).
  - A pass with fewer misses than `_STANDING_POOL_THRESHOLD` starts no pool at any width. That covers the ordinary served pass and a pass that commits a rule reaching few units.
- The oracle (`run_m1.run_oracle`): one spawn process per row range of one configuration's subset table.
  - `oracle.oracle_shard_plan` cuts every table so that each worker in the pool gets an equal share of the total, with overlay rows weighted by `oracle.OVERLAY_ROW_COST`. The parent joins the ranges' audit segments, store segments, and settle-memo parts back in row order.
  - In `rebuild/tools/artifact_cycle.py`, `ORACLE_SHARD_BYTES` is what one range's worker holds: its interpreter and shaper, its own range's records from the configuration's row store, the configuration's settle memo, and its walk over the range. The memo is mapped read-only (`conform._MemoStore`), so its columns and probe index sit in the page cache once per machine however many workers map it; the worker's heap holds only the file's label and outcome tables, two bytes a row, and the windows the walk promotes or settles fresh. The walk is the largest term as measured, more than four times the whole mapping. The constant's comment has the staged measurements.
  - `sweep_job_budget` does the division, capped by the cores, after taking the settle-memo absorbs' excess (below) off the machine's memory. It is the `--jobs` the cycle passes to run_m1 and the default for a hand run.
  - `run_oracle` writes one `kind:"pool"` record per fan-out. The record has one reading per range, which the `oracle-shard` row of `make job-costs` reads, and one per configuration's part absorb, labeled `<config> absorb`, which the `oracle-absorb` row reads. The absorb runs on the same pool after every range has finished and the witness stage has returned. It holds the rows already in the settle memo file, the parts, and the index while it rewrites the file, so its cost follows the file, which grows with the alphabet, and not the width.
  - `ORACLE_ABSORB_BYTES` in `rebuild/tools/artifact_cycle.py` is what one absorb holds. At most one absorb per settlement configuration runs at once, so `sweep_job_budget` takes that many absorbs' excess over `ORACLE_SHARD_BYTES`, when there is one, off the machine's memory before it divides.
  - Each reading is the worker process's peak memory, so a range that ran second in a reused worker, or an absorb, reads at or above the range before it. Read the record for the pool as a whole, not for one range's cost.
- gate:conform's per-edit conformance sweep (`run_m1.run_font_conformance`): one spawn process per unit at `conform.SWEEP_MAX_LENGTH`, the same units as the deep sweep (`run_m1.sweep_units`): the ss10 overlay whole, and each settlement configuration once per alphabet symbol, over the texts that end in it. The pool runs one unit per process (`max_tasks_per_child=1`).
  - Each settlement unit maps its configuration's settle memo, writes the windows it settled fresh as a part, and returns the rows it reached. Once every unit has finished and the counts check, the parent ORs the reaches and, on the same pool, prunes each configuration's file to them and merges the parts (`conform.absorb_sweep_memo`), one absorb per configuration that has a part or an unreached row.
  - In `rebuild/tools/artifact_cycle.py`, `CONFORM_SWEEP_UNIT_BYTES` is what one unit or one configuration's absorb holds. The absorb that writes a dropped memo back from its units' parts is the largest of these and sets the constant. A unit holds chiefly the memo's tables and the dict of windows it settles fresh, which is empty with the memo current. The mapped file's clean pages sit in the page cache, outside the constant. The constant's comment has the measurements. `conform_job_budget` does the division, capped at the cores less the corpus build's parent and workers when the pass runs the build, and less gate:make-test's pool under `--rebuild-pool overlap`, the default, on a pass that runs that gate, but never below the acceptance-configuration count (`_conform_core_cap`). `run_m1._spawn_pool` caps it at the unit count.
  - The conformance sweep is submitted when run_m1's gate passes, so it starts beside the corpus build. A conformance sweep still running when the build finishes, or one the queue policy starts late behind gate:make-test, runs beside the verdict-update step instead. Before dividing, the cycle subtracts the larger of those two steps that the pass runs (`_conform_build_lane`): the build's parent and its `corpus_job_budget` workers, or the verdict update and its `standing_fill_jobs` refill pool. The land that follows them in the same lane (`LAND_BYTES` in `rebuild/tools/artifact_cycle.py`, three parsed verdict stores and the new corpus's ids in one process) holds less than either, which `test_the_land_holds_less_than_either_build_lane_step_before_it` checks, so the reservation covers it and no width depends on it. The land row of `make job-costs` checks the constant against the land step's peak. Under `--rebuild-pool overlap`, on a pass that runs gate:make-test, that gate's pool is subtracted too. A pass that runs neither step subtracts nothing for the build lane.
  - The cycle passes the width on gate:conform's argv at every value, including one, and `run_m1._spawn_pool` never starts more workers than its caller submits units.
  - A hand `run_m1 --conform-only` with no `--jobs` uses `conform_job_budget(skip_gates=True, skip_corpus=True)`, which assumes nothing else is running. A bare `run_m1` uses the oracle's `sweep_job_budget()`.
  - A pooled conformance sweep at its own maximum length writes one `conform-sweep` pool record with one observation per configuration, the highest peak footprint among its units as `run_m1._conformance_unit` returns them, and one per absorb, labeled `<config> absorb`. That record is the `conform-sweep` row of `make job-costs`. The serial conformance sweep and a deeper sweep write none.

In a table build that reads previous memos, the shared `default` memory holds two corpus-sized memos: the fresh `default` snapshot and the previous build's `default` memo, filtered at load to drop keys that name edited runes. The previous memo answers unaffected windows that the `default` enumeration does not add to its fresh snapshot, and `default`'s memo write, in line or beside the wave, does not release it. Each delta's own previous memo keeps only keys naming its unlocking runes and drops keys naming edited runes. Read-journal exclusions still apply to the kept entries at lookup and when writing. The aggregate and per-memo `shared_memo_hits` cache-stats lines show which retained shared memos answer windows (`fanout.rs` sets their lookup order), so the memory they cost can be weighed against how much they are used.

The kernel's table digest (`table_digest` in `rebuild/kernel-rs/src/artifacts.rs`) streams each section through `sha256::Sha256` and holds no copy of the message. The folded transitions and the sorted cells and provenance stay resident, so streaming the hash does not bound the fold's memory.

## Everything else

- The window packing behind the table build (`run_m1.Packing`) and the shipped-order walks (`run_m1.run_emitted_order`) are both sized by `run_m1._core_bound_threads`: one task per settlement configuration, capped at `usable_cores()`, with no constant and no override.
  - A packer holds a zlib stream and a copy buffer. A walk is one single-threaded crate process that holds the rules and the labels and streams the rows, with no engine and no memo. Neither holds anything the kernel's memory division accounts for.
  - `AMS_KERNEL_THREADS` narrows neither. It exists to keep the table build out of swap, so a build set to width one still packs and walks every configuration at once.
  - The walks are not narrowed for the oracle's pool either; "One gate at a time" describes that overlap.
- Font-suite workers (`FONT_SUITE_WORKER_BYTES` in the root `conftest.py`) are small enough that the core count limits the pool before memory does, so the root `conftest.py` resolves `-n auto` to `memory_budget.usable_cores()`: the cores this process may actually run on, counting the affinity mask and the cgroup CPU quota that `os.cpu_count()` ignores. The rebuild suite gets the same width because none of its tests reads a live artifact (`rebuild/conftest.py`'s audit guard enforces this), so no pytest run is budgeted for a heavier worker.
- The corpus build's ink-signature pool (`_resolve_signature_digests` in `rebuild/review/build.py`), which shapes the signature store's misses before the units phase.
  - A worker holds one comparator over the two fonts, and its resident set does not grow with the number of signatures it shapes, so cores limit this pool while memory limits the unit worker. `signature_job_budget` in `rebuild/tools/artifact_cycle.py` is the core count, with no memory division and not the corpus build's cap. Under a gated cycle nothing is subtracted for gate:make-test's pool, which shares those cores while both run.
  - The build computes no width of its own. The cycle passes `--signature-jobs`, which is independent of `--jobs`, so a machine where the pooled corpus build falls to one worker still shapes its signatures on every core. A hand run defaults to the same core count.
  - Below `_SIGNATURE_POOL_THRESHOLD` misses the phase runs serially at any width, so a pass with the signature store filled starts no pool. A pooled pass writes a `signature` pool record, the `signature-worker` row of `make job-costs`, which reports the observations and checks no constant.
- The corpus build's ink-signature store write (`_SignatureWrite` in `rebuild/review/build.py`), which runs on one thread during the units phase of a pooled build (`_RecomputeRunner.pooled`) and is joined in the cache phase.
  - It has no width and no constant. The thread starts only when the units phase is pooled, because only then is the parent idle in `wait`. The serial build writes inline at the same point, because a CPU-bound parent would compete with a thread instead of overlapping it. On both paths the store's entries are freed when the write finishes, so they overlap the pool only for the length of the write.
  - The corpus-build step, which `CORPUS_PARENT_BYTES` covers, reaches its peak at the load boundary, where the row columns and both signature tables sit beside the workload table. Each `[t] review.build` line carries `rss_gb=`, the step's peak so far, and `rss_now_gb=`, the phase's current resident set. On fully recomputed and cached passes alike, the load line's `rss_gb=` is already the step's peak, and its `rss_now_gb=` is the highest of any phase. The constant's comment has the readings.
- Under a cycle, gate:make-test's pool runs at the width the cycle sets (`make_test_pool_width` in `rebuild/tools/artifact_cycle.py`), passed to that one child through `PYTEST_XDIST_AUTO_NUM_WORKERS`, so the pool that runs is the pool the cycle reserved memory for. On a pass whose build lane runs (run_m1 or the corpus build) that width is the gate lane's share of the cores (`memory_budget.split_cores`), and on a pass that runs neither it is every core. It runs on the same passes the cycle reserves for: the plan and `make test`'s wrapper both decide to skip with one predicate (`make_test_skippable`), and a forced pass (`--fresh`, `--force-make-test`) passes `FORCE=1` to the wrapper.
- Under a cycle, gate:rebuild-contracts' pool runs beside the corpus build at the width `contracts_pool_width` in `rebuild/tools/artifact_cycle.py` computes: the cores, minus the build's parent and its `corpus_job_budget` workers on a pass that runs the build, minus gate:make-test's pool under `--rebuild-pool overlap`, the default, on a pass that runs that gate, floored at one. A pass with neither subtraction gives the suite every core. The cycle passes it to that one child through `PYTEST_XDIST_AUTO_NUM_WORKERS`. It is derived from `corpus_job_budget` instead of restating it, so the two widths cannot disagree. Beside a corpus build at its lane share the result is the gate lane's share under the queue policy and on a pass that skips gate:make-test, and one under the overlap policy on a pass that runs gate:make-test, where that gate's pool already holds the gate lane; `contracts_pool_width`'s docstring explains that trade-off, and the module docstring of `rebuild/tools/artifact_cycle.py` gives the reason for the default policy. A hand run still uses every core.
- The scoped-anchor review tool's pool (`_review_pool_width` in `tools/review_scoped_anchor_selectors.py`, run by `make review`): one worker process per family with suggestions, up to `--jobs`, which defaults to `usable_cores()`. The pool is core-bound: a worker is one scoped Senior build plus a HarfBuzz search, so on the fleet (`doc/fleet.md`) the cores limit it before memory does. No `REVIEW_WORKER_BYTES` exists, because it would never bind and the tool writes no pool record for `make job-costs` to check it against. `make test-and-review` runs this pool beside the font suite's, each sized to the whole machine, and no budget covers that overlap.
- `build_font`'s pool (`main` in `tools/build_font.py`, run by `make all`): half of `usable_cores()`, capped at the jobs it submits first (the non-Senior font builds and the Senior layout compile) and floored at one. It takes half because it often shares the machine: when the font suite's root `conftest.py` runs the build, pyright runs beside it, and `tools/build_check_html.py` runs the font suite in-process.
- The baseline extractor's shard pool (`_shard_workers_default` in `rebuild/baseline/extract.py`): `usable_cores()`. A worker's peak memory is unmeasured, so no constant divides the memory; the function's docstring names the `memory_budget.how_many_fit` form the width takes once it is measured. The width cannot change the extracted table.
- The `woff2` target in the `Makefile`: `xargs -P` at `usable_cores()`, one `woff2_compress` process per built OTF.
- The standing daemon (`rebuild/tools/standing_daemon.py`), which holds one review corpus and its font pair for the standing probe and the standing dry run, so that neither loads the corpus in each process.
  - Its width is one: `serve` exits 1 when another `serve` holds its lock (`lock_path`) or a daemon already answers at its socket, as the module docstring describes.
  - No constant budgets its memory, because no width would be computed from such a constant: its own width is one, and `corpus_job_budget` and `kernel_threads_budget` assume no daemon is running. Stop it before a cycle pass (`make standing-daemon-stop`). It also exits by itself once the corpus it holds is rebuilt.
  - One figure cannot describe its peak either: when it serves a pooled dry run, it is the refill pool's parent and holds at most one wave of chunks at a time, the pool width times `_STANDING_POOL_CHUNK` units (`rebuild/tools/standing_verdicts.py`). The pool width is at most the `--jobs` the client sends, so the daemon's peak grows with that `--jobs`.
  - The `peak rss` line it prints at exit, in `var/standing-daemon.log`, is the highest resident set the daemon process reached since `serve` started, so it reflects only the requests that daemon served. It covers the daemon process only, not its refill pool's workers.

## Overriding a width

For a one-off run, set an environment variable. Never edit the checked-in values.

- `PYTEST_XDIST_AUTO_NUM_WORKERS` sets any `-n auto` pool.
- `AMS_KERNEL_THREADS` sets the kernel fan-out, which is only the table build's delta wave.
- `AMS_REPLAY_THREADS` sets the string replay's width, `AMS_DEEP_REPLAY_THREADS` sets the deep replay's, and `AMS_DEEP_SWEEP_JOBS` sets the deep sweep's (`--jobs` on `make conform-deep` overrides it). `--replay-threads` on `run_m1` overrides `AMS_REPLAY_THREADS`, as `--kernel-threads` overrides `AMS_KERNEL_THREADS`.
- `AMS_TOTAL_MEMORY_BYTES` replaces the memory probe but not the policy, so a large machine can reproduce a small one's widths. A value that does not parse is ignored.
- `AMS_DEEP_REPLAY_MEMO_WINDOWS` sets the deep replay's memo limit, not a width. The width is still estimated at the checked-in limit (`DEEP_REPLAY_MEMO_WINDOWS`), so set `AMS_DEEP_REPLAY_THREADS` beside a larger limit.
- `AMS_DEEP_SWEEP_MEMO_WINDOWS` sets the deep sweep's window ceiling (`DEEP_SWEEP_MEMO_WINDOWS`). Unlike the deep replay's limit, it moves the width too, because each settlement unit is priced at the smaller of its bound and the ceiling.

A width set by one of the first three items replaces the memory-derived width, and no memory arithmetic narrows it. A kernel or string-replay width set this way is still capped at the configuration count and the cores, as a derived width is, and a deep-sweep or deep-replay width at the unit count. Of the pools sized by the cores alone, the window packing and the shipped-order walks (`run_m1._core_bound_threads`), `build_font`'s pool, and the `woff2` target's `xargs -P` take no override; the corpus build's ink-signature pool, the scoped-anchor review tool's pool, and the baseline extractor's shard pool take a command-line flag instead (`--signature-jobs`, `--jobs`, `--workers`).

## One gate at a time

Widths are computed from total memory, never from free memory, so a gate started while another is running does not see it. Neither sees a standing daemon holding a corpus, which is why the daemon is stopped before a pass. Two gates started together each size themselves to the whole machine and slow each other through paging or CPU contention. The artifact cycle runs its build steps one after another. While its build lane runs, it splits the cores between the build lane and the gate lane (`memory_budget.split_cores`): the corpus build's parent and workers hold the build lane's share (its cap is that share less the parent), and gate:make-test's pool is the gate lane's share, so the two lanes' longest-running pools never book the same core. Memory is not split: before dividing for a pool, the cycle subtracts the memory of every pool it budgets beside that one. On a pass that runs gate:make-test, that gate's pool comes off before dividing for the table build's delta wave, the string replay, the corpus build, and the standing fill's refill pool. Before dividing for the conformance sweep, the larger build-lane step comes off, plus gate:make-test's pool under the default overlap policy on a pass that runs that gate. Nothing does this across independent processes. A workflow that runs agents in parallel therefore runs its gates in a single serialized stage, after every agent's edits are made, instead of having each agent run the gates on its own work.

Inside a cycle, some overlaps are not budgeted. Each case below is a brief, documented overuse of cores or memory:

- The standing fill's refill pool runs inside the verdict-update step, which starts beside gate:rebuild-contracts and may overlap gate:make-test and gate:conform's sweep. Its width subtracts gate:make-test's bytes but not its cores, so the refill pool oversubscribes the cores beside that pool while both run. It leaves the conformance sweep out: the conformance sweep's width subtracts the verdict-update step's memory (`_conform_build_lane`) but not its cores (`_conform_core_cap`), so on such a pass the two pools briefly oversubscribe the cores. It leaves the contracts pool's memory out, because no constant measures a rebuild-suite worker (`calibrate_budgets.UNITS` records that position); the cores limit that pool (`contracts_pool_width`), and its bytes come out of the reserve. The overuse happens on a pass that drops the standing-fill memo.
- Inside the run_m1 step, the table-only branch (the string replay, the witness stage, and the shipped-order walks) runs beside the glyph chain. The oracle's pool starts as soon as the string replay has returned, by which time the replay's crate has exited (`run_m1.TableGates.wait_for_replay`), and the oracle holds its own settle-memo writes until the witness stage's writes are done. The witness stage and the shipped-order walks can therefore still be running when the oracle's pool starts. The witness stage is one thread of run_m1's parent plus the `settle-cases` crate it spawns one wave at a time, and the walks run one per configuration up to the cores (`run_m1._core_bound_threads`). Both share the machine with the oracle's pool for the rest of their run. The witness stage is already one serial walk. Narrowing the walks to the cores the pool leaves would serialize them, because the pool takes the whole machine, and would put their whole duration on the run's critical path. What either holds is far below the replay's memory estimate.
- Inside the run_m1 step, the oracle's pool runs at the width `sweep_job_budget` computes, capped at every core rather than at the build lane's share, and on a pass that runs gate:make-test it shares the cores with that gate's pool, at the gate lane's share, for as long as both run. Its width subtracts neither that pool's cores nor its bytes, which fit inside the reserve; the budget's docstring gives the reasons.
- The packers run beside the string replay crate, the witness stage, the walks, and the glyph chain, and the walkers run beside the replay crate and the witness stage. On a rune edit, whose narrowed replay returns during the glyph chain, both also run beside the oracle's pool. On a machine whose memory-derived width is below the configuration count, these two phases keep more threads busy than the kernel's width. Every task in either pool holds a small working set that does not grow, and both phases are off the run's critical path, which runs through the kernel, the longer of the replay and the glyph chain, and the oracle.
- Under a gated cycle the corpus build's ink-signature pool runs at the core count, and on a pass that runs gate:make-test it shares those cores with that gate's pool for as long as both run. On a pass that runs gate:conform, the conformance sweep starts with the corpus build unless the queue policy holds it behind a still-running gate:make-test. When it starts with the build, the signature pool, which runs in the build's load phase, overlaps the sweep for its first minute or two. The conformance sweep's cap takes the build's parent and workers off the cores (`_conform_core_cap`) only where the cores left reach the acceptance-configuration count, and it never takes the signature pool off, which runs at the core count in the build's load phase, so a pass with the signature store dropped briefly overuses the cores. Under the default overlap policy, gate:rebuild-contracts' pool starts with the sweep and overlaps the signature pool too; `contracts_pool_width` subtracts the build's parent and workers but not the signature pool. The 18-core machine's `--fresh` passes, timed under both policies, drop the signature store and run gate:make-test, which finishes there before run_m1 does, so under either policy the sweep and the suite start beside the build, and the build lane ends the pass (bare `make cycle-timings` lists those passes step by step). On a pass whose build lane ends last the contention can lengthen the pass, and the signature pool saves less time there. If such a pass that drops the signature store shows a corpus-build row measurably longer under the overlap policy than under the queue policy (`ARGS='--inner'` shows the load and units phases), revisit these widths.
- Where the cores the corpus build leaves fall short of the acceptance-configuration count, the conformance sweep's cap is that count (`_conform_core_cap`), so the sweep's processes run beside the build's parent and workers and oversubscribe the cores for as long as the two overlap. A build at its lane share leaves the gate lane's share, which on the 12-core machine (`doc/fleet.md`) equals that count, so under the queue policy the floor binds on no fleet machine. Under the overlap policy, on a pass that runs gate:make-test, that gate's pool holds the whole gate lane, so there the floor binds on every machine; the Lane conform line of the cycle's plan says which cap bound. The floor keeps the sweep at one process per configuration, so a cycle never runs it narrower than the configuration count.
- The contracts pool beside the corpus build runs on every full pass, at the process count `contracts_pool_width` computes, and its pytest controller is one more process, which no width subtracts.
- Under the default overlap policy, gate:conform's sweep and gate:rebuild-contracts' pool both start when the run_m1 gate passes, and the suite's width and the sweep's core cap are both the cores the corpus build and, on a pass that runs it, gate:make-test's pool leave, each with its own floor (`contracts_pool_width`, `_conform_core_cap`); neither subtracts the other. On a pass that runs both, the two pools oversubscribe those cores while they overlap, and where the sweep's floor binds, its processes run beside the suite's as well as the build's. Each pool runs longer than it would alone. Beside a corpus build at its lane share, on a pass that runs gate:make-test, the subtraction of that gate's pool leaves the suite its floor of one worker and the sweep its floor, whether or not that pool is still running when they start. On the `--fresh` passes behind the default, both pools finished before the build lane, which ended the pass, so neither their slowdown nor the suite's single worker lengthened it. An overlap-policy pass with gate:make-test's pool at the gate lane's share (its run line's `plan.make_test_workers`) that a `gate:` step ends is the signal to revisit these widths; in `make cycle-timings ARGS='--critical-path'`, whose row for a pass shape also counts passes run at other gate:make-test widths, it shows as growth in a `gate:` step's count in the ended-last tally. `contracts_pool_width`'s docstring gives the reasons for what the two widths subtract, the module docstring of `rebuild/tools/artifact_cycle.py` gives the reason the overlap policy is the default and the passes that reason rests on, and `make cycle-timings` on the 18-core machine records the whole-pass times. `make artifact-cycle ARGS='--dry-run'` prints both widths.
- A hand `make test-rebuild` whose pyright closure has changed runs pyright beside the full-width pool (`rebuild/tools/pyright_gate.py`, joined by the root `conftest.py` at session end). That is one process using about one core while it runs beside the pool (about a core and a half on an idle machine), which no constant accounts for, since nothing accounts for a rebuild-suite worker either. The cycle's contracts spawn sets no `AMS_RUN_PYRIGHT`, so a cycle pass never runs pyright there.

## Measuring

- `make cycle-timings` summarizes what each step costs, tagged by host; `ARGS='--by-step'` compares step medians across machines. Read it before deciding a run is hung and before choosing a watcher's timeout.
  - The `gate:rebuild-contracts` row mixes widths. `contracts_pool_width` subtracts the corpus build's processes on a pass that runs the build, and gate:make-test's pool under the overlap policy on a pass that runs that gate, so a pass's width is every core, what one of those subtractions leaves, or the floor of one where both together, or gate:make-test's pool alone on a pass with no build lane, hold every core. The row's median therefore moves with the mix of passes, which is expected.
  - Each pass's width is `contracts_workers` in its run line's plan block, beside the width of every other pooled step (`artifact_cycle.cycle_summary_payload` writes the block), each null for a step the pass skipped; the block's `kernel_threads`, `overlap_memo_writes` and `replay_threads` are null only on a gates-only rerun. A run line whose plan block lacks the field has only the `kind:"pool"` record with unit `rebuild-contracts` that the pass's pytest controller writes; that record has no run id, so match it to the pass's step row by host and `finished_at`.
- `make cycle-timings ARGS='--critical-path'` shows which step ended each pass, per host, pool policy and pass shape (which of run_m1, the corpus build and gate:make-test ran): how often each step ended last, the median margin by which the lane that ended the pass outlasted the other lane, the median wall, and the median gate:make-test width. The gate lane is the `gate:` steps and the build lane every other step, so a pass whose build lane ends last names that lane's closing step, which is review-facts on every pass but a staging one. The view computes each pass's timeline from its step rows, so it covers every finished pass whose run line carries its start stamp, including one whose plan block lacks the widths, where only the width reads `unrecorded`. An interrupted pass is left out, and so is the job-costs step, which runs once every lane has joined.
- `make job-costs` prints each checked-in per-unit constant beside what this host measured and the width each implies. `ARGS='--check'` exits nonzero when an observed peak exceeds its constant. The artifact cycle runs that form on every pass without failing the pass on it, and its OVERRUN status quotes the tripped row's proposal. To accept a new measurement, re-measure the constant and commit it.
  - Each checked constant's comment but `TABLE_BUILD_PEAK_BYTES`'s states the rule that sets it from its highest reading, a headroom to multiply it by (none for `FONT_SUITE_WORKER_BYTES`) and a multiple to round up to, and the unit's `headroom` and `quantum` in `rebuild/tools/calibrate_budgets.py` restate it. When the highest reading put through that rule comes out above the constant, the row prints that raised value and the width it gives here, and under `ARGS='--host all'` the width on each host in the window; before any peak exceeds the constant the line is marked as headroom used. The tool only proposes raises and writes nothing. The kernel-build row proposes no value and names the kernel constants to re-measure instead, and it reads every record since its constant's commit rather than the newest `--recent`.
- The kernel's `--cache-stats` flag on `enumerate`, `enumerate-configs`, `build-tables`, and `replay-strings` prints what each memo holds per configuration. On a table build, `shared_memo_hits` beside `trace_cache` shows how many windows a delta or a build reading previous memos took from a shared memo against how many it traced itself. On the replay, the walk's own memo and tables beside the engine's memos show how the walk's peak divides between the two. Use it for any memory argument about the kernel.

## Writing code against these limits

The Python and Rust here run against hard limits with no spare headroom. A routine that holds a little more per unit raises a per-unit peak, which narrows a fan-out, which lengthens every later cycle. A routine that is correct and simple but materially raises a peak is not finished.

- Think about the working set before the algorithm: what the code holds live at its peak, for how long, and whether that is the whole corpus, one configuration, one unit, or one row. Stream instead of materializing a list. Release a large structure after its last reader, not at function exit. Prefer one pass that folds everything over several passes that each re-read the input.
- Estimate the cost of the most frequently run code at the scale it runs at. A cost that is negligible per call dominates the build when the call runs per window, per candidate, or per row. Move invariant work out of the loop, memoize on the key the caller actually varies, and avoid intermediate strings, dicts, or `Vec`s that the next line only takes apart.
- In Python, prefer idioms that run in C: comprehensions, `dict` and `set` lookups, `bytes` and `memoryview`, tuple keys, and the standard library's compiled paths. When a Python pass is still the bottleneck, the fix is usually to move it into the crate, not to write a cleverer loop.
- In Rust, pay as much attention to allocation and cloning as to asymptotics: borrow instead of calling `.clone()`, size a `Vec` or map up front when the count is known, keep per-entry structures flat, and chain iterators instead of collecting between stages.
- A change that moves a per-unit peak revises the `*_BYTES` constant, and the comment or docstring that justifies it, at the same call site, because nothing else checks the widths derived from it. `make job-costs` computes the proposed value once the readings have used a constant's headroom, and the person still revises the constant and its comment or docstring at the call site. Measure a performance change before relying on it. When two versions perform the same, choose the clearer one.
