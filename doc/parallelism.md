# Parallelism and memory budgets

Every fan-out width in this repository is computed from the machine it runs on: total physical memory, clamped by any cgroup limit, minus a reserve, divided by a measured per-unit peak, capped by any non-memory bound, and floored at one. `rebuild/tools/memory_budget.py` implements that arithmetic and documents the policy, including why the budget never reads free or available memory. Each per-unit cost is a named `*_BYTES` constant at the call site that uses it, and the comment or docstring there records the measurements behind it and explains the width it implies, so a number and its justification stay in one file. `doc/fleet.md` lists the machines and is the key for reading host-tagged output.

## The memory-bound fan-outs

Each fan-out below defines its per-unit cost where its width is computed.

- The kernel's table build: one `build-tables` process over every settlement configuration (`conform.SETTLEMENT_CONFIGS`; the ss10 overlay settles and enumerates nothing).
  - `default` enumerates first and alone, writes its memo file, and keeps its trace memo. Because that write runs before the delta wave, the `memo[default]` timing line is time the wave waits for, and the rows the writer holds are never resident beside a delta at its peak.
  - The other configurations then run as deltas over that memo, `--threads` at a time, heaviest first by unlocking-rune count (`fanout::delta_worklist` in the crate). `default`'s own fold takes one of the `--threads` slots. Each delta writes its own memo file when its enumeration finishes and holds no memo through its drain, sort, or fold.
  - The width has two terms, both constants in `rebuild/pipeline/kernel_exec.py`. `DEFAULT_MEMO_BYTES` is subtracted from the machine's memory before the division: the fresh `default` memo snapshot that stays alive for the wave, plus the filtered previous-build `default` seed when one is present. `DELTA_PEAK_BYTES` is the divisor: one delta, bounded by a configuration enumerated from scratch and held through its memo write.
  - The two are chosen together so that the 48 GiB machine runs the whole delta wave in one round, alone and under a gated cycle, and the 32 GiB machine runs one fewer than the delta count at once, in either case. On the 48 GiB machine the width exceeds the delta count, so `default`'s fold uses a slot the deltas would have left idle, and every delta and `default`'s fold are resident at once.
  - `TABLE_BUILD_PEAK_BYTES` is the peak of the whole process those two terms bound; `make job-costs` compares the run_m1 step against it.
  - `kernel_threads_default` computes the width for a bare `run_m1` (`KERNEL_THREADS_DEFAULT`). `kernel_threads_budget` in `rebuild/tools/artifact_cycle.py` computes a cycle's width and also subtracts gate:make-test's pytest pool before the division. `run_m1._table_build_threads` caps either at the configuration count and the cores. The cycle's budget applies the same cap itself, as `replay_threads_budget` does, so the plan line and the argv show the width the wave runs at.
  - The window packing behind the build and the shipped-order walks on the same branch are sized by the cores, not by this width; see "Everything else".
- The string replay that follows the table build (`run_m1.run_replay_strings`, on run_m1's table-only branch): one crate process over every settlement configuration at horizon 4.
  - `REPLAY_PEAK_BYTES` in `rebuild/pipeline/kernel_exec.py` is what one configuration's walk holds: the trace memo over the windows the string universe's texts reach, plus the window memo's inverse label map and block buffer. The constant's comment has the measurements.
  - Nothing is subtracted before the division, because the replay's engines are built after the table build's process has exited and none of its memos survive.
  - `replay_threads_default` divides the machine's memory by it for a bare `run_m1`. `replay_threads_budget` in `rebuild/tools/artifact_cycle.py` computes a cycle's width after subtracting gate:make-test's pytest pool. `run_m1._replay_threads` caps either at the configuration count and the cores, and the cycle's budget applies the same cap, as the kernel's does. The constant is chosen so both fleet machines replay every configuration in one wave.
  - After a whole-universe walk, the settle-memo absorbs (`run_m1._absorb_replay_memo`, one spawn process per walked configuration, each holding one configuration's dump, columns, and probe index) run at the same width once the crate has exited, because each holds a fraction of `REPLAY_PEAK_BYTES`.
- The deep replay (`make replay-deep`, `rebuild/tools/deep_replay.py`): one crate process over every settlement configuration at horizon 5.
  - Each configuration's walk holds at most `DEEP_REPLAY_MEMO_WINDOWS` windows in its walk memo. Before any text that could push the memo past that limit, the walk releases the walk memo and its engine's memos (the crate's `--memo-windows`). What a walk holds therefore does not grow with the corpus, apart from the settled records and labels it keeps, which grow with the number of distinct records.
  - `DEEP_REPLAY_PEAK_BYTES` in that module is the peak at that limit, and `replay_threads` divides the machine's memory by it, capped at the configuration count. `AMS_DEEP_REPLAY_THREADS` sets a width instead.
  - A memo limit set above the checked-in one has no memory estimate, so set `AMS_DEEP_REPLAY_THREADS` with it.
- The review-surface build, in `rebuild/tools/artifact_cycle.py`.
  - `SURFACE_PARENT_BYTES` is the parent process. It holds the whole corpus at any width, as columns over the unit's ordinal (`audit.UnitTable` and `unit_store.UnitStore` in `rebuild/review/`), and materializes a unit as a record only for the reader that needs one. It is subtracted before the division.
  - `SURFACE_WORKER_BYTES` is what one worker holds, `SURFACE_JOBS_CAP` is the width past which the build stops scaling, and `surface_job_budget` does the division.
  - A machine the pooled build does not fit gets width one, which is the serial build.
- The standing fill's refill pool (`_prefill` in `rebuild/tools/standing_verdicts.py`), which decides across a spawn pool the units the memo cannot serve: every unit when the memo was dropped, or the units a changed standing rule can reach.
  - A worker holds its interpreter, a `SlideContext` over the surface's font pair, and one chunk of units with that chunk's memos, which it releases after each chunk.
  - The parent, the verdict chain, keeps ids, decisions, and memo entries, writes pool misses to a temporary gzipped spool, and submits at most one wave of chunks (the pool width times `_STANDING_POOL_CHUNK` units) at a time. Its memory grows with ids and decisions, not with the full human corpus; the docstrings of `_prefill` and `rebuild/tools/verdict_chain.py` have the details. The standing daemon holds its own surface outside this budget.
  - In `rebuild/tools/artifact_cycle.py`, `STANDING_FILL_PARENT_BYTES` is the chain parent and is subtracted before the division, `STANDING_FILL_WORKER_BYTES` is what one worker holds, and `standing_fill_jobs` does the division, capped by the cores.
  - The fill computes no width of its own, and without one it runs serially. The cycle passes one on the chain's command line (`--standing-fill-jobs`, forwarded as the fill's `--jobs`). A hand run over the whole domain, such as the dont-bug-me-about-this-ever-again skill's final pass, passes the width the cycle's plan prints (`make artifact-cycle ARGS='--dry-run'`, the `plumbing --standing-fill-jobs` line).
  - A pass with fewer misses than `_STANDING_POOL_THRESHOLD` starts no pool at any width. That covers the ordinary served pass and a pass that commits a rule reaching few units.
- The oracle (`run_m1.run_oracle`): one spawn process per row range of one configuration's subset table.
  - `oracle.oracle_shard_plan` cuts every table so that each worker in the pool gets an equal share of the total, with overlay rows weighted by `oracle.OVERLAY_ROW_COST`. The parent joins the ranges' audit segments, store segments, and settle-memo parts back in row order.
  - In `rebuild/tools/artifact_cycle.py`, `ORACLE_SHARD_BYTES` is what one range's worker holds: its interpreter and shaper, its own range's records from the configuration's row store, the configuration's settle memo, and its walk over the range. The memo is mapped read-only (`conform._MemoStore`), so its columns and probe index sit in the page cache once per machine however many workers map it; the worker's heap holds only the file's label and outcome tables, two bytes a row, and the windows the walk promotes or settles fresh. The walk is the largest term as measured, more than four times the whole mapping. The constant's comment has the staged measurements.
  - `sweep_job_budget` does the division, capped by the cores. It is the `--jobs` the cycle passes to run_m1 and the default for a hand run.
  - `run_oracle` writes one `kind:"pool"` record per fan-out, which is the `oracle-shard` row of `make job-costs`. The record has one reading per range and one per configuration's part absorb, labeled `<config> absorb`. The absorb runs on the same pool after every range has finished and the witness stage has returned. It holds the rows already in the settle memo file, the parts, and the index while it rewrites the file.
  - Each reading is the worker process's peak memory, so a range that ran second in a reused worker, or an absorb, reads at or above the range before it. Read the record for the pool as a whole, not for one range's cost.
- gate:conform's belt, the per-edit conformance sweep (`run_m1.run_font_conformance`): one spawn process per acceptance configuration (`conform.ACCEPTANCE_CONFIGS`), each sweeping its configuration at `conform.BELT_HORIZON`.
  - In `rebuild/tools/artifact_cycle.py`, `CONFORM_BELT_BYTES` is what one worker holds: chiefly the pages of its configuration's settle memo, mapped read-only, that its probes touch, and the dict of windows its walk settles fresh, which is empty on a warm memo and holds every window on a cold one. The constant's comment has the measurements. `conform_job_budget` does the division, capped at the acceptance configurations and the cores.
  - The belt is submitted when run_m1's gate passes, so it starts beside the surface build. A belt still running when the build finishes, or one the queue policy starts late behind gate:make-test, runs beside the plumbing step instead. Before dividing, the cycle subtracts the larger of those two steps that the pass runs (`_conform_build_lane`): the build's parent and its `surface_job_budget` workers, or the chain parent and its `standing_fill_jobs` refill pool. Under `--rebuild-pool overlap`, gate:make-test's pool is subtracted too. A pass that runs neither step subtracts nothing for the build lane.
  - The cycle passes the width on gate:conform's argv at every value, including one, and `run_m1._spawn_pool` never starts more workers than its caller submits tasks.
  - A hand `run_m1 --conform-only` with no `--jobs` uses `conform_job_budget(skip_gates=True, skip_surface=True)`, which assumes nothing else is running. A bare `run_m1` uses the oracle's `sweep_job_budget()`.
  - A pooled belt at its own horizon writes one `conform-belt` pool record with one observation per configuration, each worker's peak returned to the parent by `run_m1._priced_conformance_config`. That record is the `conform-belt` row of `make job-costs`. The serial belt and a deeper sweep write none.
- The standing daemon (`rebuild/tools/standing_daemon.py`), which holds one review surface and its font pair for the standing probe and the standing dry run, so that neither loads the surface in each process.
  - `STANDING_DAEMON_BYTES` there is what that one process holds. `serve` computes `describe_fit(…, cap=1)` at startup, and the width is one because `serve` refuses to start beside a daemon that already responds.
  - No cycle width subtracts it: `surface_job_budget` and `kernel_threads_budget` assume no daemon is running. Stop the daemon before a cycle pass (`make standing-daemon-stop`). It also exits by itself once the surface it holds is rebuilt.

In a seeded table build, the shared `default` memory holds two corpus-sized memos: the fresh `default` snapshot and the previous build's `default` memo, filtered at load to drop keys that name edited runes. The previous memo answers unaffected windows that the seeded `default` enumeration does not add to its fresh snapshot, and `default`'s memo write inside `enumerate_for_tables` does not release it. Each delta's own previous seed keeps only keys naming its unlocking runes and drops keys naming edited runes. Read-journal exclusions still apply to the kept entries at lookup and when writing. The aggregate and per-seat `memo_base_hits` census lines show which retained bases answer windows (`fanout.rs` sets their lookup order), so the memory they cost can be weighed against how much they are used.

The kernel's table digest (`table_digest` in `rebuild/kernel-rs/src/artifacts.rs`) streams each section through `sha256::Sha256` and holds no copy of the message. The folded transitions and the sorted cells and provenance stay resident, so streaming the hash does not bound the fold's memory.

## Everything else

- The window packing behind the table build (`run_m1.Packing`) and the shipped-order walks (`run_m1.run_emitted_order`) are both sized by `run_m1._core_bound_threads`: one task per settlement configuration, capped at `usable_cores()`, with no constant and no override.
  - A packer holds a zlib stream and a copy buffer. A walk is one single-threaded crate process that holds the rules and the labels and streams the rows, with no engine and no memo. Neither holds anything the kernel's memory division accounts for.
  - `AMS_KERNEL_THREADS` narrows neither. It exists to keep the table build out of swap, so a build set to width one still packs and walks every configuration at once.
  - The walks are not narrowed for the oracle's pool either; "One gate at a time" describes that overlap.
- Font-suite workers (`FONT_SUITE_WORKER_BYTES` in the root `conftest.py`) are small enough that the core count limits the pool before memory does, so the root `conftest.py` resolves `-n auto` to `memory_budget.usable_cores()`: the cores this process may actually run on, counting the affinity mask and the cgroup CPU quota that `os.cpu_count()` ignores. The rebuild suite gets the same width because none of its tests reads a live artifact (`rebuild/conftest.py`'s audit guard enforces this), so no pytest run is budgeted for a heavier worker.
- The surface build's ink-signature pool (`_resolve_signature_digests` in `rebuild/review/build.py`), which shapes the signature store's misses before the units phase.
  - A worker holds one comparator over the two fonts, and its resident set does not grow with the number of signatures it shapes, so cores limit this pool while memory limits the unit worker. `signature_job_budget` in `rebuild/tools/artifact_cycle.py` is the core count, minus gate:make-test's two cores under a gated cycle, with no memory division and no `SURFACE_JOBS_CAP`.
  - The build computes no width of its own. The cycle passes `--signature-jobs`, which is independent of `--jobs`, so a machine where the pooled surface build falls to one worker still shapes its signatures on every core. A hand run defaults to the core count with nothing subtracted.
  - Below `_SIGNATURE_POOL_THRESHOLD` misses the phase runs serially at any width, so a warm store starts no pool. A pooled pass writes a `signature` pool record, the `signature-worker` row of `make job-costs`, which reports the observations and checks no constant.
- The surface build's ink-signature store write (`_SignatureWrite` in `rebuild/review/build.py`), which runs on one thread during the units phase of a pooled build (`_FreshRunner.pooled`) and is joined in the cache phase.
  - It has no width and no constant. The thread starts only when the units phase is pooled, because only then is the parent idle in `wait`. The serial build writes inline at the same point, because a CPU-bound parent would compete with a thread instead of overlapping it. On both paths the store's entries are freed when the write finishes, so they overlap the pool only for the length of the write.
  - The surface-build step, which `SURFACE_PARENT_BYTES` covers, reaches its peak at the load boundary, where the row columns and both signature tables sit beside the workload table. Each `[t] review.build` line carries `rss_gb=`, the step's peak so far, and `rss_now_gb=`, the phase's current resident set. On full-fresh and served passes alike, the load line's `rss_gb=` is already the step's peak, and its `rss_now_gb=` is the highest of any phase. The constant's comment has the readings.
- `make test-rebuild-slow` sets a narrow width in the Makefile instead of deriving one. Every worker collects the whole suite before the slow marker deselects nearly all of it, so a worker slot the selection cannot fill costs a full collection and gains nothing.
- Under a cycle, gate:make-test's pool runs at the width the cycle sets (`make_test_pool_width` and `MAKE_TEST_POOL_WORKERS` in `rebuild/tools/artifact_cycle.py`), passed to that one child through `PYTEST_XDIST_AUTO_NUM_WORKERS`, so the pool that runs is the pool the cycle reserved memory for. It runs on the same passes the cycle reserves for: the plan and `make test`'s wrapper both decide to skip with one predicate (`make_test_skippable`), and a forced pass (`--fresh`, `--force-make-test`) passes `FORCE=1` to the wrapper.
- Under a cycle, gate:rebuild-contracts' pool runs beside the surface build at the width `contracts_pool_width` in `rebuild/tools/artifact_cycle.py` computes: the cores, minus the build's parent and its `surface_job_budget` workers, minus gate:make-test's pool under `--rebuild-pool overlap`, floored at one, and every core on a pass whose surface build does not run. The cycle passes it to that one child through `PYTEST_XDIST_AUTO_NUM_WORKERS`. It is derived from `surface_job_budget` instead of restating it, so the two widths cannot disagree. On a ten-core machine beside a surface build at `SURFACE_JOBS_CAP` the result is one; `contracts_pool_width`'s docstring explains that trade-off. A hand run still uses every core.

## Overriding a width

For a one-off run, set an environment variable. Never edit the checked-in values.

- `PYTEST_XDIST_AUTO_NUM_WORKERS` sets any `-n auto` pool.
- `AMS_KERNEL_THREADS` sets the kernel fan-out, which is only the table build's delta wave.
- `AMS_REPLAY_THREADS` sets the string replay's width, and `AMS_DEEP_REPLAY_THREADS` sets the deep replay's. `--replay-threads` on `run_m1` overrides `AMS_REPLAY_THREADS`, as `--kernel-threads` overrides `AMS_KERNEL_THREADS`.
- `AMS_TOTAL_MEMORY_BYTES` replaces the memory probe but not the policy, so a large machine can reproduce a small one's widths. A value that does not parse is ignored.
- `AMS_DEEP_REPLAY_MEMO_WINDOWS` sets the deep replay's memo limit, not a width. The width is still estimated at the checked-in limit (`DEEP_REPLAY_MEMO_WINDOWS`), so set `AMS_DEEP_REPLAY_THREADS` beside a larger limit.

A width set by one of the first three items replaces the memory-derived width, and no memory arithmetic narrows it. A kernel or string-replay width set this way is still capped at the configuration count and the cores, as a derived width is. The two pools sized by the cores alone, the window packing and the shipped-order walks (`run_m1._core_bound_threads`), take no override.

## One gate at a time

Widths are computed from total memory, never from free memory, so a gate started while another is running does not see it. Neither sees a standing daemon holding a surface (`STANDING_DAEMON_BYTES`), which is why the daemon is stopped before a pass. Two gates started together each size themselves to the whole machine and slow each other through paging or CPU contention. The artifact cycle serializes its own steps and subtracts the steps that overlap: gate:make-test's pool before dividing for the kernel, and the larger build-lane step before dividing for the belt. Nothing does this across independent processes. A workflow that runs agents in parallel therefore runs its gates in a single serialized stage, after every agent's edits are made, instead of having each agent run the gates on its own work.

Inside a cycle, some overlaps are not budgeted. Each case below is a brief, documented overuse of cores or memory:

- The standing fill's refill pool runs inside the plumbing step, which starts beside gate:rebuild-contracts and may overlap gate:make-test and gate:conform's belt. Its width subtracts gate:make-test's pool, both bytes and cores. It leaves the belt out, because the belt's own width subtracts the plumbing step. It leaves the contracts pool's memory out, because no constant measures a rebuild-suite worker (`calibrate_budgets.UNITS` records that position); the cores limit that pool (`contracts_pool_width`), and its bytes come out of the reserve. The overuse happens on a pass that drops the standing-fill memo.
- Inside the run_m1 step, the table-only branch (the string replay, the witness stage, and the shipped-order walks) runs beside the glyph chain. The oracle's pool starts as soon as the string replay has returned, by which time the replay's crate has exited (`run_m1.TableGates.wait_for_replay`), and the oracle holds its own settle-memo writes until the witness stage's writes are done. The witness stage and the shipped-order walks can therefore still be running when the oracle's pool starts. The witness stage is one thread of run_m1's parent plus the `settle-cases` crate it spawns one wave at a time, and the walks run one per configuration up to the cores (`run_m1._core_bound_threads`). Both share the machine with the oracle's pool for the rest of their run. The witness stage is already one serial walk. Narrowing the walks to the cores the pool leaves would serialize them, because the pool takes the whole machine, and would put their whole duration on the run's critical path. What either holds is far below the replay's memory estimate.
- The packers run beside the string replay crate, the witness stage, the walks, and the glyph chain, and the walkers run beside the replay crate and the witness stage. On a rune edit, whose narrowed replay returns during the glyph chain, both also run beside the oracle's pool. On a machine whose memory-derived width is below the configuration count, these two phases keep more threads busy than the kernel's width. Every task in either pool holds a small working set that does not grow, and both phases are off the run's critical path, which runs through the kernel, the longer of the replay and the glyph chain, and the oracle.
- Under a gated cycle the surface build's ink-signature pool runs at the core count. On a pass that runs gate:conform, the signature pool and the belt start at the same moment and overlap for the first minute or two. The belt runs at the width `conform_job_budget` computed with the build subtracted, but that budget divides bytes and does not count either pool's cores against the other's, so a cold-store pass briefly overuses the cores. The overlap is off the critical path: gate:rebuild-contracts is queued behind conform under the default policy and runs beside the build only on the cores the build leaves. The signature pool saves less time on such a pass. If the conform row in `make cycle-timings` grows measurably, revisit these widths.
- The contracts pool beside the surface build runs on every full pass, at the process count `contracts_pool_width` computes; its pytest controller is the one process over the core count.
- A hand `make test-rebuild` whose pyright closure has changed runs pyright beside the full-width pool (`rebuild/tools/pyright_gate.py`, joined by the root `conftest.py` at session end). That is one process using roughly a core and a half while it runs, which no constant accounts for, since nothing accounts for a rebuild-suite worker either. The cycle's contracts spawn sets no `AMS_RUN_PYRIGHT`, so a cycle pass never runs pyright there.

## Measuring

- `make cycle-timings` summarizes what each step costs, tagged by host; `ARGS='--by-step'` compares step medians across machines. Read it before deciding a run is hung and before choosing a watcher's timeout.
  - The `gate:rebuild-contracts` row mixes two widths: `contracts_pool_width`'s narrow width on a pass that runs the surface build, and its wide width on a pass that does not. The row's median therefore rises as narrow passes accumulate, which is expected.
  - Each pass's width is on the `kind:"pool"` record with unit `rebuild-contracts` that its pytest controller writes. That record has no run id; match it to the pass's step row by host and `finished_at`.
- `make job-costs` prints each checked-in per-unit constant beside what this host measured and the width each implies. `ARGS='--check'` exits nonzero when an observed peak exceeds its constant. The artifact cycle runs that form on every pass without failing the pass on it. To accept a new measurement, re-seed the constant and commit it.
- The kernel's `--cache-census` flag on `enumerate`, `enumerate-configs`, `build-tables`, and `replay-strings` prints what each memo holds per configuration. On a table build, `memo_base_hits` beside `trace_cache` shows how many windows a delta or a seeded build took from a base against how many it traced itself. On the replay, the walk's own memo and tables beside the engine's memos show how the walk's peak divides between the two. Use it for any memory argument about the kernel.

## Writing code against these limits

The Python and Rust here run against hard limits with no spare headroom. A routine that holds a little more per unit raises a per-unit peak, which narrows a fan-out, which lengthens every later cycle. A routine that is correct and simple but materially raises a peak is not finished.

- Think about the working set before the algorithm: what the code holds live at its peak, for how long, and whether that is the whole corpus, one configuration, one unit, or one row. Stream instead of materializing a list. Release a large structure after its last reader, not at function exit. Prefer one pass that folds everything over several passes that each re-read the input.
- Estimate the hot path's cost at the scale it runs at. A cost that is negligible per call dominates the build when the call runs per window, per candidate, or per row. Move invariant work out of the loop, memoize on the key the caller actually varies, and avoid intermediate strings, dicts, or `Vec`s that the next line only takes apart.
- In Python, prefer idioms that run in C: comprehensions, `dict` and `set` lookups, `bytes` and `memoryview`, tuple keys, and the standard library's compiled paths. When a Python pass is still the bottleneck, the fix is usually to move it into the crate, not to write a cleverer loop.
- In Rust, pay as much attention to allocation and cloning as to asymptotics: borrow instead of calling `.clone()`, size a `Vec` or map up front when the count is known, keep per-entry structures flat, and chain iterators instead of collecting between stages.
- A change that moves a per-unit peak revises the `*_BYTES` constant, and the comment or docstring that justifies it, at the same call site, because nothing else checks the widths derived from it. Measure a performance change before relying on it. When two versions perform the same, choose the clearer one.
