# Parallelism and memory budgets

Every fan-out width in this repository is computed from the machine it runs on: total physical memory, clamped by any cgroup limit, minus a reserve, divided by a measured per-unit peak, capped by any non-memory bound, and floored at one. `rebuild/tools/memory_budget.py` implements that arithmetic and documents the policy, including why the budget never reads free or available memory. Each per-unit cost is a named `*_BYTES` constant at the call site that uses it, and the comment or docstring there records the measurements behind it and explains the width it implies, so a number and its justification stay in one file. `doc/fleet.md` lists the machines and is the key for reading host-tagged output.

## The memory-bound fan-outs

Each fan-out below defines its per-unit cost where its width is computed.

- The kernel's table build: one `build-tables` process over every settlement configuration (`conform.SETTLEMENT_CONFIGS`; the ss10 overlay settles and enumerates nothing).
  - `default` enumerates first and keeps its trace memo while a delta is left to read it. The other configurations then run as deltas over that memo, `--threads` at a time, heaviest first by unlocking-rune count (`fanout::delta_worklist` in the crate). `default`'s fold preparation (its expansion, row chains and first rules) takes one of the `--threads` slots.
  - Where memory has room, the heaviest deltas in that order enumerate from scratch beside `default` instead, from the start, each in a slot of its own (the crate's `--scratch-beside-default`, at most one less than `--threads`), so they do not wait for `default`'s enumeration; the rest run as deltas once it ends. They are taken in whole tiers of equal unlocking-rune count (`fanout::scratch_tiers`): a delta left tied with one taken still runs after `default`, as long as the one taken would have, while `default` enumerates more slowly beside the ones taken, so part of a tier costs time. A configuration enumerated from scratch traces every window `default`'s memo would have answered, which costs CPU. When every delta starts that way, `default` keeps no memo and releases it at its release point as they do (`fanout::default_access`). The tables are the same bytes either way.
  - `kernel_exec.deltas_from_scratch` bounds how many: it takes the largest count of them, in that order, at which the build's booking at its width, with each of them booked at `SCRATCH_PEAK_BYTES` less its parked product in place of a delta's slot, fits, so memory alone decides the count (the `SCRATCH_PEAK_BYTES` comment gives the measured trade of memory and CPU for wall time). Such a build is booked at no less than its start, where each of them holds a `SCRATCH_PEAK_BYTES` before any delta starts and `default` an `UNCAPPED_SCRATCH_PEAK_BYTES` beside them, since `default` keeps every window its trace memo settles while a delta is left to read it; once every delta starts from scratch, `default` books a `SCRATCH_PEAK_BYTES` as they do, so every delta can fit where one fewer does not, and every count is tried. The width is decided first, and the count never narrows it. A bare `run_m1` decides it with nothing beside the build; the artifact cycle decides it with gate:make-test's pytest pool off the machine (`scratch_beside_default_budget`) and passes run_m1 `--scratch-beside-default`.
  - Every configuration runs on one thread from its enumeration to its files (`fanout::run_configs_tables`), because its product holds `Rc`s. At the end of its preparation, inside its slot, it parks its prepared product compactly (`fold::Prepared::park`): the class rows coded against the previous row in blocks, the label-grain expansion as one joint bit a row, and the row chains as stretches of rows that share a parent and a chain length, beside the window options and the rest of the product, which stays as it is: its label pool, whose texts are `Rc`s, its outcome, settled and provenance tables, its deep classes and cells, and each input's run of the expansion. So at the end of the delta wave every configuration's parked product is resident at once, compact, beside the last delta's enumeration. Once every configuration has parked, each reads its product back whole (`fold::Parked::unpark`) and holds it through the cross-configuration exchange (`rebuild/kernel-rs/src/crossconfig.rs`), which holds no slot; each configuration then finishes its fold, writes its files, and frees everything inside a slot again. So at that rendezvous every configuration's whole product is resident at once, whatever the width, with no delta enumerating beside it.
  - Each width the build might take has a booking (`table_build_booking_bytes`), built from constants in `rebuild/pipeline/kernel_exec.py`: `DEFAULT_MEMO_BYTES` for the `default` memo snapshot that stays alive for the wave, with the liveness verdicts `default` publishes in it when some delta reads it; `PARKED_FOLD_BYTES` for each configuration's compact parked product; `DELTA_SLOT_BYTES` for each delta in flight, what one more delta adds to the wave beyond its own parked product, set against the whole wave rather than one configuration alone; at a width above the delta count, `FOLD_PREPARATION_BYTES` for the slot that runs only `default`'s fold preparation; and a delta started from scratch beside `default` books `SCRATCH_PEAK_BYTES` less its parked product in place of its slot. The booking is no less than the rendezvous, `READ_BACK_FOLD_BYTES` for each configuration's product read back with its share of what the exchange and the allocator hold beside it, which every width holds. The width is the widest, up to the configuration count, whose booking fits the machine's memory less the reserve. Below the whole wave that is the memory less the memo and the parked products, divided by `DELTA_SLOT_BYTES` and capped at the delta count, since there the preparation's slot passes to a delta once the preparation ends.
  - A build in which every configuration enumerates from scratch (a narrowed `rebuild/tools/scratch_build.py` set without `default`, or `default_memo_sharing=False`) books each slot at `SCRATCH_PEAK_BYTES`, one configuration enumerated from scratch and alone, less its parked product.
  - Each configuration's engine holds its prospect and candidate memos to a ceiling in buckets, clearing each in place when it fills its table (`fixpoint::TABLE_MEMO_CEILINGS` in the crate). Each engine whose memo no delta reads, every delta and `default` once every delta starts from scratch, also holds its trace memo to 2^25 buckets, clearing a shard whose next insert would double its table, and stores none of the windows with a concrete third slot and a known fourth (`fixpoint::TABLE_TRACE_CEILING`), so of all the memos only the trace memo of a `default` that a delta reads grows with the windows it settles. A forgotten entry is derived again when it is next asked for, and the tables are the same bytes at any ceiling.
  - On macOS `build_table_files` runs the `build-tables` process with the allocator's large cache off (`kernel_exec.KERNEL_ALLOCATOR_ENVIRONMENT`), so a table that a memo, the fixpoint's base index or its item table outgrows goes back to the system when it is freed instead of staying resident until the kernel reclaims it. Every kernel term is measured that way, and the tables are the same bytes either way.
  - The terms are chosen together so that the 48 GiB machines (`doc/fleet.md`) run the whole wave, every delta and `default`'s preparation at once, alone and under a gated cycle. Those machines start every delta from scratch beside `default`, alone and under a gated cycle, because the same terms leave room for all of them; `rebuild/test_memory_budget.py` and `rebuild/test_artifact_cycle.py` pin the count. A wave that takes a second round, on a machine whose width is below the delta count, holds every finished configuration's parked product beside the deltas still enumerating, which is the parked term. The `DELTA_SLOT_BYTES` comment has the readings, the margin, and the recipe each letter batch re-measures them by.
  - `TABLE_BUILD_PEAK_BYTES` is the booking at the configuration count with the deltas the 48 GiB machines start from scratch beside `default` under a bare `run_m1`, which a gated cycle never exceeds; `make job-costs` compares every run_m1 step since the constant's commit against it, reading the higher of the step's peak (a resident line) and the table build's peak footprint, which counts what the memory compressor holds of the build, and prints both.
  - `kernel_threads_default` computes the width for a bare `run_m1`, for the configurations the build names. `kernel_threads_budget` in `rebuild/tools/artifact_cycle.py` computes a cycle's width and also subtracts gate:make-test's pytest pool before the division. A narrow `AMS_KERNEL_THREADS` still parks every configuration's product and reads every one back at the rendezvous, so even a width of one holds them all at the exchange, which the booking's read-back term covers. `run_m1._table_build_threads` caps either at the configuration count and the cores. The cycle's budget applies the same cap itself, as `replay_threads_budget` does, so the plan line and the argv show the width the wave runs at.
  - The window payloads' readers beside the crate, the packing behind the build, and the shipped-order walks on the same branch are not sized by this width; see "Everything else".
- The string replay that follows the table build (`run_m1.run_replay_strings`, on run_m1's table-only branch), at maximum length 4. A full replay walks each settlement configuration in a crate process of its own, beside the spawn worker that absorbs its window memo from a FIFO as the walk writes it (`run_m1.replay_and_absorb`, one worker a configuration); a narrowed one walks the configurations it walks as threads of one crate process (`kernel_exec.replay_strings`). Each walk takes its texts a last symbol at a time and releases its memos after each, so it holds one unit's memos beside a side memo of the windows that cross units and, on a full replay, the row store it writes the memo from (`rebuild/kernel-rs/src/replay.rs`).
  - `REPLAY_PEAK_BYTES` in `rebuild/pipeline/kernel_exec.py` is what one configuration's walk and its absorb hold together, since they run at once: the walk's unit, side memo and row store, and the absorb's columns, probe index and finished file. The constant's comment has the rule and the reading, the memory series' replay holder below.
  - On macOS `kernel_exec.replay_memo_walk` and `kernel_exec.replay_strings` run the `replay-strings` process with the allocator's large cache off as well (`kernel_exec.KERNEL_ALLOCATOR_ENVIRONMENT`), so a table that the trace memo or the walk memo outgrows goes back to the system when it is freed. The deep replay's units run the same way. `REPLAY_PEAK_BYTES` and `DEEP_REPLAY_PEAK_BYTES` are measured that way, and a walk's counts and window memo are the same bytes either way. The absorb workers are Python spawn processes, which the setting does not reach, so each preallocates its columns from the memo's head in anonymous memory whose pages fill only as the rows arrive (`conform.read_replay_memo`), grows no array, and gives the columns back to the system whole when it drops them.
  - A full replay records each passing walk's own crate peak as one observation of the `replay-walk` pool (`run_m1.report_replay`), and a narrowed one its one process's peak divided by the walks it ran at once (`run_m1._record_replay_walk`); the replay-walk row of `make job-costs` checks them against the constant.
  - Nothing is subtracted before the division, because the replay's engines are built after the table build's process has exited and none of its memos survive.
  - `replay_threads_default` divides the machine's memory by it for a bare `run_m1`. `replay_threads_budget` in `rebuild/tools/artifact_cycle.py` computes a cycle's width after subtracting gate:make-test's pytest pool. `run_m1._replay_threads` caps either at the configuration count and the cores, and the cycle's budget applies the same cap, as the kernel's does. The width is how many walks run at once: a full replay gates its walks to it through a semaphore and not its absorb workers. Each worker holds its walk's slot until its settle memo file is finished; once every walk has a slot it leaves the slot and holds the file until every walk has passed, and while a walk still waits for a slot it stages the file at once and holds nothing, so the walks running and the files held never outnumber the width. Below the configuration count the workers not walking also hold their interpreters, which no constant books, and a red replay removes the files its workers staged early. The constant is chosen so both fleet machines replay every configuration in one wave.
  - Each absorb worker that read its memo whole records its peak footprint in a `replay-absorb` pool record, which the replay-absorb row of `make job-costs` reports and checks against no constant, since `REPLAY_PEAK_BYTES` books each absorb with its walk.
- The deep replay (`make replay-deep`, `rebuild/tools/deep_replay.py`): one crate process per unit, at maximum length 5. A unit is one settlement configuration over the texts that end in one alphabet symbol (`deep_replay.walk_units`, the deep sweep's settlement units), walked on one thread, and each configuration's units merge back into the counts one walk over all its texts gives.
  - Each unit's walk holds at most `DEEP_REPLAY_MEMO_WINDOWS` windows in its walk memo. Before any text that could push the memo past that limit, the walk releases the walk memo and its engine's memos (the crate's `--memo-windows`). What a walk holds therefore does not grow with the corpus, apart from the settled records and labels it keeps, which grow with the number of distinct records.
  - `DEEP_REPLAY_PEAK_BYTES` in that module is one walk's peak at that limit, and `replay_threads` divides the machine's memory by it, capped at the cores. `AMS_DEEP_REPLAY_THREADS` sets a width instead. Either is capped at the unit count.
  - A walk at that limit records each configuration's highest unit peak as the `deep-replay-walk` pool beside its check line (`deep_replay.record_walk_peaks`), which the deep-replay-walk row of `make job-costs` checks. No cycle runs the deep replay, so the row moves only when someone runs it.
  - A memo limit set above the checked-in one has no memory estimate, so set `AMS_DEEP_REPLAY_THREADS` with it.
- The deep sweep (`make conform-deep`, `rebuild/tools/deep_sweep.py`): one spawn process per unit, at maximum length 5 or more. A unit is the ss10 overlay whole, at its own maximum length, or one settlement configuration over the texts that end in one alphabet symbol (`run_m1_gates.sweep_units`, shared with gate:conform's pooled sweep), and each configuration's units merge back into the result one walk over all its texts gives. A configuration whose features rename a few runes (`conform.renamed_runes`) shapes only the texts that name one of them, so its units shape fewer texts than `default`'s; `deep_sweep.sweep_triggers` decides which configurations do.
  - A settlement unit shares no settle memo at this depth and keeps every distinct window it settles except the pinned ones (`conform._SettledWindowWalk`, `horizon`), so below the window ceiling the next item describes its windows grow through its walk, and its footprint peaks at the window dict's last doubling late in the walk, when it briefly holds the old and new tables together.
  - Each unit's walk holds at most `DEEP_SWEEP_MEMO_WINDOWS` windows. Before a wave of settles that could push them past that ceiling, the walk empties its window dict and continues (`max_windows`), settling again the windows it meets after that. The ceiling is the most windows a dict holds before it doubles, so a walk at the ceiling fills one table and never doubles past it. `AMS_DEEP_SWEEP_MEMO_WINDOWS` states another ceiling, and the price below follows it.
  - The width is fixed before anything is spawned, not from a live reading: it prices the smaller of the windows the heaviest unit could hold at the end of its walk and the ceiling at a per-window cost that covers that peak, as every settlement unit's need.
  - `window_bound` counts in closed form, from the alphabet, the ligature runes and the symbols each ends in, the boundaries, and the glyph inventory's cells per family, an upper bound on the windows the unit whose texts end in one symbol holds at the requested maximum length: the asks whose last token ends in that symbol and the asks a boundary cuts short, less the pinned windows. Its docstring has the argument. `unit_window_bounds` bounds every symbol's unit in every configuration, since nothing `window_bound` counts from depends on the configuration: the inventory spans every configuration's tables, and the renaming maps labels one to one. A unit that skips texts shapes a subset of the texts of its own configuration's unit over every text that ends in its symbol, so it holds a subset of that unit's windows and the same bound covers it. `settlement_worker_bytes` prices the smaller of the heaviest bound and the ceiling at `DEEP_SWEEP_WINDOW_BYTES` a window beside `DEEP_SWEEP_BASE_BYTES`, the worker before its walk holds anything, which is also all the ss10 overlay holds. At maximum length 5 every bound is below the ceiling, so the bound sets the width; it grows with the alphabet, so a new letter needs no new measurement. At maximum length 6 every settlement unit is priced at the ceiling, so a unit's price, and with it the width, does not depend on the alphabet: every fleet machine sweeps as many units at once as it has cores. The constants' comments have the measurements they are set from and hold the first full run at maximum length 5 and the one-unit runs at maximum length 6 against them.
  - `sweep_width` divides the machine's memory, less the overlay worker, by the settlement unit's need, capped at the cores and the unit count. The overlay runs first in one of those slots, which then takes settlement units. The plan line prints the heaviest unit, its bound, the ceiling, and the arithmetic. When even one settlement unit exceeds the memory less the reserve, the width is floored at one and `memory_shortfall` warns; when it exceeds the machine's memory in all, the sweep refuses to start. Under the checked-in ceiling neither happens on a fleet machine at any length. `AMS_DEEP_SWEEP_JOBS` sets a width instead, and `--jobs` overrides both, for debugging; a stated width also starts a run that would otherwise be refused, with the warning.
  - Each run writes a `conform-deep` check line to the cycle-timings journal with each configuration's highest unit peak footprint (`peak_rss.peak_footprint_bytes`) beside its estimate.
  - `--targeted` runs units of one settlement configuration over a slice of at least `TARGETED_UNIT_TEXTS` of the texts the `settle:bk1-la4` rules give (`deep_sweep.targeted_units`), with no overlay unit. A unit's walk holds at most one window per character of its texts, so `settlement_worker_bytes` prices the heaviest unit's character count, capped at the ceiling, and `sweep_width` divides the memory by that with nothing subtracted for an overlay. The constant's comment has the measurement it is set from.
  - While it runs, the parent prints a progress report every 20 minutes: texts shaped, rates, an estimated finish, every running unit's footprint, and the swap in use, in total and per configuration over its units. The workers report their counts to it through shared memory and print nothing. `AMS_DEEP_SWEEP_REPORT_SECONDS` sets the interval in seconds, so a short debugging run can report every few seconds. The module docstring describes the report and how the finish is estimated.
- The review-corpus build, in `rebuild/tools/artifact_cycle.py`.
  - `CORPUS_PARENT_BYTES` is the parent process. It holds the whole corpus at any width, as columns over the unit's ordinal (`audit.UnitTable` and `unit_store.UnitStore` in `rebuild/review/`), and materializes a unit as a record only for the reader that needs one. It reads the audit, through one descriptor it holds, as a stream one window at a time (`audit.stream_workload`), so its load holds one window's rows and no row columns, and its whole-corpus passes answer from columns: the plan's input-key index, the window index the triage sort walks and the primary-unit search bisects, and the id index sorted 256 top-byte buckets at a time. From the units phase to the end of the write it also holds every recomputed unit's fragment, deflated alone against a checked-in preset dictionary, in one arena (`build._FragmentArena`), which grows with the recomputed units; the `[t] review.build units` line reports its size and the ratio the dictionary reached, and the constant's comment has the arithmetic. It is subtracted before the division.
  - On macOS the cycle's corpus-build step runs the build with the allocator's large cache off (`kernel_exec.KERNEL_ALLOCATOR_ENVIRONMENT`, overlaid on the step's environment by `artifact_cycle._do_corpus_build`), and every pool's workers, the pack's, the signature pool's, the units pool's and the write's, inherit it from the build, so the large blocks the load and the write free go back to the system as they are freed instead of staying in the parent's footprint. The memory series' corpus lines and pack children run with it too. A hand `make review-build` runs without it. The corpus is the same bytes either way.
  - `CORPUS_WORKER_BYTES` is what one worker holds, and `corpus_job_budget` does the division. Its cap is a count of cores less the parent: every usable core for a hand build and under `--skip-gates`, and the build lane's share under a gated cycle (`memory_budget.split_cores`), which leaves the gate lane to gate:make-test's pool or, when that gate skips, to the other gates.
  - The width is decided again when the units pool starts, after the load and plan phases. When gate:make-test, gate:conform and gate:rebuild-contracts have each skipped or finished by then, the gate lane holds nothing, and the pool takes a hand build's width instead (`corpus_gates_idle_job_budget`). On a pass that runs neither gate:make-test nor gate:conform, gate:rebuild-contracts waits until the units pool has finished, so there the pool always takes the hand build's width. The driver writes `var/cycle/gates-idle` at that moment, and the build reads it; the `[t] review.build units` line names the width the pool took and the gate lane's state.
  - A machine the pooled build does not fit gets width one, which is the serial build.
  - The write (phase 2, `build._write_corpus`) runs a pool of its own once the units pool has stopped. `CORPUS_WRITE_WORKER_BYTES` is what one write worker holds: the string table, the workload table's pools and the preset dictionary, received once; one chunk of the run it is writing at a time, the rows of the columns the write reads and the chunk's recomputed fragments that the parent gathers for it (`build._write_chunks`), with that chunk's results until it replies with them; and the compressed sidecar lines of every run it has written (`build._SidecarLines`), which it keeps until the parent has written the manifest and pulls them, one run's lines for one sidecar at a time (`build._WritePool.lines`). Only the lines grow with the corpus, as the worker's share of it. `corpus_write_job_budget` fits as many as the memory of a units pool started as the write starts allows, the hand build's width once the gate lane has nothing left to run, so the build step never holds more than a units pool would; a build at one job writes in its own process, as it drafts, and holds every run's lines there. The build caps it at the unit total over its largest class's units, rounded up (`build._write_width`), because one process writes a class from start to end, and the largest class bounds the phase. On the fleet machines the fit is above that cap at 45 runes, so the cap sets the width, and by 57 the Mac mini's fit can fall to three; the constant's comment has the arithmetic.
  - Each units worker and each write worker reports its peak footprint (`peak_rss.peak_footprint_self_bytes`) when it stops, and the parent writes them, with its own peak footprint as the controller's, to the `corpus` and `corpus-write` pool records that the corpus-worker and corpus-write-worker rows of `make job-costs` read. A units worker's footprint leaves out the clean pages of the subset pack it maps, which the page cache holds once however many workers map it.
- The standing fill's refill pool (`_prefill` in `rebuild/tools/standing_verdicts.py`), which decides across a spawn pool the units the memo cannot serve: every unit when the memo was dropped, or the units a changed standing rule can reach.
  - A worker holds its interpreter, a `SlideContext` over the corpus's font pair, and one chunk of units with that chunk's memos, which it releases after each chunk.
  - The verdict update's process, the pool's parent, keeps ids, decisions, and memo entries, writes pool misses to a temporary gzipped spool, and submits at most one wave of chunks (the pool width times `_STANDING_POOL_CHUNK` units) at a time. Its memory grows with ids and decisions, not with the full human corpus; the docstrings of `_prefill` and `rebuild/tools/verdict_update.py` have the details. The standing daemon holds its own corpus outside this budget.
  - In `rebuild/tools/artifact_cycle.py`, `STANDING_FILL_PARENT_BYTES` is what the verdict update's process holds and is subtracted before the division, `STANDING_FILL_WORKER_BYTES` is what one worker holds, and `standing_fill_jobs` does the division, capped by the cores.
  - The fill computes no width of its own, and without one it runs serially. The cycle passes one on the verdict update's command line (`--standing-fill-jobs`, forwarded as the fill's `--jobs`). A hand run over the whole domain, such as the dont-bug-me-about-this-ever-again skill's final pass, passes the width the cycle's plan prints (`make artifact-cycle ARGS='--dry-run'`, the `verdict-update --standing-fill-jobs` line).
  - A pass with fewer misses than `_STANDING_POOL_THRESHOLD` starts no pool at any width. That covers the ordinary served pass and a pass that commits a rule reaching few units.
- The oracle (`run_m1_gates.run_oracle`): one spawn process per row range of one configuration's subset table, and one per settle-memo absorb, each task in a fresh process (`max_tasks_per_child=1`). Every range reads the parent's spec dump and writes no `spec.json` of its own.
  - `oracle.oracle_shard_plan` cuts every table so that each worker in the pool gets an equal share of the total, with overlay rows weighted by `oracle.OVERLAY_ROW_COST`. Each range copies its audit lines, compressed, into a POSIX shared memory segment the parent names for it, a range of a cut configuration copies its store segment into another, and a range that settled windows fresh copies them, compressed a block at a time (`conform.FreshMemo`), into a third, and its result carries only their names and lengths and the fresh windows' counts (`oracle.ship`). The parent maps and unlinks the audit and store segments as their range lands, writes the audit once, in row order, and each cut configuration's store once its last range has returned (`oracle.InOrderWriter`). Meanwhile it holds a landed range's compressed lines until every range before it is written, and a cut configuration's segments until its last range lands. A range's settle-memo segment waits, unmapped, for its configuration's absorb. Those bytes count in no process's footprint while they wait, so the parent's `[t] oracle_fan_in` line reports the most the writer held at once as `held_gb` and the most the settle-memo segments held as `memo_held_gb`.
  - In `rebuild/tools/artifact_cycle.py`, `ORACLE_SHARD_BYTES` is what one range's worker holds: its interpreter and shaper, its own range's records from the configuration's row store, the configuration's settle memo, which it maps read-only, its walk over the range, whose `windows` holds the windows it settles fresh and the memo hits a later row can read again (a hit whose window spells out its whole row stays in the mapped memo), and the compressed audit lines, store segment and fresh settle-memo windows it copies into shared memory. The memo is a base and up to 21 segments (`row_delta.SEGMENT_CAP` and `FOLD_OVERRUN`), each a mapping, and the walk holds each segment's Bloom filter's pages as it probes them and a dead byte and a reached byte a row over every part's rows. The constant's comment says which term is largest and which kind of pass reads highest, and has the measurements.
  - `sweep_job_budget` does the division, capped by the cores, after taking the settle-memo absorbs' excess (below) off the machine's memory. It is the `--jobs` the cycle passes to run_m1 and the default for a hand run.
  - `run_oracle` writes one `kind:"pool"` record per fan-out. The record has one reading per range, which the `oracle-shard` row of `make job-costs` reads, and one per configuration's absorb, labeled `<config> absorb`, which the `oracle-absorb` row reads. A configuration's absorb (`run_m1_gates._absorb_memo`, over `conform.absorb_settle_memo`) is submitted to the same pool as soon as all of its ranges have landed and the witness stage has returned, and runs in a fresh process in the next slot free, ahead of the ranges still to be submitted, since the parent submits a range only while the ranges and absorbs it has out number fewer than the width; a configuration none of whose ranges settled anything fresh gets none. Its route is planned before the first absorb is submitted (`conform.plan_settle_memos`). On the segment route it maps its ranges' shared memory segments and the standing memo, and holds the standing memo's flags and names, the fresh rows, the segment's index and Bloom filter in heap while it writes one segment of the fresh rows, with dead bitmaps naming the standing rows it drops, and commits its head. On a base route, a fold among them, it writes the whole file once, copying the standing rows from the mapped part, or on a fold the rows it carries from every part into anonymous memory, and holds the standing flags and selector over every part's rows, over a single file its kept-row map, the fresh rows, the new index and, once a window repeats an earlier row's, the merge's keep flags and renumbering counts in heap, so its cost follows the memo, which grows with the alphabet, and not the width.
  - `ORACLE_ABSORB_BYTES` in `rebuild/tools/artifact_cycle.py` is what one absorb holds, read as each absorb's own peak footprint. At most one absorb per settlement configuration runs at once, and each runs in a range's slot, so `sweep_job_budget` takes that many absorbs' excess over `ORACLE_SHARD_BYTES` off the machine's memory before it divides, which is nothing while the absorb's constant is at or under the range's.
  - Each reading is its process's peak footprint over its whole life (`peak_rss.peak_footprint_self_bytes`), and each process runs one task, so every reading is that range's or that absorb's own. A footprint leaves out the clean pages of the settle memo parts a range or an absorb maps.
- gate:conform's per-edit conformance sweep (`run_m1_gates.run_font_conformance`): one spawn process per unit at `conform.SWEEP_MAX_LENGTH`, the same units as the deep sweep (`run_m1_gates.sweep_units`): the ss10 overlay whole, and each settlement configuration once per alphabet symbol, over the texts that end in it. The pool runs one unit per process (`max_tasks_per_child=1`).
  - Each settlement unit reads the parent's spec dump, maps its configuration's settle memo, copies the windows it settled fresh, compressed, into a POSIX shared memory segment the parent names for its slot, and returns the rows it reached. The parent submits units only as slots free. As soon as all of a configuration's units have finished and their counts check, the parent ORs their reaches and submits that configuration's absorb to the same pool (`run_m1_gates._absorb_memo`, over `conform.absorb_settle_memo`), which runs in a fresh process in the slot a unit frees, on the route planned before the first absorb was submitted (`conform.plan_settle_memos`), maps the units' shared memory segments in unit-slot order, and writes one segment of the fresh windows whose dead bitmaps name the rows no unit reached, in any part, and commits its head; a configuration with no fresh window and no unreached row gets none. The parent's `[t] conform_fan_in` line reports the most the units' segments held at once while they waited as `memo_held_gb`, and a killed sweep's segments are unlinked by the next sweep over the same out directory (`run_m1_gates._SweepSegments`).
  - In `rebuild/tools/artifact_cycle.py`, `CONFORM_SWEEP_UNIT_BYTES` is what one unit or one configuration's absorb holds. The highest unit and an absorb, whether it prunes the memo or writes a dropped memo back from its units' fresh windows, hold about the same, and the constant covers both; an absorb on the segment route holds less than one that writes a whole file. A unit holds chiefly the memo's tables and the dict of windows it settles fresh, which is empty with the memo current, beside a dead byte and a reached byte a row over every part and each segment's Bloom filter. The mapped parts' clean pages sit in the page cache, outside the constant. The constant's comment has the measurements. `conform_job_budget` does the division, capped at the cores less the corpus build's parent and workers when the pass runs the build, and less gate:make-test's pool under `--rebuild-pool overlap`, the default, on a pass that runs that gate beside the build lane, but never below the acceptance-configuration count (`_conform_core_cap`). `run_m1._spawn_pool` caps it at the unit count.
  - The conformance sweep is submitted when run_m1's gate passes, so it starts beside the corpus build. A conformance sweep still running when the build finishes, or one queued behind gate:make-test (`gates_queue`), runs beside the verdict-update step instead. Before dividing, the cycle subtracts the larger of those two steps that the pass runs (`_conform_build_lane`): the build's parent and its `corpus_job_budget` workers, or the verdict update and its `standing_fill_jobs` refill pool. The land that follows them in the same lane (`LAND_BYTES` in `rebuild/tools/artifact_cycle.py`, the two corpora's human unit ids and the verdict stores read as streams in one process) holds less than either, which `test_the_land_holds_less_than_either_build_lane_step_before_it` checks, so the reservation covers it and no width depends on it. The land row of `make job-costs` checks the constant against the land step's peak. Under `--rebuild-pool overlap`, on a pass that runs gate:make-test beside the build lane, that gate's pool is subtracted too. A pass that runs neither step subtracts nothing for the build lane.
  - The cycle passes the width on gate:conform's argv at every value, including one, and `run_m1._spawn_pool` never starts more workers than its caller submits units.
  - A hand `run_m1 --conform-only` with no `--jobs` uses `conform_job_budget(skip_gates=True, skip_corpus=True)`, which assumes nothing else is running. A bare `run_m1` uses the oracle's `sweep_job_budget()`.
  - A pooled conformance sweep at its own maximum length writes one `conform-sweep` pool record with one observation per configuration, the highest peak footprint among its units as `run_m1_gates._conformance_unit` returns them, and one per absorb, labeled `<config> absorb`. That record is the `conform-sweep` row of `make job-costs`. The serial conformance sweep and a deeper sweep write none.

The shared `default` memory holds one corpus-sized memo, `default`'s finished snapshot, from `default`'s release point until the last delta over it has enumerated, and none when every delta starts from scratch. Read-journal exclusions apply to its entries at lookup. The aggregate and per-memo `shared_memo_hits` cache-stats lines show how many windows it answers for each delta, so the memory it costs can be weighed against how much it is used.

The kernel's table digest (`table_digest` in `rebuild/kernel-rs/src/artifacts.rs`) defines the byte stream and hashes each section incrementally through `sha256::Sha256`, the constant-space RustCrypto `sha2::Sha256` wrapper in `rebuild/kernel-rs/src/sha256.rs`, holding no copy of the message. The folded transitions and the sorted cells and provenance stay resident, so streaming the hash does not bound the fold's memory.

## Everything else

- The window payloads' readers (`run_m1._take_windows`, through `kernel_exec.stream_payloads`) are one thread per configuration the build names, for the crate's whole run, not capped at the cores, with no constant and no override, because each must read its FIFO for as long as the crate writes it. Each gzips its payload, the rows that differ or the whole enumeration, into its configuration's next segment or base as the crate writes it, so the compression runs inside `[t] kernel_build_tables`, during the crate's write phase.
- The previous windows rows' feeders (`run_m1.WindowsRoute.prior_parts`, through `kernel_exec.build_table_files`) are one thread per part the build's heads list on the segment route, a base and up to twenty segments a configuration, for the crate's whole run, not capped at the cores, with no constant and no override: each decompresses its part into a pipe the crate inherits (`kernel_exec._InheritedPipes`) and blocks on it until the crate reads the part at its configuration's finish. Each copies through one buffer of `kernel_exec.FEED_CHUNK_BYTES`, 64 KiB, beside its gzip stream's read buffer and inflate window, and a base's header lines are checked in bounded reads and never held whole (`table.check_windows_header`). Blocked feeders over six bases with an 8.7 MB head line each add 0.006 GB to their process's footprint, 0.060 GB with sixteen segments a configuration and 0.073 GB at the widest, twenty, about 0.6 MB a feeder, and the freed blocks stay in the footprint once the feeders end. No constant books them, as decision 45 and comment 07 of #618 have it: they sit in run_m1's own process beside the payloads' readers, the run-m1-parent row below.
- The subset pack's processes (`subset_pack.write_pack`, run by `ensure_pack` in the corpus build's parent when the pack is not current for the tables): one spawn process an acceptance configuration, whatever `--jobs` says, with no constant and no override. They run both passes over the tables before any of the build's pools starts and have exited before the load begins, so they sit inside the corpus-build step's booking, the parent's `CORPUS_PARENT_BYTES` beside the units pool's workers it has not started yet. Each holds one table's field memos and a chunk of its encoded rows, and no table; the parent holds the pass-1 sets and the header. A table whose keys do not strictly increase is packed in the parent alone (`write_pack_in_memory`).
- The packing behind the table build once its crate has exited (`run_m1.Packing`: each staged head file's rename and its windows head's commit) and the shipped-order walks (`run_m1.run_emitted_order`) are both sized by `run_m1._core_bound_threads`: one task per settlement configuration, capped at `usable_cores()`, with no constant and no override.
  - A packing task holds only a rename and a small head, and a window payload's reader holds a zlib stream and a copy buffer. A walk is one single-threaded crate process that holds the rules and the labels and streams the rows, with no engine and no memo. None of them holds anything the kernel's memory division accounts for.
  - Each walk's crate reads the shipped order, its configuration's context and its windows from pipes it inherits, each written by a thread of its own (`kernel_exec._InheritedPipes`): two writer threads a walk and one decompressor thread a part its windows head lists, the base on its standard input and each segment on a pipe of its own, which the crate merges by key, not capped at the cores, with no constant and no override, since each must write for as long as its crate reads. Every walk's order writer writes from the one encoded copy of the order `run_m1.run_emitted_order` holds, so the parent holds the order once however many walks run, and the copies pass through the pipes' kernel buffers.
  - `AMS_KERNEL_THREADS` narrows none of them. It exists to keep the table build out of swap, so a build set to width one still reads, packs and walks every configuration at once.
  - The walks are not narrowed for the oracle's pool either; "One gate at a time" describes that overlap.
- Font-suite workers (`FONT_SUITE_WORKER_BYTES` in the root `conftest.py`) are small enough that the core count limits the pool before memory does, so the root `conftest.py` resolves `-n auto` to `memory_budget.usable_cores()`: the cores this process may actually run on, counting the affinity mask and the cgroup CPU quota that `os.cpu_count()` ignores. The same hook serves bare rebuild and mixed font/rebuild runs, honoring `PYTEST_XDIST_AUTO_NUM_WORKERS`; explicit worker counts bypass it. The rebuild suite gets the same width because none of its tests reads a live artifact (`rebuild/conftest.py`'s audit guard enforces this), so no pytest run is budgeted for a heavier worker.
- The corpus build's key-only read (`_key_only_read` in `rebuild/review/build.py`): six processes, `KEY_ONLY_PROCESSES`, a fixed count with no memory constant and no override, each a subprocess of the standard-library module `rebuild/review/audit_stream.py` that imports nothing of the build's. Each walks one window range of the audit in lockstep through the parent's held descriptor, keys the rows of every window with siblings and probes the prior ink-signature store's keys, so the build knows every miss before its full read; each holds its job, those keys and one window, and replies in frames under 1 MB, and the load phase's `[t] review.build load` note reports the largest one's resident peak, which each process reads of itself as it finishes. They run after the pack's processes have exited and before the signature, units and write pools start, and have exited before the stream reads its first window, so they sit inside the corpus-build step's booking. A pass whose store records this audit's identity and these family keys skips the read.
- The corpus build's ink-signature pool (`_shape_misses` in `rebuild/review/build.py`), which shapes the signature store's misses before the units phase, from the key-only read's misses, or in the in-memory source from its own.
  - A worker holds one comparator over the two fonts, and its resident set does not grow with the number of signatures it shapes, so cores limit this pool while memory limits the unit worker. `signature_job_budget` in `rebuild/tools/artifact_cycle.py` is the core count, with no memory division and not the corpus build's cap. Under a gated cycle nothing is subtracted for gate:make-test's pool, which shares those cores while both run.
  - The build computes no width of its own. The cycle passes `--signature-jobs`, which is independent of `--jobs`, so a machine where the pooled corpus build falls to one worker still shapes its signatures on every core. A hand run defaults to the same core count.
  - Below `_SIGNATURE_POOL_THRESHOLD` misses the phase runs serially at any width, so a pass with the signature store filled starts no pool, and a miss the stream meets that the key-only read did not report is shaped in the parent as the stream reads its window. A pooled pass writes a `signature` pool record, the `signature-worker` row of `make job-costs`, which reports the observations and checks no constant.
- The corpus build's ink-signature store write (`_SignatureWrite` in `rebuild/review/build.py`), which runs on one thread during the units phase of a pooled build (`_RecomputeRunner.pooled`) and is joined in the cache phase.
  - It has no width and no constant. The thread starts only when the units phase is pooled, because only then is the parent idle in `wait`. The serial build writes inline at the same point, because a CPU-bound parent would compete with a thread instead of overlapping it. It writes from the store's columns (`unit_cache.SignatureArrays`): the prior entries the build hit merged in key order with the misses it shaped. A pass that hit every prior entry and missed none writes nothing and leaves the store as it is. On every path the columns are freed when the write finishes, or at its start when there is none, so they overlap the pool only for the length of the write.
  - The corpus-build step, which `CORPUS_PARENT_BYTES` covers, reaches its peak at the end of the write, as the parent writes the sidecars after the manifest, where the steady columns, the table, the store's columns and the snapshot sit beside the arena of recomputed fragments, at its largest on a fully recomputed pass; the units phase and the load sit under it, the load because the large blocks it frees go back to the system with the allocator's large cache off. Each `[t] review.build` line carries `rss_gb=`, the step's peak so far, and `rss_now_gb=`, the phase's current resident set. The constant's comment argues where the peak sits and names the readings that set the figure.
- Under a cycle, gate:make-test's pool runs at the width the cycle sets (`make_test_pool_width` in `rebuild/tools/artifact_cycle.py`), passed to that one child through `PYTEST_XDIST_AUTO_NUM_WORKERS`, so the pool that runs is the pool the cycle reserved memory for. On a pass whose build lane runs (run_m1 or the corpus build) that width is the gate lane's share of the cores (`memory_budget.split_cores`), and on a pass that runs neither it is every core; the plan's t0 lane line states it. It runs on the same passes the cycle reserves for: the plan and `make test`'s wrapper both decide to skip with one predicate (`make_test_skippable`), and a forced pass (`--fresh`, `--force-make-test`) passes `FORCE=1` to the wrapper.
- Under a cycle, gate:rebuild-contracts' pool runs at the width `contracts_pool_width` in `rebuild/tools/artifact_cycle.py` computes: the cores, minus the build's parent and its `corpus_job_budget` workers on a pass that runs the build, minus gate:make-test's pool under `--rebuild-pool overlap`, the default, on a pass that runs that gate beside the build lane, floored at one. A pass with neither subtraction gives the suite every core. The cycle passes it to that one child through `PYTEST_XDIST_AUTO_NUM_WORKERS`. It is derived from `corpus_job_budget` instead of restating it, so the two widths cannot disagree. Beside a corpus build at its lane share the result is the gate lane's share under the queue policy and on a pass that skips gate:make-test, and one under the overlap policy on a pass that runs gate:make-test, where that gate's pool already holds the gate lane; `contracts_pool_width`'s docstring explains that trade-off, and the module docstring of `rebuild/tools/artifact_cycle.py` gives the reason for the default policy. The suite starts beside the corpus build, except on a pass that runs the build and neither gate:make-test nor gate:conform (`Plan.contracts_after_units`): there it waits until the build's units pool has finished, so that pool takes every core less its parent, and then runs at the gate lane's share beside the build's write and the rest of the build lane. A pass that runs gate:make-test and neither run_m1 nor the corpus build runs the heavy gates one at a time under either policy (`gates_queue`), so there the suite starts once gate:make-test has finished and takes every core. A hand run still uses every core.
- The scoped-anchor review tool's pool (`_review_pool_width` in `tools/review_scoped_anchor_selectors.py`, run by `make review`): one worker process per family with suggestions, up to `--jobs`, which defaults to `usable_cores()`. No `REVIEW_WORKER_BYTES` exists, because it would never bind and the tool writes no pool record for `make job-costs` to check it against. `make test-and-review` runs this pool beside the font suite's, each sized to the whole machine, and no budget covers that overlap.

## Overriding a width

For a one-off run, set an environment variable. Never edit the checked-in values.

- `PYTEST_XDIST_AUTO_NUM_WORKERS` sets any `-n auto` pool.
- `AMS_KERNEL_THREADS` sets the kernel fan-out, which is only the table build's delta wave.
- `AMS_REPLAY_THREADS` sets the string replay's width, `AMS_DEEP_REPLAY_THREADS` sets the deep replay's, and `AMS_DEEP_SWEEP_JOBS` sets the deep sweep's (`--jobs` on `make conform-deep` overrides it). `--replay-threads` on `run_m1` overrides `AMS_REPLAY_THREADS`, as `--kernel-threads` overrides `AMS_KERNEL_THREADS`.
- `AMS_TOTAL_MEMORY_BYTES` replaces the memory probe but not the policy, so a large machine can reproduce a small one's widths. A value that does not parse is ignored.
- `AMS_DEEP_REPLAY_MEMO_WINDOWS` sets the deep replay's memo limit, not a width. The width is still estimated at the checked-in limit (`DEEP_REPLAY_MEMO_WINDOWS`), so set `AMS_DEEP_REPLAY_THREADS` beside a larger limit.
- `AMS_DEEP_SWEEP_MEMO_WINDOWS` sets the deep sweep's window ceiling (`DEEP_SWEEP_MEMO_WINDOWS`). Unlike the deep replay's limit, it moves the width too, because each settlement unit is priced at the smaller of its bound and the ceiling.

A width set by one of the first three items replaces the memory-derived width, and no memory arithmetic narrows it. A kernel or string-replay width set this way is still capped at the configuration count and the cores, as a derived width is, and a deep-sweep or deep-replay width at the unit count. Of the pools sized by the cores alone, the packing and the shipped-order walks (`run_m1._core_bound_threads`), `build_font`'s pool, and the `woff2` target's `xargs -P` take no override; the corpus build's ink-signature pool, the scoped-anchor review tool's pool, and the baseline extractor's shard pool take a command-line flag instead (`--signature-jobs`, `--jobs`, `--workers`). The corpus build's write pool has neither: its width follows the units pool's `--jobs`, or `--gates-idle-jobs` when the gate lane is idle as the write starts, through `corpus_write_job_budget`.

## One gate at a time

Widths are computed from total memory, never from free memory, so a gate started while another is running does not see it. Neither sees a standing daemon holding a corpus, which is why the daemon is stopped before a pass. Two gates started together each size themselves to the whole machine and slow each other through paging or CPU contention. The artifact cycle runs its build steps one after another. While its build lane runs, it splits the cores between the build lane and the gate lane (`memory_budget.split_cores`): the corpus build's parent and workers hold the build lane's share (its cap is that share less the parent), and gate:make-test's pool is the gate lane's share, so the two lanes' longest-running pools never book the same core. A corpus build whose units pool starts once the gate lane has nothing left to run takes every core less its parent. Memory is not split: before dividing for a pool, the cycle subtracts the memory of every pool it budgets beside that one. On a pass that runs gate:make-test, that gate's pool comes off before dividing for the table build's delta wave, the string replay, the corpus build, and the standing fill's refill pool. Before dividing for the conformance sweep, the larger build-lane step comes off, plus gate:make-test's pool under the default overlap policy on a pass that runs that gate beside the build lane. A pass that runs neither run_m1 nor the corpus build has no build lane to split the cores with, so gate:make-test's pool takes every core, and when that gate runs, the heavy gates run one at a time under either policy (`gates_queue` in `rebuild/tools/artifact_cycle.py`): beside that pool the suite and the sweep would book its cores twice or fall to their floors, and the suite would read the site fonts while gate:make-test's `make all` rewrites them. Nothing does this across independent processes. A workflow that runs agents in parallel therefore runs its gates in a single serialized stage, after every agent's edits are made, instead of having each agent run the gates on its own work.

Inside a cycle, some overlaps are not budgeted. Each case below is a brief, documented overuse of cores or memory:

- The standing fill's refill pool runs inside the verdict-update step, which may overlap gate:rebuild-contracts, gate:make-test and gate:conform's sweep; a suite held until the corpus build's units pool finishes is the one most likely to be running still. Its width subtracts gate:make-test's bytes but not its cores, so the refill pool oversubscribes the cores beside that pool while both run. It leaves the conformance sweep out: the conformance sweep's width subtracts the verdict-update step's memory (`_conform_build_lane`) but not its cores (`_conform_core_cap`), so on such a pass the two pools briefly oversubscribe the cores. It leaves the contracts pool's memory out, because no constant measures a rebuild-suite worker (`calibrate_budgets.UNITS` records that position); the cores limit that pool (`contracts_pool_width`), and its bytes come out of the reserve. The overuse happens on a pass that drops the standing-fill memo.
- Inside the run_m1 step, the table-only branch (the string replay, the witness stage, and the shipped-order walks) runs beside the glyph chain. The oracle's pool starts as soon as the string replay has returned, by which time the replay's crate has exited (`run_m1.TableGates.wait_for_replay`), and the oracle holds its own settle-memo writes until the witness stage, which reads the settle memos and writes none, has returned. The witness stage and the shipped-order walks can therefore still be running when the oracle's pool starts. The witness stage is one spawned process (`run_m1._spawn_rule_witnesses`), handed one configuration's decision table at a time, plus the `settle-cases` crate it spawns one wave at a time, and the walks run one per configuration up to the cores (`run_m1._core_bound_threads`). Both share the machine with the oracle's pool for the rest of their run. The witness stage is one serial walk, in a process of its own so that it does not hold run_m1's interpreter lock while the glyph chain and the oracle's setup run; a process per configuration would need a width of its own and would take cores from the pool. On a rune edit the narrowed replay returns during the glyph chain, so the witness stage runs beside the pool for most of its walk and the pool's ranges can finish first; the oracle's absorbs then wait for the witness stage's process, so the stage reads each file as the replay left it, and `[t] witness_memo_wait` reports the part of that wait left after the oracle's last range has landed. Narrowing the walks to the cores the pool leaves would serialize them, because the pool takes the whole machine, and would put their whole duration on the run's critical path. What either holds is far below the replay's memory estimate (`kernel_exec.REPLAY_PEAK_BYTES` at the replay's width); the witness stage's process reports its own peak as the `rss_gb=` on `[t] rule_witnesses`.
- Inside the run_m1 step, the oracle's pool runs at the width `sweep_job_budget` computes, capped at every core rather than at the build lane's share, and on a pass that runs gate:make-test it shares the cores with that gate's pool, at the gate lane's share, for as long as both run. Its width subtracts neither that pool's cores nor its bytes, which fit inside the reserve; the budget's docstring gives the reasons.
- The window payloads' readers run beside the crate's write phase, one per configuration whatever the cores or the kernel's width, so on a machine with fewer cores than configurations, or at a width below the configuration count, the compressors and the crate's writers keep more threads busy than either. Each reader holds a small working set that does not grow, and the crate's writer for a configuration waits on its reader, so this overlap is on the run's critical path, inside `[t] kernel_build_tables`.
- The packing tasks run beside the string replay crate, the witness stage, the walks, and the glyph chain, and the walkers run beside the replay crate and the witness stage. On a rune edit, whose narrowed replay returns during the glyph chain, both also run beside the oracle's pool. On a machine whose memory-derived width is below the configuration count, these two phases keep more threads busy than the kernel's width. Every task in either pool holds a small working set that does not grow, and both phases are off the run's critical path, which runs through the kernel, the longer of the replay and the glyph chain, and the oracle.
- Under a gated cycle the corpus build's ink-signature pool runs at the core count, and on a pass that runs gate:make-test it shares those cores with that gate's pool for as long as both run. On a pass that runs gate:conform, the conformance sweep starts with the corpus build unless the queue policy holds it behind a still-running gate:make-test. When it starts with the build, the signature pool, which runs in the build's load phase, overlaps the sweep for its first minute or two. The conformance sweep's cap takes the build's parent and workers off the cores (`_conform_core_cap`) only where the cores left reach the acceptance-configuration count, and it never takes the signature pool off, which runs at the core count in the build's load phase, so a pass with the signature store dropped briefly overuses the cores. Under the default overlap policy, gate:rebuild-contracts' pool starts with the sweep and overlaps the signature pool too; `contracts_pool_width` subtracts the build's parent and workers but not the signature pool. On a pass that runs neither gate:make-test nor gate:conform, the suite waits for the build's units pool, so no gate pool overlaps the signature pool. The `--fresh` passes behind the default overlap policy drop the signature store, and on them the sweep and the suite start beside the build and the build lane ends the pass (the module docstring of `rebuild/tools/artifact_cycle.py`). On a pass whose build lane ends last the contention can lengthen the pass, and the signature pool saves less time there. If such a pass that drops the signature store shows a corpus-build row measurably longer under the overlap policy than under the queue policy (`ARGS='--inner'` shows the load and units phases), revisit these widths.
- Where the cores the corpus build leaves fall short of the acceptance-configuration count, the conformance sweep's cap is that count (`_conform_core_cap`), so the sweep's processes run beside the build's parent and workers and oversubscribe the cores for as long as the two overlap. A build at its lane share leaves the gate lane's share, which on the 12-core machine (`doc/fleet.md`) equals that count, so under the queue policy the floor binds on no fleet machine. Under the overlap policy, on a pass that runs gate:make-test, that gate's pool holds the whole gate lane, so there the floor binds on every machine; the Lane conform line of the cycle's plan says which cap bound. The floor keeps the sweep at one process per configuration, so a cycle never runs it narrower than the configuration count.
- The contracts pool runs on every full pass, beside the corpus build or, held until the build's units pool finishes, beside the build's write and the rest of the build lane, at the process count `contracts_pool_width` computes, and its pytest controller is one more process, which no width subtracts.
- Under the default overlap policy, on a pass that runs gate:conform, gate:conform's sweep and gate:rebuild-contracts' pool both start when the run_m1 gate passes, unless the pass also runs gate:make-test and neither run_m1 nor the corpus build, where the heavy gates run one at a time (`gates_queue`). Where the two start together, the suite's width and the sweep's core cap are both the cores the corpus build and, on a pass that runs it, gate:make-test's pool leave, each with its own floor (`contracts_pool_width`, `_conform_core_cap`); neither subtracts the other. On a pass that runs both, the two pools oversubscribe those cores while they overlap, and where the sweep's floor binds, its processes run beside the suite's as well as the build's. Each pool runs longer than it would alone. Beside a corpus build at its lane share, on a pass that runs gate:make-test, the subtraction of that gate's pool leaves the suite its floor of one worker and the sweep its floor, whether or not that pool is still running when they start. `contracts_pool_width`'s docstring gives the reasons for what the two widths subtract, and the module docstring of `rebuild/tools/artifact_cycle.py` gives the passes the overlap policy rests on, where both pools finished before the build lane ended the pass, and the signal to time both policies again. `make artifact-cycle ARGS='--dry-run'` prints both widths.
- A hand `make test-rebuild` whose pyright closure has changed runs pyright beside the full-width pool (`rebuild/tools/pyright_gate.py`, joined by the root `conftest.py` at session end). That is one process using about one core while it runs beside the pool (about a core and a half on an idle machine), which no constant accounts for, since nothing accounts for a rebuild-suite worker either. The cycle's contracts spawn sets no `AMS_RUN_PYRIGHT`, so a cycle pass never runs pyright there.

## Measuring

- `make cycle-timings` summarizes what each step costs, tagged by host; `ARGS='--by-step'` compares step medians across machines. Read it before deciding a run is hung and before choosing a watcher's timeout.
  - The `gate:rebuild-contracts` row mixes widths. `contracts_pool_width` subtracts the corpus build's processes on a pass that runs the build, and gate:make-test's pool under the overlap policy on a pass that runs that gate beside the build lane, so a pass's width is every core, what one of those subtractions leaves, or the floor of one where both together hold every core. The row's median therefore moves with the mix of passes, which is expected.
  - Each pass's width is `contracts_workers` in its run line's plan block, beside the width of every other pooled step (`artifact_cycle.cycle_summary_payload` writes the block), each null for a step the pass skipped; the block's `kernel_threads`, `scratch_beside_default` and `replay_threads` are null only on a gates-only rerun. The block's `contracts_after_units` says whether the pass held the suite until the corpus build's units pool finished. A run line whose plan block lacks the field has only the `kind:"pool"` record with unit `rebuild-contracts` that the pass's pytest controller writes; that record has no run id, so match it to the pass's step row by host and `finished_at`.
- `make cycle-timings ARGS='--critical-path'` shows which step ended each pass, per host, pool policy and pass shape (which of run_m1, the corpus build and gate:make-test ran): how often each step ended last, the median margin by which the lane that ended the pass outlasted the other lane, the median wall, and the median gate:make-test width. The gate lane is the `gate:` steps and the build lane every other step, so a pass whose build lane ends last names that lane's closing step, which is review-facts on every pass but a staging one. The view computes each pass's timeline from its step rows, so it covers every finished pass whose run line carries its start stamp, including one whose plan block lacks the widths, where only the width reads `unrecorded`. An interrupted pass is left out, and so is the job-costs step, which runs once every lane has joined.
- `make cycle-timings ARGS='--writes'` shows what each class of pass writes on each host. A pass's write class is the kind of change it ran for (`cycle_timings.write_class`: a letter batch, whose M1 alphabet differs from the one this host's latest pass that finished ok recorded on its run line, a full or a narrowed string replay, a gates-only rerun, the corpus, the verdicts, a test gate alone, or nothing), and its figure is the write meter's over the whole pass (`rebuild/tools/write_meter.py`). A change that lowers a class's writes reads its before and after there, and replaces that class's `None` in `cycle_timings.PASS_WRITE_CEILING_BYTES` with a ceiling argued from the readings after it; until then `cycle_timings.write_ceiling` derives the class's ceiling from this host's first passes of it.
- `make job-costs` prints each checked-in per-unit constant beside what this host measured and the width each implies. `ARGS='--check'` exits nonzero when an observed peak exceeds its constant. The artifact cycle runs that form on every pass without failing the pass on it, and its OVERRUN status quotes the tripped row's proposal. To accept a new measurement, re-measure the constant and commit it.
  - Two rows report a process no constant books and check nothing: run-m1-parent, run_m1's own process, whose peak footprint, which leaves out what the oracle's fan-in holds in shared memory while it waits (`oracle.InOrderWriter`, `run_m1_gates._OracleMemos`; `[t] oracle_fan_in` reports them as `held_gb` and `memo_held_gb`), a bare run records once its oracle and table-only branch have finished (`run_m1.PARENT_POOL_UNIT`), and replay-absorb, above. The run-m1-parent row's process holds, during the table build and again during the shipped-order walks, a decompressor thread a previous windows part, up to 0.073 GB at once at the widest heads, which stays in its footprint for the rest of the run, and that row books it nowhere (#618's decision 45 and comment 07).
  - Each checked constant's comment but `TABLE_BUILD_PEAK_BYTES`'s states the rule that sets it from its highest reading, a headroom to multiply it by (none for `FONT_SUITE_WORKER_BYTES`) and a multiple to round up to, and the unit's `headroom` and `quantum` in `rebuild/tools/calibrate_budgets.py` restate it. When the highest reading put through that rule comes out above the constant, the row prints that raised value and the width it gives here, and under `ARGS='--host all'` the width on each host in the window; before any peak exceeds the constant the line is marked as headroom used. The tool only proposes raises and writes nothing. The kernel-build row proposes no value and names the kernel constants to re-measure instead, and it reads every record since its constant's commit rather than the newest `--recent`.
- `make memory-series` (`rebuild/tools/memory_series.py`) runs one whole build at each of several alphabet cuts and writes one line a cut to `rebuild/memory-series.txt`, replacing only the lines of the holder it measured. - The kernel's `--cache-stats` flag on `enumerate`, `enumerate-configs`, `build-tables`, and `replay-strings` prints what each memo holds per configuration. ## Writing code against these limits

The Python and Rust here run against hard limits with no spare headroom. A routine that holds a little more per unit raises a per-unit peak, which narrows a fan-out, which lengthens every later cycle. A routine that is correct and simple but materially raises a peak is not finished.

- Think about the working set before the algorithm: what the code holds live at its peak, for how long, and whether that is the whole corpus, one configuration, one unit, or one row. Stream instead of materializing a list. Release a large structure after its last reader, not at function exit. Prefer one pass that folds everything over several passes that each re-read the input.
- Don't buy memory with SSD writes. Writing intermediate data to disk only to read it back later wears the SSD on every pass. Partition the work so each part goes from the code that produces it to the code that consumes it in memory, recompute what is cheap to recompute, and read inputs once, in order, since reads cost the SSD nothing. A scratch spool is the last resort, and a change that adds one states how many bytes a pass writes.
- Don't buy SSD writes back with RAM either: a RAM disk or a RAM-backed temporary directory spends the memory every width here is divided from.
- A pass writes in proportion to what it changes. An output whose bytes would come out the same is not written again: a whole-file writer goes through `rebuild/pipeline/output_sink.py`'s `write_output` or `replace_output` with `keep_if_equal=True`, which compares the new bytes with the file on disk in chunks and leaves an equal file in place, and the crate's table writer makes the same compare. A large output is split so that a small edit rewrites only the parts it touches. A code edit that changes no output and a verdict pass write megabytes; a rune edit writes the rows it changes, which is hundreds of megabytes, since a rune's rows run through every part of each large output; a letter batch writes what it changes.
- A perf check writes no more than 1 GB of its own. Its timed runs write no outputs, so it trades timing fidelity for SSD wear rather than the other way round.
- Estimate the cost of the most frequently run code at the scale it runs at. A cost that is negligible per call dominates the build when the call runs per window, per candidate, or per row. Move invariant work out of the loop, memoize on the key the caller actually varies, and avoid intermediate strings, dicts, or `Vec`s that the next line only takes apart.
- In Python, prefer idioms that run in C: comprehensions, `dict` and `set` lookups, `bytes` and `memoryview`, tuple keys, and the standard library's compiled paths. When a Python pass is still the bottleneck, the fix is usually to move it into the crate, not to write a cleverer loop.
- In Rust, pay as much attention to allocation and cloning as to asymptotics: borrow instead of calling `.clone()`, size a `Vec` or map up front when the count is known, keep per-entry structures flat, and chain iterators instead of collecting between stages.
- A change that moves a per-unit peak revises the `*_BYTES` constant, and the comment or docstring that justifies it, at the same call site, because nothing else checks the widths derived from it. `make job-costs` computes the proposed value once the readings have used a constant's headroom, and the person still revises the constant and its comment or docstring at the call site. Measure a performance change before relying on it. When two versions perform the same, choose the clearer one.
