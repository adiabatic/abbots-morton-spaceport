# What next

## Before the next release

**The pending pins and the expected-failure regression checks wait on the author's ruling.** Each pending pin keeps the author's text and carries `data-expect-pending` with what the engine does instead (`doc/data-expect.md` § Pending pins); the attributes on the three site pages are the list, and `engine/out/build/manual_pins_summary.json`'s `pending` list names them after each build. The any-of regression checks that Senior shapes otherwise are strict expected failures in `test/test_calt_expectations.py`, whose `SHAPED_INSTEAD` names each with what Senior shapes. For each, the ruling is to rewrite the pin or check to Senior's shaping, or to change the runes, and either way to drop the mark. The Manual's pin that types VS2 for a joining half ·Zoo waits on the forced-stance fork below.

**Some expectations of the old engine's regression tests have no test, and wait on a ruling too.** Those tests left the tree with the old engine. Senior shapes these otherwise and no ruling says it should, so each is a rune change or an accepted change: `·Ah ~x~ ·Gay ~b~ ·Ooze`, and the same after ·No and ·Utter, though commit `253c4c52` is “Don’t join ·Gay·Ooze” (`glyph_data/runes/qsGay.yaml` refuses the join only for a ·Gay with no entry); `·Tea ~b~ ·No.alt | ·Thaw ~b~ ·-ing` after every letter that leaves at the baseline, where the old font kept ·No apart; `·Excite | ·Tea ~b~ ·Ah` and `·Excite | ·Tea.half ~x~ ·Awe`, where it joined ·Excite to ·Tea; `·May ~b~ ·Gay ~x~ ·Oy` and `·Excite ~b~ ·No.alt ~b~ ·Tea`; and `·Et ~b~ ·Pea | ·Ah` and `·Owe | ·Fee.ex-ext-3 ~x~ ·May`, the ·{Et,Awe}·Pea and ·Owe·Fee·May regroupings in contexts beyond those `SHAPED_INSTEAD` lists. This paragraph is the only record of them. The expectations the fonts meet that no pin states are checks in `test/test_contextual_shaping.py`.

**The kerning the import left for the author.** The rune files' `kern:` blocks start from the old font's Senior kerning (`doc/kerning-design.md` §8), and the kerning view (`#view=kern`) marks each pair the import set as carried over until the author reviews it. The import never carried the old font's seven ·Owe rules, because it ran before ·Owe had a rune file (`var/kern/import-report.json`'s `inert_rules`): ·See before ·Owe at −1, ·Zoo before ·Owe at −1, ·He before ·Owe at −2, and ·Owe before ·Bay, ·Thaw, ·Way and ·Why at −1 each. The same report lists the rest of what it left for a ruling: the joined groups the old rules moved (`joined`: dropped, or a `contract`), the facing pairs whose members the old rules gave different values (`disagreements`), and the ligature pairs that take their last letter's records through inheritance where the old font left them at 0.

**The release path has never run against GitHub.** The steps HACKING.md § Cutting a release lists, `make draft-release`, the tag push and the `.github/workflows/deploy.yml` run it starts, have never run against the real repository, so the next release is their first run.

**The deep checks are due.** `make conform-deep ARGS=--status` and `make replay-deep ARGS=--status` say what has moved since each last ran; the cycle's summary prints both statuses.

**The public documents describe the 16.000 fonts.** `README.md` and `FONTLOG.md` change only with a release (HACKING.md § Cutting a release), and the fonts `make all` publishes differ from 16.000's in ways a user sees:

- ss02 is gone, and README's ss08 bullet still calls it a set only the rebuilt font has (`glyph_data/script.yaml`'s `features` holds the sets). README's `## Stylistic sets` list is the authority the review build's `FEATURE_DESCRIPTIONS` and the review app's set colors (`engine/review/static/app.css`) are tested against, so the edit that drops ss02 there updates them in the same commit.
- In Senior a variation sequence selects its stance's shape unjoined: the selected glyph joins neither neighbor (`doc/engine-design.md` §7).
- Junior's namer dot stays raised before a ZWNJ, as Senior's does.
- Junior and Mono drop the glyphs no text reaches, Junior's ligatures among them, and an alternate takes the name Senior gives it (`qsNo.flipped`, `qsUtter.alternate`, `qsOwe.sole.ss06`).
- Senior's OTF is about six times the size of 16.000's: the 16.000 zip's `AbbotsMortonSpaceportSansSenior-Regular.otf` is 544,552 bytes, and `ls -l site/*.otf` gives the current sizes. `doc/engine-design.md` §7 says where the size comes from.

**A second checkout needs three steps after it pulls.** Move its untracked `rebuild/out` to `engine/out`, so the build and the cycle find their records; move a verdict store stamped for a review corpus that no longer exists (`verdicts-autosave.json` at the repo root) under `var/keep/`; and run `make review-snapshot-remake`, which installs the accepted snapshot `engine/review-snapshot.json` names.

## Open forks

**Forced stances that join.** Settlement reads only the raw cmap glyphs, so the glyph a variation sequence selects (`glyph_data/script.yaml`'s `variation_sequences`) joins neither neighbor in Senior, where the old font's `calt` went on to join the stance it selected. Whether settlement gains forced-stance letters is the author's call, and one Manual pin waits on it (§ Before the next release).

**The review diff's long-context gap.** The table diff finds a settlement change by shaping the changed rules' certificates and every text of at most three letters that holds the letter (`doc/review-design.md` §2.3), so a change that only a longer context shows can be missed. Diffing the window rows themselves would close the gap.

**How should a gate see a rule that matches across a ZWNJ?** HarfBuzz skips a ZWNJ that a context class does not name, and the ZWNJ lock leaves a rune without an entry (·She and some ligatures) raw after a ZWNJ, so for those windows the emitted rule order is the only protection. The shipped-order walk matches `uni200C` literally and cannot see the skip, so such a fault surfaces only in the conformance sweep or the deep sweep, and not at all when it needs a text longer than the deep sweep's maximum length. The candidates are an emit-time scan that first-matches every real window containing a ZWNJ under the skip, with each raw-after-ZWNJ glyph placed after it, and moving the crate's third-slot boundary row ahead of its block's fourth-slot rows (`rulefold.rs`), as the other slots already do.

**Should a pin edit rerun the build's pin gate?** The build's key holds none of the three pinned pages (`corpus.PIN_PAGES`), so an edit to a pin leaves the build skipped and `engine/out/build/manual_pins_summary.json` as the last build wrote it. `make test`, whose key holds the pages, checks the edited pin through the same checker, and `run_build --gates-only` rewrites the summary. The candidates are leaving the pins to `make test` and adding the pages to the inputs that plan a gates-only rerun.

**How the cycle splits the cores between its lanes.** While the build lane runs, gate:make-test's pool takes the gate lane's share of the cores (`memory_budget.split_cores`, `artifact_cycle.make_test_pool_width`), and under the overlap policy the conformance sweep and the engine suite subtract that pool. gate:make-test starts once run_build's gate passes, and from then on the build lane holds only the corpus build's one process and the land, so most of its share sits idle while the gate lane's pools wait on theirs. The candidates are keeping the split and giving gate:make-test every core less the corpus build's process. Only the 18-core machine has timed the split; `make cycle-timings ARGS='--critical-path'` shows which lane ends each pass on each machine.

**The constants that wait on measurement.** `REPLAY_PEAK_BYTES`, `deep_replay.DEEP_REPLAY_PEAK_BYTES` and the scaling series wait for the run-time optimization work, which would make readings taken before it stale. The two constants have their tools on the M5 Pro MacBook Pro (`make memory-series ARGS='--holder replay …'` and `var/keep/ram-inventory/v4/change21-readings/probe.py`), and `engine/scaling-series.txt` keeps its ·-ing readings.

**The land's end-to-end checks.** A pass keeps the review server running: it builds beside the served corpus and lands the corpus and the store together (`doc/review-cycle.md` § The server and the pass). No automated test drives a browser across a land, so these checks are made by hand on real passes: two open tabs verdicting during the build and the land, a tab closed and reopened mid-pass, a Ctrl-C during the land, and a `kill -9` of the land's child inside its locked section, whose store the next save carries onto the served corpus. The store's lock hold time is the land step's `[t] land-locked` line (`make cycle-timings ARGS='--inner'`). Issue #204, a worktree pass beside the main checkout's server, is answered by the same design: a worktree pass's land takes the worktree store's own lock, and `/capabilities` names the main checkout's server as another checkout's, so the pass leaves it alone and builds its corpus in place. A pass in a scratch clone bears that out, and the issue closes once a worktree pass confirms it, since a clone exercises nothing specific to git worktrees.

**Where a glyph with no rune file keeps its kerning.** Punctuation, the namer dot and the Latin letters lead and follow Quikscript letters, and the old font kerns some of them. The font's one kerning between a rune and such a glyph is `leave-space-for-j` in `glyph_data/opentype-features.yaml`, which reaches every glyph before Latin `j`. The candidate is the same `kern` list on the glyph's own entry in its `glyph_data/` file, with `right: {glyph: …}` naming a follower that is not a rune.

**How the kern records reach Junior.** Junior's letters never join, so its pairs are the ones ss10 reaches, and the author's ruling is that they kern (`doc/kerning-design.md` §1). Junior is built from each letter's isolated cell (`engine/pipeline/build_family.py`) and carries no kerning of the runes, so which of a rune's records Junior reads, and on top of which default spacing, since Junior lacks the Senior tightening, is open.

**Can a stylistic set lift a refusal?** In `doc/core-idea.md` a stylistic set adds capability: an unlock enables a join that no stance declares by default, as ss05 does for ·Tea's both-baseline pairing, and taste vetoes are a separate layer on top of what is allowed. Whether a set can also lift a veto is undecided. The rune grammar cannot express such a lift: a `when:` condition's `feature:` names a single active `ssNN` (`featureTag` in `engine/schema/rune.schema.json`), so a `refuse` can be limited to configurations where a set is on, but never to those where it is off.

**How do extensions that are not for joins behave?** Core-idea makes a join extension a parametric adjustment that a stance owns, and the `extend` and `contract` records (`doc/engine-design.md` §3.3) always target an entry or exit at a named height. Whether an extension made for some other reason works the same way is undecided.

## The rune-schema hover documentation

The side-quest beside the work above: write and clean up the hover documentation in `engine/schema/rune.schema.json`. These are the JSON Schema `description` strings that VS Code (through the Red Hat YAML extension) shows as tooltips while authoring `glyph_data/runes/*.yaml`. The only audience is the owner, so the text explains the schema-specific machinery without re-teaching font internals the owner already knows. The hover text lives only in `rune.schema.json`.

`engine/schema/BETTERRUNESCHEMA.md` is the tracker and holds everything else: the governing decisions D1–D6 (D6 is the one-hover-per-round drafting loop), the walk status and the command that lists which `$defs` are still bare, what the walk does next, and the open leans to react to. Don't restate any of that here. This section keeps the side-quest visible from the main to-do list without a second copy of its state.

One standing authorization lives only here: per-round commits are pre-authorized for this effort.
