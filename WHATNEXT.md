# What next

## The main thread — M1 rune migration

The rebuild migrates the cursive-join engine rune by rune and checks each batch against the old font through the oracle.

**Next step: the qsHe batch is closed; the next migration is not selected.** `make verdict-ready` is the readiness check, `glyph_data/runes/` lists the migrated runes, and `make novelty-order` orders the remaining blanks.

**Where the state lives:** `make verdict-ready` and the app’s banner report whether the corpus, the gates, and the verdict store are ready, `rebuild/out/cycle_summary.json` is the last cycle’s record, and `doc/note-taking.md` § Counts and drifting state and `doc/review-cycle.md` name the other records.

## Open forks in the gates

**How should a gate see a rule that matches across a ZWNJ?** HarfBuzz skips a ZWNJ that a context class does not name, and the ZWNJ lock leaves a rune without an entry (·She and some ligatures) raw after a ZWNJ, so for those windows the emitted rule order is the only protection. The shipped-order walk matches `uni200C` literally and cannot see the skip, so such a fault surfaces only in the conformance sweep or the deep sweep, and not at all when it needs a text longer than the deep sweep's maximum length. The candidates are an emit-time scan that first-matches every real window containing a ZWNJ under the skip, with each raw-after-ZWNJ glyph placed after it, and moving the crate's third-slot boundary row ahead of its block's fourth-slot rows (`rulefold.rs`), as the other slots already do.

**Should the oracle also refuse a row of an `ink_identical: true` class whose placed ink differs?** The review build already lists each such unit under the change group of what it shows (`change_groups.reroutes`), so every “Looks identical” class in the app holds only units whose picture matches the old font, and the review-facts pins count the re-routed units per ledger class (the volatile block's `unmatched_groups.rerouted`), which shows a broken identical claim as a number. The oracle still files those rows under the identical classes in `rebuild/out/m1/divergence-audit.tsv`, because it enforces the flag only through its position check, which compares glyph origins and advances (`_position_mismatch` in `rebuild/pipeline/oracle_positions.py`), and a redraw that keeps every origin and advance passes it. The candidates are leaving the oracle as it is, with the re-routed counts as the signal, and a placed-ink check over the rows such a class takes that refuses a row whose ink differs, which would leave those rows unmatched in the audit too.

**Should the position check blame a shift on a kern earlier in the row?** `_position_mismatch` counts a mismatch as the kern's when every mismatching slot follows a kern-attributable slot, one whose old advance carries a kern or that sits next to a ZWNJ, and a row in a single ink-identical class keeps that class when its mismatch is the kern's and no class takes the row with the mismatch. In ·X·Way·Cheer·Gay and ·X·Way·Cheer·No, where the old font kerns the lead ·X against ·Way, the one-pixel shift from ·Gay's entry contraction or ·Cheer's exit contraction therefore counts as that kern's, and the rows stay in `identical-unused-join-name`, while ·Way·Cheer·Gay, ·Way·Cheer·No, ·Cheer·Gay, and ·Cheer·No, with the same shift and no kern before it, are unmatched. The question is whether a mismatch with a cause of its own at a later junction should count as the kern's.

**The build lane's share is the width to revisit on the 12-core machine.** A gated cycle splits the cores between the build lane and the gate lane (`memory_budget.split_cores`), and the corpus build's units pool keeps the build lane's share whenever the gate lane still has work as the pool starts. On the 12-core machine, a pass that runs gate:conform, as a `--fresh` pass does, still has gate:conform and gate:rebuild-contracts running when the units pool starts, so it does not reach the widening for an idle gate lane. A pass that runs neither gate:make-test nor gate:conform holds gate:rebuild-contracts until the units pool finishes, so it reaches the widening there too; the probe pair that checks this on the 18-core machine (issue #306) has yet to run on the 12-core one. The build lane ends a `--fresh` pass there under either `--rebuild-pool` policy, and the units phase at the build lane's share runs far longer than at every core less its parent. The gate lane does not keep its own share busy through that phase. Under the overlap policy, gate:rebuild-contracts runs one worker wide after gate:make-test ends, and under the queue policy the gate lane empties before the units pool does. Issue #506 has the timings; `make cycle-timings ARGS='--critical-path'` and `ARGS='--inner'` read them from the journal.

## The review server through a pass

**The land's end-to-end checks are open.** A pass keeps the review server running: it builds beside the served corpus and lands the corpus and the store together (`doc/review-cycle.md` § The server and the pass). No automated test drives a browser across a land, so these checks are made by hand on real passes: two open tabs verdicting during the build, the verdict update and the land, a tab closed and reopened mid-pass, a Ctrl-C during the land, a `kill -9` of the land's child inside its locked section, and a `merge_verdicts --restore-as-of` replay compared against the store and the orphan documents. The store's lock hold time is the land step's `[t] land-locked` line (`make cycle-timings ARGS='--inner'`). Issue #204 (a worktree pass beside the main checkout's server) is answered by the same design: a worktree pass's verdict update writes only its scratch store, its land takes the worktree store's own lock, and `/capabilities` names the main checkout's server as another checkout's, so the pass leaves it alone and a worktree's first pass, which builds in place, is not refused by it; it closes once a worktree pass confirms that.

**The carry's marker strip awaits the first pass that carries the store onto a new stamp.** The carry copies each note as written, less any `[carried …]` marker in its leading marker run (`verdict_notes.drop_carried_markers`). A pass that leaves the store on its stamp merges into it, and the merge keeps the store's record unless the incoming one has a strictly newer `at` (`merge_verdicts.merge_into`), so the store's notes keep their markers until a pass carries the store onto a new stamp. After that pass, the landed `verdicts-autosave.json` should hold as many records as before it and no `[carried` marker outside the units a tab still on the old corpus saved during the pass, since such a tab sends the note its input shows, marker included; the `[standing:` and `[duplicate-fill` markers the fills write from then on should survive two more stamp moves. The land peaks from then on are the next measurement set for `LAND_BYTES`: revise the measurement sentence above it in `rebuild/tools/artifact_cycle.py` from them, since every store it cites carries the markers. Once no tab opened before that pass remains, remove the outbox's allowance for the markers (`CARRIED_PREFIX` and `heldByServer` in `rebuild/review/static/outbox.js`, and the case in `rebuild/review/jstests/outbox.test.js` that covers it) and the “carry's provenance prefix” clause of rule 2 in `rebuild/review/verdict_store.py`; removing them early costs only a replay, which rule 2 applies.

## The review app's kinds of change

The items below that move unit ids or counts do so on purpose, so each of them is a pass of its own, with its expected deltas written down before it runs.

**Retire the classes that reach no unit and fold the ones the change groups cover.** `joins-next-letter-after-zwnj` and `join-height-after-zwnj` reach no unit and stay only as records of the rulings `split-by-space-or-zwnj` relies on; they can retire into its `why`. `spacing-at-kerned-pairs` and `new-joins-near-tea-oy` can fold into the change groups, whose clusters hold the same pixel changes. Each needs the oracle to change with it.

**Rename the oracle's class strings and narrow its predicates.** The oracle and `rebuild/test_conform.py` still name the classes by their engine ids, which the ledger's `match.predicate` values map to the reviewer-facing ids. The rename goes with narrowing the predicates that reach further than their rulings: `half-day-closer-at-baseline-join` takes half-·Day after any letter, `ss03-tea-oy-ligature-kept` keeps a dormant namer-dot ·Day·Utter branch, and `identical-unjoined-from-left` takes any no-entry rename. Until then, a new row one of them takes is listed under a ruled class, which the Queue never shows.

**Move `may-closer-at-baseline-join`'s highlight onto the join into ·May.** In most of its units the amber band marks the unchanged `·May ~x~ ·J’ai` pair. `highlight` is in the unit id, so the fix re-keys those units through a forward map (`rebuild/tools/rekey_verdicts.py`).

**Fix the per-unit summaries.** Some units fall back to the false “only the boundary marker's glyph changed”, some say “settles as a different cell”, and some quote rune record indexes such as `policy.refuse[4]`, which go stale when a record is inserted. `summary` is outside the unit id, so these fixes re-key nothing.

**The author rewords the `why:` in `glyph_data/runes/qsTea_qsOy.yaml`.** It names a group by an id no corpus has. Agents never write a rune `why:`.

## Open questions from the requirements

`doc/core-idea.md` records the rebuild’s requirements, and `doc/rebuild-design.md` settles the questions its interviews raised and keeps to its decisions, except the ones below.

**Does each rune’s own ductus gate its migration, in place of finishing all of the ductus first?** Core-idea makes finishing the whole ductus a precondition for the rewrite (its section “The stance set’s truth is held jointly by ductus _and_ bitmaps”), and `doc/rebuild-design.md` §3.1 makes each rune’s migration wait on that rune’s own ductus instead. §15 item 10 records the departure and what the per-rune order gives up. The departure waits on the author’s sign-off.

**Can a stylistic set lift a refusal?** In core-idea a stylistic set adds capability: an unlock enables a join that no stance declares by default, as ss05 does for ·Tea’s both-baseline pairing, and taste vetoes are a separate layer on top of what is allowed. Whether a set can also lift a veto is undecided. The rune grammar cannot express such a lift: a `when:` condition’s `feature:` names a single active `ssNN` (`featureTag` in `rebuild/schema/rune.schema.json`), so a `refuse` can be limited to configurations where a set is on, but never to those where it is off.

**How do extensions that are not for joins behave?** Core-idea makes a join extension a parametric adjustment that a stance owns, and the rebuild’s `extend` and `contract` records (`doc/rebuild-design.md` §3.3) always target an entry or exit at a named height. Whether an extension made for some other reason works the same way is undecided.
