Would rewriting the Python in Rust actually help?

Yes — for exactly one function, by a measured 20.1×. But that number is measured against a baseline you should not be comparing to. Six ordinary memoizations and a gc.freeze() take the same function 2.28× faster for about fifty lines, with a byte-identical artifact. Stack mypyc on top and it is 3.87×. Against that, a Rust port is worth 5.2–7.0× — and the thing that decides whether you need it is not seconds per day. It is how far the alphabet migration is going — and, it turns out, which letters it adds.

Finding

The bottleneck is one function, and it is the only place Python is the problem

The last dozen commits in this repo are about avoiding work, and they succeeded: make test’s skip path costs 78 ms to avoid 2,212 CPU-seconds — a 28,000× avoidance ratio. The build drivers, the fingerprints, the green records are already free. Rewriting them would save fractions of a second.

What is left is genuinely irreducible compute, and it is not evenly distributed. Two of the three big workloads are dominated by code this repo does not own, so their ceiling under an infinitely fast rewrite is barely above 1×. The third is the opposite in every respect.

The one that matters

rebuild/pipeline/table.build_tables — the M1 decision-table settlement fixpoint — is 337.9 s cold / 194.9 s warm across six acceptance configurations, and a /usr/bin/sample call graph of a live build contains zero frames of harfbuzz, zlib, hashlib, json, pickle or re across 25,565 samples. It is 30.8% bytecode and 69.2% CPython interpreter overhead — object allocation, refcounting, dict lookup, generated dataclass dunders. It is armed by 41.2% of commits and is about 60% of all the time you spend waiting.

It is also strictly single-threaded — not because it cannot be parallelised, but by design: a cross-configuration trace share must live in one process, and that share is measured at 1.896×. Giving it up to run six configurations in parallel costs you most of what parallelism buys.

Measurement

What Rust actually buys, measured rather than assumed

The honest way to answer “how much would Rust help” is to write the thing and run it. A structurally faithful model of the fixpoint was implemented three times — Python, Rust, Go — against one shared spec, then checked far harder than a benchmark usually is.

Why you can trust the multiplier

All three implementations produce the same 428,971 window rows, the same 135 cells, and the same FNV-1a checksum 2964411847154100471 — over a canonical rendering of every row’s settled cell, adjustments, joint-floor flag, prospect value and carried extension. They also produce identical kernel call counters to the digit (4,903,617 candidates / 4,006,506 _prospect / 1,690,599 transition_trace / 5,049,965 _prefer_favors), which means the ports execute the same control flow rather than merely arriving at the same answer. Rust was built --release with LTO; every generated string is folded into a printed accumulator so the optimiser could not delete the work.

Two results that argue against a naive port

At the primitive level, CPython beats both Rust and Go at inserting a ten-slot string key — 76 ns against 154 and 170 — because it caches string hashes. The same insert on a packed u64 key is 4.82 ns in Rust. The win is the packing, not the language: 254.2 bytes per memo entry becomes 10.

And a hand-rolled FxHash with a bare finish() measured 25,744 ns/op — a 600× blowup against SipHash — because this key’s low bits are a five-value alphabet. A port that skips the finalizer is slower than the Python it replaced.

The catch

The baseline moves 3.87× before you write a line of Rust

Every rewrite multiplier is a ratio, and nobody had checked what the denominator could be. Stacking the ordinary Python levers on the real kernel — not a model — produces a byte-identical artifact digest and the same 682,842 windows / 2,667 rules / 3,563 treaty rows in every arm, with 182 of 182 repo kernel tests passing.

What this does to the decision

Against shipped Python, Rust is worth 20.1×. Against a levered Python it is 8.8×. Against levers plus mypyc it is 5.2–7.0× — about 426–499 machine-seconds a day on a stage costing roughly 2,040. That is the number a rewrite decision should actually be argued against, and it is a quarter of the headline.

Three accelerators that lost

  • PyPy is dominated — drop it, don’t rank it. It is 1.53× on the shape the code actually runs, and PyPy plus the memoizations (1.74×) is slower than stock CPython plus the same memoizations (2.13×). The memos delete precisely the interpreted work the JIT was earning its keep on, at 4.6× the memory.
  • Free-threaded 3.14t is 1.65×, not the 3.18× first reported — that figure used a baseline with the trace share switched off. Its “free” single-thread win also reverses once gc.freeze() is on, which means the win was the garbage collector, not free-threading. It additionally cannot install uharfbuzz at all, and fontTools.feaLib.lexer re-enables the GIL process-wide on import.
  • PyO3 was struck, not weighed. Its only advantage over a plain subprocess is saving a serialization measured at 2.5% of the build — and handing Python objects across the boundary rebuilds the exact 254 B → 10 B object graph the packing exists to delete.

The question that actually decides it: how many letters?

Nobody had measured how this workload grows. It grows steeply — steeply enough that the rewrite is not a seconds-per-day decision at all, it is a headroom decision. Growth model

Why the exponent rises: the deep slots are waking up

Two things are going on, and only one of them is real. The first is arithmetic: this is not a power law at all. Each two runes added multiplies CPU by a near-constant 2.17, 2.04, 2.24, 2.22, 2.25, 1.79 — a constant multiplicative step, which fits an exponential 4.4× more tightly than a power law (RMS log-residual 0.053 against 0.231, with the power-law residuals in a tell-tale U). Force an exponential through a power-law lens and the apparent exponent must climb linearly, as k(n) = n ln b. That predicts 2.66 / 3.42 / 4.18 / 4.94 / 5.70 against the measured 2.69 / 3.19 / 4.41 / 5.17 / 6.08 — five spans of six.

The second is a real mechanism, and it is the more useful finding: _ProspectLiveness’s pruning is getting weaker as the alphabet grows. The liveness ladder exists to stop the 19⁴ slot product being enumerated — and it is losing its grip.

The caveat that undercuts extrapolating at all

That live-rate jump is concentrated in one step, and the runes added there were ·May and ·No (then ·Pea and ·Roe) — precisely the families with the elaborate join machinery: the ex-noentry stances, noentry_after propagation, ·Roe’s shortened_top. Two specific letters more than doubled the deep-slot live rates. So the growth rate is a property of which letters you add, not how many. Whether the remaining 29 behave like ·May and ·Roe or like ·Ah and ·Et is unknown until they are modelled — which means no curve through these seven points can be trusted to reach 44.

What that does to the headroom table: at today’s 337.9 s tolerance and the optimistic letters^4.0–4.5 model, shipped Python supports 15.0 letters, the levers 18.0–18.4, levers plus mypyc 20.3–21.0, a Rust port 29.2–34.2 serial and 34.6–43.5 parallel. Under either of the other two models every one of those numbers is smaller, and under the best-fitting one nothing reaches even the low twenties.

There is also a consequence for the rewrite case that a fixed exponent hides. A constant-factor win buys multiplicative letter headroom, and a rising exponent erodes it: at e = 4.25 a 20× port buys 201/4.25 = 2.03× the letters (15 → 30); at e = 6 it buys only 1.65× (15 → 25). Attacking liveness attacks the exponent itself, which no language change can reach — and it is the same 336-line class that is already 78.7% of runtime. It is simultaneously the hottest code in the build and the code whose effectiveness is decaying. WHATNEXT already names persisting the liveness verdicts; on this evidence that is worth more than it looked.

The cheapest way to settle the whole question: the live-rate row is a leading indicator, and one sweep measures it. If slot 3 and slot 4 plateau, growth reverts to a genuine A⁴ power law and the hours-scale projection holds. If they keep climbing, nothing measured here reaches a full alphabet in any language, and work avoidance stops being optional.

Recommendation

Do these three, then decide the port on the alphabet

  1. gc.freeze() + gc.disable() at run_m1’s entry

    Measured 1.14× twice at full scale on the real kernel (81.25 → 71.24 and 80.65 → 70.45 CPU-s), byte-identical digest every time. The fixpoint runs 15,692 collections that collect twelve objects in total. About five lines; costs +15% peak RSS. Worth roughly 252 machine-seconds a day.

  2. Six memoizations and a RightToken NamedTuple in settle.py

    With the above, a measured 2.28× on the real kernel at full scale — 78.93 → 34.66 CPU-s, identical artifact digest, 182/182 kernel tests passing including the one that drives a real persisted trace store and a live share. About fifty lines, one file pair, no new runtime and no new tool. Best ratio of anything here. Two blemishes to fix before landing: _PAIRING_SETS sits at module level with no cap where the repo’s own _GUARD_STATES pattern caps at 8, and one patch declares two caches it never uses.

  3. Re-baseline, then decide

    One make artifact-cycle with cycle-timings.ndjson landing, plus one run of the alphabet sweep. Zero code. What it is worth is not seconds but honesty: it changes the Rust port’s advantage from 20.1× to 5.2–8.8×. No port should be benchmarked against a denominator these two steps move by 2.28×.

After those, mypyc is the next-best ratio and the last thing available before a port — but it is the first option with real ongoing cost: mypy becomes a second type checker that disagrees with pyright, per-platform wheels become build inputs, and inspect.getsource stops working so you can no longer step into the kernel with pdb.

Separately, the max_chars_after tier in the calt sweeps is worth more foreground seconds than a full make test rewrite could ever buy, and no rewrite can reach it — but it is a coverage decision, not a performance one, and therefore yours. The blunt cut gives up 22 of 215 reachable pair renderings; a tier that keeps the eight depth-2-dependent tests gives up nothing today, though nothing guards that it stays true as runes change.

If the port happens

The scope is smaller than it looks, and the cut line needs no FFI

The boundary is not the subprocess that exists today — run_m1 also mints glyphs, runs defect gates, emits GSUB/GPOS, compiles the font with fontTools and runs three HarfBuzz gates. It sits one level in, at build_tables, where the repo’s own byte-stable write_windows/read_windows round-trip plus a 155 KiB JSON dump of the resolved spec already carry ninety per cent of the interface. A binary that reads a spec file and writes a windows file. No PyO3, no shared memory, no FFI.

Measurement shrinks it twice more: spec_load.py is outside the runtime closure, trace_memo.py should be deleted rather than ported (at 20× the persisted memo’s whole value collapses to about 7 s), and _rules_for_input — the largest and hairiest function in table.py — is 0.6% of runtime and stays in Python. What is left is roughly 2,750 lines of semantics becoming 4,000–5,500 lines of Rust, of which about 80% is “decide what the letters do” rather than “make it fast”.

The verification story is the strongest part of the case. A test already diffs a serialized enumeration against a fresh in-process fixpoint, so a differential harness is a day or two’s work — and the conformance gate, which still settles in Python, becomes a Rust-versus-Python differential mediated by an independent shaper across every string to horizon 5 in six configurations.

The case against, measured

The port does not retire settle.py. Nineteen non-test modules reference it; conform.py alone has 75 references and settles every swept text in Python; emit_gsub.py calls formation_blocked to generate shipped FEA rows. So every future settlement change is written twice. Over this pipeline’s two-month life, 23 commits touched the kernel — 3 in June, 11 in July, 9 in August, flat to rising, at 350–500 lines each. At roughly twelve semantics commits a quarter each needing a matching Rust edit plus differential re-verification, the duplication tax is plausibly 6–12 engineer-days per month — enough to re-pay the port’s own cost every two to three quarters. And 78.7% of runtime lives in one 336-line class, _ProspectLiveness, which is simultaneously the hottest, the subtlest, and the easiest to get silently wrong: an under-opened liveness verdict omits windows and the font is simply wrong in a way only the conformance sweep catches.

Three author-facing things also break and should be budgeted: explain.py and probe.py — whose entire value is replaying the same code that built the table — would explain what Python thinks rather than what the font was built from; settle.py’s _incomparable_message, which prints a paste-ready YAML resolve stub, lives inside the kernel; and uv sync stops being sufficient to reproduce the project.

If it happens: Rust, not Go — Rust’s multiplier is flat across volume while Go’s decays, and this workload is the best possible shape for an arena and the worst for a tracing collector.

What is still unknown

  • The real build cadence is unmeasured, and this machine contradicts the model. Every seconds-per-day figure assumes one refreshing cycle per arming commit — but the green records show zero M1 builds across the 80-commit window in which 76 of those commits landed. This is the single largest uncertainty in the whole study, and one make artifact-cycle closes it. If the real cadence is a quarter of assumed, M1 is still 52% of foreground wait but every daily figure divides by four and the port’s payback passes two years.
  • The model spec’s condition contents are synthetic. Its shape is copied from the real spec by introspection — per-rune stance counts, the refuse/prefer/extend/contract census, eight predicate classes at real sizes, the real prefer-chain reach histogram — but the condition contents come from a seeded PRNG. Real rune family masks have structure a PRNG does not, which could shift branch prediction either way. This is the largest residual risk in the 20.1× and it cannot be closed without writing the real port.
  • The verdict plumbing chain has never been measured anywhere. It carries 208 s/day — 5% of the foreground — on a pair of numbers from a docstring.
  • Whether the trace share can be made value-keyed. If private per-thread specs could share the donor’s memo, parallelism and the share would stop excluding each other and both the free-threaded and parallel-Rust figures rise by about 1.9×. Its keys look value-comparable on inspection, but FeatureSensitivity is built from self.spec and _guard_state is keyed on id(spec). One experiment could move free-threading from “dominated” to “competitive”.
  • Whether the memoization patches survive the full rebuild suite. 182 kernel tests pass; the full 1,162-test suite was never run against them.
  • Whether the deep-slot live rates plateau. This is now the single most decision-relevant unknown, and it is cheap to watch. If slot 3 and slot 4 saturate, growth settles into a genuine A⁴ power law and the hours-scale projection holds; if they keep climbing, the effective exponent keeps climbing with them and no language change reaches a full alphabet. It cannot be measured beyond 18 runes until more runes exist — the sweep is bounded by what is modelled, so this question can only be answered as the migration proceeds.
  • How many of the remaining 29 letters carry deep prefer-chains. Adding ·May and ·No alone more than doubled the deep-slot live rates. Seven of the eighteen modelled runes already reach depth ≥ 2. Whether that ratio holds, falls, or rises across the rest of the alphabet decides the growth curve — and it is a question about Quikscript’s join semantics, answerable by inspection before the runes are written.

Method

Twenty-six agents across two workflows: a mapping and attribution pass over the build system, an exclusive-machine calibration run, native-versus-Python CPU attribution by /usr/bin/sample and cProfile reconciled against each other, three-language kernel ports with checksum and call-counter equivalence, an exclusive serial benchmark phase, and an adversarial verification pass whose corrections are printed above. Machine: Apple M4 Pro, 12 logical cores (8P + 4E), macOS 15.6, CPython 3.14.6, Rust 1.97.1 (--release, LTO, codegen-units=1), Go 1.26.5 (default build). Raw evidence under tmp/perf/ and tmp/perf2/; the full written model is tmp/perf/cost-model.md and tmp/perf2/decision.md.
