4. METHOD B -- cProfile attribution fractions, and its distortion
================================================================================
bench.py runs _phase1_unit / _phase2_unit over stride samples of the REAL 63,442
units, with three DISJOINT slices so the process-global shaper memo never warms
one measurement with another's shapes.  (An earlier run that reused one slice
silently produced a 100%-memo-hit profile with zero shaping in it; the disjoint
slicing is what fixes that.)

  phase1-bench.txt   1200 units/slice
    unprofiled, COLD shaper memo   1.344 s CPU = 1.120 ms/unit
    unprofiled, WARM shaper memo   1.165 s CPU = 0.971 ms/unit
    profiled,   COLD shaper memo   3.982 s CPU  -> cProfile slowdown 2.96x
    profiled,   WARM shaper memo   3.210 s CPU  -> cProfile slowdown 2.76x
    tottime split (cold): python frames 87.0% | builtin+C 13.0%
      by file: ink.py 51.1% | settle.py 16.7% | <builtin/C> 13.0%
               shaping.py 8.0% | enrich.py 4.8% | build.py 2.9%
    biggest single entries: ink.py:88 genexpr 3,136,170 calls / 1.486 s tottime;
                            ink.py:89 genexpr 5,539,320 calls / 0.480 s

  phase2-bench.txt   1200 units/slice
    unprofiled 0.363 s CPU = 0.303 ms/unit; profiled 1.031 s -> 2.84x
    tottime split: python 81.7% | builtin+C 18.3%
      by file: yaml/emitter 24.9% | build.py 21.3% | <builtin/C> 18.3% |
               yaml/serializer 7.0% | yaml/representer 5.2% | spec_load 4.5% |
               drafts.py 4.3% | json/encoder 1.8%
    top entry: build.py:189 config_badge 0.122 s tottime for 1200 units

DIRECTION AND SIZE OF THE cProfile BIAS: cProfile makes this workload 2.8-3.0x
slower, and essentially all of that overhead lands on Python frames -- ink.py's
two generator expressions alone are 8.7 M calls per 1200 units.  A 9.5 us
HarfBuzz call absorbs one hook.  So cProfile OVERSTATES python_bytecode +
interpreter_overhead and UNDERSTATES native_extension.  Quantified on the same
slice: cProfile puts shaping at 8.0-8.2% of phase 1, while the direct cold-memo
vs warm-memo ablation puts it at 13.3% -- a 1.6x deflation of the native share.
Method B is therefore an UPPER bound on the rewritable fraction; Method A is the
number to trust, and Method A is the LOWER of the two.

7. JSON                                                        [json-bench.txt]
================================================================================
Over the 27 shards this build actually wrote (279.7 MB / 266.7 MiB):
  read the bytes            0.026 s CPU   10,602 MB/s
  json.loads                1.347 s CPU      208 MB/s   (C decoder)
  json.dumps(indent=1)      0.936 s CPU      299 MB/s   (279.7 MB out)
  json.dumps(compact)       0.924 s CPU      256 MB/s   (236.9 MB out;
                                                        indent=1 inflates 18%)
  build._write_json         1.008 s CPU      277 MB/s   (dumps + write)

SHARE: 0.94 s of a 125.19 s cold build = 0.75%.  On the warm path, json.dumps
0.94 + json.loads 1.35 (prior fragments) + 0.31 (unit-cache store) = 2.60 s of
13.69 s = 19%.

serde_json comparison: ESTIMATE, NOT MEASURED HERE -- serde_json's to_writer on
string-heavy structures is commonly reported at roughly 1.5-3x CPython's C
encoder, i.e. ~450-900 MB/s against the 299 MB/s measured here.  Best case that
saves ~0.6 s of a 125 s cold build (0.5%) or ~1.7 s of a 13.7 s warm build
(12%).  JSON is not the bottleneck on either path.
