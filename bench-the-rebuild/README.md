# bench-the-rebuild

Measurement scaffolding, built for one question that is now answered: **is Python what makes the rebuild slow, and would a Rust or Go port help enough to be worth it?** The port landed and the kernel crate is the engine of record; `RUST-PORT-PLAN.md` holds the decision, the thresholds it turned on, and the design facts that came out of measuring it. What is left here has a job the answer did not retire: `scaling/` is the migration's early-warning ladder, driven through the kernel crate like everything else that builds a fixpoint now; `levers/kernel_all_configs.py` is the six-configuration endpoint's kernel arm, with the font-build and surface lever probes beside it; `ram/` holds the attribution harnesses behind the tracker issue #50 — **what occupies the rebuild's RAM high-water mark?** — and `rebuild/tools/peak_rss.py` is the one yardstick every RSS figure in this tree goes through; and `ink-and-tsv/`, `primitives/` and `cut-the-work/` price the port candidates and the coverage levers no language change reaches. This file says what is here and how to run it.

Everything here reads the repo and writes only under this directory. Nothing in `make test`, `make all`, `make test-rebuild` or the artifact cycle touches it, and `bench-the-rebuild/` is in `MAKE_TEST_EXEMPT_PREFIXES` so editing a harness cannot re-arm gate:make-test. Pytest never collects it — `testpaths` is `test/` and `site/` — and pyright does not check it, since `[tool.pyright] include` names `tools`, `test`, `conftest.py` and `rebuild` only.

## Running it

`scaling/` and `levers/kernel_all_configs.py` need cargo, because they build and drive `ams-m1-kernel` itself — `rebuild/pipeline/kernel_exec.cargo_build` is what builds it, so the toolchain they ask for is the one any M1 build already asks for. `primitives/` and `ink-and-tsv/` need Go alongside Rust, since the three-language comparison is their whole point. Everything else is `uv run`.

| Directory       | What it answers                                                                                 | Entry point                           |
| --------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------- |
| `scaling/`      | How the fixpoint grows with the alphabet — the migration's early warning                        | `uv run python scaling.py`            |
| `levers/`       | The six-configuration endpoint through the kernel, plus the font-build and surface lever probes | `uv run python kernel_all_configs.py` |
| `ram/`          | What occupies the RAM high-water mark — the attribution runs behind issue #50                   | `uv run python attr_fold.py`          |
| `primitives/`   | Per-operation costs across the three languages                                                  | `zsh run.sh`                          |
| `ink-and-tsv/`  | The two smaller port candidates: placed-ink and TSV parsing                                     | `zsh run.sh`                          |
| `cut-the-work/` | Coverage levers no language change can reach                                                    | `zsh run.sh`                          |

`ram/` holds two harnesses, one per attribution the tracker's sub-issues are still gated on: `attr_fold.py` (the rust-engine fold path — `kernel_io.read_transitions` plus `assemble_tables`) and `attr_fixtures.py` (what the rebuild suite's session fixtures materialize per xdist worker). A third, `attr_fixpoint.py`, retired at #77 with the rest of the Python-fixpoint scaffolding: what a rung's fixpoint costs in memory is now `scaling.py`'s own per-rung figure, measured on the kernel process that ran it. Each phase records both the tracemalloc peak (compression-blind) and the process high-water, plus a top-allocation-sites table; `AMS_ATTR_TRACE=0` reruns either of them untraced for a clean high-water figure. Raw rows land in `ram/out/`; the curated record is `evidence/ram/`.

Two of those want a word of their own, because they are how a claim gets re-checked rather than re-argued. `scaling/scaling.py` walks the nested rune ladder and puts every rung through the crate: one `ams-m1-kernel enumerate-configs --configs=default --threads=1` child per rung, so the ladder times what a build runs. The rungs are cut from `rebuild/tools/kernel_parity.py`, the ladder's one authority — the sweep imports it rather than reproducing it. The child is what gets measured: its wall, its CPU, and its own peak resident set, reaped with it through `peak_rss.reap_peak_rss_bytes` so a row's `rss_high_water_gb` is that rung's figure rather than the running maximum an in-process sweep charged every rung with; the kernel's own `[t]` lines split the total into `spec_parse_s`, `enumerate_s` and `emit_s`. Each rung's stream is then folded the way a build folds its own — `kernel_exec.read_stream`, then `table.assemble_tables` — outside the timed region, which is what keeps `windows`, `rules` and `cells` the counts this sweep has always printed and what gives every row a `digest` at `table.table_digest`'s contract grain. The report is the consecutive-pair exponents against runes plus the whole-ladder least-squares fit in both denominators, runes and letters. The knobs: positional arguments are the rune counts to cut rungs at, defaulting to the whole ladder; `AMS_SCALING_DUMP=<dir>` keeps each rung's `spec-r<N>.json` and its `r<N>/transitions-default.ndjson` instead of letting a temporary directory take them; `AMS_SCALING_BINARY=<path>` measures that binary as it stands rather than building the crate, which is the arm-at-another-revision knob; and `AMS_DEEP_CLASSES=0`, `AMS_SIMULATED_PROSPECT=0` and `AMS_VOTE_SLOTS=0` reach the child through `kernel_exec.world_flags()`, with every row's `world` naming the flags that rode. Rows are written to `scaling.json` beside the script, which is gitignored; `scaling.txt` is the checked-in sample of a run. Before comparing against an older row, know which arm it is: a pre-#77 row is the Python one, and the child's time now includes emitting the stream, so the two compare on exponent and not on constant.

`levers/kernel_all_configs.py` is the endpoint's arm of record, with no Python sibling left to read beside it: it dumps the live spec, hands it to `ams-m1-kernel enumerate-configs` over the same `conform.ACCEPTANCE_CONFIGS` a build answers, and prints a row per configuration. `--mode serial` is `--threads=1`, the arm a serial loop is comparable to; `--mode parallel` fans the configurations out, as wide as the machine allows unless `--threads` says otherwise. Streams go to files rather than through a pipe so the measurement is not charged for stdout plumbing, the child is what gets timed (`/usr/bin/time` for the peak resident set, `RUSAGE_CHILDREN` for the CPU, the kernel's own `[t]` lines for the per-configuration walls), and every row carries the sha256 of its stream so runs at different widths are comparable at a glance. One thing to know before running the parallel arm on a small box: the peak resident set is per configuration and a fixpoint's working set lives until it has emitted, so a full-width run wants roughly the serial peak times the configurations in flight. Do not size the box by a wide run's own reported peak either: when its system time dwarfs its user time, darwin is compressing pages to keep the run resident and the peak it reports understates what the run actually wanted, so the serial peak times the width stays the figure to plan against. `--rung N` cuts a rung of the scaling ladder instead and times the default configuration alone on it, which is how one rung is re-timed; `--spec` measures a dump already written — the one `scaling.py` leaves under `AMS_SCALING_DUMP` — and names a spec rather than a set of configurations, so a bare `--spec` over a rung dump times all six where the `--rung` that wrote it timed one.

Each harness prints one JSON object to stdout and leaves its raw output in its own `out/`, which is gitignored along with cargo targets and Go build products.

## What is checked in, and for how long

- **Harness source** — the durable part. Kept as long as the question can be re-asked. The Python-kernel harnesses retired at #77 because theirs cannot be: the fixpoint they measured is the crate's now, and git preserves them.
- **`fixtures/`** — real inputs extracted from the repo (memo keys, shaped runs, outlines, baseline rows) so `primitives/` and `ink-and-tsv/` run without regenerating them. Live build inputs, not evidence.
- **`evidence/`** — now only `evidence/ram/`: the attribution record behind issue #50's sub-issues, `attribution.md` with the `raw/` rows every figure in it cites. This is the proof pile for a still-open fork; per the repo's note-taking rules it goes when the fork closes.

`evidence/ram/` is a snapshot of one study on one machine. Where it and a harness disagree, **the harness is right** — re-run it.
