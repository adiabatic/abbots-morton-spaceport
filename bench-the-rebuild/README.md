# bench-the-rebuild

Measurement scaffolding, built for one question that is now answered: **is Python what makes the rebuild slow, and would a Rust or Go port help enough to be worth it?** The port landed and the kernel crate is the engine of record; `RUST-PORT-PLAN.md` holds the decision, the thresholds it turned on, and the design facts that came out of measuring it. What is left here has a job the answer did not retire: `scaling/` is the migration's early-warning ladder, driven through the kernel crate like everything else that builds a fixpoint now; `levers/kernel_all_configs.py` is the all-configuration endpoint's kernel arm, with the font-build and surface lever probes beside it; `rebuild/tools/peak_rss.py` is the one yardstick every RSS figure in this tree goes through, and it is what the surviving harnesses report their high-water marks through now that `ram/` has retired with the Python fold it attributed; and `ink-and-tsv/`, `primitives/` and `cut-the-work/` price the port candidates and the coverage levers no language change reaches. This file says what is here and how to run it.

Everything here reads the repo and writes only under this directory. Nothing in `make test`, `make all`, `make test-rebuild` or the artifact cycle touches it, and `make_test_exempt` (in `rebuild/tools/artifact_cycle.py`, the authority on what sits outside gate:make-test's closure) exempts `bench-the-rebuild/` wholesale, so editing a harness cannot re-arm the gate. Pytest never collects it — `testpaths` is `test/` and `site/` — and pyright does not check it, since `[tool.pyright] include` names `tools`, `test`, `conftest.py` and `rebuild` only.

## Running it

`scaling/` and `levers/kernel_all_configs.py` need cargo, because they build and drive `ams-m1-kernel` itself — `rebuild/pipeline/kernel_exec.cargo_build` is what builds it, so the toolchain they ask for is the one any M1 build already asks for. `primitives/` and `ink-and-tsv/` need Go alongside Rust, since the three-language comparison is their whole point. Everything else is `uv run`.

| Directory       | What it answers                                                                                 | Entry point                           |
| --------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------- |
| `scaling/`      | How the fixpoint grows with the alphabet — the migration's early warning                        | `uv run python scaling.py`            |
| `levers/`       | The all-configuration endpoint through the kernel, plus the font-build and surface lever probes | `uv run python kernel_all_configs.py` |
| `primitives/`   | Per-operation costs across the three languages                                                  | `zsh run.sh`                          |
| `ink-and-tsv/`  | The two smaller port candidates: placed-ink and TSV parsing                                     | `zsh run.sh`                          |
| `cut-the-work/` | Coverage levers no language change can reach                                                    | `zsh run.sh`                          |

`ram/` is gone, its last harness with it. `attr_fold.py` traced `kernel_io.read_transitions` plus `assemble_tables`, which was the build's own per-configuration fold until the crate's `build-tables` verb took it over and the Python fold was deleted; there is no such path to attribute any more, and where the RAM goes now is the kernel's own `--cache-census` and `scaling.py`'s per-rung process high-water. Its siblings had gone before it: `attr_fixpoint.py` at #77 with the rest of the Python-fixpoint scaffolding, and `attr_fixtures.py` when the rebuild suite's whole-workload session fixtures it measured were deleted, the validators lane's per-worker peak now being the line every run prints.

Two of those want a word of their own, because they are how a claim gets re-checked rather than re-argued. `scaling/scaling.py` walks the nested rune ladder and puts every rung through the crate: one `ams-m1-kernel build-tables --configs=default --threads=1` child per rung, so the ladder times what a build runs. The rungs are cut from `rebuild/tools/kernel_parity.py`, the ladder's one authority — the sweep imports it rather than reproducing it. The child is what gets measured: its wall, its CPU, and its own peak resident set, reaped with it through `peak_rss.reap_peak_rss_bytes` so a row's `rss_high_water_gb` is that rung's figure rather than the running maximum an in-process sweep charged every rung with; the kernel's own `[t]` lines split the total into `spec_parse_s`, `enumerate_s` and `fold_s`. `windows`, `rules` and `cells` are read off the artifacts that child wrote — the head of its window payload, then its body counted a line at a time — and every row's `digest` is the contract-grain scalar the child reports on stdout, at exactly `table.table_digest`'s grain; nothing on this side folds or materializes anything. The report is the consecutive-pair exponents against runes plus the whole-ladder least-squares fit in both denominators, runes and letters. The knobs: positional arguments are the rune counts to cut rungs at, defaulting to the whole ladder; `AMS_SCALING_DUMP=<dir>` keeps each rung's `spec-r<N>.json` and the artifacts its child wrote under `r<N>/` instead of letting a temporary directory take them; `AMS_SCALING_BINARY=<path>` measures that binary as it stands rather than building the crate, which is the arm-at-another-revision knob; and `AMS_DEEP_CLASSES=0`, `AMS_SIMULATED_PROSPECT=0` and `AMS_VOTE_SLOTS=0` reach the child through `kernel_exec.world_flags()`, with every row's `world` naming the flags that rode. Rows are written to `scaling.json` beside the script, which is gitignored; `scaling.txt` is the checked-in sample of a run. Before comparing against an older row, know which arm it is: a pre-#77 row is the Python one, a row carrying `emit_s` is from the enumerate-and-fold-in-Python arm, and the child's time now covers the fold as well, so any of those compares with a current row on exponent and not on constant.

`levers/kernel_all_configs.py` is the endpoint's arm of record, with no Python sibling left to read beside it: it dumps the live spec, hands it to `ams-m1-kernel enumerate-configs` over the same `conform.ACCEPTANCE_CONFIGS` a build answers, and prints a row per configuration. `--mode serial` is `--threads=1`, the arm a serial loop is comparable to; `--mode parallel` fans the configurations out, as wide as the machine allows unless `--threads` says otherwise. Streams go to files rather than through a pipe so the measurement is not charged for stdout plumbing, the child is what gets timed (`/usr/bin/time` for the peak resident set, `RUSAGE_CHILDREN` for the CPU, the kernel's own `[t]` lines for the per-configuration walls), and every row carries the sha256 of its stream so runs at different widths are comparable at a glance. One thing to know before running the parallel arm on a small box: the peak resident set is per configuration and a fixpoint's working set lives until it has emitted, so a full-width run wants roughly the serial peak times the configurations in flight. Do not size the box by a wide run's own reported peak either: when its system time dwarfs its user time, darwin is compressing pages to keep the run resident and the peak it reports understates what the run actually wanted, so the serial peak times the width stays the figure to plan against. `--rung N` cuts a rung of the scaling ladder instead and times the default configuration alone on it, which is how one rung is re-timed; `--spec` measures a dump already written — the one `scaling.py` leaves under `AMS_SCALING_DUMP` — and names a spec rather than a set of configurations, so a bare `--spec` over a rung dump times every configuration in `conform.ACCEPTANCE_CONFIGS` where the `--rung` that wrote it timed one.

Each harness prints one JSON object to stdout and leaves its raw output in its own `out/`, which is gitignored along with cargo targets and Go build products.

## What is checked in, and for how long

- **Harness source** — the durable part. Kept as long as the question can be re-asked. The Python-kernel harnesses retired at #77 because theirs cannot be: the fixpoint they measured is the crate's now, and git preserves them.
- **`fixtures/`** — real inputs extracted from the repo (memo keys, shaped runs, outlines, baseline rows) so `primitives/` and `ink-and-tsv/` run without regenerating them. Live build inputs, not evidence.
