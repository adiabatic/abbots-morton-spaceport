# Table-diff review corpus

## TL;DR

`engine/review/` is the source of a static review app, which the build writes to the gitignored `engine/out/review/`. The artifact cycle builds and serves its corpus: the accepted build, as a snapshot of one build holds it, against the working tree's build (§ The table diff below). Each unit renders side by side in the accepted build's font and the new build's through two `@font-face` rules, with the changed pair highlighted, the row's `font-feature-settings` applied, boundary marks, a one-line summary, and a note field. A verdict covers the whole unit, meaning every config in its config set. A unit whose two renderings the build shows to be equivalent is approved by machine and is not queued for review.

The sections below cover the keys, the explain panel, the triage flow, the kerning view, the table diff, and the mechanisms that approve units before a person sees them. The design record behind them is `doc/review-design.md`: the architecture, the data model, and the contract between the build and the app.

### Commands

```sh
make review-build                                     # regenerate engine/out/review/, the table-diff corpus
make review-serve                                     # serve it on http://localhost:7294/
uv run python -m engine.review.build                 # the same build, run directly
uv run python -m engine.review.serve                 # the same server, run directly
uv run python -m engine.review.snapshot take        # snapshot engine/out/build under var/keep/review-snapshot/
uv run python -m engine.review.build --out tmp/review-diff   # the current snapshot against engine/out/build
make review-accept                                    # the four-letter sweep and a dry run of the accept; ARGS=--apply takes the snapshot and empties the store
make review-snapshot-remake                           # remake the snapshot engine/review-snapshot.json names on a machine without it
```

The build runs in one Python process and builds the whole corpus each time; the cycle skips it when the served corpus already shows these inputs (`artifact_cycle.corpus_build_skippable`).

The review server uses port 7294, so it can run at the same time as `make serve` (`tools/serve.py`, port 7293).

## Quick start for triage

### Kerning is disabled

Both columns render with kerning off: the sample cells set `font-kerning: none`, which combines with each row's `font-feature-settings`. Every comparison the build makes (ink identity, highlight x-ranges, boundary-mark positions) shapes with `kern: False` in both fonts (`ink.kern_neutral`), but for the kern units (§ The table diff): each shows a moved kern value, so it is shaped, compared and drawn with kerning on in both columns.

### Keyboard map

The in-app help overlay (`?`) lists every key, and `KEY_MAP`, `REJECT_MENU_MAP`, and `NEITHER_MENU_MAP` in `static/keyboard.js` define them.

The four main verdict keys are on the left home row: `a` skip, `s` reject, `d` fine either way, `f` approve. `e` records identical and `c` records neither. `a`, `d`, `e`, and `f` record the verdict and advance to the next unit. `s` and `c` open a small menu beside the row's verdict buttons, where a second key records the verdict with no comment, with a canned note, or with a custom comment, and a digit reuses a recent note. A canned note replaces whatever was in the note field. `Escape` or a click outside the menu cancels with no verdict, and the other shortcuts are off while the menu is open. `Backspace` or `Delete` clears the current unit's verdict, and pressing a unit's active verdict key again also clears it. `u` undoes the most recent verdict from anywhere. `g` approves every unverdicted unit in the cursor's group. Shortcuts are off while a note field has focus; `Escape` leaves it.

Reject means the old behavior should come back. Neither means both behaviors look wrong, so the unit needs new authoring work. Identical means the reviewer cannot see the flagged difference in the highlighted portion; that is feedback for the ink comparator and highlight tooling, not a judgment on either font.

A verdict covers every config in the unit's config set. Most units show no config badge because they show their change under every configuration of the roster (`tablediff.SETTLED_CONFIGS`). A badge such as "only when ss03 is on" marks a narrower set; hover it for the full list.

Approving a unit outlines its after sample in green, rejecting draws a red X over the after sample, either outlines both samples in green, and neither draws the red X over both. The row's recorded verdict drives these marks, so they persist through re-render and import and clear on undo.

### Reading the explain panel

Every row shows a one-line summary under the renderings: what changed, in rune-name notation, for example "·Pea and ·May (qsPea.ex-y0 + qsMay.en-y0) no longer meet in a join at the baseline". The Why? button, or `x`, opens the full panel:

- **Explain** names the change, the configurations it shows under, how the unit's text was found, and the changed rows of the accepted and the new tables the unit stands for.
- **Provenance** lists the `glyph_data/runes/*.yaml` records the new rows credit.

### Triage flow

- The sidebar, headed "Kinds of change", lists every class by its title and summary in two sections: Open questions and a collapsed No review needed (§ Sections below). Clicking a class filters to it and opens its class header, which shows the title, id, summary, a sentence for its section and the class's `why`. Every class with units in the current batch or worklist has a light accent outline, and the class holding the cursor unit has the full cursor-blue outline; both are separate from the border that marks a clicked class filter. Within a class, units are grouped by lead-family pair (each group folds, with a button that approves its unverdicted units), ordered by code point, and paged in batches of `audit.BATCH_SIZE`; the toolbar arrows page batches, and `[` and `]` change class. A `#class=` link to an id the corpus does not have (an old id, say) toasts and clears the filter.
- The header strip starts with a chip showing the corpus's unit total. Its popover shows the generation stamp and head, how many letters have rune files, and the total split into machine-approved units (by machine check), units of the classes that take no verdict, and units left for human review, which is the Overall denominator. After the chip come Overall progress with per-verdict tallies, the selected class's progress when a class filter is on, and the current batch's progress. A batch can span classes and a class can span batches, but selecting a class narrows the batch list. Each sidebar entry's counts line (`classCountsLine` in `static/render.js`) depends on its section: "to review" in Open questions, counting blank and skipped units, then "done"; "all N done" once nothing is left; and the unit count with "no verdict needed" or "all machine-approved" in No review needed. Progress counts cover the human units only.
- Machine-approved units (ink-identical or picture-identical) and units in no-verdict classes are hidden by default. The toolbar's "Show units that need no review" toggle (`machine=1` in the URL hash) shows them in collapsed folds by class below the human units. Each row has a badge (its machine check's "… — machine approved", or "no verdict needed") and disabled verdict buttons whose title says why no verdict is needed. A `#unit=` link to one of these units while the toggle is off shows that one unit until you navigate away, and leaves the toggle and the URL unchanged. Keyboard navigation, auto-advance, and `g` cover the human units only.
- View state lives in the URL hash (`STATE_KEYS` in `static/state.js`), so reloading or sharing the URL restores the view. Verdicts autosave. After every change the app POSTs the verdicts it set or cleared (an `ams-review-verdicts-delta/1` body, never the whole store) to the serve script's `/autosave` endpoint. The server keeps the store in memory (`engine/review/verdict_store.py`) and, for each save, rewrites `verdicts-autosave.json` at the repo root whole, through a temporary file renamed over it, before it answers. It applies each save under the verdict store's lock (`engine/review/store_lock.py`), which the land and the table-diff accept also hold, and answers a save made while another writer holds it with a 503. Every change is also written to the tab's outbox in localStorage (`static/outbox.js`) when it is made and stays there until the server acknowledges it. A save refused with a 503 or cut off by a network error is retried on a doubling backoff (`AUTOSAVE_RETRY_FIRST_MS` to `AUTOSAVE_RETRY_MAX_MS` in `static/app.js`), and the status bar reads "N verdicts kept in this browser, saving…" meanwhile. The save a closing tab sends is not retried, and the next page load sends what the outbox still holds (`planOutboxReplay` in `static/outbox.js` offers entries older than `REPLAY_MAX_AGE_MS`, and entries whose set the server would refuse, as a download instead, and `unsavedFiles` in `static/verdicts.js` puts the records an Import would refuse in a separate file per corpus, apart from the rest of their corpus's entries). That file is outside `engine/out/review/`, which a pass's land replaces as a whole. On load the app restores an autosave whose stamp matches the manifest, and afterward it asks `/autosave?since=<token>` for only what other sessions changed. A reload, crash, or closed tab loses no work, and the size of a save does not grow with the number of verdicts in the store. Each save sends `base_at`, the `at` of the record the tab last saw the server hold. A tab loaded on an earlier corpus keeps saving: the server carries its changes onto the store by unit id, a unit's id being its content key, as long as the store is on the served corpus. A save made on the served corpus while the store is still on another one carries the store onto the served corpus by unit id, as the land does, and a save made on neither gets a retryable 503. A skip made on an earlier corpus is dropped, as the carry drops every skip, and the tab shows the unit blank again. A change the store cannot apply is kept in `var/verdict-orphans/<stamp>.json` and reported to the tab: a conflict (the store holds a newer record, or a newer clear) makes the tab adopt the store's record and show a "Reapply N conflicted" button, which the tab keeps in its sessionStorage across a reload, the one onto a rebuilt corpus included, and an orphan (a unit outside the served corpus's human units) is announced in a toast. The readiness banner shows the conflicts and orphans recorded since the page loaded, or since the page it moved from loaded. The outbox is kept per checkout, keyed by the repo root the server names on `/capabilities`, because every checkout's server listens on the same port. `engine/review/verdict_store.py` states the rules. On load the app does not restore an autosave stamped for another corpus, and says so in a toast. The warnings about unexported verdicts (the beforeunload prompt and a toast every 50 unexported verdicts) appear only when autosave is not working, for example when a server without the endpoint serves the corpus, and the beforeunload prompt appears only when the outbox cannot be written either. When autosave works, the status bar's unexported count ends in "(autosaved)".
- **Moving onto a rebuilt corpus.** The server reloads no tab when a file changes. The cycle sends `ams:corpus/<generated_at>` or `ams:assets/<static hash>` through livereload's `/forcereload` after it changes what the server serves, and `static/reload-plugin.js` hands the path to the app. A tab also moves when a save's reply or `/status` names a corpus other than the one it loaded, or when a byte-range read finds another build's record where its index points; the readiness banner reads "Moving onto the rebuilt corpus…" meanwhile. The app sends its unsaved changes, waits while the reader has text in a focused field (and, in a hidden tab, until the tab is shown), saves the scroll position, the queue anchor, and note drafts in sessionStorage, and reloads at the same URL hash. A reload that finds the page still on the corpus it left does not try the same move again, and the banner then reads "Corpus rebuilt since this page loaded" and asks for a reload. `static/reload.js` holds the rules.
- **The queue view** (the header's Queue button, `#view=queue`) is the live queue of the blank human units in Open questions, where blank means unverdicted or skipped. It groups them by the build's `cluster` signature, a digest of the pixels each unit's change paints, so one visual change that recurs across letter contexts, configurations and kinds of change is one card. The largest decisions come first: the first `TOP_CLUSTER_COUNT` clusters as cards with exemplar renderings and evidence from judged lookalikes, the remaining clusters as a compact table, and singletons in chunks of `SINGLETON_CHUNK` (all in `static/queue.js`). Every button is a `#units=` worklist link that carries `queue=1`, the key of the decision it stacks (`decision`: a cluster's signature, or `#singletons` for a singleton chunk), and the corpus's `generated_at` stamp, so judging uses the normal keyboard flow. Finishing a worklist opens the next decision by itself: the first one this browser has not yet opened, so leaving a card postpones it, the last open singleton included; once every open decision has been shown, the one shown longest ago comes back (`nextQueueDecision`). The rotation is kept across corpus rebuilds, because a decision's key is its cluster signature. A tab that resumes a worklist stamped for another corpus build keeps the units the new corpus still has, since a unit's id is its content key, and goes to the live queue only when none are left (`queueResumeAction`). The view recomputes from the in-memory store as verdicts are recorded, so clusters shrink, empty, and move up with no new snapshot. The view reads each class's `section` from the manifest and keeps no status list of its own. Any filter or class click leaves the view.
- Each row shows the code point string in both fonts on a checkered background. The changed pair has an amber band drawn from x-ranges in font units that the build computes; the app never measures text. A dotted line marks each boundary token (space, namer dot, or ZWNJ). To the right of each magnified cell, which is only as wide as its run, the same run appears stacked at 22px and at 11px (two font pixels per CSS pixel, then one; on a screen with exactly two device pixels per CSS pixel the 22px line is 16.5px, three device pixels per font pixel), with no checkerboard or marks. The row also has the one-line summary, a Copy button that copies a prompt preamble for the unit, and a Why? button (or `x`) that opens the explain panel. Regions without a mark render identically in both fonts or differ only in glyph names.
- The text lines use the same amber: the notation line (·May·Oy·It·May) and the code point line (E665:E679:E670:E665) underline the changed pair's tokens in the band's `--hot` color. The build computes the mapping (`pair_codepoints`, a span of code point positions, and `notation_tokens`, one per code point position) because ligatures make glyph positions differ from code point positions. A unit with no primary pair shows both lines unmarked.
- No chip strip lists every config a unit diverges under, because for most units (those that show their change under every configuration) it would say nothing. A unit whose config set is informative has a badge of inert chips, one per stylistic set that pins the set down. Each chip uses its set's color, is lit when the set must be on and muted when it must be off, and is glossed with the set's `feature_descriptions` entry. `build.config_badge` computes both the chips and their text: it finds the smallest conjunction of on/off constraints that selects exactly the unit's config set, and falls back to one literal "only under: …" chip when no short conjunction does. The app renders each clause's `text` as given. The badges mark the cases that matter for judgment (ss03-gated, ss03-excluded, and narrower two- and three-set conjunctions), which also explain the row's `font-feature-settings`. Each chip's title lists the full config set. The queue view's cluster headers show the same chips.
- The build groups a unit's configs by rendered outcome into `render_groups`, and the app draws each group after the first stacked below it, with its own config label and feature settings.
- A verdict always covers the whole unit.
- _Export_ downloads `verdicts.json` (format `ams-review-verdicts/1`, notes included), which holds the store's records. _Import_ merges an earlier export by unit id and asks before merging a file stamped for a different manifest, so triage can span sessions. `verdicts-autosave.json` holds the verdicts made since the last accept, which empties it; downloaded exports are durable copies of them.

## The kerning view

The header's Kerning button opens the kerning view (`#view=kern`): every pair of letters that meet at a break, drawn from the last build's pixels with the kern values the rune files set, which it edits. `doc/kerning-design.md` §6 is its contract. A value lives in the leading letter's rune file, in its `kern:` block: the view writes it there within about a second of the last press, and a value written there by hand shows at the next refresh. It shapes nothing. It draws every glyph from `kern-inventory.json`, which the build writes beside the font, at the pen positions the build computed and checked against the font with `kern` off, and moves each break by its value. The review server serves the inventory and the values (`engine/review/kern_routes.py`) straight from `engine/out/build`, so a kern-only cycle pass, which lands no corpus, reaches the view too.

- **Opening it.** The Kerning button, or a link with `#view=kern`. The hash also carries the focused pair of letters (`pair=qsNo:qsTea`) and facing pair (`facing=`), and a link's list of pairs (`pairs=`, below), so a reload or a shared link reopens the same place. The sidebar is hidden while the view is open, and any sidebar or filter click leaves it, dropping all three from the hash.
- **A list of pairs.** A link can name the pairs of letters to judge, in order: `#view=kern&pairs=qsSee:qsOwe,qsZoo:qsOwe,qsHe:qsOwe`, comma-separated, each `lead:follow` by family name, a ligature as the inventory names it (`qsDay_qsUtter:qsTea`), each listed once. In place of the grid the view then shows only those pairs, in that order, one row each: the two letters' names and the pair's grid cell, drawn as the grid draws it, value, `×N`, chips and marks included. The detail panel beside it and the keys act on the focused one as they do in the grid, but for the keys that step from pair to pair: the arrows move to the previous listed pair (up and left) or the next (down and right), held at either end; `]` and `[`, and up and down past the first or the last facing pair, move to the next and the previous listed pair, stopping at either end; and `g` moves on to the next carried-over facing pair among the listed pairs alone. `pair=` names the focused pair; with no `pair`, or one not in the list, the first listed pair is focused. A listed pair whose family the inventory does not have, or that is not written `lead:follow`, keeps its place with its name and a note in red, and the cursor passes over it; one whose letters never meet at a break keeps its place with a blank cell and a note saying so. A line above the list counts the listed pairs, and its **Show the whole grid** button leaves the list for the grid, keeping the focused pair. Any other move to a pair outside the list leaves the list the same way: a jump box entry (`/`) that names an unlisted pair (one that names a listed pair stays in the list), `r` and `w`, the move after `a`, and a click on a relative's tile. Leaving the list is a new history entry, so the browser's Back returns to it.
- **The grid.** The leading letter runs down the side and the following letter across the top, each ligature after its first letter. A cell draws the pair's representative facing pair at its value: the shapes the two letters settle to when written alone, where they break there, or else the facing pair that covers the most glyph pairs. The value is in the cell's top left corner when it is not 0, and `×N` in its top right says the two letters have N facing pairs. A chip at the foot says when they meet only across a ZWNJ (`ZWNJ`), only under ss10 (`ss10`), or only in those two ways. A blank cell's letters never meet at a break. A dashed outline marks a cell with a value the built font does not have yet: one set or changed since the last build, which `make artifact-cycle` makes.
- **The detail panel** shows the focused cell. The facing pairs of the two letters are listed by second shape, under a line naming it when there are several (`before ·Way[half]`), so every stance of ·Ye before half ·Way stands together; only the pairs with the selected pair's second shape are listed in full, and the others take one line each, with their value, until one is selected. Each facing pair listed in full is drawn in a text whose settlement puts that pair side by side: a word from The Manual when there is one, otherwise a short text found for it. The two shapes at the junction are in color, and the line beside them gives the text's notation, the two sides' names, how many glyph pairs the facing pair covers, what reaches it (mid-word, across a ZWNJ, under ss10) and in which configurations, the closest ink across the junction (touching or overlapping ink is flagged), and the value with the record that decides it, marked when the built font has another one. A facing pair whose side mixes shapes no record can tell apart (a `mixed` side) shows each of its drawings, and its closest ink is the worst of them: a pixel both shapes ink is an overlap, and strokes that pass each other without one are named as such. A facing pair with no such text shows its two shapes alone and says so. Below them come the joined pairs of the same two letters, drawn and marked as not kerned (a join's length is `extend` and `contract`), and the words from The Manual that hold the two letters, each drawn with every value applied: first the words where the two letters break, with the closest ink at that break, then the words where they only join, each saying at what height.
- **Staleness.** Lines under the title say when the shapes are the last build's because the runes or the build code changed since, when the inventory was built over other tables, when the Manual pages changed since it was built, when a cycle pass is running, and when the rune files' `kern:` blocks do not resolve, in which case they list the errors and the view shows the built values. The view asks the server again every few seconds while it is visible and when the window regains focus, and loads the new inventory when a build has written one. A request that fails, as while the server restarts, keeps the values the view has and says they could not be refreshed, and a view whose inventory did not load, before the first build or during a restart, tries again at the next poll.
- **Editing.** The box at the top of the detail panel holds the scope a change sets, which its two buttons choose: **This shape pair**, the selected facing pair's own record, or **All unjoined ·X·Y**, the record that names only the two letters, which every facing pair of the two takes unless it has a record of its own. With the second chosen, each facing pair that moves with it is outlined, and one that keeps a value of its own says so and from which record. The box shows the scope's record as the line its rune file holds and the file's name, or says the file holds none, and the record's note. A change moves the drawings at once and is written after a third of a second with no further press, so a run of presses is one change; until the server answers, the box and the facing pair say the change is being written. The server checks the result as the next build would (the spec loader, the kern stage and the defect gate's contact check at the new offsets) before it writes anything. A value equal to the one the scope takes without a record of its own leaves no record, and the box says so. A grid cell's value is its representative's.
- **Refusals.** A change the build would refuse, an ink overlap the allow list does not bless, a kern error or a loader error, writes nothing: the drawing goes back, and the box shows the server's message with the build's first errors, which a toast repeats. A change made against a block that moved on disk since the view's last poll, as when a pass's held changes were just written, is sent once more against the block as it stands; a second conflict writes nothing either, after which the view holds the block as it stands. A change to a file whose block the editor cannot write back exactly is refused too, and the box names that block beforehand with what to fix by hand (a comment or a blank line in the block, a multi-line `why`, a record not on one line of its own, lines that do not all end alike). A value past 64 pixels either way is refused before it is sent.
- **Undo.** `u` drops the newest change not sent yet, and otherwise undoes the newest change this tab sent that the server wrote or is holding for a pass, by its number in the journal. One still waiting for a pass is cancelled. A written one is undone only while it is the newest change the server wrote, from any tab, and its block still holds what it wrote; otherwise the box says why and nothing changes. A press that changed nothing is not a change to undo, and a reload starts the tab's undo afresh. The changes live in `var/kern/journal.ndjson`, which is outside version control.
- **During a cycle pass.** While a pass reads the runes, the server holds every change and undo in the journal, and the view keeps the change in the drawings, marked as waiting, with a line under the title saying how many wait. When the pass ends they are written in order, each checked again against the file as it then stands; one that no longer applies is dropped, and a line says why.
- **Reaching the font.** A written value is in the rune file at once and in the view at once, marked as not in the built font yet. The next `make artifact-cycle` finds that only `kern:` blocks moved and runs a kern-only pass (`run_build --kern-only`), which recompiles the font over the tables on disk and lands no corpus; the mark goes once that pass has written the font.
- **Relatives.** Under the facing pairs, the detail panel lists the selected facing pair's relatives: the facing pairs whose junction is the same one, its mirror image (`·Ah | ·Low` and `·Llan | ·Awe`), the same junction upside down, or turned half round. A junction is every gap between the two sides' ink on one row or on neighboring rows, and two are the same when they agree on every gap less than 3 px looser than the closest one, so ink set well back, such as a ligature's second letter's stem, counts for nothing; a relative that agrees on every gap says "pixel for pixel". The relatives are grouped by the value each has, those with another value first, as tiles: each is drawn small as its two shapes alone at its value, after a tile of the selected pair drawn the same way, with its name, its relation in a word (`≈` before one that is not pixel for pixel), and `−` and `+` buttons that kern it in place as its own record. The rest is in the tile's tooltip, and a click on a tile goes to its pair. A group of relatives with more than one value is kerned inconsistently: the header line counts such groups, their cells carry `≠` at the top of the cell in the grid, and their rows say so. `r` and `w` go to the next and the previous one, `t` sets the selected facing pair to the value most of its relatives have (a group's "take" button picks a particular value), `v` gives the selected pair's value to every relative that has another, each as its own record in its own leading rune's file, and `a` marks the selected pair as kerned apart from its relatives on purpose and goes on, or takes that mark off. A pair marked apart is compared with none of its relatives, a group's "mark these apart" button marks every relative at one value, and the marks are in `var/kern/apart.json`. **Near relatives**, listed after them, are facing pairs whose junction differs by at most 3 px in all, where a value may rightly differ: they are drawn for comparison and are in no count.
- **Comparables.** Three buttons at the top of the relatives section, and `c`, choose what it compares the selected facing pair with: **Same junction**, the relatives above; **Like ·X before ·Y**, every facing pair with the same second shape whose first shape is like the selected pair's (with `·Ye[loop] | ·Way[half]` selected, the letters shaped like ·Ye before half ·Way); or **Like ·Y after ·X**, the same for the second shape. Two shapes are alike when their facing edges differ, row by row, by little more than a constant, the distance each is set from the junction: within a pixel for each row of the selected shape's edge, with 4 px for a row only one of them inks. The like ones are listed most alike first, as tiles named by the shape that differs, and a button lists the rest of that column or row of the grid. Each tile gives how far apart the pair's ink is where it is closest, rows one apart counted, in color when that differs from the selected pair's; its tooltip says how far its shape is from the selected one and how much further from the junction, or nearer to it, its ink sits. A tile's `−` and `+` buttons tighten and loosen that pair in place, as its own record, and `=` sets it to the selected pair's clearance. `t`, `v` and `a` act only while the section lists the relatives.
- **Carried over from the old font.** Every facing pair the import of the old font's kerning set (`var/kern/imported.json`) is marked carried over until the author has reviewed it: `old` at the foot of its grid cell and a line on its detail row, and a count in the header line. `g` in the detail panel marks the selected scope's carried-over pairs reviewed and moves to the next carried-over pair (from a scope with nothing carried over or already marked it only moves), and the **reviewed** button does the same or takes the mark off when they all have it, and changing a pair's value marks it too, a mark that undoing the change takes off; the marks live in `var/kern/reviewed.json`. `]` and `[` jump to the next and the previous pair of letters that still has one. A pair whose value moved since the import, by the editor or by hand, no longer counts. The marks name facing pairs by their sides, so when a later build splits or renames a side (·Bay becoming `qsBay[sole]` once a second edge appears), its imported and reviewed entries no longer reach a pair: the header line counts them, and a line under the title says so when `var/kern/reviewed.json` cannot be read.
- **Keys.** The view opens with the detail panel focused when the selected pair of letters has a facing pair, and with the grid focused otherwise; the focused pane has an outline. The arrows move the grid's cursor (`e`, `s`, `d` and `f` move it up, left, down and right too), `-` and `=` tighten and loosen the focused pair of letters by a pixel (the **All unjoined** scope) without leaving the grid, and `Enter` moves to the detail panel. There `↑` and `↓` (or `e` and `d`) choose a facing pair, and past the last or the first one move on as `]` and `[` do, `←` and `→` (or `s` and `f`) tighten and loosen the chosen scope, `0` drops the scope's own record, `n` opens a one-line field for its record's note (`why:`, saved with `Enter`, removed by saving it empty, `Escape` cancels), and `Escape` returns to the grid. `g` marks the scope's carried-over pairs reviewed. `u` undoes in either pane, `]` and `[` find the carried-over pairs (in a list of pairs, the listed pairs), and each key but those two has a button in the box that shows its key. `Enter` on a focused button keeps its own meaning. `/` jumps to a pair of letters typed by name (`·no·tea`, `no tea`, `·day+utter·tea`), and `?` lists every key. The verdict keys do nothing in this view. `KERN_GRID_MAP` and `KERN_DETAIL_MAP` in `static/keyboard.js` define the keys.

## The table diff

The artifact cycle builds this corpus and lands it (`doc/review-cycle.md` § The table-diff accept and the snapshot), and `uv run python -m engine.review.build --out <dir>` builds it by hand: a corpus of what changed between the current snapshot of the accepted build (`--snapshot` names another) and the build in `engine/out/build` (`--new` names another). The before column draws the snapshot's font and the after column the new build's, both with kerning off but for the kern units. `doc/review-design.md` §2.3 is the design, and the module docstrings of `engine/review/snapshot.py` and `engine/review/diff_units.py` give the snapshot's layout and how the units are found.

- **What a unit is.** Each unit is one visible change, not one changed table row: in **Settlement**, a letter that settles to another cell than in the accepted build, whatever its left neighbor (the explain panel lists the left glyphs it was seen after), and in **Joins**, a pair of settled cells that meets differently (a pair that is gone, a new pair, or a moved junction or extension). Each unit is drawn in its shortest text that shows the change, and one unit lists every configuration that text shows it under, so its config badge says where it holds. Changes that show the same text under the same configurations are one unit: a join row that is gone, the row that takes its place and the cell change at that junction are judged once, under **Joins**, and the row key and the explain panel name each of them. A join row no text is found for is shown by its notation alone and needs a verdict. A letter whose rows changed where no text shows it drawn differently is machine-approved when every text tried draws alike, and **Provenance only** lists the letters whose rows changed only the records they credit, which take no verdict.
- **The Queue.** Units that show the same pixels share one card, whatever their configurations and whether they are joins or settlement, so one join edit is usually one card. With no unaccepted change the Queue says so, naming the snapshot's commit, and a machine with no snapshot builds a corpus with no units, whose kerning view still works.
- **Explain.** The panel names the change, the configurations, how the text was found, and the changed rows of the accepted and the new tables the unit stands for.
- **Glyphs.** A glyph drawn differently than in the accepted build, its outline, its advance and sidebearing, or its cursive anchors, with the tables unchanged, is a unit in **Glyphs**, shown in the shortest certificate that settles to it, else its code point alone, else a kerning-inventory text that holds it, else its letters under ss10. Latin, Shavian and the other glyphs outside Quikscript are units too, in the group `non-quikscript`, shown by their code point. A letter's bare glyph, which no text draws, is a unit with no text, and such glyphs of one letter share a Queue card.
- **Kerning.** A facing pair kerned by another value than in the accepted build is a unit in **Kerning**, drawn with kerning on in the kerning inventory's text for the pair. It takes no verdict: the kerning view is where kern values are judged, and the sidebar and the Queue still count these units.
- **Verdicts across edits.** The land carries the store onto each new corpus by unit id, and a unit's id is its content key, so a verdict stays while later edits leave its unit's change as it was, and goes to `var/verdict-orphans/` once an edit changes or reverts it.
- **Accepting.** Once every unit needing a verdict is verdicted and none is rejected or neither, `make review-accept ARGS=--apply`, with the review server stopped, takes a snapshot of `engine/out/build`, points the tracked `engine/review-snapshot.json` at it, which goes into the commit with the edit, and empties the verdict store, so the next corpus starts from no unaccepted change. Before the snapshot, the accept, its dry run (bare `make review-accept`) included, runs the four-letter sweep: every text of at most four letters around a changed letter, split across processes, which prints how many tasks and texts it shapes and then what it found and how long it took, about a minute and a half for a one-join edit on the M5 Pro MacBook Pro in Low Power Mode, and writes what it found to `var/review/accept-sweep.json`. When it finds changes the Queue does not show, the accept refuses and says how many; `make artifact-cycle` adds them to the corpus as ordinary units, and once they are verdicted the accept goes through. A second accept over the same build reads the record and sweeps nothing. A clone or another machine without the snapshot remakes it with `make review-snapshot-remake`, from a build of the commit that last changed the pointer. `make verdict-ready` prints a snapshot row and a diff row that counts the unaccepted changes, and names the accept once none is open. `engine/review/accept.py`'s module docstring gives the refusals.
- **What it can miss.** A cycle pass's corpus tries every text of at most three letters around a changed letter and the certificates of its rules, and the accept's sweep every text of at most four, so a change that only a context longer than four letters shows can be missed.

## Mechanisms

Each section below says what a mechanism does for the reviewer and names the module docstring or `doc/review-design.md` section that has the detail.

### Machine-approved units

The build approves a unit without a person when a machine check shows that its two renderings match. There are two checks, tried in the order `MACHINE_CHECKS` in `engine/review/audit.py` gives, so a unit carries at most one flag. The first is ink identity: a unit is `ink_identical` when both fonts place the same outlines under every config in its set, shaped with kerning off, so only glyph names differ. The module docstring of `engine/review/ink.py` says how the outlines are placed and compared. The other is picture identity, below.

A machine-approved unit takes no place in the triage index (the manifest's `human_unit_ids`), so it is in no batch, no sidebar count, and no progress denominator, and the triage flow above says how the app shows it. The cross-class search covers the human units only, so a machine-approved unit is reached through a show-machine fold or a pasted `#unit=` link.

`verdicts.json` holds human verdicts only. The manifest's `machine_approved` record holds the totals by check, with each check's method. The ink and picture checks run over each unit's text under each of its configurations, and a unit with no text stays a human unit (`doc/review-design.md` §2.1).

### Picture-identical units

The second check approves a unit whose two fonts fill the same pixel cells under every config, where the glyph-name change the audit recorded only moves ink from one glyph to a neighbor without changing the picture: a junction pixel one font draws twice and the other once, as at ·At·J’ai, or a stroke redrawn as part of the adjacent letter. The check fails closed: a window whose outlines or placements are off the pixel grid, or whose pictures differ under any config, is queued. `InkComparator.picture_identical` and `config_diff` in `engine/review/ink.py` define it. The flag is not part of a unit's content key (`diff_units.unit_identity`), so a change in the flag changes no unit's id.

### Classes that take no verdict

The `kerning` and `provenance-only` classes take no verdict (`diff_units.NO_VERDICT_CLASS_IDS`): kern values are judged in the kerning view, and a provenance-only unit draws nothing new. Their units are handled like machine-approved ones: they take no place in the triage index, are hidden behind the toggle with their controls disabled, and show a "no verdict needed" badge, and the sidebar lists the class under No review needed with "no verdict needed" in place of its progress. `needsNoVerdict` in `static/render.js` is the app's test for both kinds.

### The artifact cycle mechanized

`make review-cycle` rebuilds the font, builds the table-diff corpus, lands it with the verdict store carried onto it by unit id, runs the gates, and then serves the corpus when no server is up; `make artifact-cycle` is the same pass without the serve. The review server keeps running through every pass: the pass builds the corpus beside the served one (`engine/out/review.next`) and then lands it under the store's lock (`landing.py`), carrying the store, every verdict recorded during the pass among it, onto the new corpus by unit id. A save made while the land holds the lock gets a retryable 503 and waits in the outbox, and the open tabs then move onto the new corpus by themselves. The cycle restarts a server running older code, leaves one serving another checkout alone, and stops nothing that gives no `/capabilities` answer: a pass that would write under such a listener refuses. The land serves the new corpus as soon as the build has finished, while the heavy gates may still run, so a red pass can leave the app serving a corpus no gate has passed; `make verdict-ready` and the app banner stay NOT READY until every gate has passed on those inputs: a gate the pass did not run counts as not passed unless a green record shows the same inputs already passed. A green pass ends with a `review diff` line counting the unaccepted changes, which never fails it. `doc/review-cycle.md` is the runbook, and the module docstring of `engine/tools/artifact_cycle.py` has the rest.

### Sections

`audit.class_section` puts each class in one section, and the manifest carries the result as `section`: No review needed when the class takes no verdict or has no human unit, and Open questions otherwise. The build emits the classes in section order, then `diff_units.CLASS_IDS` order, before it sorts the triage index, so batches, `[` and `]`, and the first unverdicted unit follow the sidebar, and an entry never moves as verdicts land. The Queue reads `section`, and the app refuses a manifest without it.
