# Kerning plan (design §12)

This is the design record for the rebuild's kerning: the `kern:` block of a rune file, the stage that resolves it, the GPOS lookup it compiles to, and the editor view of the review app that writes it. Its inputs are design §12 and the kerning section of `doc/core-idea.md`. §9 orders the work, and every step of it is built: the schema key, the loader, the kern stage with its three errors and `kern.tsv`; the GPOS lookup, the kern-only rebuild, and the gates of §7; the inventory with the editor view; the editor's write route, block writer, journal and undo; and the carried-over marks over the import of the old kerning.

## 1. The rulings this plan is built on

These are the author's decisions, and each one closes a question the old font left open.

- **Kerning moves only pairs that do not join.** A joined pair's length belongs to `extend` and `contract`. The old font runs its Senior kern lookups after cursive attachment and expands a family key over every glyph of the family, so a rule set while looking at `·No.alt | ·Tea.half` also shortens `·No.alt ~b~ ·Tea`.
- **A pair's kerning lives in the leading letter's rune file.** The pair `·A | ·B` is kerned in ·A's file and nowhere else.
- **The most specific record wins, and values never add up.** `by: 0` is a real value that cancels a broader record.
- **The unit an author edits is a facing pair**: one right-hand edge against one left-hand edge (§3).
- **The editor writes each change through to the YAML**, keeps a journal for undo, and holds its writes while a cycle pass reads the runes.
- **The Senior tightening stays in the advance widths.** `tools/build_font.py` trims a pixel from every Quikscript letter's advance, so no record states it.
- **A break at a ZWNJ kerns exactly as the same two shapes kern at any other break.** The old font's rule that tightens ·He before any ZWNJ is not carried over.
- **The editor shows joined pairs and does not edit them.**
- **ss10 text kerns, and so does Junior.** Under ss10 no pair joins, so every pair of letters is a break between two isolated shapes, and those pairs take records like any other.

## 2. The record

`kern` is a top-level key of a rune file, a sibling of `policy`, and the last key in the file. It is outside `policy` because policy shapes settlement and kerning reads settlement's result.

```yaml
kern:
- {right: {family: qsBay}, by: -2}
- {stance: flipped, right: {family: qsPea}, by: -2}
- {stance: flipped, right: {family: qsTea, stance: half}, by: -1}
- {stance: loop, right: {family: qsGay}, by: -1}
```

`engine/schema/rune.schema.json` is the authority on the keys. Their meaning:

| Key                           | Names                                                           | Notes                                                                         |
| ----------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `stance`                      | This rune's stance                                              | Absent means every stance                                                     |
| `entry`                       | How this rune was entered: a height or `none`                   | For a rune whose right-hand edge depends on its entry                         |
| `bitmap`                      | A drawing a `bind:` names, a derived `padded-left-N` among them | For an edge only a bound drawing produces                                     |
| `right.family`                | The follower, one rune or a list                                | A ligature is named explicitly, as in every right-facing list (design §3.4)   |
| `right.class`, `right.except` | A predicate class or rune-local group, and carve-outs           | For a hand-written statement about many followers                             |
| `right.stance`, `right.exit`  | The follower's settled stance and exit state                    | Legal only in a kern record: both sides are settled when kerning is evaluated |
| `right.bitmap`                | A bound drawing of the follower                                 | As `bitmap`                                                                   |
| `by`                          | Whole pixels, signed                                            | Negative tightens                                                             |
| `why`                         | The author's rationale                                          | Written only from a note the author types; AGENTS.md's `why:` rule covers it  |

A record never names a boundary. A space, a text edge, and the namer dot are not runes, and a ZWNJ is invisible to kerning: a pair across one kerns as the same two cells kern side by side (§5).

**What a record matches.** A record matches a pair of adjacent settled cells when the pair is a break, the left cell is this rune's and fits the record's own-side keys, and the right cell fits `right`. A break is a pair whose left cell has no live exit and whose right cell has no live entry; the join table holds no other kind of break and no join with a declined facing side, and the kern stage asserts both.

**Precedence.** Among the records that match a cell pair, the one whose match set is contained in every other's decides the value, by the extensional order of design §6.2. Two matching records with different values and neither match set inside the other are the error `E-KERN-INCOMPARABLE`, which names both. No value is ever a sum.

**Ligatures.** A ligature stance that declares `outgoing.stance` takes the kern records of the component stance it maps to, those naming that stance and those naming none. Records with `entry` or `bitmap` stay with the component, as incoming behavior and bound drawings do under design § Preserved outgoing strokes. Every record in the ligature's own `kern` block outranks every inherited one. A ligature that opts out with `outgoing: {exception: …}` inherits nothing.

**Stale records.** A record that matches no reachable break is the error `E-KERN-UNMATCHED`. A build on a narrowed alphabet (`model.ResolvedSpec.narrowed`) reports none, since a narrowed alphabet can lack what brings a record's pair to a break; the whole alphabet's build reports them. The old font's stale prefix kerns nothing and reports nothing.

## 3. Facing pairs

Most cells of a rune look the same from one side: an entry state changes nothing on the right of most letters, and an exit extension changes nothing on the left. The kern stage groups them.

- A **side** of a rune is a maximal set of its cells that the record grammar can select together and whose facing edge is the same pixel for pixel: for the leading side, cells with no live exit and the same ink-to-advance distance on every row; for the following side, cells with no live entry and the same leftmost ink on every row.
- Each side has a **name**: the coarsest own-side pattern (`family`, then `stance`, then the join state, then `bitmap`) that selects exactly its cells among the rune's cells on that side.
- Cells the grammar cannot tell apart (they differ only in an extension, contraction, or trim amount) are one side even when their edges differ. The coverage table marks such a side, and the editor draws each of its drawings.
- A **facing pair** is a leading side and a following side with at least one reachable break between their cells, in any settlement configuration, across a ZWNJ, or under the ss10 overlay.
- **Across a ZWNJ** every cell that settles immediately before a ZWNJ meets every cell that settles immediately after one: a window whose first right slot is a boundary reads nothing past it, and the window after a ZWNJ reads nothing before it. The cell after a ZWNJ is the `.locked` copy of a word-initial cell (for a rune with no entry on any stance, the word-initial cell itself), drawn and spaced as that cell is, so it falls on the following side its twin is on. Many such pairs meet nowhere else, such as a letter before a ligature it always joins mid-word, and they get facing pairs only a ZWNJ reaches.
- **Under ss10** every ordered pair of letters is a reachable break, and a letter's `.ss10` copy is a member of the side its source cell is in, so most ss10 pairs fall into a facing pair settlement already reaches. A pair of letters whose isolated shapes always join under settlement gets a facing pair only ss10 reaches.

The editor's rows and the coverage table's rows are facing pairs, and every class of the GPOS lookup is a union of whole sides (§5). A record may be broader than one facing pair and never narrower: one that gives two cells of a side different values is the error `E-KERN-NARROWER`.

## 4. The kern stage

`engine/pipeline/kern.py` runs in the glyph chain once the tables exist and the cell glyphs are minted, before the defect gates. It reads the spec's kern records, the break rows of every `joins-<config>.tsv`, the cells each configuration settles beside a ZWNJ, the letters' ss10 copies, and the realized bitmaps. No join row crosses a boundary, so the crate records the ZWNJ cells in each configuration's windows head (`zwnj_before` and `zwnj_after`, the crate's `fold::zwnj_cells`), outside both table digests since they follow from the window rows, and the stage takes their product as that configuration's breaks. It writes under `engine/out/build/`:

- **`kern.tsv`**, the coverage table: one row per facing pair, with both side names, the value, the record that decides it (file and key path), and the configurations that reach it. It is diff-stable, so a new stance that inherits a letter-wide value shows up as added rows in a commit's diff.
- **`kern-classes.json`**, the assignment the font is compiled from: each glyph's leading and following side and every facing pair's value, 0 included, so a shaped break whose two sides are no facing pair shows a break missing from the stage's list. The glyph chain writes it once read-back has passed, so it always describes the font beside it, and the conformance sweep checks every shaped break against it (§7).
- **`kern-inventory.json`**, the editor's data (`engine/pipeline/kern_inventory.py`, whose docstring lays out the document and `check_document` checks it): every minted cell's ink and advance, the sides, the facing pairs with how many member cell pairs each has and what reaches it (a break mid-word, across a ZWNJ, or under ss10), the joined groups of the same two runes (the join rows of one stance of each at one height), one member for each drawing of a facing pair with a mixed side, the Manual's words, and for each facing pair and joined group a witness text with its settled cells and pen positions. It holds no kern value, so a kern edit changes nothing in it.

The inventory is written once read-back has passed, beside `kern-classes.json`, through a file renamed into place, and only by a build: a kern-only pass runs the chain without it, and its staged publish leaves the inventory in place. It is stamped with the tables' stamp and the digest of the Manual pages, and a build whose stamp matches the file's keeps the file and settles nothing; the Manual pages are in no build key, so a page edit reaches it with the next build that runs, and a build directory without it is no build a cycle skips (`artifact_cycle.BUILD_ARTIFACT_NAMES`). Each witness is a text the kernel settled to one of the pair's member cell pairs, found by the first step that finds one: the Manual's words under `default`; the two letters alone in each configuration that reaches the pair; one letter of context on each side from the configuration's join rows; for a pair a ZWNJ reaches, a word ending in the leading cell before a ZWNJ and one starting with the following cell after it, settled together; for a pair the overlay reaches, the two letters under ss10. A pair none of these reaches has no witness text, and the editor draws its two member cells side by side. The pen positions come from the glyph records (a join's anchors, a break's compiled advance), and the build checks every text against HarfBuzz on the font it compiled, with `kern` off, before it writes the file.

It raises `E-KERN-UNMATCHED`, `E-KERN-INCOMPARABLE`, and `E-KERN-NARROWER`, and it hands the defect gates each kerned break's value (`KernResolution.member_values`), so the off-anchor contact check (design §9) places a kerned break where the font draws it, and an overlap there is `E-CONTACT`, appealable through the allow list under a signature that names the kern (`contact:L:R:overlap:kern-2`), so a bless at one value does not cover a deeper kern of the same pair. Ink that only touches side by side across a break is no error.

**Kerning stays out of the kernel and out of every key but the build's.** `spec_load` parses `kern` into records that the kernel's spec dump does not carry, and `fingerprint.rune_file_digest` leaves the block out, so a kern edit moves neither the tables' stamp, nor the `data` component, nor the family keys of the settle memo, the string replay or the deep replay. Each rune's kern block reaches the run_build skip key through a line of its own (`fingerprint.kern_lines`). When only those lines move since the last green build, and the Stage A record shows that the summaries on disk are a passing run's over the other inputs, the cycle runs `run_build --kern-only` (`artifact_cycle.kern_only_rebuild`): the glyph chain alone over the tables on disk, the kern stage, the defect gates, the emission, the compile and read-back, and no string replay, witness stage, shipped-order walk or Manual-pin gate, whose inputs the edit did not touch. It runs the chain beside the build and replaces the build's files only once read-back passes, so a failed kern edit leaves the prior font in place and the next pass is a kern-only rebuild again (`run_build.kern_only_run`).

**The review corpus shows a kern edit as kern units.** It shapes with `kern` off and the app renders with `font-kerning: none` for every unit but a kern unit, which shows a moved kern value and is shaped, compared and drawn with kerning on (`engine/REVIEW-PLAN.md` §2.3). Its freshness compares its copied after font with `Senior-Regular.otf` byte for byte, so the cycle rebuilds the corpus after a kern-only rebuild (`artifact_cycle.corpus_build_skippable`).

## 5. Compilation

`emit_gpos.kern_plan` turns the stage's resolution into one chained-context lookup (GPOS type 8) under the `kern` feature, defined after the `curs` lookups. A value is `by` pixels of x-advance on the first glyph, applied through a single-adjustment value lookup, one per distinct value.

- **Why it is not a pair lookup.** HarfBuzz skips a ZWNJ when it matches GPOS input, so a pair lookup (PairPos) kerns across one; CoreText does not skip it, so the same lookup leaves the pair unkerned in Safari and every other CoreText client, against the ruling that a break at a ZWNJ looks like any other break. Contextual rows beside a pair lookup would kern such a pair twice in HarfBuzz. So each kerned case is a rule for the adjacent pair followed by a rule with one explicit `uni200C` between the two glyphs: a shaper applies the first rule of a lookup that matches, HarfBuzz matches the adjacent rule across a ZWNJ and never reaches the second, and CoreText matches the second. A pair across two or more ZWNJs kerns in HarfBuzz alone.
- **The rules.** The leading sides whose rows (each following side with its value) are the same form one input class, and for each value of that row one rule pair reaches the union of the following sides that take it. feaLib picks each subtable's format. A letter's `.ss10` copy is in the classes of the side its source cell is in.
- **The lookup cannot move a join.** A glyph with a live exit is in no input class and a glyph with a live entry is in no lookahead class. `kern_plan` refuses a plan that breaks this, and a following glyph with a cursive entry anchor, which a `selectable: false` entry row gives every cell of its stance, with a message saying what to change. Read-back checks the same property on the written font: no glyph the lookup adjusts carries an exit anchor in any `curs` lookup, and no glyph it reads after one carries an entry anchor.
- **No kerned pair, no lookup.** Only facing pairs whose value is not 0 are compiled, so with none the rune pipeline adds nothing to the font's `kern` feature, which then holds only the Latin pair lookups of `glyph_data/opentype-features.yaml`.
- **Read-back** splits the `kern` feature's lookups into the Latin pair lookups, which sit before the `curs` lookups and which it holds to the foreign-lookup rule (no pair of two rune-owned glyphs), and the plan's lookup, which is present exactly when the plan has a rule. For the plan's lookup it rebuilds the (first glyph, second glyph) to value relation from the compiled rules and their value lookups, once for the adjacent rules and once for the one-ZWNJ rules, and compares each with the plan's.

## 6. The editor

The editor is the `#view=kern` view of the review app. `engine/review/README.md` describes it as its user sees it; this section is the contract. The view, its keys, the read and write routes, the block writer, the journal and undo are built; the text box that settles typed text is not.

**It draws pixels and shapes nothing.** The client loads `kern-inventory.json` and draws each witness as squares at the inventory's pen positions, every break moved by its facing pair's value. A kern is a whole-pixel shift of everything after the junction, so a keypress redraws from data the client already holds, with no shaping, before the request that writes it. Browser shaping cannot serve here: a span or a margin inside a run breaks the contextual substitutions, and the browser cannot say which glyphs it drew.

**Layout.** A grid of leading rune by following rune, each cell drawing the pair's representative facing pair and its value, with a count on a cell that has several and a mark on a cell whose value the built font lacks. A rune pair's representative is the facing pair its two letters settle to under `default` when they break there, drawn as the two cells they settle to, and otherwise the one with the most member cell pairs. A rune pair whose facing pairs are reached only across a ZWNJ, only under ss10, or only in those two ways, carries a chip saying which; one with no facing pair is blank. Beside the grid, the detail panel of the focused cell: the selected scope with its record as the file holds it and the file's name, or the file's lack of one, and the controls that change it; the facing pairs of the two runes, listed by following side so that those sharing a second shape stand together, those with the selected pair's following side each in its witness, with its sides, its reach and configurations, each drawing of a mixed side, the closest ink across the junction (the worst over those drawings, an overlap being a pixel both sides ink), the record that decides its value and the mark for a value the built font lacks; the facing pairs with another following side, as one line each with its value, until one of them is selected; the joined groups of the same runes, drawn and marked as not kerned; and the Manual's words that hold the pair, with every value applied, those where the two runes break first and those where they only join after. Under the facing pairs it lists the selected one's relatives (below). A text box will settle typed text through the kernel on the server.

**Relatives.** A facing pair's junction is every horizontal gap between ink of its two sides on one row or on rows one apart, at a value of 0, so the two letters' side bearings cancel out of it. Two facing pairs are relatives when their junctions are the same once one is left as it is, has its two sides exchanged (its mirror image: `·Ah | ·Low` and `·Llan | ·Awe`), is turned upside down about the middle of the Short letters' rows (which exchanges a Tall letter's rows and a Deep letter's), or both. The same means equal on every gap less than `CLOSE_REACH` pixels looser than the closest, so ink set well back from the junction counts for nothing and a ligature is a relative of the letter whose edge it shows. The client computes the relation from the inventory's drawings (`static/kern.js`), which hold everything it needs, so neither the inventory nor a build carries it. Relatives that take more than one value are kerned inconsistently: the view marks their cells and rows, counts the classes, and steps through them. The author settles a class by taking the value most of the relatives have, by giving the selected pair's value to every relative that differs (one change per record, each to its own leading rune's file, each its own journal entry and undo), or by marking a pair as apart on purpose, which leaves it out of every comparison. A near relative, whose junction differs by at most `NEAR_BUDGET` pixels in all, is listed for comparison and is in no count, since a pixel of difference in the edges can warrant one in the value.

**Comparables.** The same section compares the selected facing pair across one of its sides instead, when the author asks: with the facing pairs that have the same following side and a leading side shaped like its own (every letter shaped like ·Ye before half ·Way), or with those that have the same leading side and a like following side. Two sides are alike when their facing edges differ, row by row, by a constant and little else; the constant is how much further from the junction one's ink is set, and what is left once it is taken out is the distance, with `MISSING_ROW` pixels for a row only one of them inks. A side is like another within a pixel for each row of the other's edge. Likeness reads the whole edge, where the relatives read only the rows that face the other side, since a letter is compared by eye with the letters that look like it. Each comparable is listed with its clearance, its junction's closest gap moved by its value, beside the selected pair's, and the view tightens or loosens it in place or sets it to that clearance. Comparables are in no count: they are an aid to the eye.

**Scope of an edit.** An edit made on the two letters sets the record that names only the two families, `{right: {family: <following rune>}}`, which every facing pair of the two without a narrower record takes. An edit made on one facing pair sets the record whose own-side keys and `right` keys are exactly its two sides' keys, read from the side names (`qsNo[flipped]` gives `stance: flipped`, `qsTea[half exit=x-height]` gives `right: {family: qsTea, stance: half, exit: x-height}`); a facing pair of two whole runes has the letters' record as its own. Either record lives in the leading rune's file, a ligature's own file for a ligature, where it outranks what the ligature inherits. A record equal to what it would inherit is removed: the server resolves the block with the record and without it, and when every facing pair takes the same value both ways, the record and its `why` go, so setting a facing pair to the value it takes anyway, or the letters to 0 with no broader record, leaves no record. The editor never rewrites a record that carries a `class`, a family list, or an `except`: it writes a narrower record beside it and shows which record each value comes from. A side split off at the last level with no bound drawing (§3) has no keys that leave its bound siblings out, so its record also moves them unless they have records of their own; the server's answer gives the values that result.

**Routes**, in a server-only module, `engine/review/kern_routes.py`, with the block writer and journal in a second, `engine/review/kern_writer.py`; `fingerprint.REVIEW_NON_BUILD_MODULES` lists both and the server's code digest covers them with the pipeline and validation trees they run (`landing.served_paths`). No route runs the kernel; they read `engine/out/build` directly, so the corpus never holds kerning and a kern-only pass reaches the view with no land. `kern_routes`' module docstring is the authority on the requests and the replies.

- `GET /kern/inventory` serves the inventory as the build wrote it.
- `GET /kern` returns every facing pair a record decides with its value and deciding records, resolved now from the rune files over the tables on disk, the built font's values from `kern-classes.json`, each rune file's `kern` block with the sha256 of its text and its records with their lines, notes and scopes, the journal's pending and dropped requests, and what the view reports as stale: tables the sources no longer give, an inventory over other tables or older Manual pages, and a running pass. `check_values_payload` is the authority on its shape.
- `POST /kern` takes a delta of sets, each naming one record by its scope (the two letters, or a facing pair's two side names) with a value within the schema's bound on `by` or null to drop the record, the `base` sha256 of the block the client last saw, and an optional `why`, the author's typed note, stored verbatim. Every rune a set names must be one the loaded spec holds under exactly that name, whatever the value, since a case-insensitive file system would open another rune's file under a misspelled one. Before anything is replaced, the server writes the new block into a temporary copy of the runes directory and runs the spec loader, the kern stage, the kern lookup's plan, and the defect gate's contact check at the kerned offset over every break the edit moves, under `engine/contact-allow.yaml`; a result the build would refuse changes nothing and comes back with the build's own messages. A file is read and written as its bytes hold it, and the block's lines end the way the file's lines do. A `base` that is not the block on disk changes nothing and comes back as a conflict carrying the block as it stands. The file is replaced atomically, and the change is appended to `var/kern/journal.ndjson` before the reply: the rune file, the whole block before and after with their sha256s, the delta and the time.
- `POST /kern/reviewed` marks a carried-over facing pair reviewed (§8), or every facing pair of two letters, or takes the mark off.
- `POST /kern/apart` marks facing pairs as kerned apart from their relatives on purpose, or takes the marks off, in `var/kern/apart.json`, refusing a pair the current build does not have; `GET /kern` lists the marks. A mark changes no rune file and is not journaled.
- `POST /kern/undo` names the change it undoes by the journal seq a write's reply gave. A change still waiting for a pass is cancelled, journaled as such, and nothing written is reverted. A written change is reverted only while it is the newest applied change no undo has reverted and its block still holds what it wrote; an older change, one never written, or one already undone is refused. The revert is checked as an edit is, and journaled.
- Every write holds the cycle's pass lock without waiting, as the table-diff accept takes it. While a pass holds it, the server journals a delta or an undo as pending, answers that it waits, and applies the pending requests in order once the lock frees, checking each against the file as it then stands; one that no longer applies, or whose application raises, is journaled as dropped with its reason, which `GET /kern` reports with the pending count, so no request waits for good. A delta made against the block a write began from still applies after that write's own pending requests, so presses queued during a pass apply one over another.

**The block writer** regenerates a rune's whole `kern` block in canonical order (a record naming no family first, then followers by code point with a ligature after its lead, a broader record before a narrower one, one flow-style record per line) and replaces the text from the `kern:` line to the end of the file, or appends the block to a file with none; when the last record goes, the `kern:` key goes with it and the file is byte for byte what it was before its first record. Every byte before that line is untouched by construction, and a test holds it to that. `tools/reflow_yaml.py` leaves the writer's output as it is. The writer keeps every record it does not change exactly as written. It refuses a block it cannot write back exactly, a comment or a blank line inside it, a multi-line string, or a record not in the one-per-line flow form among them, with a message saying what to fix by hand; `why` is where a rationale goes.

**Keys.** `static/keyboard.js` holds the view's map and its test pins it: the arrows (or `e`, `s`, `d` and `f`) move the grid's cursor, and `-` and `=` set the focused pair of letters a pixel tighter or looser without leaving the grid. In the detail panel up and down (or `e` and `d`) choose a facing pair, in the order the panel lists them, moving on as `]` and `[` do past either end, a toggle chooses between the selected facing pair and every unjoined pair of the two letters as the scope, left and right (or `s` and `f`) tighten and loosen that scope, `0` drops its own record, and `n` writes its record's note. `g` marks the selected scope's carried-over facing pairs reviewed and moves to the next one, moving on from a scope with nothing carried over or already marked too (§8); the reviewed button takes the mark off a scope that has it. `u` undoes the last change this tab made, in either pane, and `]` and `[` move to the next and the previous pair of letters with a carried-over facing pair not reviewed. `r` and `w` move, in either pane, to the next and the previous facing pair kerned differently from a relative, passing over the selected pair's own class; in the detail panel `t` takes the value most of the selected facing pair's relatives have, `v` gives its value to every relative that has another, and `a` marks it apart and moves on as `r` does, or takes the mark off. `c` steps through what the relatives section lists: the relatives, the like first shapes before the same second shape, and the like second shapes after the same first; `t`, `v` and `a` act only while it lists the relatives. Presses on one scope within about a third of a second become one request, so the journal holds one change per pause and one undo reverts it; a press the server answered as changing nothing is not one.

| `emit_gpos.kern_plan`            | Refuses a plan that would adjust a glyph with an exit anchor or read one with an entry anchor after it (`KernPlanError`)                                                                                                                                                                            |

| `conform.check_break_advances`   | At every slot of every swept text that does not exit into a join, `x_advance − x_offset` is the glyph's `hmtx` advance plus the value `kern-classes.json` gives it and the glyph after it, ZWNJ slots skipped; a shaped break between letters with no facing pair there is a `kern-side` divergence |
| `conform.check_split_buffer`     | A text split at a ZWNJ equals its segments shaped alone once the kern across the split is taken off the slot before it; a split at a space is unchanged                                                                                                                                             |

## 8. Carrying the old kerning over

The rune files' `kern:` blocks start from the old font's Senior kerning, carried over by an import from the rebuild's side, and the author refines them in the editor; `git log` holds the importer and the rules it followed. Its record is in `var/kern/`: `imported.json` lists every facing pair it set, each with its value, its record and whether that record is still in place, and `import-report.json` lists what it left for a ruling: a facing pair whose old evidence held several values, a joined pair an old rule moved, and a record the build refused. The ZWNJ rule and the Latin rules of `glyph_data/opentype-features.yaml` are not carried over.

The editor marks each facing pair the import set as carried over while the author has not reviewed it and it keeps the imported value: a chip on its grid cell and its detail row, and a count in the header line. `g` marks the selected scope's carried-over pairs reviewed in `var/kern/reviewed.json` (`POST /kern/reviewed`), and changing a pair's value marks it too, a mark its undo takes off. The marks name facing pairs by their sides, so a later build that splits or renames a side leaves marks that no longer reach a pair; the header line counts them.

## 10. Open questions

- **Glyphs with no rune file.** Punctuation, the namer dot, and Latin letters lead and follow Quikscript letters, and the old font kerns some of them. The font's one kerning between a rune and such a glyph is `leave-space-for-j` in `glyph_data/opentype-features.yaml`, which reaches every glyph before Latin `j`. The candidate is the same `kern` list on the glyph's own entry in its `glyph_data/` file, with `right: {glyph: …}` naming a follower that is not a rune.
- **How the records reach Junior.** Junior's letters never join, so its pairs are the ones ss10 reaches, and the author's ruling is that they kern. The rebuild compiles only the Senior font, so which of a rune's records Junior reads, and on top of which default spacing (Junior lacks the Senior tightening), waits until the rebuild builds Junior.
