name: dont-bug-me-about-this-ever-again
description: Turn "I keep having to verdict this same thing" about review-corpus units into a checked-in standing approval. Probe the unit the user named, survey every window that shows the same change, find where the decision is already recorded, pick or extend a rule shape until one rule covers all of those windows (or let two existing rules combine), dry-run the fill, land it, and run the cycle to READY unasked, so the review queue never asks again and the corpus is ready for review. Use when the user names units or a window and wants them auto-OKed for good, or hands over a list of approved windows at once (the batch form, which /batch-standing-approvals drives).
argument-hint: "[unit-id …]"
---

Turn a "stop asking me about this" complaint into a rule in `rebuild/standing-approvals.yaml`, which `rebuild/tools/standing_verdicts.py` applies every cycle. The unit the user names is one example of a kind of change. The job is every window that shows that change, not only the units that share the named unit's ink-delta digests. The tool's module docstring is the authority on what each rule shape checks (every shape in its `SHAPES` table, and the combined match that lets two rules explain one window between them), so read it first, and do not restate its contracts here or anywhere else.

## Hard rules

- The decision is the user's; the rule only records it. Find where it was made (an unmatched group, a rune edit, a review-session note) before writing anything, and cite it in the rule's `note:`. Never author a rune `why:`, which is written in the user's voice. The `note:` in `standing-approvals.yaml` is agent-written, in the pattern of the file's existing notes.
- A rule must fill the whole surveyed kind of change and nothing else. Every shape leaves some changes unchecked, and its docstring says what it checks. Before landing a rule, list the blank units it would fill and check each one for a change the shape does not check.
- Never hand-write the verdict store or any `verdicts-*.json`; the cycle lands the fill through `merge_verdicts`. Never join unit ids across manifests.
- Counts belong to the dry run's output and the cycle summary, never to prose or the rule's note.
- The session ends at READY without the user asking for it. A rule that is written but not landed through a cycle changes nothing the user can see, so start the passes as soon as the tree is final and run them until `make verdict-ready` reads READY. Never hand back a rule with an offer to run the cycle in place of running it.
- If no checked-in shape, as it currently matches, can name the whole survey, extend the matcher in `rebuild/tools/standing_verdicts.py` (and the probe, when it enumerates the cells) until one can. That is this skill's job. Examples of that work: extension-dropped accepts a kept `ex-ext-M`, a follower list, or `ex-con-N`; slide fills the ·See windows that a rule listing two ink-delta digests leaves waiting for human review; and redrawn fills ·Eight's pulled-in bowl, which no other shape's pixel contract fits. A whole new shape comes last, and it is still this skill's job (tests in the pattern of `rebuild/test_standing_verdicts.py`, and a matcher docstring).

## Steps

1. **Probe the units.** Run `uv run python rebuild/tools/standing_probe.py u-NNNNNN …` (read-only; it reads the live autosave to see which units are blank). Users often name the change rather than a unit, in the corpus's `data-expect` notation (`·Tea.half ~x~ ·No` → `·Tea ~b~ ·No`). `doc/data-expect.md` is the grammar, and `parse_expect` in `test/test_shaping.py` is the authority. `--find TEXT` finds the units for such a notation. It is a plain substring match over every human unit's notation, blank units first, capped, with the total stated, and `--blank-only` and `--limit N` narrow it. When the corpus is already open in front of the user, `/` in the review app searches the same units, and each row's Copy button puts a prompt preamble for that unit on the clipboard; that is the same search, with the user looking at the results.

   For each unit the probe prints the two grains side by side: the recorded glyphs, cells and junctions, and the rendered pieces of both fonts with placement, own-frame origin and cell count, each read as "same shape, placed +N col" (with any height or origin move), "redrawn", "inkless", "ink appears", or "ink vanishes". Then the probe prints what every checked-in rule makes of the unit, what the combined match counts, and how many human units share exactly its ink-delta digests and how they were verdicted. Before going further, name every change in the window from that table: a slide (same shape, origin and placement moved), a dropped extension (redrawn by exactly the tail, follower placed closer), a renaming (pieces differ, picture does not), or something else.

   The probe costs one fixed corpus load per process unless the standing daemon holds the corpus (`make standing-daemon`; `rebuild/tools/standing_daemon.py`'s docstring is the authority on what it holds and when it declines). With the daemon holding it, a probe or a dry run is a query over its socket that prints byte for byte what the in-process form prints, and `--daemon always` says so when the call cannot be served. Either way, an extra mode or unit id in the same call adds no load, and the daemon answers one request at a time, so put everything you already have into one call: `--find`, unit ids, `--coverage`, a cell enumeration. There are two limits. A bare `--shapes` menu read is the one call that never loads the corpus, so nothing else goes in it. And a flag's arguments must come from a table the probe already printed, never guessed to save a call, because a wrong `ex-ext-N` token enumerates a different survey.
2. **Survey every window that shows the change.** The named unit is one example. After naming the change, enumerate every human unit that shows it. The survey reads the index and shapes nothing, so it can go in the same call as step 1's probe, under the same corpus load. Use `--survey BEFORE_GLYPH` (or `--survey BEFORE_GLYPH AFTER_CELL`) for any change a before form names: a redraw, a gain, an entry contraction or drop, a stub drop, or a join becoming a break. It prints every human unit carrying that before glyph, grouped by the before form and the after cell it settles into, then by the left family with the junction change into the pivot, the junction change out of it, and the follower family and cell. Each group has its verdict tally, everything is in code-point order, and the survey says how many windows carry the glyph but cannot be placed. Use `--extension-cells` for an exit stretch and `--retarget-cells` for a join that changes height or is created. That set of units is the job. The units that share the named unit's ink-delta digests are evidence that the user already approved the change; they are not the fill target.
3. **Find the decision's record.** The survey's already-verdicted members usually show that the user has already approved the change through the duplicate fill. `git log -S<token> -- glyph_data/runes/qs<Family>.yaml` finds the rune edit that made the change (a narrowed `extend:` list, a dropped record) and its commit subject. A review session's parked question is in `WHATNEXT.md` or the batch progress file. If none of these exists, the change is not yet decided: stop and ask, because a rule would be inventing a verdict.
4. **Pick the smallest option, in this order.** A rule's shape is set by which key its `match.after` carries, never by its id; `SHAPES` in `rebuild/tools/standing_verdicts.py` maps each key to its shape. (a) An existing rule that already names the kind of change and only lacks a pivot form, follower, cell or digest: extend it. `uv run python rebuild/tools/standing_probe.py --coverage RULE_ID` re-runs that rule's own survey without the rule's own filters, so the candidates come as a list, each with a verdict tally, instead of as a guess. (b) Two existing rules that each explain part of the window: write no rule. The combined match fills the window once both rules exist, and the probe's `combined:` line says whether it does and which rules it counts. (c) A new rule in the structural shape that names the change. `uv run python rebuild/tools/standing_probe.py --shapes` prints the menu, generated from the `SHAPES` table, with each row giving the symptom sentence its matcher's docstring opens with. Compare the probe's rendered-grain reading of the window with that menu, pick the row whose symptom is the change you named in step 1, and then read that matcher's docstring for what it checks and what it does not check. What it does not check decides whether the rule fills only windows that show the approved change. (d) An `ink-delta` rule, only when the survey is a single digest, which means the change never appears in a window together with another change. Two or more digests for the same change mean that another change in some windows gives those windows different digests. That needs a structural shape: if no shape in the menu, as it currently matches, names the survey, extend the matcher (back to (c)) rather than listing those digests.
   - A shape that names cells needs its cells enumerated before a rule in it can be written, and the probe does that: `--extension-cells PIVOT TOKEN JUNCTION` for an extension-dropped rule, where `TOKEN` is the `ex-ext-N` the before glyph carried or the `ex-con-N` the after cell carries, and `--retarget-cells PIVOT BEFORE_JUNCTION FOLLOWER AFTER_JUNCTION` for a join-retargeted or join-created rule. Each prints every pivot cell, follower family and follower cell the rule must name, with a verdict tally per pair, in code-point order. Name them all, and set `follower:` to the family list. `--coverage` runs the same enumeration for a rule that already exists, which is why option (a) uses it. For a shape that names forms rather than cells, `--coverage` runs the survey over the rule's family and reports the before forms, the after forms as the after font names them, and, for entry-contracted, the left families the rule does not name. It relaxes each list while keeping the rule's other lists, so a before form settling into a named after form is on the candidate list and the family's unrelated positions are not. `COVERAGE_SHAPES` in the probe lists the shapes that have an enumeration. For the two it leaves out (ligature, which names no forms, and ink-delta, which names digests), the probe says so.
5. **Write the rule and dry-run it, targeted first.** Append to `rebuild/standing-approvals.yaml`, then iterate with the targeted run, `uv run python rebuild/tools/standing_verdicts.py verdicts-autosave.json --explain RULE_ID --targeted`. It evaluates only the windows the rule could match at the name grain (the name-only precheck's candidate positions for a combinable shape, the pivot's presence for the ligature shape, the digest subset for an ink-delta rule), plus any `--unit u-NNNNNN` you list. It prints only that rule's lines: its own line, every combined-match line that counts it, its rollup line, its disputed-match warning and its `--explain` block, each byte-identical to what the whole-domain run prints for the same rule (`rebuild/test_standing_verdicts.py` checks that over the frozen mini bundle). Then it prints one line per listed unit saying whether the unit is a candidate of the rule and what the corpus decided about it, which is how to find out why a named unit is missing from the explain block. It costs about one corpus load rather than an evaluation of the whole domain, writes no fill file, and never touches the memo, so after an edit to the rule you only re-run it. Its first line says how many units it evaluated. A rule whose pivot is a common letter evaluates thousands, and the targeted run is still the cheaper form. `--explain` takes one rule, so a second rule's lines need a second run.

   Read the rollup, not only the rule's own line, because the own line is easy to misread. The combined pass takes a window before any single rule is checked, so a combinable rule's own line counts only the windows no combined match took. A rule with a small count there may already reach the whole survey through combined matches, so check the rollup before concluding that the matcher needs widening. The run says in its own words when a rule reached nothing at all. It also flags two things a block of numbers hides: a matched unit carrying a verdict outside the approve/either set, which is the sign of an over-broad rule, and an `except_left` family that no window on this corpus joins from. The explain block prints the rule's matched unit ids, split the same way its line counts them, which is what the coverage check needs: filled plus already-verdicted plus blocked units must cover the survey, and the only blocking allowed is by `except_left`. Probe the filled units that are not in the survey in one call (the probe takes a list of unit ids and loads the corpus once), and confirm that nothing else changed in each. An `extension-dropped` rule cannot see a slide or a renaming elsewhere in the window, so whether a fill in that shape is correct depends on the corpus's `pair` and `secondary_junctions` fields.

   When the targeted run shows the rule is right, one whole-domain run is the final pass before step 6: `uv run python rebuild/tools/standing_verdicts.py verdicts-autosave.json --out tmp/standing-dry.json --explain RULE_ID --jobs N`. It is the only form that prints every other rule's line (where a new combinable rule shows the windows it moved off another rule's own line onto a combined-match line), the disputed-match warning across every rule, and the fill file the cycle would land. `--jobs N` decides the whole domain across a worker pool instead of one unit at a time, and the output is byte-identical at any width and whether or not the daemon serves the run. The tool derives no width of its own, so read N off the `verdict-update --standing-fill-jobs` line of `make artifact-cycle ARGS='--dry-run'`, which is the width the cycle itself uses for the refill on this machine. A rollup short of the survey sends you back to step 4, usually to extend the matcher, not to append another digest.
6. **Test and gate, sized by what changed.** There are two branches, and the diff decides which: if `git status --porcelain` names only `rebuild/standing-approvals.yaml`, take branch (a); if it names anything more, take branch (b).
   - **(a) Rule-only**: the matcher, the probe, and their tests are untouched, and no Python in the working tree has changed since its last pyright-covered run. A rule landing under an unchanged matcher needs no test of its own, and it does not need the foreground gate either. The only tests whose subject is the checked-in rules file are in `rebuild/test_standing_verdicts.py` (through `load_rules` over the real file), and the verdict-update step refuses a checked-in rule that reaches no window, which asserts the same `_decision_reach` rollup the step-5 dry run just printed. So run the targeted subset, `uv run pytest rebuild/test_standing_verdicts.py rebuild/test_standing_probe.py --lane contracts -n auto --dist worksteal`, and move on. Skip `make prettier` (black is Python-only) and skip the foreground `make test-rebuild`. The full suite is not waived: the rebuild lane's green record keys on the rules file through `rebuild_gate_closure_files` in `rebuild/tools/artifact_cycle.py`, so the lane runs again, but inside step 7's background gate pass, where nothing waits on it. Nothing else depends on this change: gate:make-test exempts all of `rebuild/` (`make_test_exempt` in `rebuild/tools/artifact_cycle.py`), and run_m1, the corpus build, and gate:conform do not key on the rules file at all.
   - **(b) Matcher changed**: add the contract cases in the pattern of the file's existing cases: the new contract's positive, its negative, and, if the shape is combinable, its combined-walk case. `uv run pytest rebuild/test_standing_verdicts.py -n auto --dist worksteal` is the loop while writing them, not a gate step. Pyright needs no step of its own: the PostToolUse hook in `.claude/settings.json` runs it on every Python write, and `make test-rebuild` runs it again inside the suite. Run `make prettier` in the foreground first, because it rewrites Python inside the closure that the gate is about to fingerprint.

     Then run the gate detached, not under a foreground Bash timeout. What matters is the order of the steps, not whether the gate runs in the foreground, and a run killed at the Bash tool's timeout records no green record, so the cycle has to run that lane again. Chain step 7's cycle onto the gate so a green gate leads straight into the pass that lands the fill, and join them with `&&` so a red gate never starts the cycle: `nohup caffeinate -i sh -c 'make test-rebuild && make review-cycle SERVE=bg; echo "rc=$?"' > tmp/cycle-pass.log 2>&1 &`. Record the pid at launch (stop the chain with `kill -TERM <pid> $(pgrep -P <pid>)`, per `doc/running-long-steps.md` § Stopping a pass). Judge liveness by `kill -0 <pid>`, never by grepping process names, because the xdist controller sits at 0% CPU while its execnet workers run the tests. Judge the outcome by the recorded `rc=`, not by grepping for any one closing line, because `rebuild_gate` has several legitimate closing lines. The cycle half of that chain keeps its own record, whatever the redirect catches: `var/build-logs/latest/` holds the resolved plan, a byte copy of the terminal, and one log per step, so read a red step's log there rather than searching `tmp/cycle-pass.log` for it.

     While the gate runs, the tree is read-only. Drafting the commit message and reading diffs may happen during the run, but nothing in the gate's closure may change: if it does, the post-run fingerprint re-check declines the green record and the whole run is wasted. The commit itself still waits for the gate's result, because a red gate must be able to stop it. Land every edit first, and run the gate last.
7. **Start the cycle, then land it, then finish at READY.** The passes take longer than anything else left, and they are the only thing that shows the fill to the user, so start them as soon as the working tree is final: before drafting the commit message, not after it is approved. Propose the commit while they run. Committing does not affect a pass: every green record digests worktree bytes, and `git commit` changes none of them, so a commit made during a pass neither invalidates the run nor is invalidated by it. An _edit_ does affect it, and avoiding edits during a pass is the point of this ordering. The closure is mainly `rebuild/` and `glyph_data/`, and `rebuild_gate_closure_files` defines it exactly, so a rule edit while a pass runs wastes the pass. `.claude/`, `tmp/`, `var/`, and Markdown other than the few files that function lists are outside the closure and can change freely.
   - **(a) Rule-only**: run both passes in one detached shell, the verdict update and review facts first and the gate run second: `nohup caffeinate -i sh -c 'make review-cycle SERVE=bg ARGS="--skip-gates"; echo "PASS1 rc=$?"; make review-cycle SERVE=0; echo "PASS2 rc=$?"' > tmp/cycle-pass.log 2>&1 &`. Record the pid at launch (stop the chain with `kill -TERM <pid> $(pgrep -P <pid>)`, per `doc/running-long-steps.md` § Stopping a pass), judge liveness by `kill -0 <pid>`, and judge the outcome by the recorded `rc=` lines.

     The verdict update's key includes the bytes of `rebuild/standing-approvals.yaml`, so landing a rule always runs the verdict update, and pass 1 lands the store it prepared while the review server keeps running (`doc/review-cycle.md` § The server and the pass); the open tab picks up the fills on its next sync. Pass 1 is short on a tree the last cycle left settled. Pending M1 or corpus work from unrelated edits runs in this pass too and makes it longer; that extra time is the cost of that work, not of the rule.

     Pass 2 runs the rebuild suite again inside the cycle, to record its green result, while the review server keeps running. Pass 1's verdict-update green record still matches, so pass 2 writes neither the corpus nor the store. If a verdict is recorded in the app during pass 1 or between the passes, pass 2 runs the verdict update again and lands the store, and the review server keeps running either way. A red pass 2 on this branch is a pre-existing failure that the pass reports, not one the rule caused: no other test in the suite reads the rules file. Each pass opens its own run directory under `var/build-logs/`, and `latest` points at the newer one, so once pass 2 has started, find pass 1's directory by its `<stamp>-<sha>` name.
   - **(b) Matcher changed**: step 6's chain already runs the cycle after the gate, so nothing new starts here. The pass that runs is the verdict-update one. Like pass 1 of branch (a), it lands the store while the review server keeps running, and `SERVE=bg` starts a server only when none is up.

   **The commit.** Write the commit message in reader terms ("Stop having to verdict …"), and let the commit wait on two things only. On branch (b) it waits for the gate's `rc=0`, because a red gate must be able to stop it. On either branch it waits for pass 1's review-facts rewrite when that pass changes the review facts: `rebuild/review-facts-pins.json` holds the last accepted review facts, and committing its diff accepts them, so the rule and the facts it changed belong in one commit, not a rule commit followed later by a separate review-facts commit. If approval arrives before the pass has printed the diff, commit the rule, and commit the review-facts diff on its own as soon as it appears. Never leave it uncommitted in the tree.

   **Finish at READY without being asked.** Between the passes, `make verdict-ready` reads NOT READY and accurately reports the gates as unverified, so the session is done only when the log has pass 2's `rc=0` (on branch (b), the chain's) and `make verdict-ready` reads READY. Watch the log until its closing banner (the summary table, then `Cycle complete.`) rather than treating the launch as the finish. Then report everything in one message: the rule's fill line from the cycle summary, the full review-facts diff, and the readiness verdict. If it still reads NOT READY, name the unmet clause and clear it. Handing back a half-run cycle with an offer to finish it is the outcome this step exists to prevent.

   When any of this needs a foreground Bash timeout, size it from bare `make cycle-timings` (recent runs' actual per-step seconds), not from `ARGS='--by-step'`, whose pooled medians trail the current cost of the longest step. This file gives no durations, because a duration written here would be wrong on another machine and would go stale on this one.

## Batches

A batch here is a list of approved windows handed over at once (many unit ids, or a whole review session's approve column), not the letter batch whose progress file step 3 names. Every step above still applies, per kind of change rather than per window; what changes is how the work is organized. `/batch-standing-approvals u-NNNNNN …` (`.claude/workflows/batch-standing-approvals.js`) runs that organization as a saved workflow. It takes the unit ids as its `args` (an array, a whitespace-separated string, or `{units: […]}`), and invoking it is the go-ahead for its lander's commits, one per kind of change. It runs only on a clean tree: its first agent stops if `git status --porcelain` lists anything, because the lander commits shared files by path and reverts, file by file, a kind of change it cannot land, so an uncommitted edit already in one of those files would be included in a commit or discarded. Its stages: one agent probes every unit in one call and clusters the changes by kind; one read-only analyst per cluster checks a rule on a scratch rules file and returns it ready to paste, with its decision record and commit subject; a single lander applies the rules in dependency order; a verifier checks every unit in the input list again; and the detached gate-and-cycle chain runs last. The workflow is the script. The bullets below say what it encodes, and what to follow when running a batch by hand.

- **Cluster by kind of change, not by window.** The first pass is one probe over every unit in the batch (the corpus loads once, so every id goes in one call), then a clustering of the distinct changes its tables print, keyed by position, before glyph, after cell and junction change. A window with two unexplained changes belongs to two clusters. The units are the evidence, and the kinds of change are the work: each kind gets its own survey (`--survey` for a change a before form names, the cell enumerations for one that names cells) and goes through steps 2 through 5 on its own.
- **Balance the clusters.** The analysis phase ends when its slowest analyst finishes, so split the kinds of change across analysts by the work each one costs, never by how many windows each cluster holds. A matcher extension, or a shape whose cells have to be enumerated, is more work than a pivot form added to a rule that already names the kind of change.
- **Analysts validate on a scratch copy and hand over paste-ready YAML.** Passing `--rules tmp/…/rules.yaml` to the probe and to the targeted dry run (`uv run python rebuild/tools/standing_verdicts.py verdicts-autosave.json --rules tmp/…/rules.yaml --explain RULE_ID --targeted`) lets an analyst check that a rule fills its survey without touching the tree; `--survey`, `--extension-cells`, `--retarget-cells` and `--coverage` all take the same `--rules`. Drafting a rule onto the same scratch copy as an earlier one shows the combined match before either rule lands. An analyst hands over the rule exactly as it will be pasted, the decision's record from step 3, the matcher extension the rule needs (when it needs one), and the commit subject. The lander's job is then mechanical: paste, run one whole-domain dry run (step 5's final pass, read against every rule already landed), run the rule-only test subset from step 6(a), and commit. A lander that probes or surveys again is repeating the analysis.
- **Land in dependency order.** When one kind of change's rule combines with another's, the rule it combines with lands first, so the second rule's dry run shows the combined-match line with both rules present. A matcher extension lands with or before the first rule that needs it, under step 6(b), and the rules that depend on it follow as rule-only commits.
- **Concurrency is memory-bound.** With the standing daemon running (`make standing-daemon`), no agent holds a corpus. The daemon holds the only copy, the analysts can run in parallel up to the core count, and each probe and targeted dry run is a query that waits behind the one in progress. Without the daemon, every probe and dry run loads the corpus (the human index records and the font pair) in its own process. No computed width accounts for that memory, so the limit is a rule the agents follow: no more agents hold a corpus at once than `CORPUS_HOLDERS` in `.claude/workflows/batch-standing-approvals.js` allows, and no agent runs two corpus-loading processes at a time. `doc/parallelism.md` says why nothing reads free memory to raise that limit. Stop the daemon before the detached gate-and-cycle chain, whose widths do not account for it. The targeted test subset takes seconds and does not limit the batch. The analysts are what runs in parallel, and the lander runs alone to keep the tree consistent, not to save memory.
- **A blank the review session approved can still be undecided.** The user approved every window in the batch, but step 3 still applies to each of them. A window whose survey has other units carrying `neither` or `reject` on the same stroke is a conflict to report, not a rule to write: hold it out of the batch and ask.
- **Gate once, at the end.** Each rule-only commit runs step 6(a)'s targeted test subset and nothing more. The rebuild suite and the cycle run once after the last commit, as step 6(b)'s detached chain (`make test-rebuild && make review-cycle SERVE=bg`), and the session ends at READY as step 7 says.

## What this costs when skipped

Each of these is easy to miss by hand, and each is a reason the probe exists:

- The same change in a different window has a different whole-window digest as soon as any other visible change is in the window. (A renaming that paints no different pixel is inside the digest's grain and does not change it.) So the approvals of the units that share an ink-delta digest prove the decision but cannot fill a window where the change appears with another change. Listing the named unit's digest (and the digest of one such combination) leaves the rest of the windows in the review queue. The first ·See rule ("Stop having to verdict the reduced whitespace for ·See") is an example.
- The slide shape ("Stop getting bothered about ·See’s movement for real this time") fills every window with the ·See column drop, including windows that also carry an approved extension.
- The extension-dropped shape checks nothing in the window except names and junctions, so read its dry-run fills rather than only counting them.
- The rendered fonts position glyphs through GPOS, so never reason about a slide from `hmtx` advances; the probe reads shaped placements.
- A `slide` rule declines a window with even one pixel outside the slide, by design. A window that pairs an approved slide with an approved extension drop is the combined match's case, not a new rule's.
- An already-verdicted duplicate group is evidence for a rule, not a substitute for one. The duplicate fill reaches only pixel-identical units, while a rule reaches windows the user has never seen.

## Scratch files

`tmp/standing-dry.json` and any survey output are scratch and never committed. The durable outcome is the rule, its tests, and the commit message; the fill itself lands through the cycle.
