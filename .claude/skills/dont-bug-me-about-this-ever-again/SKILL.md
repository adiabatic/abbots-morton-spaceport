Turn a "stop asking me about this" complaint into a rule in `rebuild/standing-approvals.yaml`, applied every cycle by `rebuild/tools/standing_verdicts.py`. The named unit is a specimen of a phenomenon; the job is every window that shows that change, not the specimen's digest family. The tool's module docstring is the authority on what each rule shape proves — every shape in its `SHAPES` table, and the composed reading that lets two rules explain one window between them — so read it first and do not restate its contracts here or anywhere else.

## Hard rules

- The decision is the user's; the rule only records it. Find where it was made (a verdict family, a rune edit, a sitting note) before writing anything, and cite it in the rule's `note:`. Never author a rune `why:` — that voice is the user's — but the `note:` in `standing-approvals.yaml` is agent-written, in the file's own idiom.
- A rule must fill the whole surveyed phenomenon and nothing else. Every shape has a blind spot, stated in its docstring; before landing a rule, list the blank units it would fill and read each one against that blind spot.
- Never hand-write the verdict store or any `verdicts-*.json`; the cycle lands the fill through `merge_verdicts`. Never join unit ids across manifests.
- Counts belong to the dry run's output and the cycle summary, never to prose or the rule's note.
- The sitting ends at READY, unasked. A rule that is written but not landed through a cycle has changed nothing the user can see, so the passes start as soon as the tree is final and run to `make verdict-ready` reading READY — never hand back a rule with the cycle left as an offer.
- If none of the checked-in shapes as they currently match can name the whole survey, extend the matcher in `rebuild/tools/standing_verdicts.py` (and the probe when it enumerates the cells) until one can — that is this skill's job. Teaching extension-dropped a kept `ex-ext-M`, a follower list, or `ex-con-N`, adding slide when two ink-delta digests left the rest of ·See queuing, and adding redrawn when ·Eight's pulled-in bowl fit no pixel contract, were that work. A whole new shape is the last move, still this skill's (tests in the file's idiom, a matcher docstring).

## Steps

1. **Probe the units.** `uv run python rebuild/tools/standing_probe.py u-NNNNNN …` (read-only; reads the live autosave for blankness). Users often name the change rather than a unit, in the corpus `data-expect` minilanguage (`·Tea.half ~x~ ·No` → `·Tea ~b~ ·No`): `doc/data-expect.md` is the grammar, and `parse_expect` in `test/test_shaping.py` is the authority. `--find TEXT` is the route from that prose to a specimen — a plain substring match over every human unit's notation, blanks first and capped with the total stated, narrowed by `--blank-only` and `--limit N` — and with the surface already open in front of the user, `/` in the review app searches the same units while each row's Copy button puts a prompt preamble for that unit on the clipboard, which is the same route with the user's own eyes on it. For each unit the probe prints the two grains side by side — recorded glyphs/cells/seams, and the rendered pieces of both fonts with placement, own-frame origin and cell count, read as "same shape placed N columns over", "redrawn", or "inkless" — then what every checked-in rule makes of it, what the composed reading credits, and how many human units share exactly its ink-delta digests and how they were verdicted. Name every change in the window from that table before going further: a slide (same shape, origin and placement moved), a dropped extension (redrawn by exactly the tail, follower placed closer), a re-spelling (pieces differ, picture does not), or something else. The probe pays one fixed surface load per process and each extra mode or unit id rides that load free, so batch everything the chain has already given you into one call — `--find`, unit ids, `--coverage`, a cell enumeration — with two limits: a bare `--shapes` menu read is the one call that never loads the surface, so nothing else may ride on it, and a flag's arguments must come from a table the probe already printed, never guessed to save a call, because a wrong `ex-ext-N` token enumerates a different survey.
2. **Survey the swath.** The named unit is a specimen. After naming the change, enumerate every human unit that shows it: `--extension-cells` for an exit stretch; for a slide or a redraw, every window whose rendered pieces carry the same pivot move or the same own-frame cell appearing or disappearing. That set is the job. The specimen's digest family is evidence the user already approved the change; it is not the fill target.
3. **Find the decision's record.** The survey's already-verdicted members usually show the user has already approved the change through echo; `git log -S<token> -- glyph_data/runes/qs<Family>.yaml` finds the rune edit that made it (a narrowed `extend:` list, a dropped record) and its commit subject; a sitting's parked question lives in `WHATNEXT.md` or the batch progress file. If none of these exists, the change is not yet decided — stop and ask, because a rule would be inventing a verdict.
4. **Pick the smallest home, in this order.** A rule's shape is which key its `match.after` carries, never its id; `SHAPES` in `rebuild/tools/standing_verdicts.py` is the map from key to shape. (a) An existing rule that already names the phenomenon and merely lacks a pivot form, follower, cell or digest — extend it, and `uv run python rebuild/tools/standing_probe.py --coverage RULE_ID` re-runs that rule's own survey relaxed of everything it names, so the candidates arrive as a docket with a verdict tally each rather than as a guess. (b) Two existing rules that each explain part of the window — no rule at all: the composed reading fills it once both rules exist, and the probe's `composed:` line says whether it does and which rules it credits. (c) A new rule in the structural shape that names the change: `uv run python rebuild/tools/standing_probe.py --shapes` prints the menu, walked off the `SHAPES` table itself, each row with the symptom its own matcher opens with. Read the probe's rendered-grain reading of the window against that menu, pick the row whose symptom is the change you named in step 1, then read that matcher's own docstring for what it proves and — the part that decides whether the rule is honest — where it is blind. (d) An `ink-delta` rule only when the survey is a single digest — the change never rides beside anything else. Two or more digests for the same change means a companion is minting new identities; a structural shape is required, and if no shape in the menu names the survey as it currently matches, extend the matcher (back to (c)) rather than listing those digests.
   - A shape that names cells has to have them enumerated before a rule in it can be written, and the probe does that enumeration: `--extension-cells PIVOT TOKEN SEAM` for an extension-dropped rule, where `TOKEN` is the `ex-ext-N` the before glyph carried or the `ex-con-N` the after cell carries, and `--retarget-cells PIVOT BEFORE_SEAM FOLLOWER AFTER_SEAM` for a join-retargeted or join-created one. Each prints every pivot cell, follower family and follower cell the rule must name, with a verdict tally per pair, in code-point order — name them all, and set `follower:` to the family list. `--coverage` is the same enumeration turned on a rule that already exists, which is why rung (a) reaches for it.
5. **Write the rule and dry-run it.** Append to `rebuild/standing-approvals.yaml`; then `uv run python rebuild/tools/standing_verdicts.py verdicts-autosave.json --out tmp/standing-dry.json --explain RULE_ID` — ask for `--explain` on the first run, because it is stdout formatting over the same run and the same payload, so the rollup and the explain block cost one surface load instead of two (it is single-valued; a second rule's ids need a second run). The run prints a line per rule and per composed credit, then a per-rule rollup that adds each rule's composed credit to what its own line accounts for: read the rollup, not the own line alone. That is the distinction that misleads — the composed pass claims a window before any single rule is asked about it, so a composable rule's own line counts only the windows no composition took, and a rule reading small there may already be reaching the whole survey through credit. Check the rollup before concluding the matcher needs widening; the run says in its own words when a rule reached nothing at all, and it also flags what a block of numbers hides — a matched unit carrying a verdict outside the approve/either set, which is the shape an over-broad rule takes from outside, and an `except_left` family no window on this surface joins from. `--explain RULE` prints that rule's matched unit ids split the same way its line counts them, which is what the coverage check needs: filled plus already-verdicted plus held must cover the survey, held only by `except_left`. Probe the filled units that are not in the survey in one call — the probe takes a list of unit ids and its load is paid once regardless — and confirm nothing else changed in each — an `extension-dropped` rule cannot see a slide or a re-spelling elsewhere in the window, so a fill of that shape is only as honest as the surface's `pair` and `secondary_seams` fields. A rollup short of the survey sends you back to step 4, usually to extend the matcher, not to append another digest.
6. **Test and gate, sized by what moved.** Two branches, and the fork is the diff itself: `git status --porcelain` naming only `rebuild/standing-approvals.yaml` is branch (a), anything more is branch (b).
   - **(a) Rule-only** — the matcher, the probe, and their tests untouched, and no Python in the working tree moved since its last pyright-covered run. A rule landing under an unchanged matcher needs no test of its own, and it does not need the foreground gate either: the only tests whose subject is the checked-in rules file live in `rebuild/test_standing_verdicts.py` (through `load_rules` over the real file), and the plumbing step's own refusal of a checked-in rule that reaches no window is what asserts the same `rule_reach` predicate the step-5 dry run just printed. So run the targeted subset — `uv run pytest rebuild/test_standing_verdicts.py rebuild/test_standing_probe.py --lane contracts -n auto --dist worksteal` — and move on; skip `make prettier` (black is Python-only) and skip the foreground `make test-rebuild`. The full lanes are not waived: both green records key on the rules file's bytes through `rebuild_gate_closure_files` in `rebuild/tools/artifact_cycle.py`, so they re-run — but inside step 7's background gate pass, off the blocking path, and nothing else was ever waiting on this change (gate:make-test exempts `rebuild/` wholesale (`make_test_exempt` in `rebuild/tools/artifact_cycle.py`), and run_m1, the surface build, and gate:conform never keyed on the rules file at all).
   - **(b) Matcher moved** — add the contract cases in the file's idiom: the new contract's positive, its negative, and, if the shape is composable, its composed-walk case; `uv run pytest rebuild/test_standing_verdicts.py -n auto --dist worksteal` is the loop while writing them, not a gate step. Pyright needs no line of its own: the PostToolUse hook in `.claude/settings.json` runs it on every Python write, and `make test-rebuild` runs it again inside the suite. Run `make prettier` in the foreground first, because it rewrites Python that is inside the closure the gate is about to freeze. Then the gate goes detached rather than under a foreground Bash timeout — the constraint was always sequencing, not foregroundness, and a run killed at the tool's ceiling records no green and re-pays that lane in-cycle — with step 7's cycle chained onto it so the green flows straight into the pass that lands the fill, and `&&` so a red gate never reaches the cycle: `nohup caffeinate -i sh -c 'make test-rebuild && make review-cycle SERVE=bg; echo "rc=$?"' > tmp/cycle-pass.log 2>&1 &`, record the pid at launch, judge liveness by `kill -0 <pid>` (never by grepping process names — the xdist controller sits at 0% CPU while its execnet workers grind), and judge the outcome by the recorded `rc=`, not by grepping for any one closing line, of which `rebuild_gate` has several legitimate ones. The cycle half of that chain keeps its own record whatever the redirect catches: `tmp/build-logs/latest/` holds the resolved plan, a byte copy of the terminal and one log per step, so a step that goes red is read there rather than scrolled for in `tmp/cycle-pass.log`. The window is read-only: drafting the commit message and reading diffs may overlap it, but nothing in the gate's closure may change — the post-run fingerprint re-check declines the green and the whole run is wasted — and the commit itself still waits for the gate to answer, because a red gate must be able to stop it. Land every edit first, gate last.
7. **Start the cycle, then land it, then finish at READY.** The passes are the longest thing left and the only thing that puts the fill in front of the user, so they start the moment the working tree is final — before the commit message is drafted, not after it is approved — and the commit is proposed while they run. Nothing about committing disturbs a pass: every green record digests worktree bytes, and `git commit` changes none of them, so a commit landing mid-pass neither invalidates the run nor is invalidated by it. An _edit_ does disturb it, which is the whole discipline here — the closure is `rebuild/` and `glyph_data/` (`rebuild_gate_closure_files`), so a rule tweak while a pass runs throws the pass away, while `.claude/`, Markdown and `tmp/` sit outside it and stay free to move.
   - **(a) Rule-only** — both passes chain in one detached shell, plumbing-plus-census first and the gate re-earn second: `nohup caffeinate -i sh -c 'make review-cycle SERVE=bg ARGS="--skip-gates"; echo "PASS1 rc=$?"; make review-cycle SERVE=0; echo "PASS2 rc=$?"' > tmp/cycle-pass.log 2>&1 &`, recording the pid at launch and judging liveness by `kill -0 <pid>` and outcome by the recorded `rc=` lines. Pass 1 takes the port and cannot be arranged otherwise — the verdict-plumbing key folds in `rebuild/standing-approvals.yaml`'s bytes, so a rule landing always runs the plumbing and writes the store, and `server_may_stay_up` in `rebuild/tools/artifact_cycle.py` grants its reprieve only to a pass that writes neither the surface nor the store — but it is short and the app is back up when it returns (on a tree the last cycle left settled, that is — pending M1 or surface work from unrelated edits folds itself into this pass and lengthens it, which is that work being paid, not the rule's cost). Pass 2 re-earns the rebuild suite's green in-cycle while the letters stay on screen: pass 1's plumbing green rides, so it writes neither surface nor store and leaves the server the port, and a verdict landed in the app between the passes just means it takes the port back and completes rather than refusing. A red pass 2 on this branch is a pre-existing failure being surfaced, not the rule's doing: no other test in the suite reads the rules file. Each pass opens a run directory of its own under `tmp/build-logs/` and `latest` follows the newer one, so reach for pass 1's by its `<stamp>-<sha>` name once pass 2 has started.
   - **(b) Matcher moved** — step 6's chain already carries the cycle behind the gate, so nothing new starts here; the pass that runs is the plumbing-only one, and it leaves the server up on the port.

   **The commit.** Commit in reader terms ("Stop having to verdict …"), and let it wait on two things only. On branch (b) it waits for the gate's `rc=0`, because a red gate must be able to stop it. On either branch it waits for pass 1's census rewrite when that pass moves one: `rebuild/review-census-pins.json` is the last accepted census and committing its diff is the acceptance, so the rule and the census it moved belong in one commit rather than in a commit and a straggler. If approval arrives before the pass has printed it, commit the rule and put the census diff in its own commit the moment it lands — never leave it sitting in the tree.

   **Finish at READY without being asked.** Between the passes `make verdict-ready` reads NOT READY with honest wording — gates unverified — so the sitting is done only when the log carries pass 2's `rc=0` (branch (b): the chain's) and `make verdict-ready` reads READY. Watch the log to its closing banner — the summary table, then `Cycle complete.` — rather than declaring victory at launch, then report in one go: the rule's fill line from the cycle summary, the census diff in full, and the readiness verdict. If it still reads NOT READY, name the clause that is unmet and clear it — a half-run cycle handed back as an offer is the one outcome this step exists to prevent.

   When any of this does need a foreground Bash timeout sized, size it from bare `make cycle-timings` — recent runs' actual per-step seconds — rather than `ARGS='--by-step'`, whose pooled medians lag what the longest step costs now; no duration written down here would survive the next box, or even this one's drift.

## What this costs when skipped

Each of these was rediscovered by hand once and is why the probe exists: the same change in a different window carries a different whole-window digest as soon as any other change rides beside it, so an ink-delta family's approvals prove the decision but cannot fill the composed window — listing the specimen's digest (and one composed companion) leaves the rest of the swath on the docket, which was the first ·See rule; "for real this time" taught slide so every window with that column drop filled, including ones that also carry a blessed extension; the structural extension shape fills blindly past anything that is not a seam, so its dry-run fills must be read, not counted; the rendered fonts position through GPOS, so never reason about a slide from `hmtx` advances — the probe reads shaped placements; a `slide` rule refuses on one stray pixel by design, and a window pairing a blessed slide with a blessed extension drop is the composed reading's case, not a new rule's; and an already-verdicted echo family is evidence for a rule, not a substitute for one — echo only reaches pixel-identical lookalikes, a rule reaches windows the user has never seen.

## Scratch discipline

`tmp/standing-dry.json` and any survey output are scratch and never committed. The durable outcome is the rule, its tests, and the commit message; the fill itself lands through the cycle.
