The user has verdicted the review app's table diff, the accepted build against the working tree's (`doc/review-cycle.md` § The table-diff accept and the snapshot), and wants its rejects turned into rune changes under `glyph_data/runes/`. A reject says the accepted build's drawing should come back; a neither says both drawings are wrong, so it needs new authoring. The design decisions are the user's, recorded in the verdicts and their notes.

## Hard rules

- Never write the verdict store, a `verdicts-*.json` or `rebuild/review-snapshot.json` by hand, never run `make review-accept`, and never rebuild the review corpus by hand (`review.build`). The `make artifact-cycle` pass in step 4 builds the corpus and lands it, carrying the store onto it by unit id, while the review server keeps running.
- Never invent a verdict. A unit without a verdict stays without one.
- Never author `why:` text. Copy the user's note verbatim onto the one record it describes. Where a record shape has no `why:` slot, put the note in a `#` comment on the record.
- Never commit without explicit approval. At the natural commit point, spawn a fresh sub-agent for commit-message suggestions that describe the reader's experience, not the mechanism.

## Steps

1. **Read the rejects.** The store is `verdicts-autosave.json` at the repo root, an `ams-review-verdicts/1` document whose `verdicts` is a list of `{unit, verdict, note, at}` records; the units whose verdict is `reject` or `neither` are the ones to work on. Read each from the served corpus through `rebuild.review.unit_index.iter_shard_fragments(Path("rebuild/out/review"))`, matching `id`: `notation` and `codepoints` give the text, `configs` where it shows, `class` the kind of change (`joins`, `settlement`, `glyphs`), `explain` the change and the changed rows of the accepted and the new tables it stands for, and `provenance` the rune records its rows credit.
2. **Reduce them to flaws.** Units on one Queue card (the same `cluster`) show the same pixels, and units that credit the same record usually share one cause, so each such set is one flaw with one note. The table diff is against the accepted snapshot, so the edit that made a flaw is in the runes' history since the pointer's commit: `git diff "$(git log -1 --format=%H -- rebuild/review-snapshot.json)" -- glyph_data/runes/` lists the candidates, and the fix is often to revert or narrow one of them.
3. **Design the minimal record change.** When a note is about the distance between two letters and does not make it depend on farther context or a configuration, the two letters that bound the space decide it (AGENTS.md's pair-wide rule): try an `extend` or `contract` on one side of that junction, the expand-or-contract-a-join skill's procedure, before any deeper condition. `doc/rebuild-design.md` §3.3 and §3.4 hold the record vocabulary. Revert an authoring decision by deleting the record that draws it, not by adding a record that cancels it, and express a revert of a join as a yielding `prefer`, which decides only a tie in join count, rather than a `refuse`. When the verdicts contradict each other, the same change approved in one unit and rejected in another, ask the user instead of editing.
4. **Rebuild and look.** Run `uv run python tools/reflow_yaml.py` on the touched runes (expect a no-op) and `uv run python -m rebuild.pipeline.run_m1`, which must end with defects 0/0 and the Manual pins clean, then `make test-rebuild`, then `make artifact-cycle` detached (`doc/running-long-steps.md` § Detach), and go on only once it ends green. When it refuses to run or to land, stop and show the user the refusal; never pass an override, and never stop or start the review server yourself. On the new corpus a fixed reject's unit is gone, since the edit that made it is undone, or shows the drawing the note asked for under a new id. A verdict whose unit an edit changed goes to `var/verdict-orphans/`, so account for every orphaned approval: either the fix meant to change that unit, or the fix reaches too far.
5. **Commit.** Show the diff, present the sub-agent's commit-message candidates, and wait for the go-ahead. Then tell the user that the open tabs move onto the new corpus by themselves when the pass reported that the review server kept running, and otherwise that `make review-serve` serves it.
