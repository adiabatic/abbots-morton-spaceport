Prepare a review session on the live review corpus (`rebuild/out/review/`, served by `uv run python -m rebuild.review.serve` on port 7294). The human decides everything in the browser, where the fonts render. The app's **review queue** (`http://localhost:7294/#view=queue`) is the queue itself. It clusters the blank units by the build-emitted `cluster` signature, largest decision first, and computes the clusters live from the in-memory verdict store, so it updates as verdicts are recorded. Your job is the work around it: audit the duplicate groups the cycle's verdict update already prefilled, snapshot the review queue for bulk proposals, and extend each bulk approval to its lookalikes.

## Hard rules

- Never hand-write the app's live verdict store (`verdicts-autosave.json`) or edit any existing `verdicts-*.json`. Everything you produce is a new `ams-review-verdicts/1` file, merged with `uv run python -m rebuild.tools.merge_verdicts <file>` (the journaled union the app's import computes, which never removes a verdict) or through the app's own import control.
- Every file you emit is stamped with the corpus's `manifest_generated_at`. Never join unit ids across manifests. If the stamps do not match, stop and say so; `carry_verdicts.py` is the fix, not `force`.
- A bulk proposal must never override a human verdict when both cover the same unit in a merge. Both the app and `merge_verdicts` keep the record with the strictly newer `at`, so stamp proposal records with the manifest's `generated_at`, as `standing_verdicts.py` and `complaint_list.py --defer` do. Any human verdict recorded on this corpus is newer and wins. Every store write is journaled in `verdicts-journal.ndjson`, and `merge_verdicts --restore-as-of <time> --apply` is how to undo a merge that wrote the wrong result.
- Treat verdicts as evidence that can be wrong. When proposing a bulk decision, state its grounds from the ledger and the user's own verdict history, say so when no verdicted unit shares the exact delta, and never propose a bulk decision where that history is split.
- Never author `why:` text, and never copy a draft's `why_stub` into a rune. That rationale must come from the user, in the user's words.

## Steps

1. **Check readiness and pick the fullest verdicts file.** Run `make verdict-ready` first. It checks corpus freshness by input fingerprint, which, unlike `repo_head`, covers uncommitted changes in the working tree. It also checks whether the gates passed in the last recorded cycle, whether the verdict store is stamped for the corpus, and whether the server is running. It names the fullest verdicts file: the `verdicts-*.json` at the repo root or under `rebuild/evidence/` whose `manifest_generated_at` matches `rebuild/out/review/manifest.json` and that has the most non-skip verdicts. If an argument is given, use it instead of the checker's pick. If the checker reports the corpus stale, the gates unknown, or gates left unverified, stop and give the user the checker's remedy instead of preparing a review session on a stale or ungated corpus. The remedy is a cycle, which verifies everything it cannot prove unchanged before the corpus is ready for review again. The same pass is the catch-up when the corpus's last cycle predates the verdict update's fill steps (the duplicate and standing fills, run until nothing changes) or ran with `--no-merge`: only a cycle, never a hand merge, adds missing fills to the store.
2. **Duplicate audit (read-only).** The artifact cycle's verdict update has already run the duplicate fill until nothing changes and merged the result. The fills are already in the store, and merging them is not your job. To report the groups whose verdicts disagree, run `uv run python rebuild/tools/duplicate_verdicts.py <verdicts-file> --out tmp/duplicate-audit.json`. Always pass an explicit `--out` under `tmp/`: the default output path (`verdicts-duplicate-fill.json` at the repo root) is the verdict update's own output file, and a run without `--out` would overwrite it with the fills still left to make, of which there are none.
3. **Snapshot the review queue.** Run `uv run python rebuild/tools/review_queue.py <verdicts-file>`. It writes `tmp/queue-data.json`: every blank cluster (id, class, configs, duplicate-group substructure, evidence from judged lookalikes), the ledger-ruled classes that still have blank units, and the duplicate groups whose verdicts disagree. The cluster ids match the cards in the app's review queue. The snapshot fixes the exact set of blank members against the verdicts file for step 5. The app view needs no snapshot and is always current.
4. **Hand over.** Give the user the summary counts (blank units, duplicate groups, clusters, ruled units, disagreeing groups) and `http://localhost:7294/#view=queue` (start the server if it isn't running). The artifact cycle's merge step has already merged the carried verdicts and the fills into the store, so there is nothing for you to merge here. Leave the disagreeing groups and the queue for the user to work through in the app.
5. **On request, emit bulk proposals.** When the user approves a whole class or cluster ("bless ss10", "cluster c-cbb49c41 approve, note …"), write one new import file per decision (e.g. `verdicts-bulk-<slug>.json`) that covers exactly the blank members from `tmp/queue-data.json`. Give each record the user's note verbatim plus a provenance tag like `[bulk: <class-or-cluster> — review queue <manifest stamp>]`, and set `at` to the manifest stamp. Report the count for the user to spot-check after import. When the approval is permanent and covers a delta _shape_ rather than this session's blank units ("I'll never judge this differently"), offer a rule in `rebuild/standing-approvals.yaml` instead. The artifact cycle applies the rules on every cycle through `rebuild/tools/standing_verdicts.py`, so units of that shape that later migrations create never wait for human review. The contexts the user still wants to see go in the rule's `except_left`. The rule's `note` is the user's rationale in the user's words, and a per-session bulk file is then redundant for the units the rule matches.
6. **Cluster the complaints and defer their lookalikes.** `uv run python rebuild/tools/complaint_list.py <verdicts-file>` (or `make complaint-list`) writes `tmp/complaints-data.json`: every open reject/neither verdict, grouped by the rune records that decided it, new complaints first. Each group lists its defer candidates (still-blank units the same records decide) and its approved units at risk (`approved_units_at_risk`: judged units the same records decide, which a fix would likely change). Report each group's headline, new complaints first, with those counts. When the user says to defer a group, re-run with `--defer g-XXXXXXXX` (plus `--note` with the user's verbatim text) to emit `verdicts-deferred-<slug>-<id>.json`. That file holds skip verdicts covering exactly the group's current blank members, with `at` set to the manifest stamp and the marker `[deferred: <target> — complaint list <manifest stamp>]`. Give it to the user to import through the **app's Import control during the session**; never run `merge_verdicts` while the server is up. Deferred units return to the queue automatically after the next cycle that rebuilds the corpus, because that cycle's carry drops skip verdicts. A pass that leaves the corpus in place keeps the stamp-aligned autosave, deferrals included. A deferral also blocks later bulk approvals with the same `at` stamp on those units, so check the deferred counts before proposing a bulk decision on overlapping clusters.

## Scratch files

`tmp/queue-data.json` and `tmp/complaints-data.json` are scratch files. They are discarded when the batch ends and are never committed. Lasting outcomes go where they are already kept: verdicts in the imported verdict files, rationale in ledger and rune `why:` fields written by the user, and follow-ups in WHATNEXT.md.
